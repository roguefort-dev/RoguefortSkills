# Lens: query-planning (67 techniques)

Cost-based choice of execution strategy, predicate handling, plan rewrites.

Format: `id | title | principle (first sentence)`. The id prefix names the cards file: `../cards/<prefix>.md`.

- duckdb-024 | Push filters as close to the data as possible, and derive new ones | Move predicates through joins, aggregates, DISTINCT, set operations, unnest and windows down to the scan.
- duckdb-025 | Read and carry only the columns that are still needed | Remove unreferenced columns at the scan, and drop columns from intermediates as soon as no later operator uses them.
- duckdb-026 | Keep per-block min/max summaries and skip blocks that cannot match | Record cheap statistics (min, max, null and all-null information) per file, row group, segment and page.
- duckdb-027 | Rewrite predicates into forms that block-skipping can use | Turn predicates that statistics cannot check (IN-lists, ORs, inequalities, functions of columns) into conservative range or set filters on bare columns.
- duckdb-028 | Order joins by cost with exact search, bounded by a budget | Enumerate join orders with dynamic programming over connected subgraphs (DPccp/DPhyp), each pair exactly once.
- duckdb-029 | Feed the cost model every cheap signal about sizes | Estimate cardinalities from distinct-count sketches, min/max domain sizes, file sizes, cached metadata and block-level statistics.
- duckdb-030 | Pick the build side by size, and by what it lets you filter | The materialized (build) side of a hash or nested-loop join should normally be the smaller input; flip outer-join types to allow it.
- duckdb-031 | Pass runtime join filters sideways into the probe-side scan | After building a hash table you know its keys.
