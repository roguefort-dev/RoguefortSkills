# Lens: observability (75 techniques)

Cheap instrumentation, counters, profiling hooks, benchmarks that guard performance.

Format: `id | title | principle (first sentence)`. The id prefix names the cards file: `../cards/<prefix>.md`.

- curl-158 | Keep a repeatable benchmark harness in the repository | Ship in-tree benchmarks: per-function micro-benchmarks reporting ns/op (median of runs) and end-to-end scenario runs with profiler hooks.
- curl-159 | Measure each micro-step separately, and on several architectures | When rewriting a hot routine, apply the changes one at a time and record the delta of each.
- curl-160 | Count allocations (and syscalls) per operation with an instrumented build | Run a debug allocator or tracer that logs every malloc and free (or syscall) and count them per standard operation (for example, "one simple HTTP GET").
- curl-161 | Profile on the platform that runs the code, and let the profile pick the target | Pick optimization targets from a profile of the real workload on the real OS.
- curl-162 | Derive tuning constants from field or test-suite distributions | Choose delays, initial capacities and orderings from measured distributions (telemetry percentiles, the share of test cases that fit), not from round numbers.
- curl-163 | Make instrumentation nearly free when it is turned off | Gate expensive diagnostics (memory fills, synced log flushing, verbose-only parsing, per-event trace lines) behind compile-time or runtime checks placed before the work.
- curl-164 | Lock in footprint wins with size assertions | Record the sizes of hot, frequently allocated structs in a unit test, and quote before/after sizes in commits that change them, so growth is a deliberate decision.
- curl-165 | Measure with a high-resolution monotonic clock in integer units | Time intervals with a monotonic, high-resolution counter, and store them as integer microseconds (or as offsets from one base time) rather than floating-point seconds.
- curl-166 | Decouple progress reporting from state updates and rate-limit it | Update counters on every event, but render progress or emit statistics at a fixed low rate, and only when the displayed value changes.

- duckdb-153 | Measure at runtime and adapt (explore / exploit) | Where the best choice depends on the data or the environment (predicate order, compression level, whether a filter pays off), time or count the alternatives while running, keep the winner, and keep exploring…
- duckdb-154 | Keep instrumentation always available but free when off; expose engine decisions | Build profiler names, debug strings and loggers only when profiling or logging is enabled.
- duckdb-155 | Prove fast paths equal the slow path | When a specialized or closed-form implementation replaces a general one, assert in debug builds that both give the same result, or test the replacement exhaustively over its parameter space.
- haproxy-173 | Normalise to calls per request: count syscalls, wakeups and function calls per unit of work | Measure how many syscalls, wakeups, failed calls and hot-function invocations each request costs, and optimise those counts directly; they are stable, explainable, and predict throughput.

- haproxy-176 | Read the profile at the instruction level: a hot trivial load means cache-line sharing | When a simple load, test or fence shows a large share of samples in an annotated profile, the cost is a cache miss or coherence stall, not computation; look at what shares that cache line.

- haproxy-178 | Sweep tuning parameters, choose the knee, and re-derive when the architecture changes | Pick batch sizes, shard counts, back-off curves and similar constants by sweeping them on representative hardware, judging throughput and tail latency together, and redo the sweep when the design or target…

- netty-176 | Keep metrics off the contended path | Derive metrics from events you already handle (chunk creation and destruction) instead of updating extra counters per operation, use striped counters for totals, and read estimates without locks.
- nginx-145 | Treat each optimization as a hypothesis, and revert it when measurement disagrees | An optimization rests on assumptions about frequency, hardware, kernel behaviour or deployment.
- nginx-146 | Profile production-like workloads, and record the measurement next to the code | Make profiling a built-in, routine capability.
- nginx-147 | Derive defaults from production data and arithmetic, not guesses | Defaults are what most deployments run. Set them from real traffic percentiles, from bandwidth-delay arithmetic, from observed allocation counts and from actual hardware needs, and write the reasoning into…

- nginx-149 | Keep diagnostics from becoming the bottleneck | Diagnostics must not change the behaviour they observe or amplify a fault.
- nginx-150 | Shed load from a cheap, sampled resource metric | Under resource pressure, answer with a cheap response or a close instead of failing badly.
- postgresql-214 | Profile a representative workload, then remove the top hotspot | Before optimizing, profile a real or standard workload.
- postgresql-215 | Make instrumentation cheap enough to leave on | Measure the cost of your own telemetry and drive it toward zero.
- postgresql-216 | Decide whether a message will be emitted before formatting it | Check the log level (or whether a feature like process titles is on) before evaluating arguments, formatting strings or doing setup work for a message.
- postgresql-217 | Keep telemetry in memory and persist it rarely, on demand | Store statistics in shared memory instead of a collector process that rewrites files.

- postgresql-220 | Keep the benchmark harness itself fast and representative | The benchmark setup should use the system's own fastest paths (bulk load, frozen data) and scale to large scripts, so measurement runs are cheap enough to repeat and the initial state matches production.
- redis-189 | Benchmark every optimization and revert the ones that don't pay | Treat a performance change as an experiment: measure before and after on realistic workloads, and back it out if the numbers don't confirm it, however plausible it looked.

- rocksdb-190 | Revisit defaults with measurements: defaults are performance features | Most users never change defaults, so periodically re-benchmark them against current hardware and workloads, and promote options proven in production.
