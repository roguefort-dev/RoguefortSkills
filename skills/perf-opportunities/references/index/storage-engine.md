# Lens: storage-engine (67 techniques)

Persistence, logs, compaction, LSM trees, on-disk formats, bloom and other filters.

Format: `id | title | principle (first sentence)`. The id prefix names the cards file: `../cards/<prefix>.md`.

- nginx-141 | Publish files atomically by writing a temp file next to the target and renaming | Write the new content to a temporary file, then `rename()` it over the final name, so readers see either the old or the new file, never a partial one.
- nginx-142 | Carry warm state across reloads and binary upgrades instead of rebuilding cold | A configuration reload or binary upgrade creates a new process generation.
- nginx-143 | Batch durable writes, bound their staleness with a timer, and compress them | Append records to a memory buffer and write it out in large chunks.
- nginx-144 | Generate unique temp names from one shared atomic counter, with a random jump on collision | When several processes create temp files in the same directories, per-process counters collide and each collision costs a failed `open(O_EXCL)` and a retry.
- postgresql-193 | Group commit: one flush makes many transactions durable | When many workers need the same expensive serialized operation, let one perform it for everyone queued so far.
- postgresql-194 | Skip logging for data that a final sync or a crash makes moot | If an object is new and invisible to others until commit, write it directly and fsync once at the end instead of logging every change.
- postgresql-195 | Skip durability work when nothing changed | Keep a cheap dirty flag and use it to skip the flush, the commit record or the checkpoint whenever there is nothing new to make durable.
- postgresql-196 | Offer an opt-in weaker durability mode, and wake the flusher promptly | Let callers acknowledge a commit before the log flush, or once a replica has the data in memory rather than on disk, while a dedicated writer flushes on a timer and as soon as a log page fills.
- postgresql-197 | Let writers copy into the shared log buffer in parallel | Reserve space in the shared append-only buffer with a tiny critical section, then let many writers copy their records into their reserved ranges at the same time.
- postgresql-198 | Log fewer, denser records: deltas, deduplicated plans, one record per page operation | Log only the data replay needs, not unchanged state.
- postgresql-199 | Shrink full-page images: drop the hole, then compress with a fast codec | Full-page images dominate log volume. Omit the unused gap inside each page, compress the rest with a codec that has a good speed-to-ratio balance, and reuse compression contexts across calls.
- postgresql-200 | Recycle and preallocate log segments, and choose the cheapest sync primitive | Treat log files as a ring. Rename old segments for reuse instead of deleting and creating files, preallocate new ones fully, and sync only data (not metadata) where the platform allows it.

- postgresql-204 | Reclaim space online and incrementally, never stop-the-world | Make garbage collection run alongside normal work.
- postgresql-205 | Keep a tiny per-page summary bitmap and skip pages it proves clean | Store one or two bits per page that say "everything here is visible to all" or "everything here is frozen".

- postgresql-209 | Do deferrable work when its fixed cost is already paid, with caps | If you are about to write a log record or full-page image for a page anyway, also do the future work on that page now (freeze every tuple).
- postgresql-210 | Write bulk-loaded data in its final state | If newly loaded data is invisible to others until commit, write it already committed, frozen and marked all-visible, so no later pass has to rewrite every page.
- postgresql-211 | Throttle background maintenance with a budget, and re-baseline it for current hardware | Pace maintenance with a cost budget (pages hit, missed, dirtied) and a sleep, so it doesn't swamp foreground I/O.

- redis-175 | Group commit: one write and one fsync per loop iteration, before any reply | Append every mutation of one event-loop iteration to an in-memory buffer, write and flush it once just before the loop sleeps, and only then let replies go out.
- redis-176 | Make durability tunable, and keep fsync off the critical thread | Offer explicit durability levels (always, every second, never) so users trade a bounded loss window for throughput.
- redis-177 | Flush large sequential writes incrementally, overlapping writeback with work | When writing a big file, sync every few megabytes instead of once at the end.
- redis-178 | Don't dirty shared pages while a fork snapshot is running | `fork()` gives a free point-in-time snapshot by sharing pages copy-on-write.
- redis-179 | Persist the in-memory encoding as-is instead of re-serializing element by element | If a structure is already a flat, position-independent byte blob, write that blob to disk or the wire in one piece and load it back as a plain buffer.
- redis-180 | Store a compact snapshot followed by a log tail | A command log is durable but slow to replay and large; a binary snapshot is compact and fast to load but misses recent writes.
- redis-181 | Compact a log without buffering new writes twice | When rewriting a log while writes continue, avoid keeping every new write in a memory buffer to merge at the end.
- redis-182 | Stream snapshots straight to the consumer, skipping the disk | Instead of writing a full snapshot to disk and reading it back to send it, serialize directly into the network, and let the receiver parse from the socket.
- redis-183 | Have the snapshot child release memory it has finished with | After a forked child has serialized a large object, it can tell the kernel it no longer needs those pages (`madvise(MADV_DONTNEED)`), bypassing the allocator.
- redis-184 | Run one fork child at a time, and stop children before bulk rewrites | Two snapshot children, or a parent that rewrites its whole dataset while a child is alive, multiply copy-on-write memory and disk contention.
- redis-185 | Serialize numbers in binary, not as decimal text | Write integers and IEEE-754 doubles in fixed-width binary (with a byte swap only on big-endian hosts) instead of formatting and parsing decimal strings.
- redis-186 | Pack many items into each logged or replicated command | When writing a compacted log or propagating a bulk change, emit variadic commands carrying up to K items instead of one command per item, and skip rewriting a command that is already in canonical form.
- redis-187 | Save data in the order that makes loading cheapest, with sizes up front | Choose the serialization order so that each insert on load hits the structure's best case, and write element counts first so the loader can allocate final sizes once.
- redis-188 | Persist expensive derived metadata so loading need not recompute it | If rebuilding derived state on load is costly, serialize it next to the data behind a versioned, backward-compatible format.

- rocksdb-023 | Apply smooth backpressure from background debt, and don't create thrash | Slow writers gradually as background debt (unmerged files) approaches a limit instead of switching between full speed and a hard stall.
- rocksdb-024 | Make range deletions first-class: fragment once, cache, and skip covered keys with one seek | Represent range deletes as non-overlapping fragments sorted by key, built once per immutable unit and cached.

- rocksdb-026 | Merge small fresh segments among themselves before merging into a big level | When the newest level is small, or the next level is busy, merge new files with each other (intra-L0) instead of rewriting a large base level each time.
- rocksdb-027 | Reclaim space incrementally instead of with occasional full rewrites | When space amplification must be reduced, compact a bounded slice of files at a time rather than waiting for a full-database merge.
- rocksdb-028 | Skip merges and searches whose result changes nothing | Don't rewrite data that was just written, don't touch levels with nothing in range, don't run a search whose outcome is predetermined, and delay rewrites that are likely to be redone soon.

- rocksdb-030 | Reorganize data based on observed read cost, and retire the heuristic when it stops paying | Use read-side signals (wasted file probes, hidden entries skipped, read frequency) to trigger merges, not just write volume.
- rocksdb-031 | Strip per-record metadata that no reader can distinguish any more | Once data is older than every snapshot and sits where no older version can exist, its version numbers carry no information.
- rocksdb-032 | Split a large merge into balanced parallel ranges using sampled key anchors | Parallelize one big merge by key range, choosing split points from sampled index keys so each range holds about the same data, and let each worker open only the input files that overlap its range.
- rocksdb-033 | Link a large pre-indexed batch in as its own immutable segment instead of re-inserting it | A large transaction already holds its writes in a sorted, indexed buffer.

- rocksdb-035 | Reserve the minimum while a background job waits, and re-pick when it runs | A queued or long-running job should not lock all of its inputs, or hold back unrelated cleanup, for its whole lifetime.
- rocksdb-036 | Put a membership filter in front of every expensive lookup that usually misses | Before probing a costly structure (a file on disk, an in-memory index, a remote service), check a compact filter with no false negatives.
- rocksdb-037 | Skip filters, and filter checks, where they cannot pay off | Don't build, cache or probe a filter where the answer is almost always "present" (the deepest level of a hit-heavy store), and don't consult a second filter or index when the first already decided.
- rocksdb-038 | Confine all probes for a key to one cache line | Choose one 64-byte block per key from the hash, then set or test all k bits inside that block.
- rocksdb-039 | Tune the space / false-positive / probe-cost trade-off precisely | Configure filters by target false-positive rate or fractional bits per key, and pick the probe count from measurements of the actual filter design rather than the textbook formula.
- rocksdb-040 | Derive all probes from one good hash, and keep persisted hashes separate from in-memory ones | Compute one high-quality hash per key and generate the k probe positions from it with cheap arithmetic (double hashing, multiply and rotate, multiply-shift range reduction).
- rocksdb-041 | Choose filter granularity: one filter per file, partitioned with a pinned top level when large | Check one whole-file filter before consulting the index, instead of per-block filters after it.

- rocksdb-044 | Treat filter readability across versions as a performance requirement | If a format or name change makes existing filters unreadable, every lookup silently falls back to reading data.
