# Lens: amortization (52 techniques)

Batching, bulk operations, incremental work spread over time, growth policies.

Format: `id | title | principle (first sentence)`. The id prefix names the cards file: `../cards/<prefix>.md`.

- curl-040 | Move maintenance sweeps out of the per-item path | Do not run an O(n) cleanup (expiry pruning, deduplication) on every lookup or every insert.
- curl-041 | Throttle periodic and cosmetic work to a time quantum | Work whose value does not depend on running every iteration (progress display, socket-buffer tuning, dead-connection pruning, liveness checks) should run at most once per interval, and per shared resource…
- curl-042 | Do several units of work per wakeup when readiness is cheap to exhaust | Once a loop has paid for a wakeup, process every queued unit it can (all pending datagrams, several turns of an opaque library) before returning, within the fairness budget.
- curl-043 | Fetch random bytes in blocks and hand out slices | If many small random values are needed, request one large block from the cryptographic RNG and consume it in pieces, refilling when it runs out.
- curl-044 | Batch tool invocations and detection work in the build and test pipeline | Spawning a process per file, compiling a probe per guess, or re-parsing the same test file per query all pay a fixed start-up cost many times.
- duckdb-055 | Group many small operations so fixed per-call costs are paid once | Appends, updates, lookups and shared-state publications each carry locks, bookkeeping and storage calls.
- duckdb-056 | Replace many small sorts with one large sort keyed by group | Instead of sorting each group's buffer separately, prefix every row with its group id, run one sort on (group, keys), and hand each contiguous run to its consumer.
- duckdb-057 | Keep setup alive across iterations of an iterative computation | In loops of query-like work (recursive CTEs, fixed-point solvers), reset and reuse operators, hash tables and filters instead of rebuilding them each round.
- haproxy-042 | Pay once at ingest: index, canonicalize and parse a single time | Do the work every later consumer would otherwise repeat (locate fields, lowercase names, validate) once, when the data enters the system, and store the result so later operations are cheap byte compares or…
- haproxy-043 | Size batches for the cache, not for the maximum | Batching amortizes overhead, but past the point where a batch's working set leaves the cache, each item is revisited cold and the batch gets slower; measure and pick the size that keeps the batch hot.
- haproxy-044 | Do more per wakeup: receive and demux several rounds before notifying consumers | While downstream buffers are free, keep receiving and parsing a bounded number of extra rounds, and make one upward call per pass instead of one per frame.
- haproxy-045 | Defer contended updates and let one owner apply them in batches | When many threads must update a shared ordered structure, try the lock once; on failure, or always, push the update to a cheap list and let a single task apply all pending updates under one lock acquisition.
- haproxy-046 | Do expensive bookkeeping once per interval or per batch | Throttle housekeeping that would run on every access to at most once per time interval, and share one expensive measurement (a timestamp) across all the work in a scheduling pass.
- haproxy-047 | Process a batch in one context and flush only at the end | When a stateful transformation (compression, encoding) has a per-flush cost, feed it everything available and flush once per batch instead of once per chunk.
- haproxy-048 | Coalesce small pieces whenever you copy them anyway | If a message made of many tiny blocks is being copied or defragmented anyway, merge adjacent blocks during that copy so every later pass pays per-block overhead fewer times.
- netty-034 | Pay synchronisation once per batch: drain, swap or reserve in chunks | Instead of a lock or CAS per element, move a whole batch at once: swap the producer's buffer for an empty one, drain everything into a private list, or reserve shared capacity in fixed-size chunks.
- nginx-018 | Accumulate small work into batches, bounded by a size threshold and a deadline | Do not pay a fixed per-call cost for every small piece.
- nginx-019 | Defer handlers to the end of the loop iteration so many triggers become one call | Instead of running a handler synchronously each time something small happens, mark the object and post one event; the loop runs it once after all of this iteration's input has been read.
- nginx-020 | Carry progress across calls instead of restarting from the beginning | Remember where the last call stopped (scan offset, tail pointer, insertion position, already-built key) on the object itself, so repeated or re-entered operations continue in O(new work) rather than O(total).
- nginx-021 | Detach the whole pending list under the lock, then process it unlocked | The consumer holds the lock only long enough to take the list head and reset it to empty; producers append in O(1) through a tail pointer-to-pointer.
- nginx-022 | Amortize cleanup: expire a few entries per operation, and only when space is needed | Instead of sweeping a table, remove one or two expired entries each time an entry is released or inserted, and run that cleanup only on the path that actually needs room.
- postgresql-059 | Buffer writes and apply them in multi-row batches, adaptively | Accumulate rows destined for the same target and write them in one call (one page lock, one log record, one round trip per batch), and turn batching off when measurements show batches stay too small to pay.
- postgresql-060 | Replace one query per object with one query for all objects | When a client needs data about many objects, fetch it with one set-based query (or batches of a tuned size) and match it locally, instead of one round trip or lookup per object; replace many point probes with…
- postgresql-061 | Serve many targets with one pass over a large structure, or probe the few directly | When N operations would each scan the same large structure (a buffer pool, a directory), collect the targets and scan once, checking each entry against the set; when the targets are few and small, look them…
- postgresql-062 | Coalesce per-call overhead: move runs, rows and chunks per call | When a routine is called once per character, field or small read, restructure so each call moves a whole run of plain bytes, a whole row or a large chunk.
- postgresql-063 | Pay setup once per batch, plan or command, not per item | Expensive per-operation setup (opening a table's indexes, building a deparse context, creating helper objects, constructing invariant output prefixes) should be done once for the whole batch and reused for…
- postgresql-064 | Run housekeeping every K events or when idle, not on every event | When exactness is not needed, run contended or expensive maintenance (advancing a queue tail, compacting an array, reporting statistics) once every K operations, on a time interval, or opportunistically when…
- redis-025 | Grow capacity geometrically, never by a constant step | A buffer, array or queue that grows by a constant amount (or reallocs on every append) costs O(N²) copying in total.
- redis-026 | Run background maintenance in short, time-budgeted, resumable slices | Housekeeping (rehashing, defragmentation, compaction) runs on a timer with a strict time budget per slice.
- redis-027 | Resize hash tables incrementally, piggybacking on the buckets you already touch | Do not double a huge table in one stop-the-world O(N) pass.
- redis-028 | Advance a cursor; compact the buffer once per batch | After consuming the front of a buffer (a partial write, a forwarded chunk), do not memmove the remainder to offset 0 each time.
- redis-029 | Cap the work per incremental step, not just the useful work | Incremental algorithms (rehash, cursor scan, sampling) count useful items, but pathological data makes them visit huge numbers of useless slots.
- redis-030 | Resize with hysteresis, and pause auto-resize during bulk mutations | Grow and shrink thresholds should be far apart (grow at 100% fill, shrink at 1/8) so a structure near a boundary does not thrash.
- redis-031 | Chunk long operations and service the event loop between chunks | When one operation cannot be avoided (loading a giant key, emptying a huge table), split it into bounded chunks and process events, progress callbacks or keep-alives between them.
- redis-032 | Amortize expensive checks: test every N iterations or after a threshold delta | If a check (read the clock, compute global memory, update a peak) costs more than the loop body, run it every N iterations, or only once a cheap local counter has moved past a threshold.
- redis-033 | Process a rotating slice of a large population per tick | Do not touch every client or database on each timer tick (O(N) per tick).
- redis-034 | Expire lazily on access plus an adaptive background sweep | Check TTLs when a key is read, which costs nothing for keys nobody reads.
- redis-035 | Spread large catch-up work across commands and a timer continuation | When a limit is suddenly far exceeded (memory over maxmemory after a big rehash allocation or a lowered limit), do not fix it all in the current request.
- redis-036 | Tune the tick rate: more frequent, smaller slices vs idle CPU | The frequency of periodic housekeeping is a latency/CPU dial.
- redis-037 | Stream accumulated deltas to the background worker continuously | While a background job builds a snapshot, the foreground keeps producing changes.
- rocksdb-051 | Update long-lived derived state by diff, not by full rebuild | When the inputs to a long-lived structure change slightly (a few files added or removed), add and remove only the affected parts instead of rebuilding the whole structure.
- rocksdb-052 | Keep running aggregates instead of recomputing per query | If a value is queried on every insert (an estimated size, a bucket count), maintain it incrementally as items are added, with one cheap update per step, rather than recomputing or dividing on each query.
- rocksdb-053 | Recompute derived state once per batch of mutations | When applying many mutations, recompute expensive derived state (scores, layouts, indexes) once at the end rather than after each one.
- seastar-036 | Accumulate updates locally and publish them once per cycle | Instead of charging every completion or event to a shared or expensive structure one at a time, sum them in a local accumulator and report once per poll pass.
- sqlite-048 | Write immutable batches and merge them, instead of updating large structures in place | Collect new entries into small sorted segments and merge segments into larger ones over time, rather than rewriting a big structure on every insert.
- sqlite-049 | Split big maintenance jobs into bounded, resumable steps | Instead of merging or compacting everything at once, do a bounded amount of work per step, persist the progress, and resume later.
- sqlite-050 | Maintain aggregates and membership incrementally instead of scanning | Keep a running sum, a per-slot count, a compact list of live entries or a sorted window up to date at each modification.
- sqlite-051 | Check rare conditions periodically, not on every step | Poll for interrupts, progress callbacks and rare error flags only at loop back-edges or every N units of work.
- sqlite-052 | Reset many flags in O(1) with a generation counter | Instead of clearing an array of "done" flags at every run, store in each slot the generation number when it was set.
- sqlite-053 | Generate in blocks and serve from a buffer | When a producer has per-call overhead, generate a whole block of output per call and hand it out from a buffer.
- tokio-029 | Funnel cross-thread updates into a lock-free list that the owner drains wholesale | Instead of letting every thread mutate a structure under a lock, have producers mark an item "queued" and push it onto an atomic stack (or a small mutex-guarded list).
- tokio-030 | Move many items per synchronization round trip (receive-many, reserve-many, N-per-poll) | Offer operations that transfer N items or N permits with one atomic update, one lock acquisition or one wakeup.
