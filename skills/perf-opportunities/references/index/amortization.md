# Lens: amortization (117 techniques)

Batching, bulk operations, incremental work spread over time, growth policies.

Format: `id | title | principle (first sentence)`. The id prefix names the cards file: `../cards/<prefix>.md`.

- aeron-028 | Coalesce small messages into one transmission unit up to a size cap | Scan forward over as many ready, contiguous small items as fit in one unit (an MTU, a frame, a page) and emit them in a single operation, without waiting on a timer to accumulate more.
- aeron-029 | Batch naturally: drain what is available, then publish progress or flush once | Consume everything that is ready up to a limit, then do the per-batch cost once: one head update, one write call.
- aeron-030 | Bound the work per cycle, and tune the bound per path | Cap the items, bytes or scans processed per loop iteration so one source cannot starve the others or stall the loop.
- aeron-031 | Run secondary work at a lower rate: every Nth cycle, on idle, or on a deadline | Keep the per-iteration loop to the latency-critical data path.
- aeron-032 | Coalesce updates to shared or remote state with hysteresis and publish-once | Don't publish a position, limit, counter or acknowledgement on every advance.
- aeron-033 | Spread bulk maintenance across cycles in proportion to throughput | Move large maintenance jobs (zeroing buffers, deleting files, freeing resources) off the producer's path onto a housekeeping loop.
- aeron-034 | Move data in contiguous blocks, not message by message | For bulk consumers (archiving, replay, bridging), hand over the whole contiguous range up to the last complete record in one call, and append blocks with a single publish.
- curl-040 | Move maintenance sweeps out of the per-item path | Do not run an O(n) cleanup (expiry pruning, deduplication) on every lookup or every insert.
- curl-044 | Batch tool invocations and detection work in the build and test pipeline | Spawning a process per file, compiling a probe per guess, or re-parsing the same test file per query all pay a fixed start-up cost many times.
- duckdb-055 | Group many small operations so fixed per-call costs are paid once | Appends, updates, lookups and shared-state publications each carry locks, bookkeeping and storage calls.
- duckdb-056 | Replace many small sorts with one large sort keyed by group | Instead of sorting each group's buffer separately, prefix every row with its group id, run one sort on (group, keys), and hand each contiguous run to its consumer.
- duckdb-057 | Keep setup alive across iterations of an iterative computation | In loops of query-like work (recursive CTEs, fixed-point solvers), reset and reuse operators, hash tables and filters instead of rebuilding them each round.
- envoy-031 | Coalesce cross-thread posts: one scheduled publish per batch, only when something changed | Instead of posting a task to every worker per changed item, append items to a pending set and schedule a single publish when the set goes from empty to non-empty, or once per event-loop iteration.

- envoy-034 | Expire many entries with one timer armed for the oldest | Keep entries in access order (an LRU list) and arm a single timer for the oldest entry's expiry.
- h2o-022 | Coalesce small writes into one flush per loop turn, but flush at once when idle | Gather output from many producers (streams, frames, header plus body) into one buffer or vector and emit it with a single write at a defined flush point. (also: NATS)
- h2o-023 | Accumulate control-plane changes and reconcile them once | Do not issue a kernel call for every interest change or submission.
- h2o-024 | Make each call into a per-call-cost API do as much work as possible | When an API has a fixed cost per invocation (setup, state checks, flush, syscall, iovec walk), give it the largest input it can process: whole buffers instead of fixed small slices, full blocks instead of…
- h2o-025 | Switch strategies at a measured break-even size | A technique with a fixed setup cost (compression framing, creating a pipe, zero-copy bookkeeping) pays off only above some payload size.
- h2o-026 | Hoist invariant work out of the per-item path | If a check or query gives the same answer for every element of an operation (buffer space for a fixed-width field, the current time, the thread ID), do it once per operation and reuse the result.
- h2o-027 | Group a received batch by destination before dispatching | After pulling many items in one go, hand consecutive items for the same destination (connection, partition, tenant) to it in one call, so lookup and state setup are paid once per run rather than once per item.
- h2o-028 | Pipeline many requests over one channel | Instead of one in-flight request per connection, keep a write queue and a read queue on a single non-blocking channel.
- h2o-029 | Acknowledge in batches sized to the flow | Do not acknowledge every packet. Let the sender ask for an ACK every N packets, with N derived from a fraction of the congestion window, and tolerate small reordering before sending an immediate ACK.
- haproxy-042 | Pay once at ingest: index, canonicalize and parse a single time | Do the work every later consumer would otherwise repeat (locate fields, lowercase names, validate) once, when the data enters the system, and store the result so later operations are cheap byte compares or…
- haproxy-043 | Size batches for the cache, not for the maximum | Batching amortizes overhead, but past the point where a batch's working set leaves the cache, each item is revisited cold and the batch gets slower; measure and pick the size that keeps the batch hot.
- haproxy-044 | Do more per wakeup: receive and demux several rounds before notifying consumers | While downstream buffers are free, keep receiving and parsing a bounded number of extra rounds, and make one upward call per pass instead of one per frame. (also: curl, memcached, Kafka)
- haproxy-045 | Defer contended updates and let one owner apply them in batches | When many threads must update a shared ordered structure, try the lock once; on failure, or always, push the update to a cheap list and let a single task apply all pending updates under one lock acquisition. - haproxy-046 | Do expensive bookkeeping once per interval or per batch | Throttle housekeeping that would run on every access to at most once per time interval, and share one expensive measurement (a timestamp) across all the work in a scheduling pass. (also: curl, PostgreSQL, H2O)
- haproxy-047 | Process a batch in one context and flush only at the end | When a stateful transformation (compression, encoding) has a per-flush cost, feed it everything available and flush once per batch instead of once per chunk.
- haproxy-048 | Coalesce small pieces whenever you copy them anyway | If a message made of many tiny blocks is being copied or defragmented anyway, merge adjacent blocks during that copy so every later pass pays per-block overhead fewer times.
