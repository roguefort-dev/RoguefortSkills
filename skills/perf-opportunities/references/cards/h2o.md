### h2o-002 — Intern well-known strings once, then compare by identity
Lens: algorithms · Source: H2O
Principle: At the input boundary, map each known name (header, keyword, symbol) to a unique static object. After that, equality is a pointer compare, "is it known?" is a range check, and per-name metadata is indexed by `token - table`.
Why it is faster: A string compare is O(length) with data-dependent branches. A pointer compare is one instruction. Static per-token metadata (static-table index, "special" flags, "likely to repeat", a lookup function) replaces repeated searches and lets ordinary names skip special-case chains. The cost is paid once per name at parse time, and unknown names still need a string path.
Applies elsewhere: Web / backend: Use constant header objects (Netty `AsciiString`, Go canonical header cache). Intern JSON keys that recur across messages. • Native / systems: Symbol and atom tables in interpreters and compilers. Enum-indexed handler tables in protocol stacks. • Data / databases: Intern column names and keywords in catalog lookups, and store the interned ID in plans. • Embedded: Map protocol field names to small enum IDs at parse time and switch on the ID.
Watch out: Identity comparison is correct only if every producer interns. A non-interned copy of a known name silently fails the pointer test. The table must be immutable, or safely published, if threads share it.

### h2o-004 — Recognize a small fixed key set with a generated decision tree
Lens: algorithms · Source: H2O · Also: memcached
Principle: For a closed set of keywords, generate code that switches on length, then on one discriminating character, then does a single compare. No hashing, no collisions, no runtime table.
Why it is faster: Two well-predicted branches narrow the set to one candidate, and the length test rejects most mismatches for free. Compile-time literals let the compiler unroll and constant-fold the final compare. Generating one matcher per name, which compares only that name's candidate values, replaces a scan of a whole table. In a dynamic language the same idea is a dict lookup instead of an if/elif chain. The cost is a build-time generator, and every new keyword means regenerating.
Applies elsewhere: Web / backend: Method and fixed-route dispatch. Event routers in JS or Python should use a map instead of chained conditionals. • Native / systems: gperf-style recognizers, command dispatch in Redis-like servers, opcode decoders in emulators. • Data / databases: SQL keyword lexers, and enum-coded wire-protocol message types. • Embedded: CLI and AT-command keyword matching without heap tables, compiled into ROM.
Watch out: Hand-maintained trees drift out of sync with the key list, so generate them. For large or open-ended key sets, a real hash table is simpler and just as fast.

### h2o-005 — Replace expensive arithmetic with cheaper exact or approximate forms
Lens: algorithms · Source: H2O
Principle: Swap slow operations on hot paths for cheaper ones: a hardware bit-scan for log2, an integer threshold for a float probability, a value precomputed once per rare event for a per-event transcendental, a polynomial for a libm call.
Why it is faster: floor(log2(x)) is `width-1-clz(x)`, one instruction, where a de Bruijn sequence needs about 8 ALU operations plus a table load. Some environments (BPF) have no floating point, and many cores do float slowly. Comparing a random u32 against a precomputed `rate * UINT32_MAX` gives the same distribution. When a value depends only on state that changes rarely (a loss event), compute it there and let the frequent path (every ACK) just read it. When about 1e-4 relative error is acceptable, a low-degree polynomial on the mantissa beats libm. Approximations need a fallback for edge inputs.
Applies elsewhere: Web / backend: `Math.clz32` for next-power-of-two sizing in JS. Integer-threshold sampling for request tracing. • Native / systems: Allocator size-class selection and histogram bucket indexes from clz. Fast exp, log or rsqrt approximations in games and DSP. • Data / databases: HdrHistogram-style bucketing. Cost-model terms precomputed per statistics refresh rather than per row. • Embedded: Fixed-point probabilities and thresholds on cores without an FPU. Polynomial sigmoid in on-device inference.
Watch out: clz of zero is undefined, so guard it (the edge-value fix above). Approximations must state their error bound and keep an exact fallback. A precomputed value is only valid until the state it depends on changes.
Seen in H2O: 4efd53db72 2023-01-04 `ullog2()` in the quantile library became `63 - __builtin_clzll(x)`. It replaced a six-step bit smear, a de Bruijn multiply and a 64-entry table. 5ee146b9f7 2023-01-04 fixed the edge values. • 499217b293 2021-04-09 The h2olog sampling rate is precomputed in userspace as a u32 threshold and compared with `bpf_get_prandom_u32()` in the kernel. 091e3d6154 2021-05-25 maps a rate of 1.0 to 232 correctly. • 9d1c84bb77 2021-12-13 The pico congestion controller computes `bytes_per_mtu_increase` (min of Reno and Cubic, using `cbrt`) once in `pico_on_lost`. `pico_on_acked` only reads it, so there is no cbrt or division per ACK. • 1ca96156a8 2026-09-09 `fast_cbrt()` evaluates a fourth-degree polynomial on the mantissa, with continuous slope at the joints. It takes about 9 clocks per call on Zen 3, which puts the worst case at about 3% of AES-GCM cost. It falls back to libc for non-IEEE and subnormal inputs.

### h2o-006 — Pick the timer structure from the timeout distribution
Lens: algorithms · Source: H2O
Principle: If every timer in a group has the same duration, a FIFO list is already sorted by expiry, so every operation is O(1). For arbitrary durations, a hierarchical timing wheel gives O(1) insert and cancel, with cascading amortized over time, instead of an O(log n) heap.
Why it is faster: Event-loop servers arm and cancel timers on almost every I/O but rarely let them fire, so insert and cancel dominate. A per-duration FIFO needs only a tail append and an intrusive unlink. A wheel picks the level from `clz(now ^ expire)`, picks the slot from time bits, and finds the next wake-up from a slot-occupancy bitmap. The trade-offs: slot-granularity precision, and cascades that move entries in bursts at level boundaries. Skipping empty slots keeps cascades cheap.
Applies elsewhere: Web / backend: One FIFO per configured idle or keep-alive timeout. A wheel (Netty `HashedWheelTimer`) for per-request deadlines. • Native / systems: User-space TCP retransmission timers, and kernel-style timer wheels in custom reactors. • Data / databases: Lock and lease expiry in a lock manager. Uniform-TTL cache expiry as a plain FIFO. • Embedded: RTOS software timers grouped by fixed period classes. A tiny wheel driven by one hardware tick.
Watch out: Per-duration lists stop working once durations become arbitrary. Size wheel levels so that common timeouts land in low levels, otherwise cascades dominate. Whatever the structure, detach due entries before running callbacks.
Seen in H2O: 164f64d4c3 2014-09-04 `h2o_timeout_t` is one fixed duration plus an intrusive list, and each entry carries its own callback. • 2170a1c319 2014-09-11 Entries store `registered_at` instead of a deadline, so expiry is `registered_at > now - timeout` and the duration can change later. • cab2e1bcc3 2014-09-04 The due list is detached before firing, so callbacks that re-arm cannot cause unbounded re-entry. • ceab5af397 2017-09-25 First hierarchical wheel: 4 wheels of 64 slots, wheel chosen by `clz(last_run ^ expire)`. 10f29eb497 2017-09-25 and 75452d34ef 2017-09-27 replaced the fixed 1 s and 100 ms lists and added `h2o_timerwheel_get_wake_at` for the poll timeout. • c9d538fc07 2017-10-31 32-bit relative tick, 6 wheels, unrolled slot computation. 3f8d5361b5 2017-11-03 takes only entries that are actually due from the boundary slot. • 097f07398e 2018-09-03 The rewritten wheel replaced `lib/common/timeout.c` entirely. 41ed90d62c 2018-08-15 skips empty slots during cascade ("O(N) -> O(1)" for large intervals). d2b6750288 2018-08-18 retuned it to 3 levels of 32 slots, so 1 s lands in level 2. d63a7af1ab 2018-09-01 dropped a re-check pass, because entries collected from wheel 0 are guaranteed to be due.

### h2o-008 — Dictionary-code repetitive keys, with a bounded table and selective admission
Lens: algorithms · Source: H2O
Principle: Replace repeated fields with small indexes into a static or dynamic dictionary. Cap the dynamic table, and insert only entries that are likely to repeat, so that encoding cost and per-connection state stay bounded.
Why it is faster: Most response headers repeat across a connection, and an index costs one byte against tens of literal bytes. Precomputing the static index per name makes the common case a table read. Dynamic-table search is linear, though, and each insertion spends bytes on the wire and table space. A small entry cap keeps the search bounded. Admitting only names flagged likely-to-repeat, with long enough values and only while there is room, keeps one-off values from churning the table. Entropy coding is applied only when it actually shrinks the string.
Applies elsewhere: Web / backend: gRPC metadata compression. Key dictionaries in telemetry and log protocols (OTLP-style string tables). • Data / databases: Dictionary encoding only for low-cardinality columns, with a capped dictionary per block. • Native / systems: LZ match finders with bounded windows, and small MRU tables for repeated values in binary RPC. • Embedded: A ROM static table of frequent field values in radio protocols, with no dynamic state at all.
Watch out: A dynamic table couples the two ends: QPACK readers can block on encoder-stream updates, and every table costs per-connection memory. If the cap is too small you lose compression ratio. If it is too large, linear search starts to show up in profiles.
Seen in H2O: 1c444a8fe1 2014-09-04 Response headers are emitted with static-table name indexes stored on each token. 15991fa96e 2014-09-04 Huffman-codes literals. b39174dbd9 2015-02-22 `encode_huffman` returns 0 when the output would not be smaller, and the raw literal is sent instead. • c90a280338 2014-09-26 Dynamic-table indexing for responses. a7c1fa973a 2014-09-26 caps it at 32 entries "so that table compression should not slow down too much". 487b2dfdbe 2014-09-26 walks the ring buffer directly and compares token names by pointer. • f38e4e0086 2015-08-22 `:method GET`/`POST` and `:scheme https` go straight to static indexes. 2aa262bb38 2015-08-22 does the same for `accept-encoding: gzip, deflate`. f509fe2871 2015-10-30 remembers the smallest name-only dynamic match so a name-indexed literal can be emitted. • e3b72f56b5 2018-11-13 added a `likely_to_repeat` token flag. 23c1d43e80 2018-11-16 The QPACK encoder with encoder streams inserts only flagged names whose values are 8 bytes or more and fit in the table, and stops inserting while blocked streams are at their limit. • c4712402e6 2026-05-25 QPACK blocking is wired into the HTTP/3 server, and 48d4c6912a 2026-05-25 derives the blocked limit from stream concurrency. 4e6a7ca185 2026-06-16 sets a 16 KB default dynamic table in both directions. • c4712402e6 2026-05-25 QPACK blocking wired into the HTTP/3 server, with 48d4c6912a 2026-05-25 deriving the limit from concurrency. 0b7ae54176 2026-05-26 enables the encoder table in the client, and 4e6a7ca185 2026-06-16 defaults the dynamic table to 16 KB in both directions.

### h2o-009 — Decode bit streams with precomputed state tables, and fold validation into the lookup
Lens: algorithms · Source: H2O
Principle: Replace bit-at-a-time decoding with a finite-state table that consumes a nibble or byte per step. Widen each table entry with classification flags, so validation comes free with decoding.
Why it is faster: A 4-bit state machine does two table lookups per input byte, with no inner per-bit loop and no data-dependent branch per bit. Flags in the same entry (invalid character, uppercase) remove a second validation pass over the output. The cost is table size, roughly states x 16 entries, which competes for cache.
Applies elsewhere: Native / systems: Multi-bit DEFLATE and zstd Huffman decoders. DFA-based UTF-8 decoders. • Web / backend: JSON and CSV tokenizers whose class table also carries "needs escaping" bits. • Data / databases: Collation tables that fold case and validate in one lookup. • Embedded: Protocol state machines stored as const tables in flash.
Watch out: On small caches or microcontrollers, a large table can evict hot data or overflow ROM. Weigh nibble against byte tables. Make sure the end-of-stream and padding states are handled.
Seen in H2O: c44e43ac2c 2014-12-30 In the founding `lib/http2/hpack.c`, `huffdecode4()` indexes `huff_decode_table[*state] + in` (an nghttp2-derived table) and is called twice per input byte, writing into a pool buffer sized `len * 2`. • d05cffa369 2016-07-21 Added an `NGHTTP2_HUFF_UPPER_CASE_CHAR` flag to the decode-table entries for 'A' to 'Z', next to the existing invalid-character flags, so header names are validated during decoding.

### h2o-011 — Summarize a large set as a compact probabilistic digest
Lens: algorithms · Source: H2O
Principle: To tell a peer "which items I already have" cheaply, send a Golomb-coded set (or Bloom filter) of truncated hashes. The receiver decodes it into a sorted array and binary-searches it.
Why it is faster: A Golomb-coded set stores sorted hash deltas with near-optimal bits per element. A few bytes in a cookie or header can describe dozens of cached resources. Decoding into a sorted `uint64_t` vector makes each membership test an O(log n) bsearch. False positives only cause a skipped push. Caching the encoded form until the set changes avoids re-encoding on every response.
Applies elsewhere: Web / backend: Mobile offline sync and package managers sending "known object" digests so already-held items are skipped. • Data / databases: Anti-entropy summaries between replicas, and LSM bloom filters in front of disk reads. • Native / systems: rsync-like tools and CDN edges exchanging compact "seen" sets.
Watch out: The digest helps only if peers actually send it. H2O deleted cache-digest support in 2026 after the mechanism saw no adoption. The false-positive rate must be tuned to what a wrong "already have it" costs.
Seen in H2O: d3d01f0e9c 2015-08-01 imported golombset. 2a6ea3763f 2015-08-09 "casper" stores SHA1(path, etag), masked to `capacity_bits`, as a sorted key vector in a cookie. The encoded cookie is cached and invalidated on insert. • e69e915da9 2016-07-15 removed the ETag from the casper key, so fresh-cached resources match and are not pushed again. • 2a889c08c0 2016-06-30 Cache Digests: base64url and Golomb decoding into a sorted `uint64_t` vector per frame, looked up with `bsearch`. f11c8bfc05 2016-06-30 parses the digest during HPACK decoding, and `push_path` refuses pushes the digest marks as fresh.

### h2o-012 — Track in-flight items in an append-only log of fixed-size blocks
Lens: algorithms · Source: H2O
Principle: Record outstanding packets, and the frames inside them, as tagged entries appended to chained fixed-size blocks. Process acknowledgements and losses with a sequential iterator, and free whole blocks from the head.
Why it is faster: Items are created in order and mostly resolved in order, so a log matches the access pattern. Appending needs no per-item heap allocation, and iterating in packet-number order is cache-friendly. A typed record per frame with an ack/lost callback avoids pointer-chasing maps. Retirement must not stop at the first entry that cannot be freed yet, or one stuck entry pins all memory behind it.
Applies elsewhere: Native / systems: Retransmission queues in user-space TCP and QUIC stacks, and outstanding-request tables in RPC clients. • Data / databases: Undo and redo logs as typed records in append-only blocks. WAL segment recycling that skips pinned segments instead of stopping. • Embedded: Fixed pools of blocks for unacknowledged radio frames, with no malloc.
Watch out: Head-only reclamation is fragile when items resolve out of order. Bound the log and handle entries that stay pinned for a long time, as the 2022 fix did.
Seen in H2O: 58a9d902ca 2019-01-18 quicly was vendored in with `sentmap.h`: `quicly_sent_t` records with an `acked` callback, `st_quicly_sent_block_t` blocks, a prepare/allocate/commit API, and an iterator used by ACK and loss processing. • 06c4e458f4 2022-05-26 Packets still counted in congestion bytes-in-flight are skipped (`quicly_sentmap_skip`) instead of ending retirement, and the iterator is rewound afterwards. This mitigated "sentmap size explosion" and added `num_sentmap_packets_max` stats.

### h2o-013 — Keep interval sets in a B+-tree with an inline first leaf and an append fast path
Lens: algorithms · Source: H2O
Principle: Store received byte ranges in a B+-tree so heavy reordering stays O(log n). Embed the first leaf in the owner so small sets never allocate, and handle "extends the last range" in O(1).
Why it is faster: A sorted array of ranges needs O(n) memmoves per insert once gaps multiply, and an attacker can force that. A B+-tree bounds insert cost at O(log n). Most streams arrive in order, so a check against the last range covers the common case with no tree walk. Embedding the first leaf (fan-out 16) defers any allocation until the set really is fragmented.
Applies elsewhere: Native / systems: TCP SACK scoreboards and reassembly queues. • Web / backend: Tracking downloaded byte ranges for resumable or range-cached HTTP objects. • Data / databases: Free-extent maps in filesystems and storage engines, and MVCC visibility interval sets.
Watch out: For tiny sets a B+-tree is more code and overhead than a short array, which is why the inline leaf matters. Still cap the total number of gaps, because even O(log n) memory can be exhausted.
Seen in H2O: 78288b39e4 2026-10-23 The quicly import adds `bplus_ranges.h`/`bplus_ranges.c` (546 lines) and switches `quicly_recvstate_t::received` to it. `quicly_bplus_ranges_add()` starts with `if (last->start <= start && start <= last->end) { extend; return 0; }`. The gap limit scales with the committed window (max(63, window/1024+1), up to 222).

### h2o-016 — Generate output only when the consumer can take it
Lens: laziness · Source: H2O
Principle: Do not serialize, encrypt or read the next chunk until the sink is ready for it. Then produce only a bounded amount and stop as soon as the sink pushes back.
Why it is faster: Output produced early is built from stale decisions, such as a priority order that changed meanwhile. It holds buffers across event-loop yields, and it may be encrypted only to wait behind a full socket. Producing just in time, in small fixed portions, keeps plaintext, ciphertext and the kernel copy in cache, lets a single recycled buffer serve every pass, and never computes bytes that cannot be sent yet. The cost is up to one extra loop iteration of delay before data moves, which H2O weighs against RTT.
Applies elsewhere: Web / backend: Honour `drain` in Node streams and produce the next chunk on demand. Fetch the next DB page only when the response socket drains. • Native / systems: Message brokers that serialize per connection only on EPOLLOUT. Streaming gzip or encryption proxies that transform only what the socket accepts. • Data / databases: WAL shippers that checksum and encrypt the next batch when the previous send completes, not the whole backlog. • Embedded: Fill the UART or radio TX FIFO from a priority queue in the TX-empty interrupt.
Watch out: Waiting for writability adds about one loop iteration of delay per write. On a busy loop relative to RTT that delay can outweigh the benefit, which is why H2O gates its latency-optimized write mode on measured loop time. Producers must be fast enough to refill synchronously.
Seen in H2O: 563323026d 2016-05-16 After a write completes, HTTP/2 waits for a writability notification (`h2o_socket_notify_write`) before generating the next frames, so the scheduler's choice is fresh. 691a68e477 2016-05-23 made this poll-then-write unconditional on the evloop backend. • 088c5c60e5 2021-10-22 TLS records are generated inside `write_core`: flush pending ciphertext, encrypt at most 4 full records, write, and stop on a partial write while remembering `pending_off`. Before, the whole write request was encrypted up front. The commit message says it "Improves locality". 8dd166cce0 2021-10-23 ported it to libuv. • 05e6bcb4cb 2022-08-08 Pull-style body vectors are read into memory only immediately before TLS record generation, not while the socket might yield to others because of a fairness cap. 9686731949 2022-08-08 triggers `write_core` when such data is pending.

### h2o-017 — Bypass layers that would pass data through unchanged
Lens: laziness · Source: H2O
Principle: When a pipeline stage (scripting layer, output filter, transform) would forward data unmodified, detect it and wire producer to consumer directly. Do not run the stage just to copy bytes.
Why it is faster: Each layer costs per-chunk dispatch, and for embedded interpreters it also costs fiber switches, GC objects and copies. A generic filter can also block a faster path: chunked encoding as a filter forced push-mode copies. Removing the stage from the chain, or folding it into the transport, removes all of that per chunk. The same reasoning stops filters from running twice on internal subrequests whose output the parent filters anyway.
Applies elsewhere: Web / backend: Pipe an upstream stream natively instead of iterating chunks in JS. Skip middleware for WebSocket upgrades. Avoid a TransformStream when the sink can frame natively. • Native / systems: At FFI boundaries (N-API, JNI, Lua), pass native buffers rather than arrays of VM strings. • Data / databases: Stream a stored procedure's unchanged result set straight to the wire. Use COPY paths that bypass row-level processing. Fuse a projection into the scan.
Watch out: Passthrough detection must be exact. Bypassing a filter that would have transformed data (compression, header rewrite, security headers) silently changes output. Folding a layer into the transport trades modularity for speed.
Seen in H2O: e3687413ba 2016-01-04 If a Rack body is an `http_request` response object, the chunked sender is fed directly from the HTTP client and no Ruby `each` fiber runs. • 96a4071d4d 2017-10-25 An mruby output filter that only passes the upstream body through unlinks itself from the chain with `h2o_remove_ostream`. • f4bbc080b7 2018-01-21 Subrequest body chunks are collected in a native `h2o_buffer_t` instead of a VM Array of new Strings, with no GC arena churn. • 37025e98d6 2018-08-01 Chunked encoding moved from a generic filter into the HTTP/1 writer (PR f52f2ec2b5 2018-08-09 deleted `lib/handler/chunked.c`). e4ef3a8bd4 2018-08-02 then let chunked responses use pull mode. • c28676dc17 2018-10-31 `req->disable_filters` stops output filters such as compression being applied a second time to internal subrequests. • 203252daba 2021-02-25 Tunnel responses (101, or 200 to CONNECT) are forwarded as-is, skipping `on_setup_ostream` and per-chunk filter dispatch.

### h2o-020 — Do not rediscover what the code already knows
Lens: laziness · Source: H2O
Principle: Pass lengths instead of rescanning for NUL. Append literals directly instead of interpreting format strings at runtime. Skip escaping for identifiers that are known to be safe. Use a tiny exact predicate instead of a general locale-aware classifier. Keep constants static instead of rebuilding them per call.
Why it is faster: `strlen` is O(n) just to test for emptiness. `sprintf` parses its format string and goes through locale machinery on every call. iostreams add virtual dispatch and state per operation. `isprint()` is locale-aware where JSON needs only `c < 0x20 || c == 0x7f`. Building a heap string for a compile-time constant allocates on every call. Each fact (a length, a key's safety, an upper bound) is known at compile time or to the caller, so recomputing it is pure waste.
Applies elsewhere: Web / backend: Hoist constant regexes and `Buffer.from` literals to module scope. Avoid `String.format` in Java hot paths. Template engines can skip escaping trusted constants. • Native / systems: `std::string_view` and `&str` APIs that carry lengths. `fmt::format_int`/`itoa` instead of printf. • Data / databases: Bind parameters with explicit lengths. CSV and JSON exporters writing column names from precomputed byte strings. • Embedded: Length-prefixed strings in ROM. Hand-rolled integer formatting instead of a full printf.
Watch out: Skipping escaping is safe only for values that are guaranteed safe by construction. Never apply it to anything influenced by input. A hand-written formatter must handle every edge value, such as INT_MIN.
Seen in H2O: 4517d48355 2014-10-07 The HTTP/1 status line uses a precomputed upper bound and a direct `sprintf` instead of the allocating `h2o_sprintf`. b9f342e73f 2015-02-24 "limit the use of sprintf (as it may be slow)": the proxy builds cookie and x-forwarded-* headers with `APPEND_STRLIT`/`APPEND`. • cb98c7c928 2017-09-06 `strlen(s) == 0` and `== 1` became `s[0] == '\0'` and `s[1] == '\0'`. • 20221d6cb6 2020-04-03 h2olog: "don't use iostream; it's too slow". 14ec4b6530 2020-04-18 uses `fwrite` wherever possible, with name lengths supplied by generated code. • 87d5349e8a 2020-04-17 JSON keys are compile-time identifiers, so `"name":` is written without escaping. 63c80f7f26 2020-04-17 replaced `isprint(3)` with a two-comparison `json_need_escape()`. • 2fd91ac451 2021-01-04 `json_write_pair_[cn]` take `value_len` "to avoid unnecessary use of strlen()". • a2c7233f7b 2024-01-16 A per-call `std::string` request literal became `static const char req[]` with `sizeof(req)-1`.

### h2o-021 — Make repeatable actions idempotent with a cheap membership check
Lens: laziness · Source: H2O
Principle: Before performing an action that may be requested repeatedly (pushing a resource, appending a token, renewing a credential), check a small set or condition that says whether it has already been done or would change anything.
Why it is faster: A duplicate server push wastes bandwidth and server work. A duplicated header token wastes bytes and confuses caches. A ticket re-issued with the same key costs an encryption and a larger handshake. A per-connection hash set, or a scan of the existing value, costs O(1) or O(header) and removes all of these. The set can be created lazily, so connections that never push pay nothing.
Applies elsewhere: Web / backend: Middleware adding `Vary` or `Cache-Control` directives. WebSocket servers deduping subscription pushes per session. JWT refresh only when the signing key actually rotated. • Data / databases: Check before appending to set-like CSV columns. Skip re-validation when the version is unchanged. • Native / systems: Reload a certificate only when its file changed. Build tools that do not append duplicate flags.
Watch out: The membership structure needs a memory bound. A bounded cache that forgets only causes redundant work, but a probabilistic structure with false positives would skip needed work.
Seen in H2O: 0fa6ecbdfc 2016-03-16 `h2o_set_header_token` checks `h2o_contains_token` on all matching headers before appending, so no `vary: accept-encoding, accept-encoding`. Used by the compress, expires and file handlers. • 7b1085eaeb 2016-05-11 A per-connection push memo: a lazily created 1024-entry cache with no mutex, keyed by the XOR of scheme, authority and path hashes. `push_path` returns early if the entry already existed. • 28f21f3bd2 2017-10-06 Session-ticket renewal is requested only when the newest key is already valid (`not_before <= time(NULL)`). ### h2o-022 — Coalesce small writes into one flush per loop turn, but flush at once when idle
Lens: amortization · Source: H2O · Also: NATS
Principle: Gather output from many producers (streams, frames, header plus body) into one buffer or vector and emit it with a single write at a defined flush point. When nothing else could join the batch, write immediately instead of deferring.
Why it is faster: Each write costs a syscall (or TLS record plus syscall) and often its own small TCP segment or packet. Coalescing frames from all multiplexed streams gives one `writev` per loop iteration and full segments. Processing all received packets before replying merges ACKs with data. Extending the previous iovec when new data is contiguous keeps vectors short. Deferral only pays when more work can arrive before the flush. Otherwise it adds a loop pass of latency, so flush directly when the connection is otherwise idle.
Applies elsewhere: Web / backend: Flush consolidation in gRPC and Netty. Batched Redis pipeline replies. Send headers and the first body bytes together. • Native / systems: Log writers that build one iovec array per tick. Network stacks that merge adjacent buffers. • Data / databases: Group commit that commits immediately when no other transaction is waiting. WAL writers that gather record headers and payloads. • Embedded: Coalesce small flash writes into page-sized writes, and send queued radio frames in one burst.
Watch out: A deferred flush with nothing else queued is pure latency. Unbounded gathering also raises tail latency and memory use. Cap the batch and keep the "idle means write now" path.
Seen in H2O: 056d6fc3e3 2014-09-04 "Gather responses of different streams into single uv_write". c2a52a44dc 2014-09-08 made the zero-timeout queue, drained before polling, the flush point. • 53531911ab 2015-11-19 Right after reading from an HTTP/2 connection, a pending write with none in flight is emitted immediately instead of waiting for the deferred slot. • fac62dbffe 2018-01-12 WebSocket queues up to 4 frames (`bufs[4]`) and sends them with one vectored write. • c5ab415032 2018-08-08 In HTTP/1 pull mode with content-length, `bufs[bufcnt - 1].len += cbuf.len` extends the last iovec instead of adding one. • 4c22d7391e 2020-02-24 HTTP/3 "read all packets before sending something": an immediate send per batch was replaced by scheduling one send after the batch. • 217185114c 2021-03-01 The HTTP/1 client writes request headers and the first chunked body piece in one `writev`. • 8268b41d8a 2023-11-01 The key-daemon client writes directly from the read callback instead of going through a zero-delay timer, removing a loop pass. • Also seen in NATS (nats-032): 640bd8d2ba 2012-11-20 "Optimize outbound traffic": `deliverMsg` stops flushing per message and records `c.pcd[sub.client]`; `readLoop` flushes each entry after `parse()`. • 8fa318738c 2013-08-19 "Attach /r/n to msg to avoid extra write": two writes per delivery instead of three. • 481697ef67 2018-06-04 Per-connection buffer chain drained by a writer with one `net.Buffers.WriteTo` (`writev`). • 2206f9e468 2023-04-25 `queueOutbound` copies into the free capacity of the last queued buffer before taking a new one.

### h2o-023 — Accumulate control-plane changes and reconcile them once
Lens: amortization · Source: H2O
Principle: Do not issue a kernel call for every interest change or submission. Record the desired state, then apply only the net difference at one reconciliation point (just before polling), or submit once enough operations have queued.
Why it is faster: read_start, read_stop, read_start in one iteration would otherwise cost three `epoll_ctl` calls for a net change of zero. Marking sockets "state changed" and comparing the computed mask with the registered one turns that into zero or one syscall. Registering an fd lazily on its first interest change folds ADD into the first MOD and makes DEL unnecessary for sockets never registered. Deferring `io_uring_submit` until a threshold amortizes the syscall across operations. Toggling read interest only on actual state transitions was measured at 10% faster for 4 KB responses.
Applies elsewhere: Web / backend: Coalesced DOM and layout updates in UI frameworks (apply the net diff once per frame). • Native / systems: kqueue changelists submitted with the next `kevent`. Lazy epoll registration in Tokio-, libuv- or Seastar-style reactors. • Data / databases: Deferred index maintenance and batched catalog updates applied at commit. • Embedded: Shadow registers flushed to the peripheral once per control cycle.
Watch out: The reconciliation point must always run before the loop blocks, or events are missed. Deferred submission adds latency for lone operations, so pair a batch threshold with a flush-on-idle path.
Seen in H2O: 1ccff7871c 2014-09-24 HTTP/2 toggles `read_start`/`read_stop` only on state change, with the check moved into `parse_input`: measured at 10% faster for 4K responses. • c44e43ac2c 2014-12-30 Founding evloop: `do_read_start`, `do_read_stop` and `do_write` call `link_to_statechanged()` (an intrusive queue), and epoll's `update_status` issues ADD or MOD only if the computed mask changed. dcdb4442da 2015-11-24 issues DEL when a socket wants neither read nor write, avoiding spurious wakeups. • acb02faa7c 2022-04-27 `H2O_SOCKET_FLAG__EPOLL_IS_REGISTERED`: fds are registered on first interest, `change_epoll_mode` picks ADD or MOD, and close skips DEL for never-registered sockets. ### h2o-024 — Make each call into a per-call-cost API do as much work as possible
Lens: amortization · Source: H2O
Principle: When an API has a fixed cost per invocation (setup, state checks, flush, syscall, iovec walk), give it the largest input it can process: whole buffers instead of fixed small slices, full blocks instead of fragments, one contiguous region instead of many pieces.
Why it is faster: Calling `SSL_write` every 16 KB, a compressor once per small fragment with a flush, or `sendmsg` with N iovecs for one contiguous region, pays the fixed overhead many times. A forced flush per fragment also hurts compression ratio. The library can still split into its own protocol-maximum units internally. The limit is whatever constraint made small calls necessary in the first place, such as small TLS records for first-byte latency.
Applies elsewhere: Web / backend: Write all gzip chunks for a response tick, then flush once, not `Z_SYNC_FLUSH` per write. Batch log lines before compressing. • Native / systems: Hash or encrypt whole mmap regions in one update. Bulk `memcpy` or `writev` instead of fixed small loops. • Data / databases: Compress whole column chunks, not individual values. Bulk-insert APIs instead of per-row calls. • Embedded: One DMA transfer per contiguous buffer instead of per-packet descriptors.
Watch out: Larger calls hold more data in flight and can delay the first byte. Keep the small-call mode where latency matters, as H2O does for the head of a TLS stream.
Seen in H2O: 5a913970fa 2016-02-26 Brotli copies input across iovecs into the ring buffer, runs `WriteBrotliData` only when a block is full, and flushes once at the end ("encode as much as possible at once"). • 05ec77b785 2021-04-14 When latency optimization is off, the TLS payload limit is `SIZE_MAX` rather than 16384. ### h2o-025 — Switch strategies at a measured break-even size
Lens: amortization · Source: H2O
Principle: A technique with a fixed setup cost (compression framing, creating a pipe, zero-copy bookkeeping) pays off only above some payload size. Measure that size, use the simple path below it, and re-measure when the surrounding costs change.
Why it is faster: gzip framing alone is at least 23 bytes, so compressing tiny bodies costs CPU and can grow them. A pipe for splicing costs syscalls and file-table work, which small bodies cannot amortize. The zero-copy threshold depends on how expensive the copy it avoids is. When the producer writes with non-temporal stores, the data is in DRAM rather than cache, a copy costs more, and the threshold drops. Intuition about these break-evens is often wrong.
Applies elsewhere: Web / backend: Compress RPC messages only above N bytes. Use `sendfile` only above a file size. Parallelize only above a batch size. • Native / systems: Offload to a GPU or DMA engine only above a transfer size. Use io_uring registered buffers only for large writes. • Data / databases: Build hash tables or indexes only above a row-count estimate. Skip page compression for pages that do not shrink. • Embedded: Switch from CPU copy to DMA above the size where DMA setup pays back.
Watch out: Break-even points depend on hardware, kernel and neighbouring optimizations. H2O moved one threshold up and another down within weeks. Make them configurable and benchmark-backed, not constants copied from documentation.
Seen in H2O: f1bcdbe33b 2015-08-11 "Do not even try to gzip response that is known not to become smaller". d191fa4643 2015-08-11 raised the threshold from 23 to 100 bytes. • 09ede83b2e 2016-05-31 The hard-coded check became the configurable `compress-minimum-size`. • 34ad5c6a4a 2022-04-19 The splice pipe reader is offered only when at least 64 KB remains, up from 16 KB: "intuition did not match the reality, as I forgot about the cost of creating a pipe". ### h2o-026 — Hoist invariant work out of the per-item path
Lens: amortization · Source: H2O
Principle: If a check or query gives the same answer for every element of an operation (buffer space for a fixed-width field, the current time, the thread ID), do it once per operation and reuse the result.
Why it is faster: A per-byte end-of-buffer check in a fixed 9-byte field is 9 branches where one length check suffices. After that, parsing can use unchecked compares and an unrolled `d*100 + d*10 + d`. Calling the clock several times within one logical operation wastes vDSO or syscall time and yields inconsistent timestamps. Two helpers each calling `gettid()` double a syscall. Fetch once, pass down, and clamp the time to be monotonic.
Applies elsewhere: Web / backend: One request-scoped `now` instead of `Date.now()` calls scattered through handlers. • Native / systems: Check buffer capacity once per message in binary decoders (RESP lengths, DNS headers), then decode unchecked. • Data / databases: A single transaction or statement timestamp. Fetch the transaction ID once per statement. • Embedded: Date and time parsing with one length check for `YYYY-MM-DD`. One tick read per control loop.
Watch out: A hoisted check must cover every access it replaces. One length check followed by unchecked reads is a memory-safety bug if the field can be longer than assumed. A cached "now" goes stale across long operations or blocking calls.
Seen in H2O: 893ee01779 2017-02-08 picohttpparser: `parse_http_version` requires `buf_end - buf >= 9` up front, and the response status needs 4 bytes. ### h2o-027 — Group a received batch by destination before dispatching
Lens: amortization · Source: H2O
Principle: After pulling many items in one go, hand consecutive items for the same destination (connection, partition, tenant) to it in one call, so lookup and state setup are paid once per run rather than once per item.
Why it is faster: Datagrams drained together usually belong to the same connection. Dispatching each one separately repeats the connection lookup, state loading and post-processing. Accumulating until the key (destination CID, address pair, TTL) changes turns N lookups into one per run. Leaving headroom in the batch array ensures one coalesced datagram that decodes into several packets never overflows it.
Applies elsewhere: Web / backend: Group queued events by tenant or user before applying them. ### h2o-028 — Pipeline many requests over one channel
Lens: amortization · Source: H2O
Principle: Instead of one in-flight request per connection, keep a write queue and a read queue on a single non-blocking channel. Send requests back-to-back, read responses until EAGAIN, and match them in FIFO order. Bound the number in flight.
Why it is faster: Strict request-response serializes callers behind the channel's round trip. Opening a channel per request multiplies connections and setup. Pipelining amortizes the round trip and the wakeups across all outstanding requests, and reading until EAGAIN collects many responses per wakeup. An in-flight cap means a message is never left half-written and memory stays bounded.
Applies elsewhere: Web / backend: Redis and memcached client pipelining. HSM or KMS clients batching sign requests. • Data / databases: PostgreSQL pipeline mode. Batched statement execution in drivers. • Native / systems: IPC to privilege-separated helpers or sidecars over one socket with a request queue. • Embedded: Command queues to a co-processor or modem with sequence-ordered responses.
Watch out: FIFO matching requires the server to answer in order. Otherwise you need request IDs. One slow request delays everything behind it (head-of-line blocking), and a failure on the channel fails every in-flight request.
Seen in H2O: d8c7e772af 2022-08-17 The first asynchronous private-key design serialized handshakes, because "there's a single neverbleed connection". • d1d80bf411 2022-12-01 added queue push/pop wrappers. ### h2o-029 — Acknowledge in batches sized to the flow
Lens: amortization · Source: H2O
Principle: Do not acknowledge every packet. Let the sender ask for an ACK every N packets, with N derived from a fraction of the congestion window, and tolerate small reordering before sending an immediate ACK.
Why it is faster: ACK generation and processing cost CPU at both ends and reverse-path bandwidth for every packet. Tying the ACK interval to cwnd (default 1/8, capped at a packet tolerance of 10) keeps ACKs proportional to what congestion control needs. Waiting for steady state (several loss episodes) before thinning ACKs protects slow start. A reordering threshold stops each out-of-order arrival from triggering its own immediate ACK.
Applies elsewhere: Web / backend: Batched acknowledgments in Kafka consumers (commit intervals) and MQTT. Watch out: Sparse ACKs slow the sender's congestion feedback and loss detection. That is why H2O enables thinning only once the controller is in steady state, and caps the tolerance.

### h2o-035 — Track in-flight items in an append-only chain of fixed-size blocks of tagged records

### h2o-039 — Borrow instead of copying: pass slices and shared references, and copy only when the source is about to change
Lens: allocation · Source: H2O

Watch out: A view is only valid while its buffer is. Compaction, realloc or recycling silently invalidates it. Every buffer-moving operation needs a clear owner that knows which views are live.

### h2o-041 — Keep payload bytes out of userspace (sendfile, splice, MSG_ZEROCOPY), but only above a measured size threshold
Lens: allocation · Source: H2O

Applies elsewhere: Web / backend: Netty `FileRegion`, Node piping file streams (sendfile under the hood). Watch out: Below the threshold, zero-copy is slower. MSG_ZEROCOPY buffers stay pinned until completion, so they need their own pool and lifetime tracking. Benchmark on target hardware: the H2O commits show the threshold moving both up and down.

### h2o-042 — Have producers write straight into the consumer's buffer, at the moment it is needed
Lens: allocation · Source: H2O
Principle: Instead of producers filling their own buffers for a later copy, let the consumer hand them a destination slice sized to what it can accept (flow window, buffer space) and call them as late as possible. Decrypt, read or generate directly into that space and use all of its reserved capacity.
Why it is faster: Push-style producers mean one intermediate buffer and one memcpy per hop. Pull-style "fill this region" APIs remove both and make each read exactly what can be sent. Delaying the fill until just before encryption or sending means data is not held in memory across event-loop yields or behind a full socket. Using the full reserved capacity, rather than exactly the requested size, lets in-place decryption succeed far more often.

### h2o-043 — Reserve header space and fill in the length after the payload is written
Lens: allocation · Source: H2O
Principle: When a prefix (frame header, varint length) depends on the payload, reserve room for it first, encode the payload in place, then write the prefix into the reserved space. Betting on the common case (a one-byte length) and memmoving only when the bet fails removes a full copy and a stack temporary. Watch out: Back-filled buffers start at a variable offset, so consumers must take the returned start pointer, not the buffer base. Reserve the maximum prefix size, or handle the overflow path correctly.

### h2o-046 — Size buffers from what you already know: per-use defaults, declared lengths, last capacity
Lens: allocation · Source: H2O

### h2o-047 — Recycle growable buffers through power-of-two size-class bins

### h2o-049 — Pool kernel-backed resources per thread, and prefill the pool at startup
Lens: allocation · Source: H2O

### h2o-053 — Grow a consume-from-front buffer by compacting first, and double only when it is genuinely full

### h2o-057 — Spill oversized buffers to a file-backed mapping above a threshold

### h2o-073 — Choose primitives that map onto hardware-accelerated instructions

### h2o-074 — Fuse two independent passes so they run on different execution units at once
Lens: cpu-microopt · Source: H2O
Principle: When an operation is two independent computations over the same data, as AES-CTR and GHASH are in AES-GCM, interleave them in one loop with several blocks in flight. The out-of-order core then overlaps their latencies, and the data is traversed once.
Why it is faster: AES rounds run on the AES unit and carry-less multiplies on the PCLMUL unit. Run separately, each pass waits on its own dependency chain and streams the data through cache again. Keeping 6 AES blocks in flight while multiplying the previous 6 ciphertext blocks by precomputed powers of H keeps both units busy. The cost is complex, hand-scheduled code that is specific to a microarchitecture.
Applies elsewhere: Native / systems: pair ChaCha20 with Poly1305 in one SIMD loop, or compute CRC while copying or transforming a buffer. • Data / databases: compute page checksums in the same pass that compresses or copies the page. • Embedded: overlap a DMA-driven cipher with a CPU MAC computation on the previous block.
Watch out: this pays off only when the two computations really use different ports and the data is large enough to fill the pipeline. Short messages need a separate tail path.

### h2o-075 — Defer modular reduction: accumulate unreduced products, reduce once per batch
Lens: cpu-microopt · Source: H2O
Principle: In multiply-accumulate over a field or ring, keep the wide partial products (hi/mid/lo) unreduced across many blocks and perform the expensive reduction once at the end.
Why it is faster: Reduction in GF(2128) costs several extra carry-less multiplies and shifts. Doing it per block nearly doubles the GHASH cost. Accumulating with XOR is cheap and associative, so one reduction per batch of 6 or more blocks amortizes it. With 256-bit lanes, the lanes are folded first and then reduced once.
Applies elsewhere: Native / systems: Poly1305 and CRC folding with PCLMUL, Montgomery multiplication with lazy reduction, and big-integer sums with deferred carry propagation. • Data / databases: rolling or polynomial hashes over columns can reduce once per vector, not once per value.
Watch out: the accumulators must be wide enough not to overflow (or, for integers, lose carries) before the reduction, which bounds the batch size.

### h2o-076 — Use non-temporal stores for output the CPU will not read again, and pick the copy strategy by cache state
Lens: cpu-microopt · Source: H2O
Principle: When a buffer's next reader is a DMA engine (the NIC), write it with streaming stores in whole cache lines. Then decide per buffer between zero-copy and a kernel copy, depending on whether the data is still in cache.
Why it is faster: Normal stores read each line for ownership and then evict useful data. Non-temporal stores write full 64-byte lines straight to memory. Once the data is in DRAM, a kernel copy would have to read it back, so zero-copy send (MSG_ZEROCOPY) wins even at 4 KB. If the producer left the data in L1, a copy is cheap and zero-copy bookkeeping is not worth it. Partial-line NT writes are slow and can clobber neighbouring data, so buffers must be line-aligned.
Applies elsewhere: Native / systems: encrypt or compress data that goes to a NIC or disk DMA, and use NT stores for large `memcpy` that will not be reread (glibc does this above a size threshold). • Data / databases: choose direct I/O for cold pages and buffered I/O for hot ones. Write log or backup streams with streaming stores. • Embedded / GPU: use write-combining staging buffers for uploads.
Watch out: NT stores hurt badly if the CPU does read the data soon after. Align buffers to the cache line, and fence before handing the buffer to another agent.

### h2o-077 — Over-read vector tails safely by checking the page boundary
Lens: cpu-microopt · Source: H2O
Principle: To load a partial vector (fewer than 16 bytes) at a buffer's end, do a full-width load and mask it whenever the load stays within the same 4 KB page. Copy byte by byte only in the rare case that it would cross into the next page.
Why it is faster: Memory protection works at page granularity, so reading past the logical end but within the page cannot fault. One unaligned load plus a shuffle or mask replaces a variable-length byte loop on every record tail. The page-crossing case is about 15 in 4096.
Applies elsewhere: Native / systems: tails of SIMD `strlen`/`memcmp`/`memchr`, and the last block of string or JSON scanners. • Data / databases: columnar decoders reading the final bytes of a page or vector.
Watch out: AddressSanitizer and Valgrind flag the intentional over-read, and the trick is invalid where protection is finer than a page (some sanitizers, guard-page allocators). Mask the extra bytes before they influence results.

### h2o-078 — Let a general library do setup, then move the bulk phase to a lean specialized engine
Lens: cpu-microopt · Source: H2O
Principle: Use the mature, feature-complete library for the complex, rare control phase. Then export its state and run the high-volume data phase on a smaller engine that supports your fast paths.

### h2o-080 — Replace a slow libm call on a hot path with a bounded-error polynomial
Lens: cpu-microopt · Source: H2O
Principle: If a control loop needs a transcendental function on every event but tolerates a small relative error, reduce the input range with bit manipulation and evaluate a low-degree polynomial.

### h2o-087 — Version-stamped thread-local copies of read-mostly shared state

### h2o-096 — Run the most recently readied work first (LIFO) for cache locality
Lens: concurrency · Source: H2O
Principle: When ordering among ready callbacks does not matter for correctness, run them newest first. The most recently touched connection state is still in cache, and a singly linked stack needs one pointer.
Why it is faster: The object just made ready was usually just written to (its buffer filled, its flags set). Running it immediately hits L1 and L2 instead of reloading it later, after other work has evicted it. A stack is also cheaper than a head-and-tail queue.
Applies elsewhere: Native / systems: the "next task" LIFO slot in Tokio and Go schedulers, and LIFO free lists. • Data / databases: waking the most recent lock waiter, whose state is still warm.

### h2o-101 — Give every event-loop turn a work budget per source
Lens: scheduling · Source: H2O · Also: libuv

### h2o-103 — Make timer bookkeeping O(1) and minimal per object
Lens: scheduling · Source: H2O

### h2o-104 — Act immediately when deferral buys nothing
Lens: scheduling · Source: H2O
Principle: Deferral exists to batch work. If nothing else is queued, or the action is already safe in the current callback, do it now instead of hopping through a zero-delay timer.
Why it is faster: Each deferral costs a timer link, at least one extra pass of the loop, and latency. When the connection is otherwise idle, there is nothing to batch with. Re-deferring an action that is already deferred doubles the hop. The counter-case is that after reading a batch of input, deferring the send so it coalesces ACKs and data is better, so the rule is to defer only when it enables batching.
Applies elsewhere: Web / backend: write in Node's `data` handler rather than `setImmediate`, and in Netty `channelRead` rather than a scheduled task. • Data / databases: group commit that commits at once when no other transaction is waiting. • Native / systems: adaptive flush at the end of a read batch in RPC frameworks.

### h2o-106 — O(1) priority scheduling with a few buckets and an occupancy bitmap or cursor

### h2o-134 — Reuse warm connections, with a cheap liveness check before reuse
Lens: networking · Source: H2O
Principle: Keep idle upstream connections in a shared pool keyed by everything that affects reuse (host, port, TLS context), hand them out synchronously when one is available, and check each with a one-byte non-blocking peek before sending on it.

Pooling the TLS connection itself means the handshake is skipped on reuse, not just the TCP connect.
Applies elsewhere: Web / backend: One shared HTTP agent per process.
