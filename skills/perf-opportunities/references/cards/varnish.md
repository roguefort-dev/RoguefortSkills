### varnish-002 — Crit-bit (radix) tree over fixed-length keys for read-mostly lookup
Lens: algorithms · Source: Varnish
Principle: Index fixed-length binary keys with a crit-bit tree: each inner node tests one bit, so lookup costs O(key bits) regardless of how many entries exist, and readers can walk it optimistically without a global lock.
Why it is faster: No hashing of the bucket, no resizing, no chain scanning, and depth is bounded by key length. Each node is two pointers; node type lives in the low alignment bits of the child pointers, and the first differing bit between two keys is found with one XOR and a 256-entry table. Because most lookups hit, readers walk the tree lock-free and only fall back to a locked insert on a miss or when a refcount of zero shows the tree changed. Nodes freed under lock-free readers need deferred reclamation.
Applies elsewhere: Web / backend: read-mostly routing tries and IP prefix tables in HTTP routers and proxies. • Native / systems: Patricia tries for longest-prefix match; tagged child pointers as in the Linux xarray. • Data / databases: radix or ART indexes over fixed-width keys (digests, integer IDs) with optimistic lock coupling. • Embedded: a 256-entry leading-bit table where the CPU has no count-leading-zeros instruction.
Watch out: lock-free readers force a reclamation scheme (cooling lists, epochs); embedding tree nodes in payload objects ties their lifetimes together and can pin memory.
Seen in Varnish: 877851aad2 2008-12-03 Added `hash_critbit.c`: "lookups do not require any locks until we reach the objhead we were looking for". Branch nodes are embedded in the objhead ("saves malloc operations big time"), child pointers carry the node kind in their low two bits, and `hcb_build_bittbl()` builds the first-differing-bit table. • c0dc75499a 2009-03-02 Fixed the refcount handling for a lost lock-free insert race. • a09153ea8c 2010-02-08 Made critbit the default hasher. • fddbc27a1b 2010-05-26 Split the inner "Y" node back out of the objhead: node and objhead lifetimes differed so much that rolling URLs kept too many objheads on the cooling list. • 197f744d65 2010-11-29 `hcb_lookup()` tries an unlocked insert first, retries with the lock, and counts the split in `hcb_nolock`/`hcb_lock`.

### varnish-004 — Match the hash function to the threat model and the table
Lens: algorithms · Source: Varnish
Principle: For in-memory tables where adversarial collisions are not the concern, use a fast non-cryptographic hash, and pick the table size or index mapping so the hash's weak bits do not decide the bucket.
Why it is faster: A cryptographic hash per lookup is wasted CPU if it buys no statistically better distribution. Weak hashes (CRC) have poor low-bit mixing for structured keys, so masking with a power of two clusters; a non-power-of-two size, or multiplicative (Fibonacci) hashing that keeps the top bits, spreads them without a modulo.
Applies elsewhere: Web / backend: xxHash/CRC32C/FNV for in-process caches and sharding keys; SipHash only where clients control keys. • Native / systems: Fibonacci hashing to pick a shard or stripe from a pointer or thread id. • Embedded: hardware CRC as a table hash. • Data / databases: multiplicative hashing before masking in hash joins and aggregation tables.
Watch out: if keys come from untrusted clients, a weak hash invites collision attacks; use a keyed hash or a digest (as Varnish later did for the object key).
Seen in Varnish: bedb73ffe7 2006-08-08 Classic hash set to 4096 buckets with 256 mutexes. • 543feafe8a 2006-08-08 CRC32 became the default hash; MD5 only a compile-time option. • f130624fff 2006-08-22 Removed MD5 ("no sufficiently strong statistical basis ... that will outweigh the performance penalty"), reduced power-of-two widths by one and raised the default to 16383 buckets. • 445a843d41 2025-07-21 Picks one of 128 private objheads with `fib((uintptr_t)wrk, 7)`: multiply by 2^64/phi and keep the top 7 bits, which spreads pointer keys with no modulo.

### varnish-005 — Indexed binary heap for deadlines, with in-place re-keying
Lens: algorithms · Source: Varnish
Principle: Keep deadlines in a binary min-heap and store each element's heap index inside the element, so peek is O(1) and insert, delete and re-key of an arbitrary element are O(log n) without searching. When a key changes, sift the element from where it is instead of delete plus insert.
Why it is faster: Scanning all entries to find expired ones is O(n) per tick; a heap gives the next deadline in O(1). The back-pointer index removes the O(n) search that a plain heap needs to delete an arbitrary element (an fd becoming active, an object being re-armed). Reordering in place does half the work of delete plus insert and avoids churning the hole.
Applies elsewhere: Web / backend: idle-connection and request timeouts in event loops; TTL expiry in in-memory caches. • Native / systems: timer heaps with decrease-key for rescheduling (libuv-style); run queues with priority updates. • Data / databases: lease and lock-timeout tracking; Dijkstra/A* with decrease-key. • Embedded: tick-less schedulers reading the next deadline in O(1).
Watch out: every swap must update the moved element's stored index; a stale index corrupts the heap silently. For many equal timeouts a FIFO list or timer wheel can be cheaper.
Seen in Varnish: ba5e84b76b 2006-06-21 Added `binary_heap.c` to track object expiry, growing the array in page-sized steps. • ca92dbff0e 2006-06-29 Tracks each object's heap position via an update callback (`o->heap_idx`); 413b69e69d 2006-07-18 deletes by index. • 0c3b22895c 2010-11-22 `binheap_reorder()` replaces delete plus insert in `EXP_Rearm()`; it "is guaranteed to work because the shuffle will always terminate either in the root position or in the bottom row". • 0f038349f 2015-05-27 The kqueue waiter tracks idle-timeout deadlines (idle + timeout) in a binheap and deletes by stored index when an fd fires; 754f386d6 2015-05-27 same for the poll waiter; 427e00c9c 2015-05-27 replaced the list of all waited entries with a plain count.

### varnish-006 — Lay out an implicit tree so each walk touches few pages
Lens: algorithms · Source: Varnish
Principle: A classic implicit heap puts children at 2i and 2i+1, so every level of a sift lands on a new memory page. Arrange the array so whole subtrees fill one page (a B-heap), and a root-to-leaf walk touches far fewer pages.
Why it is faster: With millions of entries the heap no longer fits in cache or even in resident memory; each level of a sift then costs a cache miss, TLB miss or page fault. Grouping parent and descendants within a page turns most level steps into in-page accesses. The asymptotic complexity is unchanged; the constant per level drops sharply.
Applies elsewhere: Native / systems: timer heaps in event loops with millions of timers; van Emde Boas or Eytzinger layouts for binary search arrays. • Data / databases: cache-oblivious or page-blocked trees and heaps for external sorting and priority queues. • Web / backend: large in-memory priority queues in schedulers and job systems.
Watch out: index arithmetic is more complex and only pays once the structure exceeds cache or RAM; for small heaps the classic layout is simpler and as fast.
Seen in Varnish: b4f3b04bfb 2010-04-07 "Turn the binary heap into a 'B-heap' to reduce the number of pagefaults by roughly a factor 9": new `parent()`/`child()` computed from `page_size`, `page_mask` and `page_shift`.

### varnish-012 — Normalize large rule sets, then match by binary search over a sorted table
Lens: algorithms · Source: Varnish
Principle: Before compiling a rule list, drop rules contained in broader ones and merge adjacent ones; for very large sets, emit non-overlapping entries as a sorted table searched by binary search instead of generating branch code.
Why it is faster: Folding shrinks the matcher itself. Generated nested if-trees match fastest but compile time grows super-linearly with rule count; a sorted fixed-stride table compiles in near-zero time and matches in O(log n), measured at about 3x the cost of generated code. Overlapping entries can stay as code.
Applies elsewhere: Web / backend: IP allowlists and geo tables in API gateways as sorted CIDR arrays. • Native / systems: firewall and routing-table aggregation (ipset, route summarization); huge switches replaced by tables to keep builds fast. • Data / databases: range-partition lookup via binary search over sorted boundaries.
Watch out: folding changes which rule "matched", which matters if matches are logged or have side effects.
Seen in Varnish: cc885760c1 2021-04-12 ACL `+table` flag: non-overlapping entries are emitted as a 20-byte-stride table searched by `bbsearch()` in `VPI_acl_table()`; overlapped entries still compile as code. • 01bf0dd2b0 2023-12-04 ACL `+fold`: subnets contained in supernets are dropped and adjacent prefixes merged into a shorter one; d97c4e3392 2025-07-09 enabled it by default; c3b45a3140 2025-07-21 fixes.

### varnish-013 — Build a temporary index only for a bulk phase
Lens: algorithms · Source: Varnish
Principle: If a structure is ideal for steady state but terrible for a bulk pattern (many keyed lookups into an ordered list), overlay an auxiliary index that exists only during the bulk phase and only supplies a starting point; drop it afterwards.
Why it is faster: Repeated O(n) list searches during a load become O(log n) tree lookups, while steady-state code and memory are unchanged. Populating the index lazily avoids building it when nobody queries it.
Applies elsewhere: Data / databases: a temporary hash index during restore or import, dropped afterwards. • Native / systems: build-time symbol tables in linkers. • Web / backend: startup-only lookup maps when replaying a log or warming a cache.
Watch out: the index must be kept consistent with mutations during the phase, or used only as a hint followed by a verifying scan, as here.
Seen in Varnish: f8d611fb54 2025-04-15 While persistent storage is loading (`ban_holds > 0`), a lazily populated red/black tree keyed by ban time gives `BANIDX_lookup(t)` a start point for `VTAILQ_FOREACH_FROM`; it is freed when holds drop to zero. Loading 289k objects with 7689 bans went from about 21-28 s to about 1.3 s.

### varnish-014 — Two indexes for two access patterns
Lens: algorithms · Source: Varnish
Principle: One structure keyed by a mutable value (a count) cannot also find entries by identity. Keep one index keyed by identity for lookup and another keyed by (value, identity) for ordering; update the ordering index by remove and reinsert.
Why it is faster: Each query uses the index that makes it O(log n) instead of a scan, and mixing both roles in one tree, which broke here, is avoided.
Applies elsewhere: Web / backend: leaderboards and top-K endpoints (Redis sorted set plus hash). • Data / databases: LFU caches and heavy-hitter tracking with a map plus heap or ordered set. • Native / systems: schedulers with a lookup table plus a priority structure.
Watch out: every update must touch both indexes atomically with respect to readers.
Seen in Varnish: 1161711e1 2014-09-15 varnishtop keeps `h_key` (hash, tag, length, memcmp) and `h_order` (count descending, then key) trees.

### varnish-015 — Resume from a remembered position instead of rescanning from the start
Lens: algorithms · Source: Varnish
Principle: When a sequence only grows at the end, keep a cursor (last consumed element and cumulative offset, or an open file descriptor) and continue from it; compare old and new versions of an ordered list side by side instead of rebuilding.
Why it is faster: Re-walking from the head after every append makes total work O(n²); a checkpoint makes each resume O(1) and the whole stream O(n). For files that are only appended, keeping the fd open and parsing only the new tail avoids re-reading; dropping checks that falsely force a full re-read keeps the incremental path in use.
Applies elsewhere: Web / backend: tailing readers and `tail -F`-style log shippers; chunked-upload assembly. • Data / databases: WAL replay from an offset; keyset pagination instead of OFFSET. • Native / systems: "wait for more data" loops over growing linked buffers; incremental config reload.
Watch out: the cursor is only valid while elements before it are not removed or reordered; detect truncation or recreation and fall back to a full scan.
Seen in Varnish: 77fec1b05 2015-11-26 A client streaming an object that is still being fetched resumed by walking the chunk list from the head after every new chunk; the iterator now keeps `checkpoint` and `checkpoint_len`. • cbdfa1aad 2017-11-06 VSM index refresh diffs the old and new segment lists side by side (inserts are always at the tail) and updates only changed segments, instead of remapping everything. • 4c381b27df 2019-07-31 Parses the VSM `_.index` file with an incremental line parser; 666d8427d2 2019-08-13 keeps the fd open and continues reading until the file is recreated. • e264e7ea80 2019-09-09 Removed an `st_mtime` check that marked the index as new and forced "a reread of the entire index"; ec19cc19ec 2019-09-09 keeps a resume cursor so segment search doesn't restart from the head.

### varnish-017 — Keep scanned arrays dense: swap-remove and a high-water mark
Lens: algorithms · Source: Varnish
Principle: When an array is scanned in full (a poll set), remove entries by moving the last one into the hole and keep the scan bounded by the highest live index.
Why it is faster: Swap-with-last removal is O(1) and leaves no holes, so the scan length equals the live count. Tracking the high point means the kernel or loop never walks empty slots. A parallel owner array keeps the dense array itself in the exact format the consumer needs.
Applies elsewhere: Native / systems: poll/select fallbacks; connection tables. • Web / backend: game-server entity arrays and ECS component storage (swap-remove). • Embedded: fixed slot tables for sockets or tasks.
Watch out: swap-remove changes element order and the moved element's index; anything holding indexes must be updated.
Seen in Varnish: 0836714de0 2007-10-09 "Keep track of the highest fd so we don't give poll(2) more pfd's to chew than necessary." • cbc829fef 2015-05-21 Poll waiter rewrite "to handle sparse fd-sets efficiently": `vwp_del` copies `pollfd[hpoll-1]` into the freed slot, a parallel index array tracks owners, space grows by `1<<16`, and new fds arrive through a pipe up to 128 pointers per `read()`; comment: "keep the high point as low as possible".

### varnish-018 — Order linear lists so scans hit usable entries first
Lens: algorithms · Source: Varnish
Principle: If a list must be scanned linearly, arrange it so likely matches are near the head: move active entries to the front, park in-progress entries at the tail, and keep it sorted so a search can stop early.
Why it is faster: The expected scan length drops without changing the structure. Entries that cannot be used (still being built) no longer sit in front of complete ones, and a sort key lets a cheap test end the scan before slower filters run.
Applies elsewhere: Web / backend: connection pools keeping half-open or handshaking connections at the tail. • Data / databases: keeping pinned or in-flight pages away from the scan head. • Embedded: self-organizing (move-to-front) lists for hot command handlers.
Watch out: move-to-front writes on reads, which costs cache-line traffic and locking under concurrency; past a modest n, switch structures instead.
Seen in Varnish: 6e9a25436a 2007-10-08 Poll acceptor moves active entries "to the front of the linked list where they will be found faster". • 5d5c3453a9 2011-04-29 "Put busy elements at the tail of the objhdr list, move them to the front when unbusy'ing ... keep the busy objects out of the way for lookups". • 3c5fc3266c 2018-03-05 The VCL compiler keeps its symbol list sorted, so the `strncasecmp` early exit happens before the version filter, and asserts the order.

### varnish-021 — Decide relevance at the first record; don't collect what you'll discard
Lens: laziness · Source: Varnish
Principle: In a stream consumer, make the keep/drop decision as early as possible (on the first record of a group) and stop tracking dropped groups, instead of buffering everything and filtering at output.
Why it is faster: Filtering at output still pays for tracking, buffering and grouping every item, and raises overrun risk. Deciding at the start removes that memory and CPU for everything filtered out.
Applies elsewhere: Data / databases: predicate and projection pushdown into scans. • Web / backend: filter Kafka or log events before deserialization; drop unsampled traces at the agent. • Native / systems: in-kernel BPF filters for packet capture.
Watch out: an early decision needs the deciding information to arrive first; otherwise you must buffer anyway.
Seen in Varnish: 8a9610c8dc 2021-01-18 `vslq_candidate()` drops sessions and non-matching client/backend transactions at their Begin record when `-c`/`-b` is given; 3b74d51ce3 2021-01-18 extends this to request grouping; 53b83f275f 2021-01-18 moves ESI (`-E`) filtering into libvarnishapi so ESI subrequests are not collected.

### varnish-023 — Skip writes that don't change state; track change coarsely
Lens: laziness · Source: Varnish
Principle: Before unsetting and re-setting a value, rewriting a file, or tearing down and recreating a resource, check whether it is already in the desired state; keep "changed" flags at a coarse level (per segment) so unchanged groups are skipped in O(1).
Why it is faster: Redundant writes cost arena space, log records, file mtime bumps (which trigger rebuilds downstream) and reader re-discovery. A visibility flag is far cheaper than destroy plus recreate. Per-group dirty state avoids touching every element on each refresh.
Applies elsewhere: Web / backend: skip DOM or virtual-DOM writes when values are equal; skip UPDATEs for unchanged rows. • Native / systems: write-if-changed for generated build files; dirty bits per page instead of per row. • Data / databases: soft-disable resources with a flag instead of dropping and recreating them.
Watch out: the equality check must itself be cheaper than the write; comparing large values can cost more than overwriting.

### varnish-025 — Lazy invalidation: append a rule with a generation, test on access
Lens: laziness · Source: Varnish
Principle: Make invalidation O(1) when issued: append the rule to a list with an increasing generation number. Each item remembers the generation it was last checked against; on access, test only newer rules and advance its mark.
Why it is faster: Nothing scans the whole cache when a rule is issued, and items that are never requested again are never tested. Each item is tested against each rule at most once. The trade is a growing rule list and per-access checking, which later needs background pruning.
Applies elsewhere: Web / backend: CDN purge-by-pattern with per-entry epochs; cache invalidation via version stamps. • Data / databases: MVCC-style "invalid if version < X"; lazy schema changes applied to rows when read. • Native / systems: generation-checked handles and TLB-style shootdown epochs.
Watch out: the rule list grows until something proves old rules no longer apply; per-lookup cost grows with it.
Seen in Varnish: 0fe81f4626 2006-06-29 "instantly ban/purge all cached objects matching a given regexp": `AddBan()` inserts at head with `gen = ++ban_next`; `BAN_CheckObject` walks while `b->gen > o->ban_seq` and then sets `o->ban_seq` to the newest; regexes compile with `REG_NOSUB`.

### varnish-027 — Short-circuit once the outcome is decided
Lens: laziness · Source: Varnish
Principle: Once an error or terminal decision is reached, latch it and make every later step return immediately, instead of running the rest of a chain or method.
Why it is faster: Doomed work is skipped and callers need fewer checks. In generated code, a check after each statement stops execution as soon as a terminal action is set.
Applies elsewhere: Web / backend: stop middleware chains once a response is committed; sticky-error writers (Go `bufio.Writer`). • Native / systems: poisoned states in compression and TLS streams. • Data / databases: rule engines stopping at first match.
Watch out: cleanup steps must still run; latch only the work, not the release of resources.
Seen in Varnish: 238705413 2015-04-29 `VDP_bytes` stores the first delivery error in `req->vdp_errval` and returns it on every later call. • 9849fd067 2017-02-03 The VCL compiler emits `if (*ctx->handling) return(1);` after every statement; 3bd4f5165 2017-02-03 removes now-redundant returns.

### varnish-029 — Set up eagerly for the overwhelmingly likely next step
Lens: laziness · Source: Varnish
Principle: When the next step is almost certain, prepare for it unconditionally at the start and remove the check-and-setup branch from the common path.
Why it is faster: It is the counterpart of laziness: when the probability of use is near 1, deferral only adds a check and a later setup step. Doing it up front makes the hot path straight-line code.
Applies elsewhere: Web / backend: allocate per-connection parse buffers at accept. • Native / systems: speculatively prepare the next pipeline stage in protocol handlers. • Embedded: keep the receive DMA armed between packets.
Watch out: for idle connections the eager resources are held for nothing; pair with releasing them when a connection goes idle.
Seen in Varnish: 76da77000 2015-03-23 "Optimistically setup session file descriptor for HTC reception no matter what protocol, a request is quite likely to happen soon-ish": blocking mode, request and receive buffer set up at session start, removing the check from the HTTP/1 state machine.

### varnish-030 — Delete checks, features and optimizations that no longer pay
Lens: laziness · Source: Varnish · Also: jemalloc
Principle: Re-measure hot-path checks, counters, fast paths and speculative features; remove those whose cost (parsing, locking, struct size, code complexity) exceeds their benefit, especially after the platform changes.
Why it is faster: Every check and counter on the hot path costs cycles and sometimes a shared lock. Old optimizations can stop paying when the allocator, kernel or surrounding code improves, while still costing state, branches and struct bytes. Removing them is an optimization in its own right.
Applies elsewhere: Web / backend: drop per-request telemetry hooks and always-on feature flags; retire stale prefetch heuristics. • Native / systems: remove custom allocators and hand-unrolled loops that modern mallocs and compilers beat. • Data / databases: audit memoization flags guarding now-cheap operations. • Embedded: validate at boundaries only.
Watch out: measure before deleting; some checks are security boundaries, not performance features.

### varnish-031 — Buffer records per thread or transaction, flush to the shared ring in one batch
Lens: amortization · Source: Varnish
Principle: Each worker or transaction appends records to a private buffer and copies the whole batch into the shared ring with one locked reservation, at the end of the transaction or when full. Size the buffer so a typical transaction fits, and fill it right to the edge before flushing.
Why it is faster: The shared lock is taken once per transaction instead of once per record, so contention falls by the record count. A batch also keeps a transaction's records together for readers, and a batch header lets readers skip a whole group in one jump. Too small a buffer causes needless mid-transaction flushes; reserving the worst-case record size before every write wastes the tail, so formatting into the remaining space and retrying only on real overflow keeps flushes near one per transaction.
Applies elsewhere: Web / backend: per-request log buffers flushed at response end; batched metrics points before push. • Native / systems: per-CPU trace buffers (ftrace, LTTng); async loggers with thread-local queues. • Data / databases: WAL group commit; per-transaction redo buffers. • Embedded: per-task log buffers drained by a low-priority task.
Watch out: buffered records are lost on crash and appear late to live readers; flush before long waits and on abnormal exits.

### varnish-033 — Make each syscall carry more work
Lens: amortization · Source: Varnish
Principle: Submit interest-list changes together with the wait call, fetch many ready events per wait, drain many queued items per read from a hand-off pipe, and read whole buffers instead of a byte at a time.
Why it is faster: A syscall's fixed entry/exit cost dwarfs the per-item work for small items. Piggybacking changes on the wait removes a syscall per change; larger event batches cut wake-ups per event under load; bulk pipe reads replace one read per session with one per batch.
Applies elsewhere: Native / systems: io_uring submission batching; `recvmmsg`/`sendmmsg`; coalescing `epoll_ctl` calls. • Web / backend: event loops that process all ready events before polling again. • Data / databases: bulk fetch instead of row-at-a-time cursors. • Embedded: DMA block transfers instead of per-byte UART writes.
Watch out: large batches add latency for the first item and memory for the batch array; cap them.

### varnish-034 — Move from item-at-a-time push to batched, non-blocking pull
Lens: amortization · Source: Varnish
Principle: Instead of a callback iterator that delivers one buffer per call and may block, let the consumer pull a batch: storage fills a caller-provided scatter array with many extents, returns "try again" plus a notification instead of blocking, and the consumer returns finished leases in batches.
Why it is faster: Per-call overhead (indirect calls, locking, filter-chain traversal) is paid per batch, the transport can hand many iovecs to the kernel in one call, and a waiting stream no longer ties up a thread. Returning leases in batches lets storage free segments outside its lock.
Applies elsewhere: Native / systems: io_uring-style submission/completion with buffer leases. • Data / databases: vectorized batch pull instead of Volcano tuple-at-a-time execution. • Web / backend: reactive streams with demand signalling; batched body readers feeding `writev`.
Watch out: leases must be returned promptly or storage cannot free memory; the API is more complex, so keep a synchronous wrapper for simple callers.

### varnish-036 — Process large sets in bounded batches with a resumable bookmark
Lens: amortization · Source: Varnish
Principle: When collecting work into fixed scratch space, loop in rounds instead of failing when it fills; release the lock between rounds and resume from a referenced bookmark element rather than from per-element "done" flags.
Why it is faster: Memory stays bounded by the scratch size and locks are held per round, not for the whole set. A held reference to the last processed element is a stable resume point; mutable "processed" flags break when concurrent processors reset them, which caused a livelock.
Applies elsewhere: Data / databases: batched deletes with LIMIT and keyset continuation. • Web / backend: paginated scans with continuation tokens in KV stores. • Native / systems: incremental GC sweeps and chunked eviction.
Watch out: the bookmark element must be pinned so it cannot be freed while the lock is dropped.

### varnish-037 — Drain the backlog before re-checking expensive status
Lens: amortization · Source: Varnish
Principle: While a consumer has work and no interruptions, keep dispatching; check an expensive health or status call once per drained backlog, not between every batch.
Why it is faster: The status check is amortized over the whole backlog instead of being paid per batch, so a consumer that has fallen behind catches up faster.
Applies elsewhere: Web / backend: Kafka consumers processing a full batch before checking rebalance; event loops draining ready queues before re-polling. • Native / systems: NAPI-style interrupt-to-polling switch under load. • Data / databases: replication appliers checking cancellation per batch.
Watch out: bound the drain or interleave interrupt checks, or a never-ending backlog starves signal handling.

### varnish-038 — Split hot bookkeeping fields away from the bulky object
Lens: memory-layout · Source: Varnish
Principle: Fields read or written by housekeeping on many objects (index positions, LRU links, timestamps, owner pointers) belong in a small, always-resident handle. The large payload struct should be touched only when the object itself is used.
Why it is faster: Heap sifts, LRU moves and eviction scans touch neighbours that are not being served. If their bookkeeping lives inside multi-KB objects, each step pages in or cache-misses on cold memory. A 40-byte handle is far more likely to be resident already. The reverse also holds: a field only needed while the object is in use (Varnish's LRU timestamp in 2009) can go back into the big struct.
Applies elsewhere: Native / systems: Keep timer-heap keys or ECS components in dense side arrays instead of inside entity structs. • Data / databases: Keep buffer descriptors (pin count, dirty bit, LRU link) in an array apart from the page frames, as PostgreSQL does. • Web / backend: Let an in-process cache's eviction index hold small metadata records that point to large value blobs, so eviction never touches the values.
Watch out: Splitting adds a pointer and a second allocation or lookup. A field that is only read when the object is in use anyway should stay with the object.

### varnish-041 — Keep phase-specific state out of long-lived structs
Lens: memory-layout · Source: Varnish
Principle: State used during one phase of an object's life (hashing, idling in the event loop, a backend connection) should live on the stack, be passed in a context argument, or be reserved from the object's arena only for that phase. It should not be a permanent field.
Why it is faster: A permanent field costs memory for the object's whole life and for every live instance, even though it is used briefly. Moving it to the stack or a temporary arena shrinks every resident object, and it often removes back-pointers and failure-unwinding code too.
Applies elsewhere: Web / backend: Keep per-step scratch in function locals or a request-scoped arena, not as fields on a session object that lives for the whole keep-alive. • Native / systems: Keep TCP parser state allocated only while a connection is mid-message. • Data / databases: Allocate operator scratch (hash contexts, sort state) from the per-query memory context and free it when the operator closes.
Watch out: Reserving at phase start can fail when the arena is exhausted, so that path needs handling. If the phase covers most of the object's life, a plain field is simpler.

### varnish-043 — Pack booleans into bit-fields, and partition flag words by the lock that guards them
Lens: memory-layout · Source: Varnish
Principle: Store many independent booleans as one-bit fields generated from a single table. Where different flags are written under different locks, give each lock its own flag word.
Why it is faster: A dozen `int` or `char` booleans can cost 12 to 48 bytes, where bits cost 2. Splitting the word by owning lock also keeps two threads from doing read-modify-write on the same word under different locks, which would lose updates.
Applies elsewhere: Native / systems: Use the Rust `bitflags` crate or C bit-fields generated from an X-macro table. • Data / databases: Use per-row flag bytes or bitsets in tuple headers. • Embedded: Pack status bits into registers or RAM bytes.
Watch out: Bit-field writes are read-modify-write of the whole word, so they are not atomic. Never let two locks guard bits in the same word.

### varnish-044 — Keep a presence bitmap for optional attributes
Lens: memory-layout · Source: Varnish
Principle: When attributes are stored out of line or behind an abstraction, keep a small bitmap in the hot handle of which ones exist. "Has X?" is then a single bit test.
Why it is faster: Without the bitmap, an existence check means an indirect call into a storage backend that may page in the object. The bitmap answers from memory that is already hot, and it cost nothing because it filled space freed by narrowing other flags.

### varnish-046 — Store optional fields as small offsets into the owner's arena
Lens: memory-layout · Source: Varnish
Principle: Instead of a full pointer per optional attribute, store a 16-bit offset into the object's own arena. Attributes with the same value can share one offset until they diverge.
Why it is faster: Four 8-byte pointers become four 2-byte slots, which shrinks the hot struct. Offsets are position-independent, so they also survive relocation and work in shared or persistent memory. Aliasing equal values avoids storing two copies of one address.
Applies elsewhere: Native / systems: Use relative offsets in mmap'd or serialized structures, such as FlatBuffers vtables. • Data / databases: Use slot or offset arrays in slotted pages instead of pointers. • Web / backend: Store uint16 offsets into a per-request byte buffer for parsed fields.

### varnish-049 — Store the length with constant strings

### varnish-052 — Don't write statistics into read-mostly cached data

### varnish-054 — Reserve the rest of the arena, write in place, commit the actual length
Lens: allocation · Source: Varnish · Also: Pebble
Principle: When an output's size is unknown but bounded, reserve all remaining arena space, format or receive directly into it, then release everything past the bytes actually written. This gives exactly one allocation of exactly the right size, with no worst-case sizing and no temporary buffer.
Why it is faster: The alternatives are guessing high (wasting arena) or formatting into a temporary and copying (double work). Reserve-and-commit does a single write into final memory and gives back the tail. The arena is locked while the reservation is open, so APIs must make failure release it.
Applies elsewhere: Web / backend: Go `strings.Builder.Grow` plus a write, or `strconv.Append*` into a reused slice. • Native / systems: `snprintf` into the tail of a growable buffer, then commit. Ring-buffer reserve/commit (DPDK, io_uring SQEs). • Data / databases: Serialize a tuple directly into page free space, then advance the free pointer.
Watch out: While a reservation is open, no other allocation can happen in that arena, so nested calls deadlock or fail. Keep reservations short and never across calls that might allocate.

### varnish-064 — For unknown-length data, allocate in capped chunks and trim only when the slack is worth it
Lens: allocation · Source: Varnish
Principle: When the final size is unknown, allocate reasonably sized chunks, fill them, then give back the unused tail. Pass "unknown" down to the storage layer so it chooses chunk sizes, cap the maximum chunk, and skip the trim when the slack is too small to justify a copy.
Why it is faster: Large default chunks waste memory on small and streamed bodies, while tiny chunks multiply allocations. Trimming recovers slack but costs a copy. Applies elsewhere: Native / systems: `shrink_to_fit` only when slack passes a threshold. `realloc` down after reading a file of unknown length. • Web / backend: Stream uploads to disk in chunks instead of buffering the whole `Content-Length`. • Data / databases: Rewrite a page only once free space passes a fill factor. Watch out: Never move or trim memory a concurrent reader may be using. Varnish had to stop trimming streamed chunks and later delay freeing trimmed segments.

### varnish-065 — Recycle objects through LIFO pools with a background guard and a per-thread spare

### varnish-068 — Small bounded scratch goes on the stack; large buffers do not
Lens: allocation · Source: Varnish
Principle: Short-lived, fixed-size, small buffers and control structs belong on the stack: zero allocation cost, cache-hot, freed automatically. Large or parameter-sized buffers do not, because they force every thread to reserve a big stack.

Watch out: Stack overflow is a crash, not an error. Bound every stack buffer at compile time, and watch for deep recursion or JIT code that also uses stack.

### varnish-073 — Approximate LRU: rate-limit recency moves and skip them when the lock is busy
Lens: caching · Source: Varnish · Also: memcached
Principle: On a hit, move an object to the LRU head only if it has not moved within a time window, and only if the LRU lock can be taken without waiting. Accept an imperfectly ordered list in exchange for removing a global lock from the hit path.
Why it is faster: Exact LRU needs a write under a global lock on every hit, so the hottest objects create the most contention. A hot object hit 1000 times a second is moved at most once per window, and any contended touch is simply dropped. Eviction quality barely changes, because an object hit recently enough to be moved will not be near the tail anyway.
Applies elsewhere: Web / backend: Caffeine's buffered access recording, and rate-limited "last accessed" updates in session stores. • Data / databases: CLOCK or second-chance buffer pools, and InnoDB's young-list promotion delay. • Native / systems: Filesystem `relatime`, and Redis-style sampled LRU.
Watch out: With a window longer than an object's typical reuse interval, recency degrades to roughly FIFO. Scale the window to the cache's turnover time.

### varnish-074 — Evict only when allocation fails, inside the allocator, under a per-operation budget

### varnish-075 — Cache the decision not to cache

### varnish-076 — Briefly cache failures so a queue of waiters drains at once

### varnish-085 — Back the cache with a large mmap'd file and steer the kernel's paging
Lens: caching · Source: Varnish

### varnish-086 — Use append-only, bump-allocated segments for persistent storage

Applies elsewhere: Data / databases: LSM write-ahead segments, Kafka logs, Bitcask. • Embedded: Flash-friendly log-structured key-value stores (wear leveling for free). • Native / systems: Append-only caches on SSD with segment-level reclamation.

### varnish-087 — Keep each object in one store, and spread objects across stores without a central lock
Lens: caching · Source: Varnish
Principle: Allocate all of an object's segments from the backend that holds its header. Choose a backend per object by rotating a pointer rather than taking a shared lock.
Why it is faster: Splitting one object over several disks means extra seeks and faults on every delivery. Rotation spreads load well enough, and avoids a lock that every allocation would otherwise contend on.
Applies elsewhere: Native / systems: Extent allocation that keeps a file contiguous on one device. • Data / databases: Keep a row and its TOAST or overflow data together. Shard so one request's data sits on one node. • Web / backend: Round-robin shard selection using a per-thread or atomic counter.

### varnish-090 — Do at compile time everything that does not depend on the request

Lens: cpu-microopt · Source: Varnish

### varnish-093 — Compile regular expressions once, natively, and only for the answer you need
Lens: cpu-microopt · Source: Varnish

### varnish-103 — Split one hot lock into many: stripes, shards and per-purpose locks
Lens: concurrency · Source: Varnish

### varnish-161 — Format straight into the log buffer's free space, and size the buffer to a transaction
Lens: observability · Source: Varnish
Principle: Write each record into whatever space remains in the private log buffer and flush-and-retry only the one record that overflows; size the buffer so a typical transaction needs one flush; route diagnostics into an existing buffer when one is available.
Why it is faster: Reserving the worst-case record size before each write forces flushes whenever free space dips below the maximum, even for tiny records. Watch out: per-transaction buffers multiply by concurrency; a bigger buffer must come out of a memory budget somewhere.

### varnish-166 — Maintain the segment index as an append-only log readers tail incrementally

### varnish-172 — Keep the consumer's hot loop free of redundant work
