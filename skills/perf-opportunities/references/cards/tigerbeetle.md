### tigerbeetle-001 — Use one hash probe per check-and-insert, and pick the map shape for how it is iterated
Lens: algorithms · Source: TigerBeetle
Principle: Do "does it exist, otherwise insert" as a single get-or-put. Reserve capacity up front so the table never rehashes. Choose an insertion-ordered (array-backed) map when the set is walked as often as it is probed, and a hash set of values projected by key when the key already lives inside the value.
Why it is faster: `contains` followed by `put` hashes and probes twice; get-or-put does it once. Pre-sizing removes rehash pauses and the pointer chasing of chained tables. Open addressing over-allocated about 2x keeps linear-probe clusters short. An array hash map stores entries densely, so walking a batch's keys is a sequential scan instead of skipping empty buckets. Projecting the key from the value saves one duplicated key per entry. The cost is that capacity must be known up front.
Applies elsewhere: Web / backend: use Rust `entry()`, Java `computeIfAbsent` or Python `setdefault` instead of check-then-put. In JS, use a single `Map.get` and test for undefined rather than `has` then `get`. • Native / systems: `reserve()` plus `try_emplace` in C++. Use an indexmap-style map when a request's keys are iterated in insertion order. • Data / databases: keep dedup sets for batch keys in an array-backed map so the later fetch loop is a dense walk.
Watch out: an assume-capacity insert is only safe if the capacity bound really holds. A void-valued map's `put` will not overwrite an existing entry, so use get-or-put and then assign.

The state machine (d68ff95677) detects duplicates with `getOrPutAssumeCapacity` and branches on `found_existing`. • f8c29f1655 2021-08-25 The client table over-allocates 2x "to reduce the probability of clustering, for efficient linear probing". • de1828a0b2 2023-08-08 The prefetch key set moves from HashMap to ArrayHashMap because it iterates better. • fddb0edda2 2024-02-23 The cache stash goes from `HashMap(Key, Value)` to `HashMap(Value, void)`, with hash and eql on `key_from_value`, so the key is not stored twice. • d754a25451 2026-05-17 Prefetch uses `GetOrPutResult` instead of a membership test plus `putAssumeCapacityNoClobber`. 4a583e55fc switches to `ArrayHashMapUnmanaged` for "more efficient iterating over entries", reporting "minor but consistent gains".

### tigerbeetle-002 — Hash fixed-width keys with an inlined multiply-mix, and map to N buckets with fastrange
Lens: algorithms · Source: TigerBeetle
Principle: When a key is a known-size integer, hash it with a few inlined multiply-xor steps instead of a general byte-stream hasher. Reduce a hash to the range [0, n) with `(hash * n) >> bits` instead of `%`.
Why it is faster: A slice hasher pays for loop setup and length dispatch even on 8 or 16 bytes. A compile-time-sized mix constant-folds to a handful of instructions. A 64-bit division costs tens of cycles, while a multiply-high costs a few. Fastrange also lets a table be any size, not just a power of two, so a cache can fill its whole memory budget. Multiplying by odd constants gives several cheap independent hash bits from one hash, which is useful for filters.
Applies elsewhere: Web / backend: map a request hash onto N backends or shards with a multiply-high, so N does not have to be a power of two. • Native / systems: use a multiply-shift hash, not SipHash, for maps keyed by trusted integer IDs. • Embedded: a single 32x32→64 multiply replaces a software division on cores without a hardware divider. • Data / databases: size bloom, cuckoo and hash tables to the exact memory budget and select the bucket with fastrange.
Watch out: fastrange uses the high bits, so the hash must mix well into them. Weak multiply-mixes are not safe against keys an adversary controls.

### tigerbeetle-003 — K-way merge: from a binary heap to a cache-aligned struct-of-arrays loser tree
Lens: algorithms · Source: TigerBeetle
Principle: Merge k sorted streams with a tournament (loser) tree: one leaf-to-root path of log2(k) compares per output, with nodes in an implicit flat array, keys and ids in separate cache-aligned arrays, and the winner held in registers. Break ties by stream index so precedence costs no callback.
Why it is faster: A heap's pop-then-push does two sifts. "Replace top" halves that, but a sift-down still costs about 2·log2(k) compares on unpredictable branches. A loser tree compares exactly once per level along a fixed path. In struct-of-arrays layout the hot compare reads only the dense key array, which stays in L1. Swapping small stream ids instead of stream state keeps data movement minimal. Ordering inputs newest-first lets `a.id < b.id` stand in for a precedence callback and its context pointer. Taking the winner's value and then feeding the same stream's next key gives one tree update per output, with no loop.
Applies elsewhere: Data / databases: external-sort merge phases, merging SSTable iterators and merging per-shard query results. Tie-break by source rank so the newest version wins. • Web / backend: merge time-ordered events from N Kafka partitions or N paginated feeds. Python `heapq.merge` and Java `PriorityQueue` pay the heap's extra compares. • Native / systems: merge posting lists in a search engine; pick timers in a scheduler with a loser tree when k is fixed.
Watch out: for k = 2 any tree is overkill. Layout experiments can backfire (ids-only nodes were slower), so benchmark each variant.

### tigerbeetle-004 — Exploit existing order: track sortedness, sort small suffixes into runs, and merge
Lens: algorithms · Source: TigerBeetle
Principle: Append to a flat buffer and keep a running "still sorted" flag, sorting only if it is false. Sort each newly appended suffix as it arrives, so the buffer becomes a sequence of sorted runs, and k-way merge the runs at flush time instead of sorting everything at once.
Why it is faster: Real keys (timestamps, sequential IDs) often arrive almost in order, and a one-compare-per-append flag skips the sort entirely. Sorting small suffixes keeps each sort in cache and spreads the O(n log n) cost evenly over time, so no single request pays for a whole-table sort. Merging k runs costs n·log k instead of n·log n, and dedup can run during the merge. The main win is tail latency, not throughput.
Applies elsewhere: Data / databases: time-series and log ingest buffers that sort per interval and merge at flush. Skip the sort when a monotonic key arrives in order. • Web / backend: sort each fetched page of a virtual list as it arrives and merge on demand, rather than re-sorting the whole list. • Native / systems: event queues that are almost sorted; use a run-adaptive sort (TimSort-style) when runs are not tracked explicitly.
Watch out: the run count must be bounded or the merge degrades. Point lookups against unsorted or multi-run buffers need another path (TigerBeetle serves them from a cache).

### tigerbeetle-005 — Sort fixed-width integer keys with an LSD radix sort that skips trivial passes
Lens: algorithms · Source: TigerBeetle
Principle: For unsigned fixed-width keys, use a stable out-of-place LSD radix sort. Build every pass's histogram in one read and skip any pass whose digit puts all elements in one bucket. Pick a wider digit for large records, and fall back to insertion sort for tiny inputs.
Why it is faster: Radix sort is O(n·passes) with no data-dependent compares, so there are no mispredictions. One histogram read replaces one read per pass. Clustered keys, such as timestamps sharing their high bits, skip most passes. With 128-byte or larger values, 11-bit digits mean fewer passes, and each pass moves the whole record. Ping-ponging between two buffers needs a copy-back only when the number of non-trivial passes is odd. The cost is a scratch buffer as large as the input and a histogram that must stay cache-sized.
Applies elsewhere: Data / databases: sort u64 IDs or timestamps in ingest buffers, or before bulk-loading a B-tree. • Web / backend: a radix sort over a `Uint32Array` or `BigUint64Array` can beat `Array.prototype.sort` with a comparator by a wide margin. • Native / systems: sort game draw calls by a 32-bit key; sort packets by flow hash.
Watch out: it needs O(n) scratch memory and only works for keys that map to unsigned integers. For tiny n, the histogram cost dominates, so keep a cutoff.
Seen in TigerBeetle: 2b53b64e6f 2025-09-15 Ports "the optimized radix sort from our sorting benchmark" to `stdx/radix.zig`, with a one-pass histogram, trivial-pass skipping and buffer swapping. • 1317ec7ff8 2025-09-18 Adds the insertion-sort cutoff (32 or fewer), a 64-byte-aligned histogram and a 200 KiB comptime cap on histogram size. • 2c2be78ae9 2025-09-15 Drops raw-pointer bucket cursors and scatter prefetch because the gain was below 2%. • 42afb7fac0 2025-09-19 Replaces `std.mem.sort` in the memtable's `sort_suffix_from_offset`. • f8c787e1fe 2026-06-29 Removes a hidden `llvm.memcpy` of the histogram array, building it in place and taking `&histograms[pass]`. 0d6f7aa3ad inlines the key extractors.

### tigerbeetle-007 — Use the lightest primitive the inputs allow (2-way, or synchronous, merge)
Lens: algorithms · Source: TigerBeetle
Principle: Do not reuse a general k-way or async-capable merge iterator when the inputs are known to be two streams or fully in memory. Use a direct compare-and-pop loop or the bare tree.
Why it is faster: The general machinery costs something on every element: heap maintenance and callback indirection for k = 2, and "pending" states, refill logic and error paths for inputs that can never block. A specialized loop compares two `peek()` keys directly and has no state machine.
Applies elsewhere: Native / systems: keep separate sync and async iterator paths, such as Rust `Iterator` versus `Stream`, or a ready-future fast path. • Data / databases: use an in-memory merge operator distinct from the spill-to-disk one; merge two posting lists with a two-pointer loop. • Web / backend: use a plain loop instead of an `async` generator when all the data is already in an array.
Watch out: each specialization is extra code to test. Keep the general primitive as a reference and fuzz the specialized one against it.

### tigerbeetle-009 — Set-associative cache with dense metadata arrays, SIMD tag match and CLOCK counters
Lens: algorithms · Source: TigerBeetle
Principle: Hash a key to one small set of ways. Keep per-entry 8-bit tags, 2-bit CLOCK counters and per-set hands in separate packed arrays. Compare the target tag against all ways at once, and touch the large value array only on a tag hit.
Why it is faster: A lookup reads one compact cache line of tags instead of chasing pointers through an LRU list. A 64 GiB cache of 64 KiB blocks needs only 1 MiB of tags. One vector compare plus a bitmask replaces up to 16 key compares. CLOCK with saturating counters approximates LRU with no list updates on hits. With no matching tag, the probe returns before touching any values. A fixed-trip loop over all ways has no serial ctz dependency chain, which helps out-of-order execution. Alignment rules were later relaxed to keep only the hot invariant (a clock hand never spans lines), which made the minimum cache 8x smaller.
Applies elsewhere: Data / databases: buffer pools or page caches whose tag array is scanned before any page is touched. • Web / backend: in-process object caches (DNS, routes, sessions) built on Swiss-table-style control bytes instead of a linked-list LRU. • Embedded: 1–2 bit CLOCK counters when LRU list pointers would cost more than the payload.
Watch out: limited associativity causes conflict misses that a fully associative LRU would not. Entries evicted while still needed must be caught somewhere else (TigerBeetle adds an overflow stash).
Seen in TigerBeetle: 78f7353715 2022-05-16 `SetAssociativeCache`: ways restricted to 2, 4 or 16 so hands pack without padding, with 16 ways matching 128-bit SSE. babe2eb25d adds a packed sub-byte integer array. • e8ba8c3dff 2022-05-16 Tag search with `@splat(ways, tag) == tags_vector`, bit-cast to `u16` and walked with ctz. e104eb41c6 fuzzes the SIMD path against a scalar reference. • b3897a5102 2022-05-16 CLOCK: `count +| 1` on a hit, and decrement while sweeping on eviction. bd1bec0f2c bounds the sweep. • 27561f7b52 2024-05-10 The grid cache declares `cache_line_size = 16`, measured with no performance impact, so 256 MiB caches are possible instead of 1 GiB. 156f3302ae and 0676125f8f compute the required multiple per component, taking the grid minimum from 512 to 64 values. • b77087b4c3 2025-08-23 The probe gains an early return on no tag match, iterates all ways "to help the OOO execution", converts the mask with `@bitCast`, uses fastrange set selection, and drops `BitIteratorType`. • b77087b4c3 2025-08-23 (merged b48efeabbc 2025-08-25) Early return when no tag matches, a fixed-trip loop over all ways "to help the OOO execution", `@bitCast` of the bool vector, and `fastrange(entropy, sets)` in place of modulo.

### tigerbeetle-011 — Eytzinger (BFS-order) search layouts, and deleting them when a simpler scan catches up
Lens: algorithms · Source: TigerBeetle
Principle: Storing a static sorted key sample in breadth-first order makes the top levels of the search share a few cache lines and makes descendants prefetchable. Use it as a small index that narrows a search over a larger values array. Re-measure periodically: once prefetching binary search matched it, the layout was removed.
Why it is faster: In sorted order, the first several binary-search probes touch different cache lines. In BFS order, the hot top of the tree is contiguous, and the descendants B levels down sit in one line that can be prefetched. Searching a cache-resident key index before the large values array cuts misses. The cost is an extra block per table, build work and derived layout constants. When plain binary search with dual prefetch got close, that cost was no longer worth it.
Applies elsewhere: Data / databases: read-only sorted ID lists and static lookup tables (IP ranges, GeoIP) in analytics engines. • Embedded: static search trees in flash for firmware lookup tables. • Web / backend: an Eytzinger-ordered typed array for large immutable sorted datasets searched in the browser.
Watch out: it only works for static data, since rebuilding costs O(n). Keep the benchmark that justified it and delete the layout once simpler code is within noise.

### tigerbeetle-014 — Resume iterators from a saved cursor, validated by a generation counter
Lens: algorithms · Source: TigerBeetle
Principle: An iterator over several containers should store where it was and continue there, not restart its outer loop. If the container can change between calls, store its generation number with the cursor: resume in O(1) when it matches, and re-seek by the last key when it does not.
Why it is faster: Restarting from the first container on every `next()` costs O(containers) per item. A generation check costs one compare and keeps correctness when the structure was reset in between. The fallback re-seek is a binary search, not a full scan.
Applies elsewhere: Web / backend: keyset pagination instead of OFFSET; cursor tokens that carry a version and fall back to "seek after last id". • Native / systems: turn Java `modCount` fail-fast iterators into resume-or-reseek iterators. • Data / databases: multi-shard scanners that resume per shard.
Watch out: every mutation, including bulk resets, must bump the generation. A missed bump resumes a stale cursor.
Seen in TigerBeetle: 885ea68694 2023-09-18 "ForestTableIterator: Avoid O(trees) loop": adds a `tree_id: ?u16` cursor and resumes through an inline switch. • a8ea440137 2024-06-05 ManifestLevel bumps its `generation` on `reset`, so the scrubber resumes when `position.generation == manifest_level.generation` and otherwise searches from the previous `key_max`.

### tigerbeetle-016 — Count interval overlaps with a two-pointer sweep instead of per-item binary search
Lens: algorithms · Source: TigerBeetle
Principle: To find, for each interval in sorted list A, how many intervals in sorted list B overlap it, advance two monotonic pointers. One counts B intervals that end before A starts, the other counts B intervals that start before A ends, and the overlap is the difference.
Why it is faster: Binary-searching B for every A costs n·log m, and range counting made it worse. Both pointers only move forward, so the sweep is O(n + m). Exit early on zero overlap, then run a single binary search to get the winning range.
Applies elsewhere: Web / backend: calendar conflict counts and booking availability over sorted intervals. • Data / databases: interval joins (genomics, time ranges), and merge planning in time-series stores.
Watch out: both lists must be sorted by start, and for disjoint-per-list intervals also by end. Overlapping intervals within B need a different counting method.
Seen in TigerBeetle: d3f4d9b895 2026-03-28 `table_with_least_overlap` computes `count_b_max - count_b_min` from two iterators. The previous approach "had sub-quadratic time complexity. The new implementation achieves linear time."

### tigerbeetle-017 — Weighted random choice in one pass with O(1) memory (weighted reservoir sampling)
Lens: algorithms · Source: TigerBeetle
Principle: Keep a running weight sum and replace the current pick with item i with probability `w_i / sum_i`. A single pass yields a choice proportional to weight, with no weights array and no CDF.
Why it is faster: Building a weights table and then a second pass costs memory proportional to the item count and two traversals. The streaming version is one pass with two integers of state.
Applies elsewhere: Web / backend: weighted load balancing or A/B bucket choice without building a CDF. • Data / databases: pick a weighted random row in one cursor pass; sample log lines from a stream. • Embedded: weighted selection with no buffer.
Watch out: it uses one random number per item. For repeated draws from a fixed distribution, a precomputed alias table is cheaper per draw.

### tigerbeetle-018 — Track out-of-order completions as a watermark plus coalesced disjoint ranges
Lens: algorithms · Source: TigerBeetle
Principle: Keep an "everything below N is done" prefix and a small sorted list of disjoint completed ranges, merging neighbours and advancing the prefix when the first range touches it.
Why it is faster: A priority queue of completed items grows with the number of items. Ranges grow only with the number of concurrent producers (gaps), so capacity can be fixed at init. Memory stays bounded and the structure is allocation-free.
Applies elsewhere: Native / systems: TCP SACK scoreboards; tracking downloaded byte ranges in a range downloader. • Web / backend: committing consumer offsets with out-of-order acks (Kafka, SQS workers). • Data / databases: run containers in Roaring bitmaps; tracking applied log sequence numbers.
Watch out: the range count must really be bounded by concurrency. Adversarial or heavily fragmented completion patterns break the capacity bound.

### tigerbeetle-019 — Reject lookups with a min/max check before any search or I/O
Lens: laziness · Source: TigerBeetle
Principle: Keep the [min, max] key of every searchable unit (a tree, a sorted run, a result window). A key outside it cannot exist there, so answer with two comparisons, and prune whole units from range scans before reading them.
Why it is faster: A negative lookup in a multi-level store otherwise walks every level: cache, memtable, index, filter and data blocks. For monotonic keys (timestamps, sequential IDs), most create-if-absent checks miss, and the range check rejects them in about 1 ns. In range scans, dropping non-intersecting runs and reslicing the rest with lower-bound makes scan setup logarithmic per run instead of linear.
Applies elsewhere: Data / databases: zone maps, Parquet row-group statistics, BRIN indexes and partition pruning. • Web / backend: check an ID or date range before a network fetch or before scanning a sorted array. • Native / systems: axis-aligned bounding box rejection before precise collision tests.
Watch out: random keys (UUIDv4) span the whole range and get no benefit. Bounds must be widened on every insert and must be correct for the snapshot being read.

### tigerbeetle-020 — Split execution into a prefetch phase and a synchronous execute phase
Lens: laziness · Source: TigerBeetle
Principle: Before executing a batch, gather every key it will touch, dedup them, and resolve them concurrently, cheapest source first (object cache, range reject, in-memory table, then disk). Then run the business logic synchronously from memory. Enqueue dependent keys in loops that already walk the input.
Why it is faster: I/O for the whole batch overlaps up to the device's parallelism instead of serializing one fault at a time, and the state machine stays free of async logic. Tiered resolution means most keys never reach disk. A second tier picks up keys revealed by the first, such as the accounts of a pending transfer. Folding enqueues into an existing loop saves a full pass. A known timestamp hint skips a secondary-index scan entirely.
Applies elsewhere: Web / backend: DataLoader-style batching; `SELECT ... WHERE id IN (...)` before the business loop instead of N+1 queries; ORM `prefetch_related`. • Data / databases: multi-get every key a transaction reads before executing it. • Native / systems: stream the assets a game level needs before simulation starts.
Watch out: it only works when the key set can be computed up front. Data-dependent chains need extra tiers, and the prefetch maps must be sized for the worst case.

### tigerbeetle-021 — Single-flight: never do the same in-flight work twice
Lens: laziness · Source: TigerBeetle
Principle: Before starting an expensive fetch, check whether the same key is already queued, in flight, or being written. If so, attach to it or serve from it instead of issuing another one.
Why it is faster: Batches often repeat dependencies: many transfers touch the same two accounts. Coalescing reads of one address turns N disk reads into one, with every waiter completed from the single I/O. A block in a write queue is already in memory, so serving reads from it (as CPUs do with store-to-load forwarding) avoids a disk read or a redundant repair. Checking the write queue before the read queue keeps a later read from waiting behind an earlier one.
Applies elsewhere: Web / backend: Go `singleflight`, CDN request collapsing, a memoized in-flight promise map in Node. • Data / databases: deduplicate page-ins in a buffer manager; serve reads from the write-back buffer for read-your-writes. • Native / systems: a sync client serving GETs from its pending-upload buffer.

### tigerbeetle-023 — Collapse duplicate writes and cancel opposing ones before they are persisted
Lens: laziness · Source: TigerBeetle
Principle: In a write buffer, keep only the last write per key, and where semantics allow (an index whose key is its whole value, with no upserts), let an insert and a delete of the same key annihilate each other. Do this as early as possible: in the buffer and again in every merge.

Applies elsewhere: Data / databases: an insert and a delete inside one transaction that net to nothing in index maintenance; memtable last-write-wins. • Web / backend: coalesce add/remove events in an event-sourcing buffer or an offline sync queue before upload. • Native / systems: undo/redo coalescing; CRDT op-log tombstone annihilation.

### tigerbeetle-042 — Right-size identifiers and fields, and spend the saved bytes deliberately

### tigerbeetle-066 — Store both fence keys and checksums for every child in the index block

### tigerbeetle-067 — Make a filter probe touch one cache line and hash once, and delete the filter when cheaper ones cover it
Lens: caching · Source: TigerBeetle
Principle: If you need a Bloom filter, use a split-block design (all bits for a key in one 256-bit block, tested with one vector op). Derive bit positions by multiply-shift, hash each key once and carry the fingerprint through every probe. Remove the filter entirely once range checks, fence keys and cached lookups answer the negatives.
Why it is faster: A classic Bloom filter makes k random memory accesses. A split-block filter makes one. Applies elsewhere: Data / databases: split-block Bloom filters (as in Parquet and Impala); skip per-file filters for time-ordered keys where min/max pruning suffices. • Web / backend: compute a request key's hash once at the edge and reuse it for routing, the cache and the filter. • Native / systems: one-line filters for packet allowlists; multiply-shift range reduction for non-power-of-two tables.
Watch out: a filter's value depends on the key distribution. Track its negative-hit rate and its I/O cost, and be ready to remove it, as TigerBeetle did.

### tigerbeetle-071 — Don't let a cache duplicate data that is already held elsewhere
Lens: caching · Source: TigerBeetle

### tigerbeetle-073 — Relax power-of-two and alignment rules so caches fit the memory budget

### tigerbeetle-080 — Software-prefetch every possible next address in pointer-free searches

### tigerbeetle-085 — Compare many small fingerprints with one vector instruction
