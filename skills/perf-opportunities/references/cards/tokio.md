### tokio-001 — Use a fixed-capacity, power-of-two, single-producer ring instead of a general concurrent deque
Lens: algorithms · Source: Tokio
Principle: When one thread owns the producer side, a bounded ring with masked indices beats a growable lock-free deque. You give up capabilities the workload never uses (growth, popping from both ends, epoch reclamation) and get rid of their fences and their memory management.
Why it is faster: A growable Chase-Lev deque pays for buffer reallocation, epoch-based garbage collection and extra fences on every operation. A fixed ring of 2k slots indexes with `pos & MASK` (no division) and never reallocates. Because only the owner writes the tail, a push is a plain slot write plus one Release store. Consumers coordinate through a single CAS on the head. Packing two narrow cursors into one atomic word lets "a steal is in progress" be detected without a lock. The cost is fixed capacity, so the design needs an overflow policy, and the counters wrap, which opens an ABA window if they are too narrow.
Applies elsewhere: Native / systems: per-thread job rings in game-engine job systems; per-core packet queues in NIC drivers. • Embedded: DMA descriptor rings and UART buffers sized to 2k, indexed with a mask. • Data / databases: SPSC or SPMC log and WAL staging buffers between a writer thread and flushers. • Web / backend: per-worker request queues in thread-per-core servers, in place of a shared growable queue.
Watch out: a full ring needs a defined spill path (see "Spill and refill in halves"). Cursors only a little wider than the capacity can wrap while a stalled thread holds an old value, so use the widest cursor the platform's atomics allow.
Seen in Tokio: ed5a94eb2d 2019-10-19 The scheduler rewrite replaced crossbeam's Chase-Lev deque with a 256-slot `Box<[MaybeUninit<Task>]>`. Owner pops and stealers both CAS on `head: AtomicU32`. `tail` is written only by the owner. Indices use wrapping u32 arithmetic and `& MASK`. PR benchmarks: `chained_spawn` 2,019,796 → 147,943 ns/iter, `ping_pong` 1,279,948 → 537,744, `spawn_many` 10.28M → 7.45M. Hyper hello-world rose from 113.9k to 152.3k req/s. • 1cb1e291c1 2020-03-26 Limited the queue to one concurrent stealer. • 58ba45a38c 2020-04-09 Packed `head` as `pack(steal, real)`, two u16 cursors in one `AtomicU32`, with `tail: AtomicU16`. Cursors wider than the 256-slot capacity can tell "full" from "empty". fa4fe9ef6f 2020-04-02 fixed a `+` to `wrapping_add` on the narrow cursors. • 78fc94099b 2022-09-28 Where 64-bit atomics exist, the queue now uses 32-bit cursors packed into a 64-bit word (16/32 otherwise). The commit reports this "greatly improves resilience to ABA and has no impact on performance on 64-bit platforms".

### tokio-003 — Hierarchical timing wheel with per-level occupancy bitmaps instead of a heap
Lens: algorithms · Source: Tokio · Also: Kafka
Principle: For large numbers of deadlines at a fixed resolution, bucket them into a few levels of 64-slot wheels. Use bit operations to pick the level and to find the next non-empty slot, so insert, cancel and next-expiry are all O(1).
Why it is faster: A binary heap costs O(log n) per insert and cancel and needs an index map to cancel arbitrary entries. A hierarchical wheel files a deadline at `level = (63 - leading_zeros(now ^ when)) / 6`, with no loop. Each level keeps a 64-bit `occupied` mask, so the next non-empty slot is `occupied.rotate_right(now_slot).trailing_zeros()`, about one instruction. Slot boundaries for power-of-two ranges are masks, not modulo. The trade-offs are a fixed resolution (1 ms) and a maximum range, and entries cascade down levels as time advances. Edge cases such as draining "everything" or top-level wrap-around need explicit handling.
Applies elsewhere: Web / backend: idle, keep-alive and request timeouts for 100k+ connections in proxies and gateways. • Native / systems: TCP retransmit and delayed-ACK timers; game cooldowns and scheduled events. • Data / databases: lock-wait timeouts, TTL expiry and lease renewals in caches and DBs. • Embedded: a software timer service on a tick interrupt, with a bitmap of occupied slots.
Watch out: with a handful of timers, or when exact ordering matters below the resolution, a heap is simpler and just as fast. "Drain everything" and wrap-around are the usual bug sites, so test far-future deadlines explicitly.

### tokio-004 — Keep an occupancy bitmap so searches skip empty candidates
Lens: algorithms · Source: Tokio
Principle: Next to a set of queues, shards, workers or branches, keep one word of bits that says which are non-empty, idle or still enabled. Searchers mask and count bits instead of probing (and locking) each candidate.
Why it is faster: Probing an empty queue still costs a cache miss, and often a lock. One atomic load of a bitmask tells a thief which victims are worth trying, or tells a consumer which shards hold work. Branch-free bit scans (`trailing_zeros`) then pick a candidate. If bits change only under the owning lock, they are exact at unlock and merely hints elsewhere, so a stale bit costs one wasted probe and never correctness.
Applies elsewhere: Embedded: RTOS ready-priority bitmaps (the highest set bit picks the next task). • Native / systems: allocator free-block search with `ffs`; per-NUMA "non-empty run queue" masks. • Web / backend: load balancers keeping a bitmap of healthy or non-saturated backends. • Data / databases: free-space maps; bitmaps of dirty pages or non-empty partitions.
Watch out: treat any bit read outside the lock as a hint and re-check under the lock. One word covers 64 entries, so chunk larger sets. Bits updated without a lock need careful ordering, or a set bit can be lost.
Seen in Tokio: 19500f7df8 2018-03-28 Timer-wheel levels: a 64-bit `occupied` mask per level (see the timing-wheel entry). • 8cf98d6946 2020-01-22 `select!` keeps a stack `Mask` of disabled or completed branches and skips them, with no allocation. • a58beb3aca 2023-07-21 The alternative scheduler activated `IdleMap` (chunks of `AtomicUsize` bits). `steal` snapshots it to "avoid trying to steal from idle workers". • 1604bc3351 2026-04-10 A sharded `spawn_blocking` queue, reverted in 56aaa43e91 2026-04-16 after a hang, then re-landed opt-in by 8b13642a1f 2026-08-09. It has 16 shards and a `non_empty_mask: AtomicUsize` updated with `fetch_or`/`fetch_and` (Relaxed) under the shard lock, so consumers skip empty shards without locking them.

### tokio-005 — Index-plus-generation handles (slabs, stacks, tokens), and know when a pointer is cheaper
Lens: algorithms · Source: Tokio
Principle: Address objects by a small slot index and spend the remaining bits of the word on a generation counter. Stale handles and ABA are then detected with one compare. Once the index-to-slot lookup itself becomes the hot cost, switch to the object's address and defer frees instead.
Why it is faster: Small indices leave room for a wide ABA tag without double-width CAS. A slab with geometrically growing pages never moves entries, so readers can index without locks, and generation tags filter events meant for a slot's previous occupant, which removes spurious wakeups. Local and remote free lists make most inserts synchronization-free. The slab still costs an address decode and a generation check per lookup, and its pages need compaction to shrink. When ownership can guarantee that an object outlives its registrations (frees are deferred until no event can refer to it), using the pointer as the token turns dispatch into a cast.
Applies elsewhere: Native / systems: generational entity IDs in ECS game engines; io_uring `user_data` carrying slot + sequence. • Embedded: fixed object pools with index free lists and tagged heads, no heap and no DCAS. • Data / databases: lock-table and buffer-pool slot reuse guarded by generations. • Web / backend: connection tables keyed by (slot, generation), so late events for a closed connection are dropped.
Watch out: generation fields are only a few bits wide and wrap eventually. Size them for the realistic reuse rate. Pointer tokens are only safe when frees are deferred until the poller can no longer report that object.
Seen in Tokio: a87936080b 2018-01-31 Capped the number of registered I/O resources to reserve token bits. 08c21e7bac 2018-03-22 encoded a generation in the epoll token (`TOKEN_SHIFT = 22`), and dispatch returns early if it doesn't match ("Reduce spurious wakeups caused by Reactor"). • c17ecb53e7 2018-07-16 Tree at this commit: the sleeping-worker Treiber stack keeps the head index in 16 bits and an ABA sequence in the other 48 (`ABA_GUARD_SHIFT = 16`), plus a per-entry `pushed` bit. • 7eb264a0d0 2019-10-28 `RwLock<Slab>` became a lock-free slab based on mimalloc: each shard has a sync-free local free list and an atomic remote free list that is taken wholesale, pages grow geometrically, and addresses carry generations. 69975fb960 2019-11-20 extracted it as `util/slab` (`INITIAL_PAGE_SIZE = 32`, `TransferStack`). • 8feebab7cd 2020-08-11 Paged slab: pages are never moved, reads go "fully unsynchronized" through cached page pointers, alloc and free take a per-page mutex, and `compact()` releases empty pages ("does not impact benchmarks"). 1e585ccb51 2020-10-02 runs compaction every `COMPACT_INTERVAL = 255` driver ticks. • a0557840eb 2020-09-23 Packs a 7-bit resource generation into the same atomic word as readiness and the driver tick, so stale OS events can't hit a reused slot. • b573adc733 2023-06-29 Deleted the 854-line slab. `ScheduledIo` lives in an `Arc`, the epoll token is its pointer, and frees are deferred to `release_pending_registrations` between polls. ### tokio-006 — Validate only the newly appended suffix
Lens: algorithms · Source: Tokio
Principle: When a buffer grows by appending to a prefix already known to be valid, check only the new bytes. Re-validating the whole buffer on each append is quadratic over a stream.
Why it is faster: A full re-check costs O(total length) per append, so n appends cost O(n²). Validating the appended slice costs O(new bytes). Tokio falls back to a full validation only on error, to report the correct position, so the fast path loses nothing.
Applies elsewhere: Web / backend: streaming `TextDecoder`/UTF-8 decoders that carry state across chunks. • Data / databases: incremental checksums on append-only logs; validating only new WAL records. • Native / systems: incremental parsers that resume from the last consumed offset.
Watch out: a multibyte sequence can straddle the boundary. Validate from the last complete character, or rely on the prefix being complete, as `read_line` does.
Seen in Tokio: a63c6418fd 2026-11-08 `read_line`: the new `into_string(vector, appended)` runs `str::from_utf8` on only the last `appended` bytes, then `String::from_utf8_unchecked`. `read_until` updates the read count before `consume` so the appended count is exact.

### tokio-007 — Use a cheap sampled heuristic instead of full validation on a hot path
Lens: algorithms · Source: Tokio
Principle: When a property only steers behaviour (it doesn't gate correctness), estimate it from a small prefix or a bounded tail scan instead of examining the whole input.
Why it is faster: The Windows console needs whole UTF-8 characters per write. Validating every large buffer is O(n), and treating binary data as text truncates writes. Checking the first 32 bytes to guess "text?", then scanning at most 4 bytes backward to trim a partial character, makes the cost O(1) per write.
Applies elsewhere: Web / backend: MIME and content sniffing on a prefix; trimming split multibyte characters at chunk boundaries. • Data / databases: sampling-based type inference and validation on bulk imports. • Embedded: framing heuristics that look only at the header bytes of a packet.
Watch out: only use this where a wrong guess degrades gracefully (an extra write, a slower path). Never use it for security or integrity checks.
Seen in Tokio: 1684e1c809 2020-10-05 `io/stdio_common.rs`: `from_utf8(&buf[..32])` as the text guess, and a backward scan with `position(|b| b < 0x80 || b >= 0xC0)` limited to `MAX_BYTES_PER_CHAR = 4`. Small buffers skip all checks. The test asserts at most 2 writes for MAX_BUF+1 bytes of pseudo-text.

### tokio-008 — Private per-worker queues plus one shared injection queue, with an atomic length in front of its lock
Lens: scheduling · Source: Tokio
Principle: Give each worker a private run queue for work it creates, and send work from outside the pool to a single shared queue that any free worker drains. Mirror the shared queue's length in an atomic so pollers can see "empty" without taking the lock.
Why it is faster: Pushing external work to a random worker's queue unbalances load. Resources the task creates get pinned to that worker too. A shared queue lets whichever worker is free take the work. Its mutex is touched only when it actually holds something, because an idle or busy worker first reads an atomic count, which costs a cache-line read rather than a lock round trip. The common path, a task spawning or waking tasks on its own worker, never touches shared state.
Applies elsewhere: Web / backend: one accept/dispatch queue feeding per-thread run queues in a thread-per-core server. • Data / databases: per-core operator queues plus one admission queue for new queries. • Native / systems: job systems with thread-local queues and a main-thread injection queue. • Embedded: an ISR-fed shared mailbox with an atomic count checked by the main loop before it disables interrupts.
Watch out: the atomic length is a hint. A push racing an "empty" read must still be caught by the wakeup protocol. Workers that always prefer local work can starve the shared queue (see the fairness-interval entry).
Seen in Tokio: e27b0a46ba 2018-10-03 External submissions first went to a random worker. fdf4aba621 2018-12-28 replaced that with a global MPMC queue: "all workers have equal chance of running this task, which means IO handles will be assigned to reactors more evenly". • ed5a94eb2d 2019-10-19 `queue/global.rs`: a `Mutex<Pointers>` intrusive list plus `len: AtomicUsize` that "helps prevent unnecessary locking in the hot path" (its LSB doubles as the closed flag). • 1cb1e291c1 2020-03-26 / 58ba45a38c 2020-04-09 Tree at these commits: `Inject::is_empty()` reads `len` before `pointers.lock()`, and reads `len` plainly while holding the lock.

### tokio-009 — Same-thread submissions skip synchronization
Lens: scheduling · Source: Tokio
Principle: If the code scheduling work is already running on the thread that owns the target queue, push to an unsynchronized local structure. Only foreign threads should go through the locked or atomic cross-thread path.
Why it is faster: Most wakeups in an event loop come from the loop itself (a task sends to a channel, the receiver wakes). Routing them through a mutex-protected remote queue pays for a lock and possibly an unpark syscall for nothing. A thread-local "am I the owner?" check (a scoped TLS pointer, or a thread-id compare) costs nanoseconds and picks a plain `VecDeque` push.
Applies elsewhere: Web / backend: Netty-style `inEventLoop()` checks; Node/libuv enqueueing directly when called from the loop thread. • Native / systems: GUI toolkits running `invokeLater` inline (or into a local queue) on the UI thread. • Data / databases: per-core executors skipping their MPSC inbox for same-core submissions.
Watch out: the identity check must be exact. Two pools or runtimes on one thread broke Tokio's first version. A local fast path that pushes to the front can starve older work.

### tokio-011 — Steal half of the victim's queue in one claim, and run one stolen task immediately
Lens: scheduling · Source: Tokio
Principle: An idle worker should take a batch (half of what the victim has), not one item. Claim it with one atomic operation, run one task directly, and publish the rest to its own queue with one store.
Why it is faster: Every steal costs a CAS on the victim's head and transfers contended cache lines. Stealing one item sends the thief back almost at once. Stealing `n - n/2` balances load in one round trip, amortizes the cross-core traffic, and leaves the victim enough work. Returning one task straight to the thief skips a push and pop. A thief whose own queue is already more than half full aborts, which prevents work from ping-ponging.
Applies elsewhere: Native / systems: Rayon/TBB-style pools; GC mark-stack stealing. • Data / databases: morsel-driven parallel scans where idle threads grab a range of morsels. • Web / backend: distributed job workers pulling a batch per poll; rebalancing half of an overloaded shard.
Watch out: batch steals move more data per steal. With very coarse tasks, half can be too much. The copy must complete before the claim becomes visible, or a concurrent owner pop can see torn state.
Seen in Tokio: 96b556fbff 2018-08-09 `steal_task` → `steal_tasks` using crossbeam's `steal_many`. • ed5a94eb2d 2019-10-19 `local::Queue::steal`: computes `n = avail - avail/2`, copies n tasks, claims them with one CAS on the victim's head, returns one to run, and publishes the rest with a single Release store of the thief's tail. • 58ba45a38c 2020-04-09 `steal_into` claims the batch by advancing only the `real` cursor, copies, then releases `steal`. The last task is returned without being exposed to other stealers, and the thief aborts if its own queue is more than half full.

### tokio-012 — Spill and refill in batches: one lock per half-queue, and spill the newest half
Lens: scheduling · Source: Tokio
Principle: When a bounded local queue overflows, move half of it to the shared queue in one locked operation. When it runs dry, pull a proportional batch back. Pick which half to spill so that tasks just refilled from the shared queue run before they can be migrated again.
Why it is faster: Moving tasks one at a time takes the shared lock per task. Claiming half the ring with one CAS, pre-linking those tasks through intrusive pointers, and pushing the chain under one lock acquisition amortizes the synchronization. It also leaves room for many local pushes. On refill, taking `len/workers + 1` tasks (capped at half the local capacity) drains a backlog fairly in one lock acquisition and publishes them with one tail store. If the oldest half were spilled, freshly refilled tasks (which sit in the first half) would bounce straight back without running.
Applies elsewhere: Native / systems: thread-local allocator caches spilling and refilling a central free list as chains (tcmalloc/mimalloc style). • Web / backend: queue consumers fetching `backlog/consumers + 1` messages per poll (SQS, Redis lists). • Data / databases: per-core log buffers flushed to a shared writer in chunks.
Watch out: batch sizes need caps, or one worker hoards work. The policy for which half to spill matters. A naive choice causes livelock-like bouncing under overload.
Seen in Tokio: ed5a94eb2d 2019-10-19 `push_overflow` (`#[inline(never)]`, a cold path): CAS `head → head + cap/2`, chain through `header().queue_next`, then `global.push_batch(head, tail, BATCH_LEN)`. 1cb1e291c1 2020-03-26 kept the scheme in the 2020 queue. • 3a94eb0893 2023-05-23 Locally idle workers pop `n = min(inject.len()/num_workers + 1, min(remaining_slots, cap/2))` via `inject.pop_n`, return the first, and bulk-write the rest with `push_back(ExactSizeIterator)`, which publishes `tail` once. 7c54fdce3e 2023-08-04 forces `n >= 1`. • 4165601b1b 2023-07-21 The alternative scheduler pulls `cap/2` on core acquisition and dispatches to peers in batches. The commit reports "~10%" better results on most benchmarks below 16 threads, with mutex contention dominating above that. • 203af02126 2026-04-11 `push_overflow` now spills the second (newest) half: it CAS-claims all slots, stores back `tail + NUM_TASKS_TAKEN` and pushes from `head + NUM_TASKS_TAKEN`. ### tokio-013 — Check the shared queue first every N ticks, with N tuned from measured task cost
Lens: scheduling · Source: Tokio
Principle: Prefer cheap local work, but every Nth scheduling tick look at the shared queue first. Pick N so the check is rare but starvation stays bounded. Better still, derive N from a time target and a moving average of task duration.
Why it is faster: Always checking the global queue costs a lock per task. Never checking it starves external work. A periodic check bounds latency for external work while keeping the hot path lock-free. A prime interval avoids lining up with periodic workloads. A fixed count fails when tasks are slow (61 × 1 ms is a long wait), so converting a target of 200 µs into a count via an EWMA of poll time keeps latency bounded whatever the task cost.
Applies elsewhere: Web / backend: event loops deciding how many callbacks to run before polling I/O, from measured callback cost. • Native / systems: game loops sizing work per frame from measured frame time. • Data / databases: background compaction sliced by observed per-unit cost; admin queues checked every N operations. • Embedded: super-loops servicing a low-priority mailbox every N iterations.
Watch out: adaptive intervals need clamps and hysteresis, or noise makes them oscillate. Let users pin a fixed value for latency-critical deployments.

### tokio-014 — Poll the event source with a zero timeout while busy; never block-park with work pending
Lens: scheduling · Source: Tokio · Also: libuv
Principle: A busy executor must still look at I/O and timers periodically, without blocking. Before going to sleep, re-check every work source. If anything is pending, do a non-blocking poll instead of a blocking park.
Why it is faster: An executor that only drains its run queue never sees new socket events, so I/O-driven tasks starve and their latency grows without bound. A zero-timeout `epoll_wait` every N tasks costs one cheap syscall and injects ready work. Conversely, hooks that run just before parking can create work. Blocking at that point stalls it until an unrelated event arrives, and skipping the driver entirely starves timers under repeated short calls.
Applies elsewhere: Native / systems: game loops pumping OS messages every frame even under load; GUI loops processing events between work batches. • Data / databases: long scans polling a cancellation or completion queue every N rows. • Embedded: main loops checking interrupt flags between work items instead of only in idle.
Watch out: polling too often wastes syscalls, and too rarely adds I/O latency. Tie the interval to the fairness tick. A large event batch in a non-blocking poll can overflow local queues.

### tokio-015 — Throttle idle-worker wakeups: cap searchers, wake only when nobody is searching, chain the rest
Lens: scheduling · Source: Tokio
Principle: When new work appears, wake a sleeping worker only if no worker is already looking for work, and let the last searcher that finds work wake exactly one more. Cap concurrent searchers at about half the workers.
Why it is faster: Waking a thread per spawned task causes wake storms: each wake is a syscall and a context switch, and most woken threads find nothing. A searching worker will find the new task anyway. Chained wakeups ramp parallelism up progressively, matched to the actual backlog. Too many concurrent thieves contend on the same victims' cache lines, so the cap trades a little latency for much less coherence traffic. Packing the searching and unparked counts into one atomic gives a lock-free fast path. The check can be Relaxed, because exceeding the cap is harmless.
Applies elsewhere: Native / systems: thread pools using `notify_one` chains instead of `notify_all`; GC worker wakeups. • Web / backend: connection-pool waiters that wake one, which wakes the next if capacity remains; `EPOLLEXCLUSIVE`/`accept_mutex`-style herd control. • Data / databases: capping concurrent cache-refill or compaction workers.
Watch out: the protocol is subtle. A missed "last searcher notifies" or a wrong state transition either strands work (a lost wakeup) or brings the storm back. Tokio needed an RMW, not a load, to make the check visible.

### tokio-031 — One allocation per object, hot fields first, cold fields last
Lens: memory-layout · Source: Tokio
Principle: Put everything an object needs into one contiguous block. Order it as a fixed-layout hot header, then the variable payload, then rarely used fields in a trailer the hot path never touches.
Why it is faster: Separate allocations for the object, its payload and its side data each cost a malloc/free and a pointer chase, and each can land on a different cache line. A fixed header offset also lets type-erased code reach every field through a single `*mut Header`. When the payload's type varies, its offset varies too. So the trailer's offset is stored in the per-type vtable, and fields placed before the payload keep type-independent offsets. The cost: the layout has to be `repr(C)` and is harder to change.
Applies elsewhere: Web / backend: Allocate a request object and its small inline buffer together, with routing and state fields first and debug or trace metadata last. • Native / systems: Use VM object headers before fields, and keep a kernel struct's hot members together at the front. • Data / databases: Put the tuple header before the payload, and move rarely read columns into a separate cold segment. • Embedded: Use one static pool slot per job with control fields first, so an ISR touches one line.

### tokio-032 — Pack an object's flags, counters and generation into one machine word
Lens: memory-layout · Source: Tokio
Principle: When several small fields describe one object's state, bit-pack them into a single word. One load then gives a consistent snapshot, and one read-modify-write makes any transition.
Why it is faster: Separate atomics need separate RMWs, and getting their combined ordering right is hard. Readers can also see a torn mix of old and new values. A packed word costs one CAS or `fetch_*` per transition, takes 8 bytes instead of several words, and can carry extra guards (a generation, a tick, a shutdown bit) at no added load cost. A check that used to go through a separate lock, such as "is the driver shut down?", becomes a bit test on a word the hot path already reads. The limit is bit budget. Narrow counters wrap, so give generations and refcounts enough bits.
Applies elsewhere: Native / systems: `shared_ptr`-style control blocks with flag bits, and futex words that combine "locked" and "waiters" bits. • Data / databases: A buffer-pool page latch word holding pin count, dirty bit and an I/O-in-progress bit. • Web / backend: A connection state machine where state, close-requested and in-flight count share one atomic integer. • Embedded: A status register image in one `uint32_t` updated with a single LDREX/STREX.
Watch out: Every bit you add shrinks the counter fields, and an overflow corrupts the neighbouring flags. Write named mask and shift helpers. Hand-written bit math in many places is where bugs show up.

### tokio-034 — Shrink the handle users embed; keep data in the shared node

### tokio-037 — Keep big values off the stack: heap-allocate early and construct in place

### tokio-039 — Read into uninitialized memory and track an "initialized" watermark
Lens: allocation · Source: Tokio

Applies elsewhere: Web / backend: Node `Buffer.allocUnsafe` for socket reads, and Go `bufio` buffers reused without clearing. • Native / systems: `malloc` instead of `calloc` for I/O buffers, and C++ `resize_and_overwrite`. • Data / databases: Read pages into uninitialized buffer-pool frames, and receive network results into reused arenas. • Embedded: DMA into uninitialized RAM regions (`.noinit`) without a memset first.
Watch out: Never expose uninitialized bytes to code that might read them, and never trust an arbitrary reader to only write. Buffers that cross a security boundary should still be cleared.

### tokio-052 — Resolve bindings once at construction, not on every use
Lens: caching · Source: Tokio
Principle: If an object will always be created inside the context it depends on (a runtime, a driver, a connection), look up and store that dependency in the constructor. Don't check and publish it lazily on every operation.

### tokio-056 — Use a CPU spin hint, not a yield syscall, for nanosecond waits

### tokio-095 — Keep a copy pipeline full, and flush when the source stalls
Lens: io · Source: Tokio

### tokio-098 — Size the event batch to what the consumer can absorb, and reuse the array

Principle: Fetch OS events into one preallocated array that lives for the life of the loop. Limit how many events you take per poll to roughly how much work you can queue locally. Anything left stays in the kernel for the next poll.
Why it is faster: Reusing the event array removes an allocation per poll. The batch limit matters under overload. If one zero-timeout poll returns 1024 events but the worker's local run queue holds 256 tasks, the excess spills to a shared queue, adds contention and builds a backlog. Taking fewer events leaves backpressure in the kernel, where it costs nothing.
Applies elsewhere: Web / backend: Tune `maxevents` in `epoll_wait` per poll type: large when idle-blocking, small when polling between tasks. • Embedded / drivers: Use a NAPI-style budget: process at most N packets per poll and leave the rest in the RX ring. • Data / databases: Set a consumer's `max.poll.records` to what one processing cycle can handle.
Watch out: Too small a batch means more syscalls per event when load is high but queues are not full. Keep the blocking-poll batch large and limit only the busy polls.

### tokio-099 — Pack readiness, an event tick, a slot generation and a shutdown flag into one atomic
Lens: io · Source: Tokio
Principle: Keep all per-resource I/O state that is checked on every operation in one machine word. One load gives a consistent snapshot, and one conditional RMW clears readiness only if no newer event arrived. Generation bits make stale events for a reused slot harmless.
Why it is faster: Separate fields would need a lock or several atomics to read consistently. The tick makes "clear readiness" safe without a lock: a clear succeeds only if the tick still matches the event that was observed, so a racing new event is never lost. The generation filters events queued for a slot's previous occupant, preventing spurious wakeups. Putting a shutdown bit in the same word removes a separate global "is shut down?" check (an `RwLock` read in Tokio's case) from every I/O call.
Applies elsewhere: Native / systems: Put slot index plus generation in epoll `data.u64` or io_uring `user_data`, and drop completions whose generation doesn't match the slot. • Web / backend: Pack a connection's state (readable, writable, closing) plus a sequence number into one atomic, so cross-thread checks never take a lock. • Data / databases: Pack pin count, dirty, I/O-in-progress and a "file closed" flag into a buffer-pool page header word.
Watch out: Narrow fields wrap. An 8-bit tick or 7-bit generation offers only probabilistic protection, so size them for how long a stale event can realistically be in flight.

### tokio-100 — Keep the registration path thin: owner-held handles, pointer tokens, no syscalls under locks
Lens: io · Source: Tokio
Principle: The poller should only need a cheap token for each registered resource. The user handle owns the OS object. Closing it lets the kernel drop the registration. The token can be the object's address, so dispatch is a cast rather than a table lookup. Registration syscalls run outside any lock.
Why it is faster: Sharing every I/O object between handle and loop through a refcount costs atomic traffic and an explicit deregister call. Applies elsewhere: Web / backend: Store a connection pointer in `epoll_event.data.ptr` and free connections only at a safe point after the poll batch. • Native / systems: Rely on `close()` to remove the fd from epoll instead of paying an extra `EPOLL_CTL_DEL` (when the fd is not duplicated). • Data / databases: Release the table latch before issuing the read for a page you just reserved a frame for.

### tokio-102 — Turn asynchronous OS notifications into one coalesced event-loop wakeup

### tokio-103 — Make child-process exit an event, not a scan

### tokio-108 — Give each worker its own timer structure; send cross-thread changes as messages
Lens: scheduling · Source: Tokio
Principle: A single shared timer structure behind one lock serializes every core that creates or cancels timers. Let a single owner thread mutate each timer structure. Other threads post registrations or cancellations into a small queue that the owner drains in batches.

Applies elsewhere: Native / systems: Use per-CPU timer bases (as the Linux kernel does). A cancel from another CPU is posted to the owner instead of taking a global lock. • Web / backend: Shard-per-core servers (Seastar, Netty event loops) keep one timer wheel per loop and post cross-loop cancels as tasks. • Data / databases: Keep per-thread TTL expiry structures in a cache, with remote deletes queued to the owning thread.
Watch out: Sharding a shared structure is not the same as giving it single-thread ownership. Tokio's sharded version regressed. With per-owner wheels, a timer created on one worker and polled on another needs a remote path, and the owner must drain that queue promptly.

### tokio-117 — Make instrumentation compile out, and borrow rather than clone on the poll path
Lens: networking · Source: Tokio
Principle: Instrumentation that is disabled should cost nothing: replace it with a zero-sized mock or a compile-time-false branch. Instrumentation that is enabled should avoid refcount traffic and allocation on every poll.
Why it is faster: A runtime "metrics enabled?" check still costs a load and a branch per event, and it keeps counter fields in hot structs. A mock module or `cfg!` guard lets the compiler delete the code and the fields. Entering a tracing span via `clone().entered()` costs an atomic increment and decrement per poll, while `enter()` on a borrowed span costs neither.
Applies elsewhere: Web / backend: Gate verbose tracing behind build flags or tree-shakeable modules. Pass OpenTelemetry context by reference, not by copying per call. • Embedded: Use macros that expand to nothing in release firmware, so trace points cost neither flash nor cycles. • Native / systems: Use static tracepoints (USDT, kernel static keys) that are a nop until enabled.
Watch out: If production builds exclude the instrumentation, you can't turn it on in production. Pick which signals must always be available and make those cheap instead.

### tokio-118 — Clamp memory that grows exponentially with a precision setting
Lens: networking · Source: Tokio
Principle: When a configuration knob (histogram error target, filter false-positive rate) controls a bucket count exponentially, clamp it to a hard maximum, so a small value in a config file cannot allocate gigabytes.
Why it is faster: Histogram buckets scale as 2^precision. One step past the intended maximum doubles memory and cache footprint for every histogram instance. A loop bound costs nothing.
Applies elsewhere: Web / backend: Cap HDR histogram significant digits, and cap per-route metric cardinality. • Data / databases: Cap Bloom-filter and sketch sizes derived from target error rates, and cap cache sizes derived from a percentage of RAM.
Watch out: A silent clamp hides a misconfiguration. Validate the setting or log when the clamp applies.

### tokio-120 — Expose the batch sizes and intervals that trade latency for throughput
Lens: networking · Source: Tokio
Principle: Hard-coded event batch sizes, polling intervals and buffer sizes fit the average workload. Exposing them as configuration, with documented defaults, lets latency-sensitive and throughput-sensitive deployments each tune them.
Why it is faster: The best number depends on the workload: task length, connection count, file sizes. A knob costs nothing at runtime, because it is read once into a field, and it lets an operator fix a pathological case without forking.
Applies elsewhere: Web / backend: nginx-style `worker_connections` and `multi_accept`. A libuv thread-pool size env var. • Data / databases: Kafka `max.poll.records`, JDBC fetch size, WAL group-commit delay.
Watch out: Every knob is a support burden and a way to misconfigure. Pick good defaults, validate the range, and prefer self-tuning where it can be done reliably.
