### tokio-001 — Use a fixed-capacity, power-of-two, single-producer ring instead of a general concurrent deque
Lens: algorithms · Source: Tokio
Principle: When one thread owns the producer side, a bounded ring with masked indices beats a growable lock-free deque. You give up capabilities the workload never uses (growth, popping from both ends, epoch reclamation) and get rid of their fences and their memory management.
Why it is faster: A growable Chase-Lev deque pays for buffer reallocation, epoch-based garbage collection and extra fences on every operation. A fixed ring of 2k slots indexes with `pos & MASK` (no division) and never reallocates. Because only the owner writes the tail, a push is a plain slot write plus one Release store. Consumers coordinate through a single CAS on the head. Packing two narrow cursors into one atomic word lets "a steal is in progress" be detected without a lock. The cost is fixed capacity, so the design needs an overflow policy, and the counters wrap, which opens an ABA window if they are too narrow.
Applies elsewhere: Native / systems: per-thread job rings in game-engine job systems; per-core packet queues in NIC drivers. • Embedded: DMA descriptor rings and UART buffers sized to 2k, indexed with a mask. • Data / databases: SPSC or SPMC log and WAL staging buffers between a writer thread and flushers. • Web / backend: per-worker request queues in thread-per-core servers, in place of a shared growable queue.
Watch out: a full ring needs a defined spill path (see "Spill and refill in halves"). Cursors only a little wider than the capacity can wrap while a stalled thread holds an old value, so use the widest cursor the platform's atomics allow.
Seen in Tokio: ed5a94eb2d 2019-10-19 The scheduler rewrite replaced crossbeam's Chase-Lev deque with a 256-slot `Box<[MaybeUninit<Task>]>`. Owner pops and stealers both CAS on `head: AtomicU32`. `tail` is written only by the owner. Indices use wrapping u32 arithmetic and `& MASK`. PR benchmarks: `chained_spawn` 2,019,796 → 147,943 ns/iter, `ping_pong` 1,279,948 → 537,744, `spawn_many` 10.28M → 7.45M. Hyper hello-world rose from 113.9k to 152.3k req/s. • 1cb1e291c1 2020-03-26 Limited the queue to one concurrent stealer. • 58ba45a38c 2020-04-09 Packed `head` as `pack(steal, real)`, two u16 cursors in one `AtomicU32`, with `tail: AtomicU16`. Cursors wider than the 256-slot capacity can tell "full" from "empty". fa4fe9ef6f 2020-04-02 fixed a `+` to `wrapping_add` on the narrow cursors. • 78fc94099b 2022-09-28 Where 64-bit atomics exist, the queue now uses 32-bit cursors packed into a 64-bit word (16/32 otherwise). The commit reports this "greatly improves resilience to ABA and has no impact on performance on 64-bit platforms".

### tokio-002 — Intrusive linked lists: embed the link in the object that waits
Lens: algorithms · Source: Tokio
Principle: Store list pointers inside the waiting object (a pinned future, a timer, a task header) instead of allocating a separate node. Insert and unlink are then O(1) with no allocation, and you can split or concatenate whole chains by relinking at the boundary.
Why it is faster: An allocated waiter node costs a malloc and a free per wait. Cancelled waiters can also pile up in lock-free stacks that can't remove from the middle. With an intrusive node, the object itself is the node. Cancelling (dropping) it unlinks it in place in O(1), so memory never grows with abandoned waiters. A pre-linked chain can be handed to another queue under one lock acquisition. Satisfied waiters at the front of a list can be split off in O(1) by rewriting the head pointers. The trade-offs: the object must have a stable address (pinning), the code is unsafe, and an object can only sit in as many lists as it has link fields.
Applies elsewhere: Native / systems: Linux `wait_queue_entry` on the waiter's stack; `list_head` embedded in structs. • Embedded: RTOS timer and wait lists threaded through TCBs, with no heap at all. • Data / databases: lock-manager request nodes embedded in the transaction's lock request; LRU links inside buffer-pool frames. • Web / backend: per-connection idle-timer nodes embedded in the connection object (nginx-style).
Watch out: a node must be unlinked before its memory goes away. Dropping a pinned future has to take the list lock, and moving a linked object corrupts the list. In garbage-collected languages the win is smaller, because the allocation was cheap to begin with.
Seen in Tokio: ed5a94eb2d 2019-10-19 The global injection queue is an intrusive list threaded through each task header's `queue_next`. A whole pre-linked batch can then be pushed with `push_batch(head, tail, n)`. • 06bcbe8dcf 2020-02-27 Generalized `LinkedList` with a `Link` trait so the pointers can live anywhere in the node. c9f5bc2915 2020-09-02 made `LinkedList::new` a `const fn`. • acf8a7da7a 2020-03-23 The semaphore's allocated atomic waiter stack, which "requires a heap allocation for every waiter" and blew up memory (#2237), became an intrusive list. ### tokio-003 — Hierarchical timing wheel with per-level occupancy bitmaps instead of a heap
Lens: algorithms · Source: Tokio
Principle: For large numbers of deadlines at a fixed resolution, bucket them into a few levels of 64-slot wheels. Use bit operations to pick the level and to find the next non-empty slot, so insert, cancel and next-expiry are all O(1).
Why it is faster: A binary heap costs O(log n) per insert and cancel and needs an index map to cancel arbitrary entries. A hierarchical wheel files a deadline at `level = (63 - leading_zeros(now ^ when)) / 6`, with no loop. Each level keeps a 64-bit `occupied` mask, so the next non-empty slot is `occupied.rotate_right(now_slot).trailing_zeros()`, about one instruction. Slot boundaries for power-of-two ranges are masks, not modulo. The trade-offs are a fixed resolution (1 ms) and a maximum range, and entries cascade down levels as time advances. Edge cases such as draining "everything" or top-level wrap-around need explicit handling.
Applies elsewhere: Web / backend: idle, keep-alive and request timeouts for 100k+ connections in proxies and gateways. • Native / systems: TCP retransmit and delayed-ACK timers; game cooldowns and scheduled events. • Data / databases: lock-wait timeouts, TTL expiry and lease renewals in caches and DBs. • Embedded: a software timer service on a tick interrupt, with a bitmap of occupied slots.
Watch out: with a handful of timers, or when exact ordering matters below the resolution, a heap is simpler and just as fast. "Drain everything" and wrap-around are the usual bug sites, so test far-future deadlines explicitly.
Seen in Tokio: 1f0d2198ad 2016-09-07 2016: a binary heap plus a slab mapping handle → heap position (O(log n) arbitrary removal) replaced a single-level wheel, for "more predictable performance semantics". 8327d327c1 2016-08-13 rewrote `next_timeout` so a fold no longer moves `Option<Instant>` values. b320d9ee58 2017-09-12 moved the expensive heap-consistency asserts behind a dedicated cfg so users' debug builds aren't slowed. • 19500f7df8 2018-03-28 The hierarchical hashed wheel: six levels × 64 slots, 1 ms resolution, `MAX_DURATION = 1 << 36`, `level_for` via XOR and `leading_zeros`, `next_occupied_slot` via `rotate_right` and `trailing_zeros`. • d822b721b4 2018-08-20 Factored the wheel into a reusable `wheel/` module (it also backs `DelayQueue`). • ae67851f11 2020-11-23 Driver rewrite: wheel levels hold intrusive entry lists, and expired entries move to a `pending` list that is processed separately. • 28b983c4bc 2022-02-15 `level_start = now & !(level_range - 1)` replaces `now - now % level_range`. • 2fb5757a97 2026-10-11 The top level wraps like a ring, so the scan starts one past `now_slot`, which stops the next expiration from being computed too early. • 6fa334aee7 2026-10-03 Shutdown ("fire everything", `now == u64::MAX`) walks the occupied slots and expires their entries directly. ### tokio-004 — Keep an occupancy bitmap so searches skip empty candidates
Lens: algorithms · Source: Tokio
Principle: Next to a set of queues, shards, workers or branches, keep one word of bits that says which are non-empty, idle or still enabled. Searchers mask and count bits instead of probing (and locking) each candidate.
Why it is faster: Probing an empty queue still costs a cache miss, and often a lock. One atomic load of a bitmask tells a thief which victims are worth trying, or tells a consumer which shards hold work. Branch-free bit scans (`trailing_zeros`) then pick a candidate. If bits change only under the owning lock, they are exact at unlock and merely hints elsewhere, so a stale bit costs one wasted probe and never correctness.
Applies elsewhere: Embedded: RTOS ready-priority bitmaps (the highest set bit picks the next task). • Native / systems: allocator free-block search with `ffs`; per-NUMA "non-empty run queue" masks. • Web / backend: load balancers keeping a bitmap of healthy or non-saturated backends. • Data / databases: free-space maps; bitmaps of dirty pages or non-empty partitions.
Watch out: treat any bit read outside the lock as a hint and re-check under the lock. One word covers 64 entries, so chunk larger sets. Bits updated without a lock need careful ordering, or a set bit can be lost.
Seen in Tokio: 19500f7df8 2018-03-28 Timer-wheel levels: a 64-bit `occupied` mask per level (see the timing-wheel entry). • 8cf98d6946 2020-01-22 `select!` keeps a stack `Mask` of disabled or completed branches and skips them, with no allocation. • a58beb3aca 2023-07-21 The alternative scheduler activated `IdleMap` (chunks of `AtomicUsize` bits). `steal` snapshots it to "avoid trying to steal from idle workers". • 1604bc3351 2026-04-10 A sharded `spawn_blocking` queue, reverted in 56aaa43e91 2026-04-16 after a hang, then re-landed opt-in by 8b13642a1f 2026-08-09. It has 16 shards and a `non_empty_mask: AtomicUsize` updated with `fetch_or`/`fetch_and` (Relaxed) under the shard lock, so consumers skip empty shards without locking them.

### tokio-005 — Index-plus-generation handles (slabs, stacks, tokens), and know when a pointer is cheaper
Lens: algorithms · Source: Tokio
Principle: Address objects by a small slot index and spend the remaining bits of the word on a generation counter. Stale handles and ABA are then detected with one compare. Once the index-to-slot lookup itself becomes the hot cost, switch to the object's address and defer frees instead.
Why it is faster: Small indices leave room for a wide ABA tag without double-width CAS. A slab with geometrically growing pages never moves entries, so readers can index without locks, and generation tags filter events meant for a slot's previous occupant, which removes spurious wakeups. Local and remote free lists make most inserts synchronization-free. The slab still costs an address decode and a generation check per lookup, and its pages need compaction to shrink. When ownership can guarantee that an object outlives its registrations (frees are deferred until no event can refer to it), using the pointer as the token turns dispatch into a cast.
Applies elsewhere: Native / systems: generational entity IDs in ECS game engines; io_uring `user_data` carrying slot + sequence. • Embedded: fixed object pools with index free lists and tagged heads, no heap and no DCAS. • Data / databases: lock-table and buffer-pool slot reuse guarded by generations. • Web / backend: connection tables keyed by (slot, generation), so late events for a closed connection are dropped.
Watch out: generation fields are only a few bits wide and wrap eventually. Size them for the realistic reuse rate. Pointer tokens are only safe when frees are deferred until the poller can no longer report that object.
Seen in Tokio: a87936080b 2018-01-31 Capped the number of registered I/O resources to reserve token bits. 08c21e7bac 2018-03-22 encoded a generation in the epoll token (`TOKEN_SHIFT = 22`), and dispatch returns early if it doesn't match ("Reduce spurious wakeups caused by Reactor"). • c17ecb53e7 2018-07-16 Tree at this commit: the sleeping-worker Treiber stack keeps the head index in 16 bits and an ABA sequence in the other 48 (`ABA_GUARD_SHIFT = 16`), plus a per-entry `pushed` bit. • 7eb264a0d0 2019-10-28 `RwLock<Slab>` became a lock-free slab based on mimalloc: each shard has a sync-free local free list and an atomic remote free list that is taken wholesale, pages grow geometrically, and addresses carry generations. 69975fb960 2019-11-20 extracted it as `util/slab` (`INITIAL_PAGE_SIZE = 32`, `TransferStack`). • 8feebab7cd 2020-08-11 Paged slab: pages are never moved, reads go "fully unsynchronized" through cached page pointers, alloc and free take a per-page mutex, and `compact()` releases empty pages ("does not impact benchmarks"). 1e585ccb51 2020-10-02 runs compaction every `COMPACT_INTERVAL = 255` driver ticks. • a0557840eb 2020-09-23 Packs a 7-bit resource generation into the same atomic word as readiness and the driver tick, so stale OS events can't hit a reused slot. • b573adc733 2023-06-29 Deleted the 854-line slab. `ScheduledIo` lives in an `Arc`, the epoll token is its pointer, and frees are deferred to `release_pending_registrations` between polls. The commit cites the slab's "more expensive token lookup path". 2f899144ed 2024-11-16 dropped a leftover pointer→reference→pointer round trip.

### tokio-006 — Validate only the newly appended suffix
Lens: algorithms · Source: Tokio
Principle: When a buffer grows by appending to a prefix already known to be valid, check only the new bytes. Re-validating the whole buffer on each append is quadratic over a stream.
Why it is faster: A full re-check costs O(total length) per append, so n appends cost O(n²). Validating the appended slice costs O(new bytes). Tokio falls back to a full validation only on error, to report the correct position, so the fast path loses nothing.
Applies elsewhere: Web / backend: streaming `TextDecoder`/UTF-8 decoders that carry state across chunks. • Data / databases: incremental checksums on append-only logs; validating only new WAL records. • Native / systems: incremental parsers that resume from the last consumed offset.
Watch out: a multibyte sequence can straddle the boundary. Validate from the last complete character, or rely on the prefix being complete, as `read_line` does.
Seen in Tokio: a63c6418fd 2026-11-08 `read_line`: the new `into_string(vector, appended)` runs `str::from_utf8` on only the last `appended` bytes, then `String::from_utf8_unchecked`. `read_until` updates the read count before `consume` so the appended count is exact.

### tokio-007 — Use a cheap sampled heuristic instead of full validation on a hot path
Lens: algorithms · Source: Tokio
Principle: When a property only steers behaviour (it doesn't gate correctness), estimate it from a small prefix or a bounded tail scan instead of examining the whole input.
Why it is faster: The Windows console needs whole UTF-8 characters per write. Validating every large buffer is O(n), and treating binary data as text truncates writes. Checking the first 32 bytes to guess "text?", then scanning at most 4 bytes backward to trim a partial character, makes the cost O(1) per write.
Applies elsewhere: Web / backend: MIME and content sniffing on a prefix; trimming split multibyte characters at chunk boundaries. • Data / databases: sampling-based type inference and validation on bulk imports. • Embedded: framing heuristics that look only at the header bytes of a packet.
Watch out: only use this where a wrong guess degrades gracefully (an extra write, a slower path). Never use it for security or integrity checks.
Seen in Tokio: 1684e1c809 2020-10-05 `io/stdio_common.rs`: `from_utf8(&buf[..32])` as the text guess, and a backward scan with `position(|b| b < 0x80 || b >= 0xC0)` limited to `MAX_BYTES_PER_CHAR = 4`. Small buffers skip all checks. The test asserts at most 2 writes for MAX_BUF+1 bytes of pseudo-text.

### tokio-008 — Private per-worker queues plus one shared injection queue, with an atomic length in front of its lock
Lens: scheduling · Source: Tokio
Principle: Give each worker a private run queue for work it creates, and send work from outside the pool to a single shared queue that any free worker drains. Mirror the shared queue's length in an atomic so pollers can see "empty" without taking the lock.
Why it is faster: Pushing external work to a random worker's queue unbalances load. Resources the task creates get pinned to that worker too. A shared queue lets whichever worker is free take the work. Its mutex is touched only when it actually holds something, because an idle or busy worker first reads an atomic count, which costs a cache-line read rather than a lock round trip. The common path, a task spawning or waking tasks on its own worker, never touches shared state.
Applies elsewhere: Web / backend: one accept/dispatch queue feeding per-thread run queues in a thread-per-core server. • Data / databases: per-core operator queues plus one admission queue for new queries. • Native / systems: job systems with thread-local queues and a main-thread injection queue. • Embedded: an ISR-fed shared mailbox with an atomic count checked by the main loop before it disables interrupts.
Watch out: the atomic length is a hint. A push racing an "empty" read must still be caught by the wakeup protocol. Workers that always prefer local work can starve the shared queue (see the fairness-interval entry).
Seen in Tokio: e27b0a46ba 2018-10-03 External submissions first went to a random worker. fdf4aba621 2018-12-28 replaced that with a global MPMC queue: "all workers have equal chance of running this task, which means IO handles will be assigned to reactors more evenly". • ed5a94eb2d 2019-10-19 `queue/global.rs`: a `Mutex<Pointers>` intrusive list plus `len: AtomicUsize` that "helps prevent unnecessary locking in the hot path" (its LSB doubles as the closed flag). • 1cb1e291c1 2020-03-26 / 58ba45a38c 2020-04-09 Tree at these commits: `Inject::is_empty()` reads `len` before `pointers.lock()`, and reads `len` plainly while holding the lock.

### tokio-009 — Same-thread submissions skip synchronization
Lens: scheduling · Source: Tokio
Principle: If the code scheduling work is already running on the thread that owns the target queue, push to an unsynchronized local structure. Only foreign threads should go through the locked or atomic cross-thread path.
Why it is faster: Most wakeups in an event loop come from the loop itself (a task sends to a channel, the receiver wakes). Routing them through a mutex-protected remote queue pays for a lock and possibly an unpark syscall for nothing. A thread-local "am I the owner?" check (a scoped TLS pointer, or a thread-id compare) costs nanoseconds and picks a plain `VecDeque` push.
Applies elsewhere: Web / backend: Netty-style `inEventLoop()` checks; Node/libuv enqueueing directly when called from the loop thread. • Native / systems: GUI toolkits running `invokeLater` inline (or into a local queue) on the UI thread. • Data / databases: per-core executors skipping their MPSC inbox for same-core submissions.
Watch out: the identity check must be exact. Two pools or runtimes on one thread broke Tokio's first version. A local fast path that pushes to the front can starve older work.

### tokio-010 — A "run next" slot for the most recently woken task, capped for fairness
Lens: scheduling · Source: Tokio
Principle: When the running task wakes another, run the woken one next from a one-element slot ahead of the FIFO queue, because its data is still in cache. Bound how many times in a row the slot may bypass the queue, and make sure blocked or idle workers can still reach it.
Why it is faster: In message passing, the receiver needs exactly the data the sender just wrote. Running it immediately reuses hot cache lines and cuts round-trip latency. A FIFO queue would put it behind every older task. Unbounded, the slot lets two ping-ponging tasks monopolize a worker. A task in a non-stealable slot is also stranded if the worker blocks. Caps and spill rules keep the locality win without those failure modes.
Applies elsewhere: Web / backend: actor runtimes delivering a reply to the actor the sender just woke; pipeline stages run on the core that fed them. • Data / databases: running the operator just unblocked by its child before older operators. • Native / systems: coroutine schedulers handing off directly to the resumed coroutine, with an N-in-a-row cap.
Watch out: without a cap the slot creates starvation. Making it stealable costs locality and needed a revert in Tokio. Any blocking path must first move the slot's task somewhere other threads can see.
Seen in Tokio: ed5a94eb2d 2019-10-19 `Worker { next: Cell<Option<Task>> }`: `push` moves the previous occupant into the ring, `local_pop` takes `next` first, and `push_yield` bypasses the slot so yielding tasks go to the back. • caa7e180e4 2020-03-28 `Core.lifo_slot` is checked before the ring. ### tokio-011 — Steal half of the victim's queue in one claim, and run one stolen task immediately
Lens: scheduling · Source: Tokio
Principle: An idle worker should take a batch (half of what the victim has), not one item. Claim it with one atomic operation, run one task directly, and publish the rest to its own queue with one store.
Why it is faster: Every steal costs a CAS on the victim's head and transfers contended cache lines. Stealing one item sends the thief back almost at once. Stealing `n - n/2` balances load in one round trip, amortizes the cross-core traffic, and leaves the victim enough work. Returning one task straight to the thief skips a push and pop. A thief whose own queue is already more than half full aborts, which prevents work from ping-ponging.
Applies elsewhere: Native / systems: Rayon/TBB-style pools; GC mark-stack stealing. • Data / databases: morsel-driven parallel scans where idle threads grab a range of morsels. • Web / backend: distributed job workers pulling a batch per poll; rebalancing half of an overloaded shard.
Watch out: batch steals move more data per steal. With very coarse tasks, half can be too much. The copy must complete before the claim becomes visible, or a concurrent owner pop can see torn state.
Seen in Tokio: 96b556fbff 2018-08-09 `steal_task` → `steal_tasks` using crossbeam's `steal_many`. • ed5a94eb2d 2019-10-19 `local::Queue::steal`: computes `n = avail - avail/2`, copies n tasks, claims them with one CAS on the victim's head, returns one to run, and publishes the rest with a single Release store of the thief's tail. • 58ba45a38c 2020-04-09 `steal_into` claims the batch by advancing only the `real` cursor, copies, then releases `steal`. The last task is returned without being exposed to other stealers, and the thief aborts if its own queue is more than half full.

### tokio-012 — Spill and refill in batches: one lock per half-queue, and spill the newest half
Lens: scheduling · Source: Tokio
Principle: When a bounded local queue overflows, move half of it to the shared queue in one locked operation. When it runs dry, pull a proportional batch back. Pick which half to spill so that tasks just refilled from the shared queue run before they can be migrated again.
Why it is faster: Moving tasks one at a time takes the shared lock per task. Claiming half the ring with one CAS, pre-linking those tasks through intrusive pointers, and pushing the chain under one lock acquisition amortizes the synchronization. It also leaves room for many local pushes. On refill, taking `len/workers + 1` tasks (capped at half the local capacity) drains a backlog fairly in one lock acquisition and publishes them with one tail store. If the oldest half were spilled, freshly refilled tasks (which sit in the first half) would bounce straight back without running.
Applies elsewhere: Native / systems: thread-local allocator caches spilling and refilling a central free list as chains (tcmalloc/mimalloc style). • Web / backend: queue consumers fetching `backlog/consumers + 1` messages per poll (SQS, Redis lists). • Data / databases: per-core log buffers flushed to a shared writer in chunks.
Watch out: batch sizes need caps, or one worker hoards work. The policy for which half to spill matters. A naive choice causes livelock-like bouncing under overload.
Seen in Tokio: ed5a94eb2d 2019-10-19 `push_overflow` (`#[inline(never)]`, a cold path): CAS `head → head + cap/2`, chain through `header().queue_next`, then `global.push_batch(head, tail, BATCH_LEN)`. 1cb1e291c1 2020-03-26 kept the scheme in the 2020 queue. • 3a94eb0893 2023-05-23 Locally idle workers pop `n = min(inject.len()/num_workers + 1, min(remaining_slots, cap/2))` via `inject.pop_n`, return the first, and bulk-write the rest with `push_back(ExactSizeIterator)`, which publishes `tail` once. 7c54fdce3e 2023-08-04 forces `n >= 1`. • 4165601b1b 2023-07-21 The alternative scheduler pulls `cap/2` on core acquisition and dispatches to peers in batches. The inject pull is capped at `max_capacity()/2`, so refilled tasks always land in the first half and run before they can migrate again.

### tokio-013 — Check the shared queue first every N ticks, with N tuned from measured task cost
Lens: scheduling · Source: Tokio
Principle: Prefer cheap local work, but every Nth scheduling tick look at the shared queue first. Pick N so the check is rare but starvation stays bounded. Better still, derive N from a time target and a moving average of task duration.
Why it is faster: Always checking the global queue costs a lock per task. Never checking it starves external work. A periodic check bounds latency for external work while keeping the hot path lock-free. A prime interval avoids lining up with periodic workloads. A fixed count fails when tasks are slow (61 × 1 ms is a long wait), so converting a target of 200 µs into a count via an EWMA of poll time keeps latency bounded whatever the task cost.
Applies elsewhere: Web / backend: event loops deciding how many callbacks to run before polling I/O, from measured callback cost. • Native / systems: game loops sizing work per frame from measured frame time. • Data / databases: background compaction sliced by observed per-unit cost; admin queues checked every N operations. • Embedded: super-loops servicing a low-priority mailbox every N iterations.
Watch out: adaptive intervals need clamps and hysteresis, or noise makes them oscillate. Let users pin a fixed value for latency-critical deployments.

### tokio-015 — Throttle idle-worker wakeups: cap searchers, wake only when nobody is searching, chain the rest

### tokio-028 — Cheap preflight checks before maintenance, and skip it if another thread is already on it
Lens: laziness · Source: Tokio

### tokio-029 — Funnel cross-thread updates into a lock-free list that the owner drains wholesale
Lens: amortization · Source: Tokio
Principle: Instead of letting every thread mutate a structure under a lock, have producers mark an item "queued" and push it onto an atomic stack (or a small mutex-guarded list). The single owner takes the entire list in one swap and applies all changes in its own single-threaded structure.

A "queued" flag set with `fetch_or` deduplicates repeated updates to the same item, so a thousand updates before the next drain cost one queue entry. The owner pays one swap for N items. Applies elsewhere: Data / databases: single-writer designs (LMAX) where clients enqueue mutations; dirty-page lists flushed by one writer. • Native / systems: deferred-free lists drained by a GC or epoch thread; Netty posting cross-thread timer cancels as tasks. • Web / backend: per-shard cache TTL updates batched to the shard owner thread. • Embedded: ISRs pushing events to a lock-free list the main loop drains per iteration.
Watch out: the owner must drain promptly, or updates (and the memory of cancelled items) pile up. An item marked "queued" must not be freed until the drain has seen it.

### tokio-030 — Move many items per synchronization round trip (receive-many, reserve-many, N-per-poll)

### tokio-031 — One allocation per object, hot fields first, cold fields last
Lens: memory-layout · Source: Tokio
Principle: Put everything an object needs into one contiguous block. Order it as a fixed-layout hot header, then the variable payload, then rarely used fields in a trailer the hot path never touches.
Why it is faster: Separate allocations for the object, its payload and its side data each cost a malloc/free and a pointer chase, and each can land on a different cache line. With one block, a scheduler that only reads the header (state word, vtable, queue links) touches one line no matter how large the payload is. A fixed header offset also lets type-erased code reach every field through a single `*mut Header`. When the payload's type varies, its offset varies too. So the trailer's offset is stored in the per-type vtable, and fields placed before the payload keep type-independent offsets. The cost: the layout has to be `repr(C)` and is harder to change.
Applies elsewhere: Web / backend: Allocate a request object and its small inline buffer together, with routing and state fields first and debug or trace metadata last. • Native / systems: Use VM object headers before fields, and keep a kernel struct's hot members together at the front. • Data / databases: Put the tuple header before the payload, and move rarely read columns into a separate cold segment. • Embedded: Use one static pool slot per job with control fields first, so an ISR touches one line.
Watch out: A huge payload sitting between header and trailer makes the trailer a guaranteed cache miss. Only demote fields that really are rare. A single block also means the whole object lives as long as its longest-lived handle.

### tokio-032 — Pack an object's flags, counters and generation into one machine word

### tokio-041 — Reuse allocations across iterations instead of re-creating them
Lens: allocation · Source: Tokio
Principle: Allocate per-loop scratch storage (event arrays, boxed state, guard collections) once and reuse it each iteration. When an operation can succeed without the allocation, try that path first.
Why it is faster: An event loop or poll wrapper runs millions of times, and a `Vec` or `Box` built per iteration costs malloc and free each time and churns the cache. Reusing one buffer, or overwriting a boxed value in place when the new value has the same size and alignment, removes this. Restructuring code to iterate directly instead of `collect()`-ing into a temporary removes it completely. Trying the non-blocking path first (for example, acquiring a permit immediately) means the allocation for the waiting state happens only when it is actually needed.

### tokio-042 — Start small and don't inherit a grown capacity
Lens: allocation · Source: Tokio
Principle: Allocate for the typical case, not the maximum. When a new buffer replaces an old one, size it from the current need, not from the old buffer's high-water capacity.
Why it is faster: Large up-front reservations waste memory in small programs and in every instance. Copying "capacity" from a buffer that once held a 256 MB frame keeps the process at 256 MB forever, and over-allocates for every later small frame. Sizing to the actual need keeps the resident set and cache footprint proportional to the work. Sizing the replacement to cover the unconsumed data avoids an immediate reallocation. The cost is a few extra growth steps when the workload really is large.
Applies elsewhere: Web / backend: Per-connection read buffers that drop back to a small size after a large message, and JSON parser scratch space sized per document. • Data / databases: Release result-set buffers after an outlier query instead of keeping the peak. • Embedded: Size pools from measured typical load, and fall back to an overflow path for rare peaks.
Watch out: Starting too small causes many growth copies for workloads that are always large. Pick the initial size from measurements, and shrink only after a sustained drop, not on every message.

### tokio-043 — Pre-size from exact knowledge, and trust size hints only when they are reliable

### tokio-045 — Buffer small transfers, bypass the buffer for large ones, and size it for the syscall

### tokio-046 — Transfer ownership instead of copying or refcount-cloning

### tokio-058 — Dismiss guards on the success path instead of checking a flag in the destructor

Principle: Put independently written hot fields on separate cache lines, sized per architecture (128 bytes where adjacent-line prefetch pairs lines). Don't pad objects that exist in large numbers.

On x86_64, the spatial prefetcher fetches lines in pairs, so 64-byte padding is not enough and 128 bytes is needed. The other side of the trade-off: padding a per-instance object multiplies its memory and wastes cache, which costs more than it saves when instances are rarely contended.
Applies elsewhere: Native / systems: separate head/tail of SPSC rings; per-thread counter cells; C++17 `hardware_destructive_interference_size` (check it matches the platform). • Web / backend: Java `@Contended` on hot counters; LMAX Disruptor sequence padding. • Data / databases: per-core statistics arrays; latch words of hot index root pages. • Embedded: separate DMA descriptors from CPU-written state, both for coherence and for cache maintenance.
Watch out: padding is a memory and cache cost. Apply it to a handful of singletons with proven cross-core writes, not to per-connection or per-timer objects (Tokio removed it from timers for this reason).

### tokio-073 — Move syscalls, allocation and foreign code outside critical sections
Lens: concurrency · Source: Tokio
Principle: Inside a lock, do only the minimal state change. Do preparatory work (cloning, allocating, queue pushes on independently synchronized structures) before locking, and do syscalls and signalling after unlocking.
Why it is faster: Lock hold time multiplied by acquisition rate is the serialization budget. A syscall under a lock blocks every contender for microseconds. Watch out: moving work out of the lock opens a window where the state can change. Revalidate, or design so the outside work is idempotent (Tokio's optimistic waker clone is simply dropped if unused).

### tokio-074 — One critical section per operation: merge check-then-act
Lens: concurrency · Source: Tokio

### tokio-076 — Use the weakest sufficient memory ordering and weak CAS in retry loops
Lens: concurrency · Source: Tokio

### tokio-079 — Don't pay for synchronization twice

### tokio-090 — Try-lock first to skip the lock-ordering retry dance
Lens: concurrency · Source: Tokio
Principle: When lock order says parent-before-child but you already hold the child, first `try_lock` the parent. Fall back to unlock-child, lock-parent, relock-child (and revalidate) only if that fails.
Why it is faster: The safe dance always costs three acquisitions plus revalidation. Uncontended, a try-lock succeeds immediately, so the common case is one acquisition per lock, and ordering is still never violated by blocking.
Applies elsewhere: Data / databases: B-tree latch coupling when moving up to a parent. • Native / systems: filesystem inode/dentry locking; hierarchical resource managers.
Watch out: after the fallback the relationship may have changed (the parent was re-parented), so the revalidation step is mandatory.

### tokio-091 — Specialize the lock when exactly two parties share a resource
Lens: concurrency · Source: Tokio
Principle: A resource split into two halves (reader and writer) can use a two-party lock: one atomic state and at most one parked waiter.
Why it is faster: A general mutex supports unbounded waiters and fairness machinery. With two parties, the "waiter queue" is a single slot, so lock and unlock are one atomic each, and it works across tasks and threads, unlike a task-local `RefCell`.
Applies elsewhere: Native / systems: full-duplex socket halves owned by reader and writer threads. • Embedded: two-core mailbox sharing a buffer with a single flag word.
Watch out: custom lock code needs model checking, and a well-implemented standard mutex may be just as fast uncontended. Benchmark before specializing.

### tokio-092 — Register once, edge-triggered, and keep readiness in a cheap shared word
Lens: io · Source: Tokio
Principle: Subscribe to all events for a resource once instead of re-arming interest per operation. Record readiness in a per-resource word that the I/O path reads without syscalls, and clear it only when the OS reports "would block".
Why it is faster: Level-triggered or one-shot registrations need an `epoll_ctl`/`kevent` call each time interest changes, and every operation has to ask the poller first. With edge triggering the kernel reports transitions only, the poller ORs them into an atomic, and a read or write goes straight to the syscall while the cached bit says "ready". A syscall that returns `EAGAIN` is the only signal needed to clear the bit. The cost: code must drain until `EAGAIN` (or know it has drained), or it misses the next edge forever.
Applies elsewhere: Web / backend: In a custom epoll server, register sockets with `EPOLLIN|EPOLLOUT|EPOLLET` once at accept time and keep two "ready" bits per connection, instead of toggling `EPOLLOUT` with `epoll_ctl(MOD)` on every write. • Embedded: Have the ISR set a "data available" flag and let the main loop read the peripheral until it reports empty, instead of reconfiguring interrupt masks per transfer. • Native / systems: io_uring multishot poll is the same idea: arm once and receive repeated readiness completions.
Watch out: Edge triggering is unforgiving. Any path that stops reading before `EAGAIN` without clearing the cached bit correctly will hang the connection. Clearing must not race with a new edge (Tokio solved this with a tick, below).

### tokio-093 — Gather many buffers into one syscall, and forward the capability through every layer
Lens: io · Source: Tokio
Principle: When output is spread over several buffers, hand them all to the kernel in one scatter/gather call instead of one call per buffer or a copy into one contiguous buffer. Every wrapper in between must pass the vectored path through, or the benefit disappears.
Why it is faster: `writev`/`sendmsg` with N iovecs costs one kernel entry and no user-space copy. Without it you pay N syscalls, or a memcpy of header and body into a staging buffer. The iovec array size bounds how much is gathered per call. Tokio settled on 64 stack-allocated slices, which avoids heap allocation and stays well below `IOV_MAX`. A single wrapper that implements only `write` silently turns the whole stack back into one syscall per chunk.
Applies elsewhere: Web / backend: Send HTTP headers and body with one `writev`. In Node, use `cork()`/`uncork()` or a stream's `_writev` so many small writes become one. • Data / databases: Append a batch of WAL records with one `pwritev` instead of copying them into a staging page. • Embedded: Use scatter-gather DMA descriptors so a packet header and payload living in different buffers go out in one transfer. • Native / systems: When you write a stream adapter (TLS, compression, metrics wrapper), forward the vectored method and its capability flag. Audit the stack for any layer that drops it.
Watch out: Vectored writes may be partial, so the caller must advance across slice boundaries correctly. For many tiny slices, copying them into one buffer can be cheaper than building the iovec array (see the buffered-writer entry).

### tokio-094 — Infer "drained" from a short read or write, but only where that inference holds
Lens: io · Source: Tokio
Principle: If a stream read returns fewer bytes than requested, or a write accepts fewer than offered, the kernel buffer is empty (or full). Clear readiness right away instead of issuing one more syscall just to receive `EAGAIN`.
Why it is faster: The textbook edge-triggered loop reads until `EAGAIN`, so every burst costs one wasted syscall. On a server with many small requests, that can be close to half of all read syscalls. A short count already carries the information. The inference only holds for byte streams on edge-triggered selectors. Packet-mode pipes return one packet per read, and level-triggered selectors (Windows, plain `poll`) re-report readiness anyway, so clearing early there is wrong.
Applies elsewhere: Web / backend: In an epoll ET loop for TCP, stop reading after a short read instead of reading until `EAGAIN`. • Embedded: If a UART RX FIFO read returns fewer bytes than its threshold, treat the FIFO as empty and skip the next status poll. • Native / systems: Keep the heuristic behind a per-resource flag (stream vs. datagram/packet, edge vs. level selector) instead of hard-coding it in the generic read path.
Watch out: Wrong for UDP, message-mode pipes, level-triggered pollers and anything with record boundaries. Getting it wrong means a stalled connection, not just a slower one.

### tokio-095 — Keep a copy pipeline full, and flush when the source stalls
Lens: io · Source: Tokio
Principle: In a read-to-write relay, refill free buffer space whenever possible, including while the writer is blocked, so each write is as large as possible. When the reader has nothing more for now, flush buffered output, because the far side may be waiting for it before it sends more.
Why it is faster: A naive loop reads, then writes until empty, then reads again. The reader and writer never overlap, and writes shrink to whatever one read returned. Topping the buffer up while the writer is pending overlaps the two directions and produces bigger writes. The flush rule fixes a latency trap: a buffered writer that flushes only at EOF stalls request/response protocols, because the peer never sees the request it must answer.
Applies elsewhere: Web / backend: In a TCP or WebSocket proxy, keep reading from the client while the upstream write is blocked, up to the buffer limit, and flush when the client goes quiet. • Data / databases: In a replication stream, batch outgoing records, but flush when the inbound log has nothing new. Otherwise replicas lag for no reason. • Native / systems: Use the same policy for `splice`-style relays and Node `pipe()` implementations.
Watch out: Reading ahead without a limit turns backpressure into unbounded memory. Cap reads at buffer capacity. Flush-on-stall adds syscalls on chatty links, which is the price of not deadlocking.

### tokio-096 — Do more work per hand-off to a blocking thread pool
Lens: io · Source: Tokio
Principle: When an operation must be offloaded to a worker thread (file I/O, directory listing), the fixed cost of the hand-off dominates small operations. Move bigger chunks per round trip, fetch related metadata in the same trip, and skip the trip entirely for trivial requests.

Watch out: Large per-trip buffers raise memory per in-flight operation and the latency to the first byte. Make the size configurable.

### tokio-097 — Submit blocking syscalls asynchronously to the kernel instead of to a thread pool
Lens: io · Source: Tokio
Principle: Where the OS offers a completion-based interface (io_uring), submit file operations to it and receive completions on the existing event loop, instead of parking a pool thread in each blocking syscall.

Watch out: io_uring support varies by kernel and sandbox (it can be denied with `EPERM`), so a portable fallback is mandatory (see the capability-probe entry). Buffers must stay owned by the in-flight op until it completes.

### tokio-098 — Size the event batch to what the consumer can absorb, and reuse the array
Lens: io · Source: Tokio
Principle: Fetch OS events into one preallocated array that lives for the life of the loop. Limit how many events you take per poll to roughly how much work you can queue locally. Anything left stays in the kernel for the next poll.

Watch out: Too small a batch means more syscalls per event when load is high but queues are not full. Keep the blocking-poll batch large and limit only the busy polls.

### tokio-099 — Pack readiness, an event tick, a slot generation and a shutdown flag into one atomic
Lens: io · Source: Tokio
Principle: Keep all per-resource I/O state that is checked on every operation in one machine word. One load gives a consistent snapshot, and one conditional RMW clears readiness only if no newer event arrived. Generation bits make stale events for a reused slot harmless.
Why it is faster: Separate fields would need a lock or several atomics to read consistently. The tick makes "clear readiness" safe without a lock: a clear succeeds only if the tick still matches the event that was observed, so a racing new event is never lost. The generation filters events queued for a slot's previous occupant, preventing spurious wakeups. Putting a shutdown bit in the same word removes a separate global "is shut down?" check (an `RwLock` read in Tokio's case) from every I/O call.
Applies elsewhere: Native / systems: Put slot index plus generation in epoll `data.u64` or io_uring `user_data`, and drop completions whose generation doesn't match the slot. • Web / backend: Pack a connection's state (readable, writable, closing) plus a sequence number into one atomic, so cross-thread checks never take a lock. • Data / databases: Pack pin count, dirty, I/O-in-progress and a "file closed" flag into a buffer-pool page header word.
Watch out: Narrow fields wrap. An 8-bit tick or 7-bit generation offers only probabilistic protection, so size them for how long a stale event can realistically be in flight.

### tokio-105 — Push a deadline later without touching the timer structure
Lens: scheduling · Source: Tokio
Principle: When a timeout only moves later (idle timeouts refreshed on activity), update the true deadline atomically and leave the entry in its old slot. When the old slot comes due, the driver compares against the true deadline and re-files the entry instead of firing it.
Why it is faster: Idle timers are reset on every packet. Moving the entry each time costs a driver lock, a list unlink and a re-insert. A CAS that succeeds only if `new >= prior` makes extension lock-free. The cost moves to one extra re-file per timer when the stale slot comes due, which happens far less often than resets. Encoding "pending fire" and "deregistered" as sentinel values of the same deadline word means one load answers both "when" and "in what state", and one CAS settles fire-vs-reset races.
Applies elsewhere: Web / backend: For keep-alive or idle timeouts, store `last_activity` on the connection. ### tokio-107 — Cancel timers as soon as they stop mattering; complete expired ones without registering

### tokio-108 — Give each worker its own timer structure; send cross-thread changes as messages
Lens: scheduling · Source: Tokio
Principle: A single shared timer structure behind one lock serializes every core that creates or cancels timers. Let a single owner thread mutate each timer structure. Other threads post registrations or cancellations into a small queue that the owner drains in batches.
Why it is faster: Timer inserts and cancels are about as frequent as I/O operations. A single owner mutates its wheel without synchronization, and cross-thread changes cost one queue push. Tokio's history shows the order of options: a lock-free stack drained by the timer thread (2018), then one locked wheel, then N locked shards (which needed a min across all shards at park and still contended), then a per-worker wheel with a cancellation queue. Folding "is it fired?" and "register waker" into one lock acquisition halves lock round trips on the poll path.
Applies elsewhere: Native / systems: Use per-CPU timer bases (as the Linux kernel does). A cancel from another CPU is posted to the owner instead of taking a global lock. • Web / backend: Shard-per-core servers (Seastar, Netty event loops) keep one timer wheel per loop and post cross-loop cancels as tasks. • Data / databases: Keep per-thread TTL expiry structures in a cache, with remote deletes queued to the owning thread.
Watch out: Sharding a shared structure is not the same as giving it single-thread ownership. Tokio's sharded version regressed. With per-owner wheels, a timer created on one worker and polled on another needs a remote path, and the owner must drain that queue promptly.

### tokio-109 — Hold one global timer for a whole collection of deadlines

### tokio-110 — Quantize time to integer ticks at the API edge
Lens: scheduling · Source: Tokio
Principle: Convert wall-clock or monotonic instants into coarse integer ticks once, when a timer is created or reset. Everything internal works on plain integers at a fixed resolution.
Why it is faster: A coarse resolution (1 ms) is what makes O(1) bucketed timers possible, and it lets nearby deadlines share a slot and a wakeup. Converting `Instant` to ticks costs arithmetic and a time-source lookup. Doing it at every internal layer repeats that cost, whereas passing a `u64` costs nothing.
Applies elsewhere: Web / backend: In a JS scheduler, store monotonic numbers (`performance.now()` rounded to ms) instead of `Date` objects. • Embedded / native: Kernel jiffies and RTOS tick counts. Convert milliseconds to ticks in the public API only. • Data / databases: Lock managers and lease tables can compare tick counters instead of timestamps.
Watch out: Round deadlines up, never down, so a timer never fires before the time asked for. Coarse ticks are unsuitable for sub-millisecond pacing.

### tokio-112 — When firing everything, walk occupied slots directly instead of simulating time
Lens: scheduling · Source: Tokio
Principle: A hierarchical timer structure normally advances level by level, cascading entries downward. When the goal is "expire everything" (shutdown), skip the rotation and expire each occupied slot's entries directly.
Why it is faster: Advancing to "infinity" by normal rotation can take an enormous number of steps when even one far-future timer exists (up to 2^28 in Tokio's case). Walking occupancy bitmaps is proportional to the number of entries, not to the length of the time span.

### tokio-113 — Assume a fresh socket is ready; let one failed attempt correct you
Lens: networking · Source: Tokio
Principle: When a resource is very likely ready at creation (an accepted connection usually has data and is writable, and a new socket pair is writable), start it in the "ready" state and attempt I/O right away. A wrong guess costs one `EAGAIN`, which resets the state.
Why it is faster: Starting as "not ready" forces the first operation to wait for the poller to report an event. That is a full event-loop round trip, and under load it queues behind every other connection's events. A speculative syscall costs microseconds at most. The guess was grounded in measurement: a trace showed accepted sockets waiting 64-128 ms for their first read, and the first read found data on every one of 5,298 connections.
Applies elsewhere: Web / backend: Call `read()` right after `accept()` before registering for readability (or use `TCP_DEFER_ACCEPT`, nginx's deferred accept). Try a write before arming `EPOLLOUT`. • Embedded: A UART or SPI driver can assume the TX FIFO is empty right after init and write immediately. • Data / databases: A connection proxy can read the client's startup packet inline after accept instead of waiting for a poll cycle.
Watch out: If the guess is usually wrong (servers where clients connect and stay idle), every connection pays a wasted syscall. Measure the hit rate first, as Tokio did. A speculative ready bit must never override a shutdown state.
