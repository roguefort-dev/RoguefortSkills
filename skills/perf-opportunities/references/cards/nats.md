### nats-002 — Route events through an index of interested parties instead of scanning all of them
Lens: algorithms · Source: NATS
Principle: When an event must reach the few interested listeners among many registered ones, register the listeners in an index keyed by what they want (exact key or pattern) and look the event up. Do not loop over every listener asking "do you want this?"
Why it is faster: A scan costs O(listeners) per event and usually takes each listener's lock to test its filter. An index costs O(matches). For exact-key interest a hash lookup is enough. For patterns, reuse the existing cached matcher, so special-purpose dispatch (service imports, consumer signals) gets the same optimizations as normal subscriptions. A small typed trie that stores the target object directly avoids subscription structs, result-slice allocations and callback indirection.
Applies elsewhere: Web / backend: index WebSocket subscribers by topic instead of looping over all sockets; key watchers by exact key (etcd-style). • Embedded: per-event-ID handler bitmaps or tables in an event bus. • Native / systems: route special URL handlers through the main router trie, not a pre-dispatch regex list. • Data / databases: CDC or trigger dispatch indexed by table or key prefix.
Watch out: the index must be maintained on every listener change (here, on leader election), and stale entries cause missed or spurious events.

### nats-006 — Keep per-segment key summaries and a global first/last-segment index to skip data
Lens: algorithms · Source: NATS
Principle: For each storage segment keep a small map from key to {count, first, last}. Store-wide, keep each key's total and the first and last segment that contain it. Filtered reads then skip whole segments, jump to the first candidate, or answer from the summaries without reading records.
Why it is faster: A filtered read over raw records decodes everything it passes. Zone-map-style summaries turn "scan all blocks" into "visit the blocks whose summaries say they can match", often one block. Totals, last-per-key and existence questions need no data I/O at all. The global first/last pointers bound per-key work to a contiguous block range instead of a backwards scan.
Applies elsewhere: Web / backend: per-chunk tag counts in a log store so filtered queries skip chunks. • Embedded: per-flash-page min/max key headers to skip pages during lookup. • Data / databases: Parquet row-group zone maps; per-SST key ranges; Bitcask-style keydir with first/last segment per key.
Watch out: summaries cost memory per distinct key per segment and must be updated on every write and delete. For single-key or internal logs, turn them off.

### nats-007 — Intersect two indexes by walking them together
Lens: algorithms · Source: NATS
Principle: To find stored keys that match any of a set of patterns, put the patterns in a trie and walk it together with the key index, descending only where both have branches. Do not probe one structure once per element of the other.
Why it is faster: "For each filter, scan the key index" or "for each key, test every filter" costs O(|A| × |B|) or O(|A|) probes. A simultaneous walk visits only the shared paths, the same idea as a merge join. A lazy intersection run once per segment against that segment's summary visits each segment once instead of rescanning per key.
Applies elsewhere: Web / backend: matching a set of route or permission patterns against a trie of resource paths. • Native / systems: diffing two sorted directory listings in one pass. • Data / databases: merge joins of two sorted indexes; posting-list intersection in search engines.
Watch out: wildcards on both sides make the joint walk harder to bound; handle literal tokens with direct lookups and reserve pattern walks for wildcard tokens.

### nats-008 — Use a radix tree for pattern queries over many similar keys
Lens: algorithms · Source: NATS
Principle: A hash map answers exact lookups but must scan every key for a prefix or wildcard query. An adaptive radix tree stores shared prefixes once and answers pattern queries by walking only the branches that can match.
Why it is faster: Wildcard filtering over a hash map is O(keys) with tokenization and subset matching per key. The tree prunes whole subtrees at the first non-matching token. Long common prefixes (typical of hierarchical subjects) are stored once, which saves memory at hundreds of millions of keys.
Applies elsewhere: Web / backend: URL routers and ACL matchers over `/api/:id/*` patterns. • Embedded: compact key-value stores with hierarchical keys. • Data / databases: ART indexes in in-memory databases; prefix queries over metric names.
Watch out: ordered iteration of an adaptive tree requires sorting children per node; offer an unordered walk for callers that only aggregate.
Seen in NATS: d9235abbe1 2024-01-20 New `server/stree` replaces `psim map[string]*psi`; `numFilteredPending` calls `psim.Match(filter, cb)` instead of subset-matching every key (the map "suffered when trying to filter based on wildcard subjects"). • 5b529fc58e 2024-01-22 Same for memstore `fss`; 72e063785f 2024-06-21 for per-block `mb.fss`, "to provide some deduplication of long subjects in memory". • a800826e7b 2025-04-25 `matchParts` copy-on-write of the parts list appends into spare tail capacity instead of a new array.

### nats-010 — Hash set for O(1) removal, plus a lazily built flat array for bulk reads
Lens: algorithms · Source: NATS
Principle: Store a large membership group as a hash set so removal is constant time, and above a size threshold keep a flat array alongside it for bulk reads. Discard the array on any removal and rebuild it on the next insert.
Why it is faster: A slice gives fast iteration but O(n) removal, which makes mass unsubscribe quadratic. A map gives O(1) removal but slow iteration. The hybrid serves matches with one `append(results, plist...)` memcpy while churn stays cheap. The threshold keeps small nodes on the map path where the array would not pay.
Applies elsewhere: Web / backend: event-listener lists with a cached iteration snapshot. • Native / systems: sparse sets in ECS engines (dense array plus sparse index). • Data / databases: posting lists with a hash set for deletes and an array for scans.
Watch out: under steady churn the array is rebuilt constantly; it only pays when reads greatly outnumber writes.
Seen in NATS: b9c73e96ee 2018-06-04 Node `psubs` became `map[*subscription]*subscription` "to avoid quadratic time in removal with large N". • 8502fb1edc 2018-06-04 "Add fast slice for large psubs for Match": `plistMin = 256`, `n.plist` rebuilt lazily after removals.

### nats-011 — Represent sparse integer sets as balanced trees of bitmaps, and skip runs with word operations
Lens: algorithms · Source: NATS
Principle: Store a set of integers (deleted sequence numbers) as a balanced tree whose nodes each cover a fixed window with a bitmap. Lookups stay O(log n), dense runs cost one bit each, and iteration can jump over whole runs using word-level bit tricks.
Why it is faster: A hash set costs dozens of bytes per entry and must be probed per element. Bitmap nodes cost 1 bit per element in dense regions and serialize as raw words. Finding the end of a run of set bits with `^word & mask` and `TrailingZeros64` skips 64 elements per step, so scans over large deleted regions jump instead of checking each sequence.
Applies elsewhere: Web / backend: tracking seen IDs or unread ranges per user. • Native / systems: free-extent maps in allocators; TCP SACK scoreboards; GC mark bitmaps. • Data / databases: Roaring bitmaps; MVCC deletion vectors; visibility maps.
Watch out: very scattered sets (one element per window) cost a whole node each; hybrid containers (array for sparse, bitmap for dense) handle that better.

### nats-013 — Pick queue structures with O(1) ends and memory proportional to occupancy
Lens: algorithms · Source: NATS
Principle: A FIFO should push and pop in O(1) and should not reserve memory for its configured maximum. Use a fixed ring when capacity is small and known, an intrusive linked list when the maximum is a limit rather than a typical size, and reslice rather than shift when popping from an array.
Why it is faster: Shifting an array (`append(q[:0], q[1:]...)`) is O(n) per pop. Reslicing from the head leaks the head until the queue empties. A ring preallocated to a user-configured maximum costs memory and GC scan time for that maximum even when empty; an intrusive list grows only with real entries.
Applies elsewhere: Web / backend: JS queues with a head index instead of `array.shift()`; Python `deque` instead of `list.pop(0)`. • Embedded: UART RX rings; fixed audio sample buffers. • Native / systems: intrusive wait queues in kernels. • Data / databases: slow-query history as a fixed ring.
Watch out: reslicing keeps the old backing array alive; nil the slice when it drains or periodically compact.
Seen in NATS: ec8e2636de 2018-06-25 Closed-connection history in a fixed ring indexed by `total % cap`: constant memory, nothing shifted. • 610d2d21b7 2020-10-19 Pull-request wait queue became a preallocated ring with read/write indices and an explicit "full" error, replacing a slice FIFO. • 4de3142b8c 2024-03-21 That ring was replaced with an intrusive `head/tail/next` list after "very large MaxWaiting configured and causing memory and GC issues". • 8f99f6d20f 2026-11-06 Redelivery queue pops by `q = q[1:]` instead of shifting.

### nats-014 — Pay for ordering only when the caller needs it, and sort with type-specialized code
Lens: algorithms · Source: NATS
Principle: Offer both an ordered and an unordered traversal and use the unordered one for aggregations. When you must sort, use a sort specialized to the element type rather than one driven by reflection or interfaces.
Why it is faster: Ordered iteration of a radix tree collects and sorts children at every node and allocates temporary slices. Counting, summing or building sets does not care about order. A typed generic sort removes indirect calls, interface conversions and allocations per comparison.
Applies elsewhere: Web / backend: sort a typed array rather than objects with a comparator; skip `ORDER BY` in aggregates. • Native / systems: `std::sort` instead of `qsort`; `for_each` vs `for_each_sorted` APIs on tree containers. • Data / databases: hash aggregation instead of sort-based grouping when output order is irrelevant.
Watch out: unordered iteration order may vary between runs; never use it where output order is visible or must be deterministic.
Seen in NATS: 7ed08f8b08 2024-01-26 `writeFullState` walks `psim` unordered; 57afa842ce 2024-03-19 switched `enforceMsgPerSubjectLimit` to `Match(">")`: "more performant and less stressful on gc and order does not matter". • 2e7b806029 2024-08-01 `sort.SliceStable` to `slices.SortStableFunc` in tree iteration: "roughly 4x faster since there are no interface conversions"; b901047faf 2024-08-08 switched the rest of the server. • aa8a594b9e 2025-02-05 Split `Iter` into `IterFast` (raw child order) and `IterOrdered`; counting paths use the fast one, purge and compact keep ordered.

### nats-019 — Offer a cheap summary call next to the expensive full state
Lens: laziness · Source: NATS
Principle: Split state queries into an O(1) summary (counters, bounds) and a detailed version that builds lists. Make details opt-in, and switch every caller that only needs scalars to the summary.
Why it is faster: Full state may materialize lists proportional to deletes or entries: allocation, sorting and copying that most callers discard. A caller-filled summary struct under a read lock costs a few loads. Opt-in details keep response size and build cost proportional to what is actually used.
Applies elsewhere: Web / backend: REST `?expand=` parameters; GraphQL field selection; stats endpoints served from counters. • Native / systems: `stat` instead of reading the file; `size()` without materializing. • Data / databases: Redis `SCARD` vs `SMEMBERS`; table statistics instead of `COUNT(*)` scans.
Watch out: the summary must be kept accurate incrementally; a summary that drifts from the full state causes subtle bugs.

### nats-020 — Derive values arithmetically from invariants instead of tracking or scanning
Lens: laziness · Source: NATS
Principle: When a quantity follows from known invariants, compute it. If a key's count equals `last − first + 1`, its records are contiguous and any sub-range count is a subtraction. Deleted count is span minus live.
Why it is faster: Maintaining an explicit set of interior deletes grows with churn, and scanning to count is O(range). Arithmetic is O(1) and uses no memory. The rare caller that needs the explicit list can generate it on demand.
Applies elsewhere: Web / backend: pagination totals from offsets; unread counts from high-water marks. • Embedded: ring-buffer occupancy from head and tail indices. • Data / databases: consumer lag from offsets; B-tree range counts from node counts.
Watch out: the shortcut is only valid while the invariant truly holds; verify the density condition each time rather than assuming it.

### nats-021 — Use exact lookup when the pattern has no wildcard
Lens: laziness · Source: NATS
Principle: Check once whether a filter contains wildcards. If not, use a direct map or tree find; reserve the general pattern walk, tokenization and subset matching for real patterns.
Why it is faster: A wildcard walk over a trie, or tokenizing and subset-matching every key, costs far more than a hash or tree find. Most real filters are literal, so the fast path covers the common case. Removing it once caused a measured regression that had to be fixed by restoring it.
Applies elsewhere: Web / backend: routers checking a static-route map before regex routes. • Native / systems: glob matchers that short-circuit when the pattern has no metacharacters; substring search for metachar-free regexes. • Data / databases: rewriting `LIKE 'abc'` without `%` to an equality lookup.
Watch out: the literal check itself must be cheap (a byte scan); cache it with the filter when the filter is reused.

### nats-024 — Provide existence and count queries that build no result set
Lens: laziness · Source: NATS
Principle: Many callers of a matcher only need "any match?" or "how many?". Offer dedicated calls that stop at the first hit or count without collecting results.
Why it is faster: A general `Match` allocates and fills a result list and walks every branch. An existence walk returns at the first match and allocates nothing (tokens go into a stack array). Counting returns two integers.
Applies elsewhere: Web / backend: `has()` alongside `findAll()` in routing and ACL libraries. • Native / systems: trie and Bloom-filter `contains` APIs. • Data / databases: `EXISTS` subqueries; count-only index scans.
Watch out: keep semantics identical to the full match (including caches and queue groups), or callers get different answers from the two APIs.

### nats-025 — Let hints go stale and correct them when a lookup finds them wrong
Lens: laziness · Source: NATS
Principle: Keeping a hint exact on every delete (such as "first block containing key X") can be expensive. Treat it as a lower bound, let it drift, and fix it when a lookup notices it is out of date.
Why it is faster: The cost moves off the write path and is paid at most once per stale hint, only for keys that are actually queried. Correctness holds because a stale lower bound only makes the search start too early, never too late.
Applies elsewhere: Web / backend: cached "first page with results" cursors corrected on read. • Native / systems: lazy deletion in priority queues; path compression in union-find. • Data / databases: stale-but-safe optimizer statistics; per-key segment hints in log stores.
Watch out: the hint must err in a safe direction only; a hint that can point past the true answer causes missed data.

### nats-026 — Iterate live entries, not positions, and remember where the last pass stopped
Lens: laziness · Source: NATS
Principle: On sparse data, use a "next live entry" primitive that skips deleted ranges inside the store instead of probing every position. Store a progress watermark so repeated checks resume rather than restart.
Why it is faster: Probing each sequence costs a lookup and an error per hole, and when deletes outnumber live entries by orders of magnitude, that is nearly all the work. A store-level iterator skips holes using its delete map under one lock acquisition. A watermark turns a periodic O(history) check into O(new entries).
Applies elsewhere: Web / backend: cursor-based pagination that seeks to the next existing ID. • Native / systems: `SEEK_DATA`/`SEEK_HOLE` when copying sparse files. • Data / databases: LSM iterators that skip tombstone ranges; incremental scrub or vacuum cursors; Kafka consumers seeking instead of reading through.
Watch out: a watermark must be reset when the underlying data is rewritten (purge, truncate), or the next pass skips entries it should check.

### nats-028 — Defer or skip building auxiliary structures until something needs them
Lens: laziness · Source: NATS
Principle: Indexes, dedupe maps, checksums and recovery state that only some workloads use should be built on first use, or not at all when configuration makes them pointless.
Why it is faster: Eager rebuilds at startup penalize every data set for features few of them use. Lazy construction moves the cost to the first real use and makes it zero for everyone else. Deferring per-record checksum verification to first access spreads its cost and removes latency from the first read of a freshly loaded block.
Applies elsewhere: Web / backend: build per-user caches on first request rather than at boot. • Embedded: verify flash page CRCs on first read, caching a verified bit. • Data / databases: buffer pools checking page checksums on first access; no secondary index on bulk-load tables.
Watch out: the first user pays the full build cost, which can be a latency spike; and lazy integrity checks detect corruption later than eager ones.

### nats-033 — Wait briefly while a batch is still growing, then flush
Lens: amortization · Source: NATS
Principle: After a write kick, delay the flush a little so more data joins the same write. Stop waiting when the batch reaches a minimum size, stops growing between checks, or a maximum wait expires; back off between checks so a lone writer pays little latency.
Why it is faster: A fixed sleep wastes latency when traffic is light and under-batches when it is heavy. Watching growth adapts to the actual arrival rate: a burst fills a large write, and a single message goes out after a few milliseconds. The design moved from a fixed 20 ms sleep to a bounded adaptive loop.
Applies elsewhere: Web / backend: Kafka producer `linger.ms` plus `batch.size`; batching log lines to a remote sink. • Embedded: coalescing UART TX bursts with a short idle timeout. • Native / systems: Nagle-like batching in an RPC client. • Data / databases: group commit windows that close early when the queue stops growing.
Watch out: always cap the wait; latency-sensitive callers need a way to force an immediate flush.
Seen in NATS: 79b85ae385 2020-05-19 Fixed `coalesceDelay = 20ms`; 6b34d4e700 2020-05-19 10 ms, skipped when 32 KB is pending. • 4a46a92cea 2020-05-19 Yield while pending is under 64 KB and still growing; 3ab76a6dcd 2020-05-19 exponential sleep starting at 1 ms. • 93ebcafca1 2020-10-31 Per-block `flushLoop` with `coalesceMinimum = 4KB` and `maxFlushWait = 8ms`; b358773ddf 2021-02-06 raised the minimum to 16 KB. • 164f9fdf2b 2020-11-10 Consumer state written through a kicked flusher that waits 5 ms to coalesce.

### nats-034 — Batch replicated proposals up to count and byte caps, and always flush the tail
Lens: amortization · Source: NATS
Principle: Gather queued items into one replicated append until a byte limit or an entry-count limit is reached, send immediately when a cap is hit, and always send the leftover at the end. Tune the caps until throughput stops improving.
Why it is faster: Each consensus append has a round trip, an fsync and per-message overhead. Batching amortizes them across many entries. Caps keep single messages reasonable and respect wire limits (a uint16 count). Accumulating skip records and proposing them once avoids one consensus entry per item.
Applies elsewhere: Web / backend: batched INSERTs with a row cap matching protocol limits; batched outbound webhooks. • Native / systems: network packet coalescing up to MTU. • Data / databases: Kafka producer `batch.size`; DB group commit; etcd proposal batching.
Watch out: forgetting the tail flush strands entries until the next arrival; oversized batches increase per-batch latency and follower memory.

### nats-062 — Size-classed buffer pools with exact-class discipline
Lens: allocation · Source: NATS
Principle: Pool large buffers in a few fixed size classes. Allocate new buffers at full class size, recycle only buffers whose capacity matches a class exactly, grow by moving to the next class, and copy data out before a buffer can be recycled if anyone could still be viewing it.
Why it is faster: Reallocating multi-MB block buffers or per-connection write buffers churns the allocator and the GC. Classes keep pooled buffers interchangeable. If a class can hold undersized buffers, a Get returns one too small, the caller reallocates and both go back, and the pool thrashes. Pooling pointers to fixed arrays (`*[N]byte`) avoids allocating a slice header on Put. A small first class means light users do not pin MB-sized buffers.
Applies elsewhere: Native / systems: slab allocators and jemalloc-style arenas binned by exact class; lwIP pbuf pools. • Web / backend: Netty `PooledByteBufAllocator`; Node `Buffer` pools keyed by exact size; nginx buffer chains. • Data / databases: buffer pools that copy a tuple out before releasing the page pin.

### nats-063 — Recycle the buffer you just finished with

### nats-071 — Private per-thread caches invalidated by a global generation counter
Lens: caching · Source: NATS

### nats-072 — Know when a cache does not pay: skip negatives, opt out under churn, drop unbounded memos

### nats-073 — Evict before inserting, evict minimally, recycle the evicted entry, and let one pruner run

### nats-084 — Replace general-purpose machinery with specialized code on hot paths
Lens: cpu-microopt · Source: NATS

### nats-085 — Pick a fast codec and level, and compress only when it pays
Lens: cpu-microopt · Source: NATS
Principle: Compression trades CPU for bytes. Prefer fast codecs and low levels, skip payloads below a size threshold, keep the compressed form only if it is actually smaller, and compress only when the peer has said it supports it.
Why it is faster: High-ratio compression is often the bottleneck in bulk transfer, while fast codecs such as S2/Snappy, or gzip at BestSpeed, reach most of the gain at a small fraction of the CPU. Small payloads have fixed framing overhead and little redundancy, so compressing them spends CPU for nothing. A keep-if-smaller check guards against incompressible data. An optimized library implementation of the same format can be much faster than the standard one. A reused compressor avoids large per-message allocations, but it must drop its reference to the last output buffer, or that buffer can never be collected.
Applies elsewhere: Web / backend: Set a minimum length for gzip/brotli (nginx `gzip_min_length`), use zstd -1 or brotli 4 for dynamic responses, and skip already-compressed media types. • Data / databases: Use LZ4 or zstd-low on hot data and for replication streams, and compress pages only above a size floor (as Postgres TOAST does). • Native / systems: Swap zlib for zlib-ng or libdeflate. When reusing `Deflater`/zstd contexts, reset them so they don't pin buffers. • Embedded: Compress telemetry batches, never single samples, and send raw when the ratio is poor.
Watch out: A lower level is not always smaller or slower. Measure on your real payloads, as NATS did when a faster S2 mode both sped up and shrank its meta snapshots. Peers that cannot decode must keep receiving plain data.

### nats-089 — Choose hash functions by key shape and purpose; use a fast keyed hash for integrity
Lens: cpu-microopt · Source: NATS
Principle: There is no single best hash. Benchmark candidates on your real keys: setup cost dominates for short keys, throughput for long ones. For corruption detection, a SIMD keyed non-cryptographic hash is much cheaper than a cryptographic one.

### nats-090 — Size the runtime to the container's real CPU and memory limits
Lens: cpu-microopt · Source: NATS

### nats-092 — Optimistic accounting: add first, check after, undo on the rare overflow
Lens: cpu-microopt · Source: NATS
Principle: When a limit is almost never exceeded, update the counter unconditionally and compare afterwards. Roll back only in the overflow branch.
Why it is faster: The common path becomes one add and one compare, with no temporary computed beforehand and fewer dependent operations. The rare overflow path pays a subtraction. This works when the counter is private, or under a lock, so a transient overshoot is never seen by anyone else.
Applies elsewhere: Web / backend: Rate limiters can increment, then reject and decrement over budget. • Native / systems: Allocator quota tracking. NIC driver counters. • Data / databases: Memory accounting for query operators, with rollback when a reservation fails.

### nats-093 — Use a fast non-cryptographic PRNG where unpredictability is not a security property
Lens: cpu-microopt · Source: NATS
Principle: Crypto RNGs are slow, may make syscalls and can drain entropy. Use them only where an attacker must not predict the value. Draw the widest native output per call, so one call yields more bits.
Why it is faster: A math PRNG is a few arithmetic operations in user space, while `crypto/rand` can call into the kernel per read. Padding bytes, nonces that are protected by other means, reply tokens and jitter need statistical spread, not secrecy. A 64-bit draw replaces two 32-bit draws (or a 63-bit draw plus masking).
Applies elsewhere: Web / backend: Request IDs, sampling decisions and retry jitter can use xorshift/wyrand instead of `crypto.randomBytes`. • Embedded: Use an LFSR for backoff jitter, and keep the hardware TRNG for keys. • Native / systems: Fill test data and padding with PCG/xoshiro.
Watch out: Never use this for session tokens, keys or any nonce whose reuse breaks a cipher. Audit each call site before switching.

### nats-094 — Drop modulo and random draws from selection loops when they are not needed
Lens: cpu-microopt · Source: NATS

### nats-099 — Split locks by independent state: per-segment locks and narrow side locks

### nats-100 — Match the lock mode to the real access, in both directions

### nats-108 — Long-lived bounded worker pools over a queue instead of a goroutine per request
Lens: concurrency · Source: NATS
Principle: Spawning a goroutine per request with a hard in-flight cap either explodes under bursts or drops work. A fixed set of long-lived workers draining a shared queue keeps parallelism bounded, reuses per-worker context, and absorbs bursts without dropping them.
Why it is faster: Each spawned goroutine allocates a stack and scheduler state, and with thousands per second the scheduler and GC feel it. A long-lived worker reuses one context object. Bounding the worker count to the resource limit (cores, or the I/O semaphore) prevents thrashing. Parallel recovery at startup with N workers turns serial O(items × latency) into O(items × latency / N).
Applies elsewhere: Web / backend: An executor queue instead of `new Thread` per request. Bounded concurrency (`p-limit`) in Node build tools and crawlers. • Data / databases: Open shards in parallel at boot with a fixed worker count. ### nats-109 — Funnel contended work into one worker; split only genuinely independent stages
Lens: concurrency · Source: NATS
Principle: Workers that all contend on the same lock and disk add only context switches and lock thrash, so drain their inputs from one shared queue on one goroutine. Conversely, stages that would delay each other but share nothing (deliveries and acks, storing and fan-out signalling) deserve separate goroutines.
Why it is faster: Parallelism helps only when the work can actually run in parallel. With one goroutine per source all fighting over one stream lock and one file, waking N goroutines means N kernel threads contending and then serializing anyway. One consumer does the same work with no contention. Splitting independent stages, on the other hand, keeps a busy stage from delaying the other's progress. For example, acks stuck behind deliveries inflate pending counts and trigger spurious timeouts.
Applies elsewhere: Data / databases: A single writer thread for SQLite or an append-only log instead of many writers contending on the file lock. • Web / backend: Redis-style single-threaded execution for shared state. Separate ack and consume threads in broker clients. • Native / systems: Separate RX and TX processing in network stacks. One writer task per socket instead of per stream.
Watch out: One shared worker brings back head-of-line blocking between sources (the reason for the 2020 per-consumer design). Choose by whether the shared resource, not the producer, is the bottleneck.

### nats-110 — Run small work inline; hand off past a size, count or time budget
Lens: concurrency · Source: NATS

### nats-120 — With several workers on one queue, pop one item at a time
