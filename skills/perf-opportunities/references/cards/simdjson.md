### simdjson-001 — Split the work into a wide indexing pass and a narrow building pass
Lens: algorithms · Source: simdjson
Principle: First run a cheap, uniform pass over every byte that records only the positions that matter. Then run the expensive, branchy logic over that short list of positions, not over the raw input.
Why it is faster: Most of a text parser's cost is looking at every byte and taking a data-dependent branch on it. A uniform first pass can be branch-free and vectorised, so it runs near memory bandwidth with no mispredictions. The second pass still branches, but only once per token (often 5-15% of the bytes), so misprediction cost scales with structure rather than input size. The index is also reusable: other consumers (lazy iterators, skippers, stream splitters) can run on it without rescanning. The cost is an intermediate array and a second pass over it, which only pays off when the per-byte work in a single-pass design is truly branchy.
Applies elsewhere: Web / backend: HTTP header parsers that first find all `:` and CRLF positions, then slice fields; CSV readers that index delimiters and quotes, then build rows. • Data / databases: Bulk loaders that tokenize a whole block before type conversion; log indexers that build a newline bitmap, then hand out lines. • Native / systems: Compilers and assemblers that lex into a token array before parsing, so the parser never touches raw characters.
Watch out: the index costs memory proportional to token count (up to one entry per byte for pathological input), and for tiny inputs the setup of the first pass can dominate; see the trivial-shape fast path below.

Stage 1 (`find_structural_bits`) stays a pure 64-byte SIMD loop. • 2a46b40457 2018-09-24 Stages 3 and 4 merged into one `stage34_unified.cpp`, "a DFA and explicit stack" over the structural index, settling the design at two stages. • ebcb3c6b3b 2020-08-13 The On-Demand front end reuses the same stage-1 index but replaces tree building with an iterator, which shows the index is a reusable product in its own right.

### simdjson-002 — Make the index mark where every item starts, not just the delimiters
Lens: algorithms · Source: simdjson
Principle: If the consumer will need the start of every atom (number, literal, word), compute "starts" in the bulk pass as "not whitespace, not inside a string, and preceded by a delimiter or whitespace", so the consumer never searches.
Why it is faster: An index of delimiters alone forces the second pass to scan forward from each delimiter to find where the value begins, which reintroduces per-byte loops in the branchy stage. Marking atom starts costs one shift and two ANDs per block in the vector stage, so every value position arrives for free. As a side effect, malformed runs such as `true false` show up as extra index entries, and the grammar check catches them without extra validation code.
Applies elsewhere: Data / databases: Field-start detection in whitespace-delimited formats; run-start bitmaps for RLE encoders. • Web / backend: Word-start detection for search tokenizers and full-text indexing. • Native / systems: Lexers that record token starts in a vectorised pre-pass.
Watch out: the "start" rule must agree exactly with the grammar's token boundaries; an extra or missing entry silently desynchronises the second pass, so the rule needs fuzzing against the scalar reference.
Seen in simdjson: 46d55fa6ce 2018-04-13 First "pseudo-structural" characters added to the stage-1 output. • 211892439e 2018-04-14 Switched to "a simpler but more useful notion": `pseudo_structurals = ((pseudo_pred << 1) | carry) & ~whitespace & ~quote_mask`, replacing an add-with-two-overflow-checks scheme. • de8df0a05f 2019-10-01 Reworked as `start_primitive = primitive & ~follows(primitive, prev_primitive)` in the combined stage-1 rewrite (5% overall, 15% stage 1).

### simdjson-003 — Do each piece of work in exactly one place, and drop what another stage already guarantees
Lens: algorithms · Source: simdjson
Principle: Do not record what the consumer can recover cheaply by itself, and do not re-check what an earlier stage or the structure already proves. Each redundant entry or check is paid on every input.
Why it is faster: Every index entry costs a store in the producer and a load, dispatch and branch in the consumer. Every redundant check is a branch and often a live register across the hot loop. Dropping closing quotes from the index (the string parser finds them while copying) shrinks both passes and simplified the state machine. Removing depth checks that the outer-bracket check already implies takes branches out of every document. The win grows with input size, and the change costs nothing but proof that the guarantee holds.
Applies elsewhere: Data / databases: Sparse indexes that skip positions recoverable by a short scan; ORMs that stop re-validating constraints the database enforces. • Web / backend: Request pipelines where the framing layer already bounds lengths, so handlers need not re-check. • Embedded: Protocol stacks where the CRC layer already rejects corrupt frames, so field-level sanity checks can go.
Watch out: a removed check is only safe while the guarantee upstream holds; document the dependency, or a later refactor of the upstream stage silently opens a hole.
Seen in simdjson: 76ad40272e 2018-05-05 `structurals &= ~(quote_bits & ~quote_mask)`: "we've used our close quotes all we need to. So let's switch them off". The same commit made all tape writes the same size and removed DFA states 6 and 10. • 553e6d7549 2020-08-03 "Don't check max depth on startup". • abd1399a7f 2020-08-07 "Don't check depth at the end (unnecessary check)": removed `if (depth != 0) return TAPE_ERROR`, since the structure already guarantees balance.

### simdjson-005 — Walk nested structure with an explicit stack and a flat state machine
Lens: algorithms · Source: simdjson
Principle: Replace recursive descent with a loop over states and a small explicit stack per nesting level; store the cheapest possible continuation token on the stack (a flag, not a code address).
Why it is faster: Recursion pays a call and return per level, keeps stack frames alive, and has unbounded stack use. A state loop with an explicit stack bounds memory and removes call overhead. simdjson first stored computed-goto addresses per depth, giving each transition its own indirect branch site. It later found that one `bool is_array[depth]` and two predictable branches did as well: less memory per level, standard C++, and the compiler is free to lay out code. The lesson is that the continuation needs only as many bits as there are resume points.
Applies elsewhere: Web / backend: HTTP/1 and WebSocket parsers as resumable state machines; async state machines that store a small enum per frame. • Native / systems: Bytecode interpreters and regex VMs; non-recursive tree walkers in compilers. • Embedded: Parsers with a fixed maximum depth and a static stack array, so stack overflow is impossible.
Watch out: computed goto is a compiler extension (simdjson kept a switch fallback for MSVC until removing it); a fixed max depth must be enforced with an error, not assumed.
Seen in simdjson: 2a46b40457 2018-09-24 `void *ret_address[MAX_DEPTHS]; ret_address[depth] = &&start_continue; ... goto *ret_address[depth];` with states `object_begin`, `object_key_state`, `object_continue`, `array_begin`, `array_continue`, `scope_end`. • c1805783fc 2018-11-27 Store placement inside the state machine was settled by measurement: "strangely, moving this to object_begin slows things down", so the tape write for `{`/`[` sits at each call site. • 8e69103822 2020-07-27 "Remove computed GOTO": `ret_address[depth]` became `is_array[depth]`, and `CONTINUE(address)` became `if (depth==1) goto finish; if (is_array[depth]) goto array_continue; goto object_continue;`. Merged in 86162aaddb 2020-08-02.

### simdjson-006 — Separate traversal from building with a compile-time visitor
Lens: algorithms · Source: simdjson
Principle: Write the validated structural walk once, parameterised on a builder type, so each consumer gets an inlined, specialised walk without virtual calls.
Why it is faster: A virtual or callback-based SAX interface pays an indirect call per event and blocks inlining across the boundary. With a template parameter, builder calls inline into the walk, and the compiler optimises the pair as one function. The same walk can then feed the DOM tape builder or other sinks. Routing everything through overly generic hooks can still cost: the authors marked one such step "negative perf!".
Applies elsewhere: Native / systems: Compiler tree walkers with templated visitors instead of virtual `accept`; serde-style serializers specialised per format. • Data / databases: Expression evaluators specialised per output sink (vector, aggregate, hash). • Web / backend: In JIT languages, monomorphic call sites (one builder type per hot loop) give the same effect.
Watch out: every builder type instantiates the whole walk, which increases code size and compile time.
Seen in simdjson: 460cfcaf3e 2020-07-27 `parse_structurals` made `really_inline`, so the whole walk folds into its caller. • 03d54f8f6e 2020-08-03 "Use SAX model for stage 2": `src/generic/stage2/tape_builder.h`, with `structural_parser<T>` holding a `T builder`. Merged in a0b1642dc0 2020-08-04. • 03aaf189c1 2020-08-03 Routing all primitives through one `parse_primitive` was titled "negative perf!", a reminder to measure each abstraction step.

### simdjson-007 — Handle leaves inline in the loop; recurse only for containers
Lens: algorithms · Source: simdjson
Principle: In a tree walk where most nodes are leaves, process leaves directly inside the container loop and make a call only when descending into a nested container.
Why it is faster: A uniform "call process(value) for every child" pays call overhead and argument passing for every scalar, and depends on how well the compiler passes the iterator across calls. Leaves are the majority, so handling them inline removes most calls, and the remaining recursion happens only at container boundaries.
Applies elsewhere: Native / systems: AST visitors and DOM serializers; recursive file-system walkers that handle plain files inline and recurse only into directories. • Web / backend: JSON-to-object mappers and React-style tree diffing where leaf nodes dominate. • Data / databases: Nested-type encoders (Parquet repetition levels, protobuf) with an inline fast path for primitive fields.
Watch out: the inlined leaf code is duplicated at each container type; keep it small or the loop body grows past the instruction cache.
Seen in simdjson: 1f78f3ee55 2026-08-14 json2msgpack On-Demand benchmark: scalars written directly in the loop, recursion only for arrays and objects. twitter: GCC +4.8%, clang +17.8%, Apple clang +8.8%.

### simdjson-008 — Derive iterator state from the position instead of storing flags
Lens: algorithms · Source: simdjson
Principle: Remove booleans and counters that can be computed from the cursor and depth you already have; a smaller iterator stays in registers and has fewer fields to keep consistent.
Why it is faster: Every extra field in an iterator is a store on each step and a register the compiler must keep live, and in a nested walk the iterator is copied or passed often. Facts like "at first field" are a pointer comparison (`token.index == _start_index + 1`). Sharing one underlying iterator across all value types also avoids duplicate cursors. Telling the compiler the invariants (`SIMDJSON_ASSUME`) lets it drop redundant checks.
Applies elsewhere: Native / systems: Collection iterators, coroutine and generator frames: compute `is_first`/`has_next` from indices. • Data / databases: Cursor objects in drivers and executors that keep only position plus bounds. • Web / backend: Pagination cursors that encode only an offset and derive the rest.
Watch out: if the derived value is expensive to compute and read often, caching it can be right; measure both.
Seen in simdjson: 2b3c4c68e4 2020-08-31 Removed `other.has_next = false` bookkeeping from the On-Demand iterators. • c89647af9e 2020-11-30 "Make all values use same underlying iterator". • d670906ff3 2020-12-13 "Don't keep a separate at_start boolean in object": replaced by `value_iterator::at_first_field()`, computed from the token index.

### simdjson-009 — Convert a value only when the caller asks for it, in the type they ask for
Lens: laziness · Source: simdjson
Principle: Index the input cheaply, then hand the caller a cursor; decode a value only when it is requested, using the requested type to pick the decoder directly.
Why it is faster: An eager DOM or SAX parser converts every value and must switch on each value's type, which mispredicts on mixed data (the On-Demand design notes say a type switch can make code 3-4x slower). If the caller says "give me a double", there is no type switch and unrequested values are never converted. Peeking at a token and advancing only after a successful conversion makes a failed typed read recoverable without rescanning. When the caller only needs to know a number's type, a digit scan plus a terminator check answers that without converting.
Applies elsewhere: Web / backend: Bind request JSON straight to typed handler fields instead of building a generic object first; lazy protobuf/FlatBuffers accessors. • Data / databases: Late materialisation (decode a column only when projected); log query engines that extract only fields the query references; schema sniffing (int vs float) without full conversion. • Embedded: Config readers that pull only the keys the firmware uses, straight into typed variables.
Watch out: lazy APIs are forward-only or order-sensitive and have lifetime rules (values point into the input); reading every value through a lazy API can be slower than an eager tree if the caller revisits values many times.
Seen in simdjson: ebcb3c6b3b 2020-08-13 "On-demand parse implementation": `src/generic/ondemand/*` (value, array, object, document, token_iterator) on top of the stage-1 index; values are parsed by `get_double()`, `get_string()` and so on. • 9dcf5fca5b 2020-09-12 `doc/ondemand.md` "Type Blindness and Branch Misprediction" documents the rationale. • 0f515785c6 2021-01-07 "Support reading scalars out of order": `peek_scalar()` / `advance_scalar()`; `try_get_uint64` calls `parse_unsigned(peek_scalar())` and only then advances. • af4ff7cc33 2021-09-07 `get_number_type()` "bypassing get_number()": scans digits, checks the terminator, and resolves the 19/20-digit edge with a `memcmp` against `"9223372036854775808"`. • 78325888ea 2024-02-26 Extended the same classifier with big-integer detection (`digit_count > 20`) and a `BIGINT_ERROR`, rare paths marked unlikely.

### simdjson-010 — Skip unwanted subtrees by counting depth over the index
Lens: laziness · Source: simdjson
Principle: To discard a nested value, walk only the precomputed delimiter positions and track depth until it returns to the parent level; nothing inside is decoded.
Why it is faster: Skipping costs one step per structural token instead of full decoding of every string and number inside. The remaining cost is a branch per token on "open, close, or other", which mispredicts on irregular data. Replacing that switch with a 256-entry delta table (+1, -1, 0) and branching only on the exit condition makes the loop nearly branch-free. Keeping the position and depth in locals stops character loads from aliasing member fields and forcing a store each iteration.
Applies elsewhere: Web / backend: jq-like streaming filters and API gateways that drop most of a payload. • Data / databases: Skipping nested messages or groups in protobuf/Avro readers; skipping unprojected nested columns in document stores. • Native / systems: Bracket matching in editors; skipping nested sections in XML/YAML.
Watch out: depth counting assumes the index is valid (balanced, no structurals inside strings); on unvalidated input the skip can run past the end, so bound it by the index length.
Seen in simdjson: 1303a88769 2020-10-19 "Unconditionally track depth", the basis for `json_iterator::skip_child(depth_t parent_depth)`. Merged as "Permit partial iteration in On Demand" in 6b02b06581 2020-12-09. • 8c1dd8070e 2026-10-26 `skip_child` with `skip_depth_delta[256]` and locals for position and depth. Skip time dropped 38-57% with GCC and 3-42% with clang (twitter, citm access patterns); whole calls 10-20% faster. The logging build keeps the old loop.

### simdjson-012 — Search forward from where you are, with a cheap checkpoint for misses
Lens: laziness · Source: simdjson
Principle: Assume keys are requested in storage order and search forward from the current position; on a miss, restore a saved cursor instead of re-walking from the start.
Why it is faster: Callers usually read fields in document order, so a forward search makes each lookup O(1) amortised and the whole object is walked once. A checkpoint is just a saved pointer into the index, so restoring it is free; wrapping around from the object start to where the search began keeps out-of-order lookups correct without a full reset. For optional fields, restoring the position after a miss avoids rescanning everything already consumed.
Applies elsewhere: Data / databases: Avro/Thrift readers that expect schema order; finger search (start from the last hit) in B-trees and sorted runs; cursors with mark/reset. • Web / backend: HTTP header lookup in the common order; form decoders binding fields in declaration order. • Native / systems: Backtracking parsers that save/restore lexer state instead of re-lexing.
Watch out: random-order access degrades to a full scan per lookup; with many out-of-order lookups on one object, building a small map once is cheaper.
Seen in simdjson: b8426584fc 2020-12-19 "Make field lookup order-insensitive": `json_iterator::checkpoint()` / `restore_checkpoint()` and a two-phase search in `value_iterator::find_field_raw`. • 195acc3e45 2020-12-19 Both `find_field` (ordered) and `find_field_unordered` exposed. Merged in 158a3c53d8 2020-12-24. • 06856ec929 2026-09-01 `object::get_current_position()` / `revert_position()`: about 20-28% faster than `reset()` on an optional-field miss.

### simdjson-013 — Skip at the coarsest framing available
Lens: laziness · Source: simdjson
Principle: When a whole record can be skipped and records are framed by a delimiter, find the next delimiter with a fast byte search and locate it in the index by galloping search, instead of walking the record's structure.
Why it is faster: Walking the structure of an abandoned record costs one step per token inside it. In delimiter-framed streams, `memchr` finds the end at memory speed, and an exponential search followed by binary search maps that byte offset to an index position in O(log distance). The cost then depends on how far you skip, not on how much structure is inside or how big the batch is.
Applies elsewhere: Data / databases: Seeking inside sorted offset arrays; posting-list intersection (galloping is also what timsort uses). • Web / backend: Log tailing and NDJSON consumers that abandon records early. • Native / systems: Skipping records in length-less framed formats (line protocols, SSE).
Watch out: only valid when the delimiter cannot appear inside a record (or the format escapes it), and when the record really is being abandoned.
Seen in simdjson: 9b89b82d61 2026-08-12 `skip_to_delimiter` in On-Demand `document_stream`, used when the consumer leaves a document half-read (`depth()>0`) in NDJSON / RFC 7464 streams.

### simdjson-014 — Count by skipping, rewind, then fill a pre-sized container
Lens: laziness · Source: simdjson
Principle: When the destination needs its size up front, count the children by skipping over them without decoding, reset to the start, and allocate exactly once.
Why it is faster: Growing a vector element by element reallocates and copies log(n) times. With a structural index, counting costs only a walk over delimiters, so a counting pass is far cheaper than decoding twice, and the fill pass then does a single allocation.
Applies elsewhere: Data / databases: Two-pass decode into columnar arrays (count, allocate, fill); pre-sizing hash maps from objects. • Native / systems: Protobuf repeated-field pre-allocation when a cheap count is available. • Embedded: Static arena allocation sized by a counting pass.
Watch out: without a cheap index, the counting pass costs as much as a decode; then geometric growth is better.
Seen in simdjson: 16e8db1f17 2021-06-06 `array::count_elements` iterates without consuming values, then `iter.enter_at_container_start()` again. • c9179ad81d 2021-09-02 `count_fields()` for objects and documents.

### simdjson-016 — Process input in fixed-size blocks and carry only a few bits between them
Lens: amortization · Source: simdjson
Principle: Turn per-byte decisions into per-block word operations: consume a fixed block (64 bytes here) per iteration, make whole-block decisions with one test, and pass the minimum state (a carry bit, the last vector) to the next block.
Why it is faster: Loop overhead, branches and state updates are paid once per block instead of once per byte. A 64-byte block maps to one 64-bit mask per character class, so later logic works on whole words. Whole-block tests ("is this block all ASCII?") skip expensive work for most real input with one branch. Keeping the cross-block state to a carry bit or the previous vector lets each block be processed almost independently and keeps the loop free of tail cases. The step size should match the machine: wider vectors can process two blocks per iteration, while narrow ones spill registers if they try.
Applies elsewhere: Web / backend: Body validators and tokenizers that test a whole chunk for "all ASCII" or "no special bytes" before falling back to per-byte work. • Data / databases: Vectorised operators that process 1024-row batches with a per-batch null check; chunked transcoders that carry a pending partial character between chunks. • Embedded: DMA-sized block processing with a carried state word instead of per-byte interrupts. • Native / systems: Checksums and base64 codecs with a block main loop and a carried remainder.
Watch out: the last partial block needs padding or a careful tail path, and the right block size differs per ISA; make it a per-target constant, not a global one.
Seen in simdjson: 9b6377fd80 2019-11-20 "Precalculate the ASCII path": an all-ASCII 64-byte block costs a single `error |= prev_incomplete` instead of the full UTF-8 check. • de8df0a05f 2019-10-01 Stage 1 steps 128 bytes (two 64-byte blocks) per iteration so two independent chains overlap; part of a patch measured at 5% overall and 15% in stage 1. • ce824f8653 2019-11-13 Step size templatised and dropped to 64 bytes on Westmere and ARM, where two blocks per step caused register spills. • e9c91a1ce2 2020-07-20 The UTF-8 checker keeps only `prev_input_block` and `prev_incomplete` between blocks; `is_incomplete()` is one compare against a threshold table. • c09e8dc225 2023-08-18 The AVX-512 string loop advances 64 bytes per step instead of 32, halving iterations and branches. • 78d8acdd9e 2026-07-28 The ARM `is_ascii` test, run once per 64-byte block in UTF-8 validation and stage 1, made cheaper (narrow-shift plus compare instead of a horizontal reduction).

### simdjson-017 — Process record streams in fixed batches, cut at the last complete record
Lens: amortization · Source: simdjson
Principle: For streams of many records, parse fixed-size batches; find each batch's safe cut point by walking the token index backwards from the batch end, never by rescanning bytes.
Why it is faster: Fixed batches bound memory, keep buffers cache-resident and amortise per-call setup over many records. The cut point only depends on the batch tail: walking the structural index backwards, counting brackets, until a value-end is followed by a value-start costs O(tokens near the end). A multibyte character split at the batch edge is trimmed so validation stays correct. If a batch fails because the last record was incomplete, retrying with a fresh batch handles it.
Applies elsewhere: Data / databases: Chunked CSV loading with quote-aware split points; record-aligned input splits for parallel ingestion. • Web / backend: NDJSON and log ingestion in fixed-size reads; finding complete frames at the end of a TCP receive buffer. • Native / systems: Streaming length-delimited protobuf readers with bounded buffers.
Watch out: a single record larger than the batch never fits; detect it and grow the batch or fail clearly. Too-small batches lose the amortisation.
Seen in simdjson: bdc2b07339 2019-11-08 "Streams of JSON documents + Large files (>4GB)": `src/jsonstream.cpp` and a streaming stage 2 that returns `SUCCESS_AND_HAS_MORE` with `next_json`. • 29fc51522a 2019-11-21 `find_last_json` iterates backwards over `pj.structural_indexes`, counting `obj_cnt`/`arr_cnt`, and returns the start of the last whole document; one retry on error. • ea08e7d192 2020-06-09 `src/generic/stage1/find_next_document_index.h` (boundary = value-end followed by value-start with no `,` or `:` between), plus `trim_partial_utf8()` for a split character at the batch edge.

### simdjson-018 — Build the expensive index once and rewind it for every further pass
Lens: amortization · Source: simdjson
Principle: When the same input is queried more than once, keep the derived index and reset only the cursors; do not re-run the indexing pass.
Why it is faster: The structural index is the expensive, whole-input product. A second traversal only needs the cursor, the scratch-buffer pointer and the depth reset, which is O(1). Repeated path queries then cost only their walk.
Applies elsewhere: Data / databases: Re-querying page or block indexes (Parquet, log files) instead of re-scanning; multi-query JSONPath over one document. • Native / systems: Restarting iterators over a memory-mapped file without re-tokenizing. • Web / backend: Caching a parsed template's token list across renders.
Watch out: scratch state written during the first pass (decoded strings) is overwritten on rewind; anything the caller kept from the first pass may become invalid.
Seen in simdjson: 19c3b1315a 2021-06-04 "Rewind functionality": `json_iterator::rewind()` resets `token.index` to `structural_indexes.get()`, `_string_buf_loc` to `string_buf.get()` and `_depth` to 1. • ce38fe7bea 2021-06-21 `at_pointer` rewinds automatically, so repeated pointer queries reuse the same index.

### simdjson-019 — Parse invariant query inputs once, not once per node
Lens: amortization · Source: simdjson
Principle: When every node visited by a recursive query sees the same pattern or path suffix, split it into segments with precomputed flags up front and recurse on (segments, index).
Why it is faster: Re-parsing a path suffix (and allocating a converted form) at every node costs O(nodes x path length) plus allocations; with wildcards over large arrays that becomes a timeout. Pre-splitting makes the per-node cost O(1) and removes the per-node allocations.
Applies elsewhere: Web / backend: Route matchers and CSS selector engines that compile patterns once. • Data / databases: Prepared statements and compiled XPath/JSONPath; regexes compiled outside the loop. • Native / systems: Glob matchers in file walkers that pre-split the pattern by path component.
Watch out: the parsed form must outlive the traversal; for one-shot queries on tiny inputs the preparation can cost more than it saves.
Seen in simdjson: 35b9eaba28 2026-10-11 DOM `at_path_with_wildcard` parses the JSONPath once via `parse_wildcard_json_path` and drops per-node `json_path_to_pointer_conversion` allocations; fixed OSS-Fuzz timeouts. • 895255f774 2026-10-16 On-Demand `split_json_path` does the same for `for_each_at_path_with_wildcard`.

### simdjson-020 — Coalesce many small appends into one checked write
Lens: amortization · Source: simdjson
Principle: Each append carries a fixed cost (capacity check, call, small copy). Merge constant fragments into one string, fill repeated bytes with one bulk operation, and hoist per-element checks out of loops over fixed-size elements.
Why it is faster: Emitting `,`, `"key"` and `:` as three appends means three capacity checks and three variable-length copies. A single precomputed `,"key":`, padded to 16 bytes, is one check and one fixed-size move. Indentation of N spaces appended one at a time pays N checks; one memset pays one. For arrays of fixed-size elements, the worst-case output size is known, so one reservation lets the inner loop write without any per-element check or dispatch.
Applies elsewhere: Web / backend: Template engines that precompile static HTML chunks; HTTP response header emission with pre-joined constant lines. • Data / databases: Bulk INSERT generation and columnar-to-text export with per-batch reservation. • Embedded: Telemetry formatters that emit fixed frames with one length check.
Watch out: worst-case reservation can vastly over-allocate for large inputs (simdjson's 10M zeros once reserved 220 MB for 20 MB of output); cap it or reserve in blocks.
Seen in simdjson: 32b52e3f34 2026-04-30 Builder coalesces per-field separator, key and colon into one constexpr write: CITM serialization +13.7 to 19%, twitter +5.5 to 7.9%. • 514780005f 2026-10-11 `constevalutil::static_string`, `quoted_escaped_text`, `append_static_string`, and `padded_key_length` (rounded up to 16 so the copy is a fixed-size move). • 3a3ef150e0 2026-10-29 Prettify indentation via `append_n(' ', depth*indent_step)`: one capacity check and one memset instead of a per-character append loop. • 6e3d322da5 2026-11-20 `append(integer_array)`: per-type worst case (digits10 + sign + comma) reserved once, then a local-cursor loop with no per-element capacity check or dispatch.

### simdjson-021 — Make readable slack past the end of the input part of the contract
Lens: memory-layout · Source: simdjson
Principle: Require (or guarantee) that a buffer is readable some fixed number of bytes past its logical end, so every wide load, word compare and block copy can over-read without a bounds check or a scalar tail loop.
Why it is faster: Tail handling is where vector loops pick up branches, masked loads and an extra epilogue. With guaranteed slack, the last block is processed like every other block, short literals can be checked with one word load, and a digit parser can load 8 bytes even when only 1 is a digit. The cost is a few dozen bytes per buffer plus an API rule that callers must respect, or a copy when they cannot.
Applies elsewhere: Web / backend: HTTP servers can allocate receive buffers with 32-64 bytes of tail slack so header scanners never special-case the last bytes. • Embedded: Pad DMA/packet buffers to the vector or word width so checksum and parse loops have no epilogue. • Native / systems: Give string types or file buffers a guaranteed zeroed tail; LZ4-style decoders do the same with output slack. • Data / databases: Pad column buffers in a vectorized engine so filters and decoders always process full vectors.

### simdjson-059 — Prefer a predictable branch over a data dependency on the address path

### simdjson-070 — Compact (left-pack) selected bytes with shuffle masks or a hardware compress instruction
Lens: simd · Source: simdjson
Principle: To delete arbitrary elements from a vector without branches, compute a keep-mask, pack the kept bytes to the front with a precomputed shuffle (or a native compress), store the full vector and advance the output by the popcount.

### simdjson-088 — Own the rare slow path: bigint comparison instead of decimal simulation, and no locale-dependent library calls
Lens: compression · Source: simdjson
Principle: When a fast algorithm needs a fallback, make that fallback self-contained and algorithmically cheap, because adversarial or unusual inputs live there and library calls bring hidden costs.

### simdjson-089 — Check and convert eight ASCII digits as one 64-bit word (SWAR)

### simdjson-111 — Use fuzzing timeouts to find algorithmic complexity cliffs
Lens: observability · Source: simdjson
Principle: Treat a fuzzer's timeout reports as performance bugs: they point at inputs where work grows faster than linearly.
Why it is faster: Benchmarks use typical inputs, so quadratic behaviour on nested or repetitive inputs stays hidden until an attacker or an unusual dataset finds it. Continuous fuzzing explores those shapes automatically, and fixing the root cause (re-parsing a path at every node) removes an O(nodes x path length) cost for all users.
Applies elsewhere: Web / backend: fuzz route matchers, template engines and query parsers with timeouts enabled. • Data / databases: fuzz SQL and JSONPath evaluators for super-linear plans. • Native / systems: run fuzzers with tight per-input time limits, not only crash detection.
Watch out: timeouts can be noisy on shared infrastructure; reproduce locally and confirm the growth rate before rewriting.
