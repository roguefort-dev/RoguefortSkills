### envoy-001 — Prefer contiguous and open-addressed containers to node-based ones
Lens: algorithms · Source: Envoy
Principle: When you don't need pointer stability or mid-sequence insertion, store elements in arrays, open-addressing hash tables or B-trees, not linked lists, red-black trees or chained hash maps.
Why it is faster: Node-based containers make one heap allocation per element, and every lookup or iteration step chases a pointer to a random cache line. Contiguous storage keeps elements in a few cache lines, iterates with hardware prefetching, and allocates once (or a few times, when it grows). Swiss tables also probe using a metadata byte array that can be scanned with SIMD. The trade-off is that references and iterators are invalidated on growth or rehash. Keep node-based containers only where something holds pointers to elements across mutations.
Applies elsewhere: Web / backend: In Java, use `ArrayList` instead of `LinkedList`, and open-addressing primitive maps (fastutil) for hot integer keys. In Go and JS, use slices and arrays of structs for middleware and listener chains. • Native / systems: Use `hashbrown` or `absl::flat_hash_map` as the default map. Keep `node_hash_map` only for values whose address must stay fixed. • Data / databases: Use B-tree indexes instead of red-black trees for ordered in-memory catalogs. Use open-addressing hash tables for hash joins. • Embedded: Use fixed arrays and ring buffers with index links instead of malloc'd list nodes.
Watch out: A rehash or reallocation moves elements, so any saved pointer or iterator becomes a dangling reference. Erasing from the middle of a vector is O(n), so pair it with swap-and-pop or batch compaction.

### envoy-004 — Give well-known keys fixed integer slots; keep a map only for the rest
Lens: algorithms · Source: Envoy
Principle: If most accesses to a keyed collection use a small set of keys known before the collection exists, give those keys dense indexes once at startup. Store their values in a fixed array, and fall back to a general map for dynamic keys.
Why it is faster: A string-keyed lookup hashes or compares the key on every access. A slot access is a single load at a constant offset. The name is classified once, at insert time or at startup, and every later access is O(1) with no hashing. The cost is a fixed array per object (memory scales with the number of registered keys) and a registration phase that must finish before objects are created.
Applies elsewhere: Web / backend: Give request objects dedicated fields for Host, Content-Length and similar headers (as Go's `http.Request.Host` does). Python `__slots__` and V8 hidden classes apply the same idea to objects. • Data / databases: Access columns by fixed ordinals instead of looking up names per row. Store promoted hot JSON fields as real columns, with an overflow map for the rest. • Embedded: Use enum-indexed arrays for known message IDs or sensor channels, with a small table for vendor extensions. • Native / systems: In entity-component systems, use component IDs as array indexes.
Watch out: Each slot adds memory to every instance, so register only keys that are actually hot. Registration must be frozen before any map is created, and late registration breaks the layout. Keep the string-lookup API consistent, so a name lookup of a slotted key reaches the same slot.

### envoy-005 — Recognize keys from a fixed vocabulary with a precompiled decision structure
Lens: algorithms · Source: Envoy
Principle: To decide whether an input string is one of a fixed set of keys (headers, commands, directives), build a dedicated matcher at startup, such as a byte trie, a length-then-discriminating-character map, or a hash plus integer switch. Avoid generic hashing followed by full compares, and avoid chains of compares.
Why it is faster: An `if (s == "a") else if (s == "b")` chain costs O(k) compares. A generic hash map hashes the whole key and then runs `strcmp`. A 256-way trie needs at most strlen steps with no hash, but it costs about 2 KB per node. A compiled map branches first on length, then on the character index that best splits the remaining candidates, and finishes with one `memcmp`. Hits are very fast and the memory is small, while misses can be slightly slower. A case-insensitive hash plus a `switch` avoids both lower-case copies and compare chains.
Applies elsewhere: Web / backend: Dispatch on HTTP method or header with a switch on length and first byte. Use static handler maps for GraphQL resolvers or JSON key-to-setter tables. • Data / databases: Recognize SQL keywords in the lexer with gperf-style perfect hashing. • Embedded: Generate the command-string table for a CLI at build time as a length-bucketed decision tree in flash. • Native / systems: Do command dispatch in Redis-like protocols without allocating a lower-case copy.
Watch out: Hash-plus-switch needs a final equality check, or a collision-safe vocabulary, before acting on a match. Tries with wide fixed fan-out waste memory. Benchmark both hits and misses, because the miss ratio decides which structure wins.
Seen in Envoy: 0037d332da 2016-11-15 Header-name classification moved from an `unordered_map` with custom hashing and `strcmp` to a 256-way byte trie. d7757e66b0 2016-11-16 fixed it for bytes above 127. • 35827dd5c5 2019-01-11 Redis command lookup moved from a map to the same `TrieLookupTable`. • c7ce725c78 2024-05-23 `compiled_string_map.h` replaced the big trie for static header lookup. The author reports much faster hits and significantly less memory, with misses slightly slower. • 3d40929cf2 2024-11-14 CEL attribute lookups replaced long `if (name == ...)` chains with static `flat_hash_map<string_view, lambda>` tables built on first use (`bmRequestAttributes` went from 0.179 to 0.166 µs). • 5fa2c9b31b 2026-09-28 Cache-Control directive matching hashes the directive case-insensitively and switches on the integer. ### envoy-006 — Use a linear-time automaton regex engine, never a backtracking one, on configured or untrusted patterns
Lens: algorithms · Source: Envoy
Principle: Backtracking engines (ECMAScript `std::regex`, PCRE without limits) are slow and have exponential worst cases. Automaton engines such as RE2 match in time linear in the input.
Why it is faster: An automaton engine compiles the pattern into a state machine and reads each input byte once, with no backtracking and no allocation of captures. `std::regex` in particular is slow even on easy inputs and allocates heavily. Rewriting ambiguous patterns, for example replacing `.*?` with `[^.]+`, further removes the ambiguity that causes backtracking. RE2 drops backreferences and lookaround, which is usually acceptable for configuration.
Applies elsewhere: Web / backend: Use Go's `regexp` or Rust's `regex` (both automaton-based) for user-supplied patterns. In JS, avoid nested quantifiers and use negated character classes. • Data / databases: Use RE2 or Hyperscan for log-search and WAF rule engines. • Native / systems: Replace `std::regex` everywhere it runs more than once.
Watch out: RE2 rejects backreferences and lookaround, so migrated patterns must be rewritten and tested for equivalence. RE2 compile cost and memory are still high, so compile patterns once, not per match.
Seen in Envoy: 3689eeaeae 2021-09-15 Prometheus name sanitization moved from `std::regex_replace` to RE2 `replaceAll`, with a `string_view` argument that drops a copy. • 5e9ca8d520 2022-05-11 Admin `/stats?filter=` uses RE2 by default. Filtering 1M stats went from 4,131 ms to 186 ms (text and JSON) and from 4,439 ms to 429 ms (Prometheus). • 66cee7751f 2022-10-14 Moved the header-formatter utilities and JSON internals to RE2. • 6c645a13d1 2024-08-03 The access-log format parser moved from `std::regex` to RE2 and to `string_view` APIs. `BM_AccessLogFormatterSetup` went from 75,744 ns to 8,932 ns.

### envoy-011 — Compact in one pass instead of erasing inside the loop
Lens: algorithms · Source: Envoy · Also: zstd
Principle: To remove many elements from an array, partition the survivors to the front (`remove_if`) and truncate once. Don't call `erase` per element while iterating.
Why it is faster: Each middle `erase` shifts the whole tail, so removing k of n elements costs O(n·k), which is O(n²) in the worst case. A single compaction pass moves each survivor at most once: O(n). On keyed structures, walk the index buckets and batch-erase rather than doing repeated searches.
Applies elsewhere: Web / backend: In JS, use `filter` or in-place two-pointer compaction instead of repeated `splice`. In Go, use `slices.DeleteFunc`. • Data / databases: Vacuum and compaction passes that rewrite a page once. Use selection vectors in vectorized executors. • Embedded: Compact an event queue in place after a cancel sweep.
Watch out: `remove_if` leaves moved-from values in the tail until the `erase`. If elements own resources or are observed by index elsewhere, update those references.
Seen in Envoy: b1e62a3f34 2020-07-09 `updateDynamicHostList` had two loops calling `erase(itr)`. They became `std::remove_if` plus a single `erase`, about 3x faster in the new EDS benchmark. • 9dd666d841 2020-10-06 Header-map `removeIf` became O(n) when the lazy map exists. It walks map buckets and batch-erases with `std::remove_if`. • Also seen in zstd (zstd-014): f782cac3d4 2020-11-02 `ZSTD_getSequences` removes block delimiters with `in`/`out` indices instead of one `ZSTD_memmove` per delimiter.

### envoy-012 — Promote a small linear collection to a hash index lazily, above a size threshold
Lens: algorithms · Source: Envoy
Principle: Store small collections as a plain list or vector. Build a key-to-entries hash index on the first lookup once the size passes a threshold, keep it maintained after that, and pre-size it from the known count.
Why it is faster: For a handful of entries, a linear scan beats hashing and costs no index memory. For dozens of entries, O(n) lookups dominate. Building the index lazily means small objects never pay for it. Building it from a known count with `reserve` avoids rehash during construction. The threshold is a tunable that production data sets.
Applies elsewhere: Web / backend: HTTP header containers that scan below 8 entries and hash above. JS engines switch objects to dictionary mode. • Data / databases: Redis-style listpack to hashtable conversion. Small-row inline storage that upgrades to an indexed side table. • Embedded: A linear table for a few peers that is promoted to a hash only on gateway nodes.
Watch out: Every mutation must keep the index in sync once it exists. Measure the threshold on real traffic. Don't drop the index when the collection shrinks, or it will oscillate between building and freeing.
Seen in Envoy: 442b3f1683 2020-09-30 Added `HeaderList::lazy_map_` (`flat_hash_map<string_view, InlinedVector<HeaderNode,1>>`), built by `maybeMakeMap()` once the size reaches a runtime threshold. `getAll()` and `remove()` use it. • 2f54f365a0 2021-07-14 The default threshold changed from "never" to 3, which turned the index on for most real requests. • 1a62e1fe9b 2026-10-27 `maybeMakeMap()` reserves the index from the header count. This runs on every request with three or more headers and was 10-17% faster.

### envoy-013 — Prefix lookups: from per-byte tries to path-compressed radix trees in a flat arena
Lens: algorithms · Source: Envoy
Principle: For prefix or suffix matching over many keys, use a tree keyed by characters. Compress single-child chains into string edges, store only the child range that is actually used, and keep nodes in one array linked by integer indexes.
Why it is faster: A per-character trie with a 256-pointer array per node costs about 2 KB per node and one cache miss per byte. Sparse child ranges and a flat `vector<Node>` with `int32` indexes remove per-node heap allocation, recursive destructors and most of the memory. Path compression (a radix tree) turns a chain of byte hops into one prefix compare per edge, so lookup depth no longer depends on key length.
Applies elsewhere: Web / backend: URL routers built as httprouter or find-my-way style radix trees. Autocomplete stored in typed arrays of node indexes. • Data / databases: Key-prefix indexes in KV stores (ART, radix). Reversed-label tries for DNS or SNI zones. • Embedded: Topic or route tables generated as a compact index-linked tree in flash.
Watch out: Radix trees need node splitting on insert, which is more complex to mutate. They suit mostly-static tables built at config load. Hash children (as Envoy used) trade some memory for O(1) branching. Sorted child arrays are smaller but slower to search.
Seen in Envoy: 78ccd005a6 2021-06-14 The DNS filter replaced a flat map plus a list of suffix `StringMatcher`s with a trie keyed by domain suffix, so one walk finds the zone. • 40e116946d 2024-06-12 Trie nodes store only `[min_child, max_child]` instead of a 256-entry array. • 56021dbfb1 2024-07-10 All nodes moved into one `nodes_` vector with `int32` child indexes. ### envoy-015 — Use a fast, seeded, deterministic non-cryptographic hash
Lens: algorithms · Source: Envoy
Principle: For hash tables, consistent hashing and fingerprints, use a fast portable hash such as xxHash with an explicit seed instead of the platform's default string hash.
Why it is faster: `std::hash<std::string>` is implementation-defined: speed varies, and the results differ across platforms and versions. That breaks consistent hashing across a fleet. xxHash processes many bytes per cycle and is stable everywhere. A seed parameter gives independent hash functions, which Maglev's offset and skip need. Taking a `string_view` lets callers hash without building a string.
Applies elsewhere: Web / backend: Use xxHash or wyhash for cache-shard keys and consistent hashing in Node or Go. Use Murmur for bloom filters. • Data / databases: Use stable hashes for partitioning, so data placement survives upgrades. • Embedded: Use hardware CRC32C for checksums where available.
Watch out: Non-cryptographic hashes can be flooded with collisions by attackers. Use a seeded or randomized hash (SipHash or a per-process seed) for tables keyed by untrusted input. Changing the hash function moves every consistent-hash assignment.
Seen in Envoy: 8a09d86383 2017-09-12 Added `HashUtil::xxHash64` and converted header, JSON and protobuf hashing to it. • 740cb9c04b 2018-02-10 Added a seed argument, used to derive Maglev's two independent hashes. • 9c728a005a 2018-02-15 Added an xxHash-based `StringViewHash` functor for maps. • db793ca15c 2018-10-29 Made xxHash the ring-hash default.

### envoy-016 — Answer point queries directly; don't materialize a collection to test or find one item
Lens: algorithms · Source: Envoy
Principle: Provide `has()`, `exists(key)` and `get(name)` APIs on the underlying structure. Don't build a full copy, list or temporary object just to check emptiness or probe a single key.
Why it is faster: "Give me everything" accessors return maps or vectors by value. Calling one to answer a yes/no question costs O(n) allocation and copying, where O(1) would do. Building a temporary request object just to reuse a lookup helper adds allocations for no benefit.
Applies elsewhere: Web / backend: Use ORM `exists()` instead of `count()` or `list()`. Use `Map.has` instead of `Array.from(map).some(...)`. • Data / databases: Use `EXISTS` or `LIMIT 1` instead of `COUNT(*)` for presence checks. • Native / systems: Give registries lookup-by-key methods rather than snapshot accessors.
Watch out: A snapshot accessor may exist to give a consistent view under concurrency. A direct probe needs the same locking or thread-affinity guarantees.
Seen in Envoy: 6c9c032261 2025-05-27 Added `getActiveCluster(name)` to the cluster manager for the load-stats reporter, instead of calling `clusters()`. • 246bab5318 2025-06-19 `hasActiveClusters()` replaced an O(n) `clusters()` call in the config-dump handler. • c50efad91d 2026-11-04 `virtualHostExists(string_view)` replaced building a temporary `RequestHeaderMapImpl` just to probe a host.

### envoy-017 — Don't sort unless the consumer needs order; sort group keys, not every entry
Lens: algorithms · Source: Envoy
Principle: Sorting n items costs O(n log n) comparisons, which can be expensive in themselves. Emit unordered output when the protocol allows it. When order is needed, sort only the small set of group keys, and only at the output boundary.
Why it is faster: Cosmetic ordering of millions of entries, especially when each comparison decodes data under a lock, can take half of an export's time. Ordered trees (`std::map`) built only to iterate in order add allocation and pointer chasing too. A hash map plus a sorted list of a few group keys keeps deterministic output at a fraction of the cost. A format-specific handler should also run before any generic sorted structures are built.
Applies elsewhere: Web / backend: Emit JSON objects and metric families in insertion or hash order, and offer `?sort=` only when it is asked for. • Data / databases: Drop `ORDER BY` inside subqueries and CTEs that feed aggregations. Sort only the final, limited result. • Native / systems: Return unsorted directory listings unless the caller requests order.
Watch out: Downstream tools or tests may depend on stable order, so make the change opt-out or versioned. Some formats require grouping, which needs contiguity but not order.
Seen in Envoy: d94f8d8049 2021-09-15 The admin stats handler now checks for the Prometheus format before building three sorted `std::map`s of every stat, which it previously built and threw away. • 2193880c3e 2026-04-30 Prometheus output replaced a `std::map` of groups with a hash map plus a sorted key set and sanitized names in place. A production-scale scrape went from about 275 ms to about 140 ms. • 0f62b3853a 2026-11-19 `/stats/prometheus` is unsorted by default. A 2M-stat scrape went from 2.22 s to 1.42 s, since sorting had been 49% of the scrape.

### envoy-019 — Use index-based (pointer-free) hash tables for shared or relocatable memory
Lens: algorithms · Source: Envoy
Principle: When a table lives in shared memory or a mapped file, link cells by integer offsets instead of pointers. Size the buckets from a prime near the capacity, so lookups are O(1) instead of a linear slot scan.
Why it is faster: Without pointers, data structures in shared regions often fall back to linear scans. Offsets stay valid across processes and remappings, so an ordinary chained hash set works and turns O(n) allocation and lookup into O(1).
Applies elsewhere: Data / databases: mmap-backed persistent hash indexes. PostgreSQL-style shared hash tables. • Web / backend: Inter-process caches (APCu-like) shared by worker processes. • Embedded: Relocatable lookup tables in flash that use offsets so they work at any load address.
Watch out: The capacity is fixed at creation, and resizing a shared region is hard. Concurrent writers across processes need their own locking. Offsets need bounds checks if the region can be corrupted.
Seen in Envoy: 0d4e4b22f3 2018-01-17 `SharedMemoryHashSet` implements a hash set "without using pointers, suitable for use in shared memory", with `findPrimeLargerThan(capacity / 2)` buckets. It replaced the `for (i < num_stats_)` scan in hot-restart stat allocation. It was later renamed `BlockMemoryHashSet` (e0332afbb8 2018-04-20).

### envoy-020 — Shrink rule sets: express pairs as one matcher and deduplicate identical rule trees
Lens: algorithms · Source: Envoy
Principle: If users need two rules to express one intent, add a matcher that covers it in one rule. At config load, deduplicate structurally identical match trees or derived subsets by hash, so they are built, evaluated and stored once.
Why it is faster: First-match route tables are scanned linearly, so every redundant entry adds match iterations and memory per request. Identical sub-trees evaluated separately repeat the same work. Sharing one instance, and caching its per-request result keyed by its identity, turns N evaluations into one.
Applies elsewhere: Web / backend: Router DSLs with segment-boundary prefix matchers (nginx `location` semantics). Hash-consed middleware configs. • Data / databases: Common-subexpression elimination across predicates. Sharing identical plan fragments. • Native / systems: Firewall rule compilers that merge adjacent or identical rules.
Watch out: A deduplicated tree must be truly side-effect-free and context-independent. Otherwise, sharing it or caching its result changes behavior.
Seen in Envoy: 4400e53cf3 2020-01-15 The subset LB builds a single "any" subset, shared by the fallback, panic and selector paths, instead of several identical copies. • 8f9e11247a 2022-04-01 `path_separated_prefix` matches "the prefix followed by end of path or `/`", replacing pairs of exact-path and prefix routes with one entry. • 396c8c39d8 2026-01-05 proto_api_scrubber deduplicates identical `MatchTree`s by message hash at config load and caches their results per request, keyed by tree pointer: 16-21% faster on 10k-field payloads.

### envoy-021 — Bucket consumers by log2 size class for cheap approximate top-k
Lens: algorithms · Source: Envoy
Principle: To find the largest consumers quickly under pressure, keep accounts in buckets indexed by `bit_width(size >> shift)`. Move an account only when its class changes, ignore anything below a floor, and reclaim from the largest bucket down, with a cap per call.
Why it is faster: Exact ordering (a heap or sorted set) costs O(log n) on every size update. Size classes change rarely: an account moves only when it crosses a power of two. Updates are therefore usually free, and finding victims means scanning a few top buckets. Ignoring small accounts keeps the tracked set small.
Applies elsewhere: Web / backend: Shed the heaviest tenants first under memory pressure. Pick cache-eviction victims by size class in a CDN. • Data / databases: Find spill candidates in a query memory manager. • Native / systems: OOM-killer-style victim selection. Segregated free lists in allocators.
Watch out: The result is approximate: within a bucket, sizes can differ by 2x. Cap the reclaim done per call so that pressure handling doesn't cause a stall of its own.
Seen in Envoy: 4506199dc7 2021-07-30 Buffer memory accounts are classed by `absl::bit_width(balance >> 20) - 1`. Accounts move between `size_class_account_sets_[]` only when their class changes, and accounts under 1 MB are not tracked. • b51f0ea8aa 2021-08-11 Made the minimum tracked size configurable. de5bf9bf86 2021-09-07 limited the streams reset per pressure invocation, largest first.

### envoy-023 — Construct expensive objects on first use, after the decision points
Lens: laziness · Source: Envoy
Principle: Don't build per-request or per-connection helpers (filter chains, sockets, option objects, TLS contexts) until a step actually needs them. Build them after the pipeline stages that might change or cancel them have run.
Why it is faster: Most requests never touch most optional sub-objects, so eager construction and destruction are pure overhead on the common path. Deferring past the decision points also avoids building the wrong thing, such as a socket for a host a filter later replaces. The cost is a null check per access and slightly higher latency for the first user.
Applies elsewhere: Web / backend: Open DB connections only after authentication passes. Instantiate handlers only after routing. Use lazy getters for rarely used request fields. • Data / databases: Allocate a sort workspace only when a sort operator runs. Open lazy cursors. • Embedded: Power up and initialize a radio or peripheral only on its first transaction. • Native / systems: Load SNI certificates lazily, as ACME-on-demand terminators do.
Watch out: Lazy creation moves the cost, and any failure, to the first user. Initializing inside a hot path that is shared across threads needs safe publication. Don't let laziness hide configuration errors that should fail at load time.
Seen in Envoy: 5d2bd6e0f1 2018-06-26 The HTTP filter chain is created after headers are decoded instead of at stream creation. The stated motive was correctness (choosing between the WebSocket and HTTP stacks), but it also avoids building chains for streams that never get that far. • 1a41521b9f 2023-09-14 UDP proxy session filters can defer upstream socket creation and host selection until after the session filters have run. • 6bb85ba143 2025-12-17 On-demand SDS pauses the TLS handshake, subscribes to the certificate on first use, then resumes. This avoids building SSL contexts for every possible certificate up front. • 063730e3d9 2026-08-06 Upstream socket options in the filter manager are created lazily, saving 33 ns per stream (3.8% of filter-manager create and destroy).

### envoy-024 — Materialize per-thread replicas only for entities that see traffic
Lens: laziness · Source: Envoy
Principle: When every worker keeps its own copy of every configured entity, cost grows as entities × workers. Keep one shared, lightweight description and build each thread-local replica the first time that worker uses the entity.
Why it is faster: With 100k clusters and 32 workers, eagerly replicating each cluster, or each per-cluster helper such as an HTTP async client, means millions of objects, mostly for clusters that never receive a request. It also makes every config update fan out to all of them. Materializing on first access bounds memory and update work by the active set.
Applies elsewhere: Web / backend: Create per-tenant clients and caches in each worker on first request, not at boot for every tenant. • Data / databases: Create per-shard connection pools on first query. Fill per-core routing tables on first lookup. • Native / systems: Lazily JIT or link rarely called functions.
Watch out: The first request on each worker pays the build cost, so latency-sensitive entities may need prewarming. Updates must reach both materialized replicas and the shared description, without racing first-use initialization.
Seen in Envoy: 37babcfd40 2022-03-15 The per-worker, per-cluster `http_async_client_` member became `lazy_http_async_client_`, created on the first `httpAsyncClient()` call. • 4aaf17dce6 2023-08-08 The `enable_deferred_cluster_creation` option keeps a shared `ClusterInitializationObject` and builds the thread-local cluster inline on first use (`initializeClusterInlineIfExists()`). Update callbacks receive a name plus a command thunk, so they don't force the cluster to be built.

### envoy-028 — Avoid redundant validation and transformation
Lens: laziness · Source: Envoy
Principle: Transform or validate once, where the data is produced or first built, not again at every consumer. Scan read-only before copying in order to canonicalize. Detect identity operations and return the input unchanged.
Why it is faster: Most inputs are already canonical: a lowercase host, a constant without spaces, a join with an empty prefix. ### envoy-034 — Expire many entries with one timer armed for the oldest
Lens: amortization · Source: Envoy

### envoy-129 — Register interest once, then drain until the kernel says stop
Lens: io · Source: Envoy
Principle: Register a descriptor for readiness once, and on each wakeup read or write in a loop until the kernel reports it would block. Stop early when a read comes back short. Don't re-arm or re-register per operation.
Why it is faster: Level-triggered helper layers often re-arm interest after every write, which costs an extra `epoll_ctl` syscall per I/O. Edge-triggered registration with a drain loop does one registration for the life of the socket. A read that fills less than the buffer you offered means the socket is empty, so a further read only returns EAGAIN and wastes a syscall. Larger scatter reads (`readv` into several slices) move more bytes per crossing. The cost is that edge-triggered code must really drain, or it can lose a wakeup.
Applies elsewhere: Web / backend: In a custom epoll or kqueue server (game server, Redis-like store), register once with edge triggering and drain to EAGAIN. In Netty or libuv, prefer the edge-triggered transport. • Native / systems: Treat a short read as "drained" in edge-triggered loops, and use `readv` into pooled chunks to raise bytes per syscall. • Embedded: Drain a UART or NIC FIFO fully per interrupt instead of taking one interrupt per byte or frame.
Watch out: An edge-triggered loop that stops before EAGAIN can stall forever, because no new edge arrives. The short-read shortcut is unsafe for sources that can legitimately return partial data while more is queued (some TLS or record layers), so apply it only where a short read really means empty.

### envoy-130 — Ask the kernel only for events you can act on
Lens: io · Source: Envoy

### envoy-140 — Take cached timestamps at the right point in the loop
Lens: io · Source: Envoy
Principle: If the event loop caches an approximate "now", refresh it after the poll returns and before events are dispatched, and stamp received packets after the read completes.
Why it is faster: A cached coarse clock saves a clock call per use, but a value refreshed before a long blocking poll is stale for every event that follows, which skews timeouts, RTT estimates and congestion control. ### envoy-164 — Per-thread caches in front of a locked metrics store
Lens: observability · Source: Envoy
Principle: Give each worker a thread-local cache from name to metric so only the first lookup touches the locked central store, key the cache by pointers into existing name storage, and hold references rather than owning counts.
Why it is faster: Looking up a metric by name costs a hash plus a lock on the central map. A per-thread cache makes repeat lookups lock-free. Keying it by the stat's own name storage avoids a duplicate string per stat per thread. If thread-local caches own refcounts, tearing down a scope makes every thread decrement under one mutex; holding plain references avoids that storm.
Applies elsewhere: Web / backend: Resolve metric handles once per thread in Micrometer or Prometheus clients. • Data / databases: Per-core caches in front of a global dictionary or catalog. • Native / systems: Per-thread logger handles keyed by static call-site pointers.
Watch out: Invalidation is the hard part: deleting a scope must reach every thread's cache before memory is freed.

### envoy-165 — Per-thread histograms swapped and merged off the hot path
Lens: observability · Source: Envoy
Principle: Each worker records into its own log-linear histogram; at flush time the main thread asks workers to swap active and backup buffers and merges the idle buffers, so writers never contend with the merge. Size the bins to the data.
Why it is faster: A shared histogram would need atomics or locks per recorded value. Double buffering lets recording stay uncontended while merging proceeds. Fixed pre-allocated bins multiply by threads and series (128 KB per series on 64 cores), so a tunable bin count matters for sparse series.
Applies elsewhere: Native / systems: HdrHistogram `Recorder` per thread with interval swap; per-CPU latency histograms in eBPF maps. • Embedded: Double-buffered sensor statistics read by a reporting task. • Data / databases: Per-worker query latency histograms merged by a background thread.
Watch out: Memory scales with threads times series times bins; with high cardinality, preallocation dominates RSS.

### envoy-166 — Bracket metric flushes so sinks write once
Lens: observability · Source: Envoy
Principle: Give metric sinks begin and end hooks around each flush so they can fill one large buffer and write it once, and compute per-flush derived data once.
Why it is faster: Writing each metric as a separate socket write is expensive with many stats and short intervals. Bracketing lets a sink reserve a slice and memcpy names and values into it. Tags and names that are the same for the whole flush should be computed once, not per stat under a lock.
Applies elsewhere: Web / backend: Batched StatsD or OTLP exporters that build one payload per interval. • Data / databases: Bulk-insert metric rows instead of one insert per metric. • Embedded: Send one USB or radio frame per report instead of per sample.
Watch out: Large flush buffers increase peak memory and burstiness; cap the batch size.

### envoy-167 — Iterate the authoritative store instead of snapshotting it
Lens: observability · Source: Envoy
Principle: For periodic exports, walk the single canonical container under its lock with a callback, and report its size first so consumers can reserve output once, instead of building a temporary vector of every item.
Why it is faster: Building `store.counters()` meant walking every scope, deduplicating and copying shared pointers (allocation, refcount traffic, hashing) on every flush. Iterating the allocator's own hash sets avoids all of it: with 1M stats the flush went from 1.59 s to 100 ms.

Watch out: Holding the store lock during the whole iteration blocks creators; keep the per-item callback cheap.

### envoy-168 — Maintain the exported subset at creation time
Lens: observability · Source: Envoy
Principle: If only some metrics go to an exporter, evaluate the inclusion predicate once when each metric is created and keep a side index; flushes iterate only that index and emit only the representations consumers need.

### envoy-170 — Prefilter regexes by literal prefix and required substring

### envoy-171 — Tiered inclusion matching with memoized and definitive fast paths
