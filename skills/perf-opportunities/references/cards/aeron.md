### aeron-003 — Pass messages between threads as inline records in a pre-allocated byte ring
Lens: algorithms · Source: Aeron
Principle: Serialize each command into a fixed byte ring buffer as a length-prefixed record instead of queueing pointers to heap objects. Let the consumer drain a contiguous block, release it with a single head update, and control per record whether to consume, stop or commit early.
Why it is faster: A pointer queue costs a malloc per message, a dependent load on the consumer side, a free, and often a second message to return the object to its owning thread for freeing. Inline records keep the data contiguous and prefetchable, the producer's command can live on its stack, and nothing is allocated in steady state. Releasing the head once per drained block (zeroing the bytes and doing one ordered store) amortises the cross-core write over the whole batch. A controlled read lets the consumer apply back-pressure (leave a record unconsumed) or free space mid-batch without copying records aside.
Applies elsewhere: Web / backend: Node worker_threads exchanging length-prefixed records through a SharedArrayBuffer ring rather than `postMessage` objects. • Native / systems: Game-engine actor mailboxes with fixed-size records; logging frameworks that encode into the ring instead of enqueuing heap events. • Data / databases: A WAL record ring between session threads and a single log writer. • Embedded: A UART or radio RX ring parsed in place, using a controlled read to stop at an incomplete frame.
Watch out: Inline records need a size bound, so variable or huge payloads still need a pointer record type, as Aeron kept. In managed runtimes an object queue can be simpler and is fine at low rates. Aeron used one on the Java side and switched the C driver to inline records once malloc/free and ownership round trips showed up.

### aeron-004 — Pad to the end of a buffer instead of splitting a record across the wrap
Lens: algorithms · Source: Aeron
Principle: When a record does not fit before the end of a circular or segmented buffer, write a padding record over the remainder and start the record at the beginning (or in the next segment). Readers skip padding by type.
Why it is faster: Every record stays contiguous, so readers and writers never handle two-piece copies, and a record can be passed to a handler as a single (buffer, offset, length) view or sent directly from memory. In a multi-producer log, the producer whose reservation crosses the end does the padding and rotation, and the others simply retry, so no lock is needed around rotation. The cost is wasted bytes at each wrap, which is small when records are much smaller than the buffer.
Applies elsewhere: Native / systems: Kernel trace rings and GPU command buffers padded with NOPs at the end. • Data / databases: Segment-rolling WAL or Kafka-style logs where the writer that overflows seals the segment with a filler record. • Embedded: DMA rings where descriptors must be contiguous. Pad instead of wrapping a frame.
Watch out: The maximum record size must be well below the buffer size, or padding waste and rotation frequency become significant. Every reader must recognise the padding type, so a padding marker that collides with valid data is a correctness bug.

### aeron-005 — Encode stream positions as one wrap-safe 64-bit number derived by shifts
Lens: algorithms · Source: Aeron
Principle: Fold a segment number and an offset into one monotonic 64-bit position, `(segmentCount << log2(segmentSize)) + offset`, computed relative to an initial segment id so 32-bit ids can wrap. Compare deadlines and sequence numbers by the sign of their difference, and advance derived positions incrementally rather than recomputing them.
Why it is faster: With power-of-two segment sizes, position-to-segment and position-to-offset conversions are a shift and a mask, not a 64-bit divide. Subtracting the initial id first means wrapping ids never break ordering, so there is no special-case rollover code on the hot path. A single 64-bit value is also what flow control, consumers and counters compare, so there is one comparison instead of a (termId, offset) tuple compare. When a writer owns its state, adding the segment length on rotation replaces a volatile read plus a decode.
Applies elsewhere: Data / databases: Log sequence numbers that encode (segment, offset) in one 64-bit value, so segment lookup is a shift. • Native / systems: LMAX-style 64-bit ring cursors; Linux `time_after()`-style tick comparisons. • Embedded: `(int32_t)(deadline - ticks) < 0` on wrapping hardware tick counters. • Web / backend: Byte offsets in chunked upload or streaming protocols, kept as a single monotonic number.
Watch out: This requires power-of-two segment sizes, which constrains configuration. Sign-of-difference comparisons are only valid while the two values are within half the number range of each other.
Seen in Aeron: 66ac563432 2014-07-14 Enforced power-of-two term sizes. ce4fbbb894 2014-07-17 introduced `positionBitsToShift = numberOfTrailingZeros(capacity)`. • f23ad5c4b5 2014-07-05 and df4cafbe22 2014-07-25 made flow control and position tracking work when term ids roll over to negative, by computing `(long)(activeTermId - initialTermId) << shift + offset`. • 80a7624ff2 2014-12-22 The active buffer index is derived as `(termId - initialTermId) % 3`, so no separate index field has to be kept consistent. • 6e07792aea 2018-01-22 `positionBitsToShift()` became a switch over the valid term lengths, which is fast even in interpreted code and also validates the size. `ArchiveConductor` swapped `/ termLength` and `% termLength` for shift and mask helpers. • 1301c817b2 2018-12-14 Exclusive publication rotation does `termBeginPosition += termLength` instead of recomputing from term id. 8cb2834f9a (same day) and 996bf2aaf9 2018-12-15 compute `position()` and `availableWindow()` from local fields instead of decoding a volatile tail. • 151cf3f8fc 2025-10-23 Re-resolution deadlines use `(deadline - now) < 0`, which stays correct across clock overflow, instead of `now > deadline`.

### aeron-006 — Remove from unordered arrays by swapping in the last element; compact after the pass
Lens: algorithms · Source: Aeron
Principle: When element order does not matter, delete by moving the last element into the hole and shrinking (O(1)) rather than shifting the tail (O(n)). When removals happen during a hot iteration, count them and compact in a separate pass only if the count is non-zero.
Why it is faster: A middle remove from an array list copies every later element, so removing k items from n costs O(nk) memory traffic. Swap-remove touches two slots. Deferred compaction keeps the hot loop free of index adjustments, so it stays a simple counted loop (good for bounds-check elimination and rotation-safe iteration), and the rare sweep happens only when something actually expired.
Applies elsewhere: Native / systems: Rust `Vec::swap_remove`; ECS entity and component arrays. • Web / backend: Connection or timer sets in an event loop where order is irrelevant. Mark expired items and sweep at the end of the tick. • Data / databases: Tombstone during a scan and compact afterwards, as in LSM memtables or slotted pages. • Embedded: Fixed-capacity task or listener arrays without memmove.
Watch out: Swap-remove changes element order and invalidates any stored index of the moved element. Don't use it where iteration order carries meaning, such as fairness rotation, unless the round-robin start index is adjusted to match.
Seen in Aeron: 9323b236f2 2017-01-19 "Optimize away list.remove usage": added `ArrayListUtil.fastUnorderedRemove` and applied it in the client and driver conductors, multicast flow control and the receiver. 39c0ecfb57 2017-04-09 used it in `ActiveSubscriptions`. • 7655d6c62a 2017-07-01 and 32c86dff88 2017-07-26 C driver: `aeron_array_fast_unordered_remove` for the receiver image list, poller transports and epoll events. • 86861481cc 2018-02-18 "Consistent use of fastUnorderedRemove" across session workers, conductors, flow control and the receiver. • 9495f88704 2022-04-20 (Java) and c5557c21f8 2022-06-23 (C) The multi-destination send loop counts `to_be_removed` during the send pass and calls the inactive-destination sweep afterwards, only when the count is non-zero.

### aeron-007 — Bound every scan by what can actually contain a match
Lens: algorithms · Source: Aeron
Principle: Stop a scan as soon as structure guarantees nothing further can match: at the first never-used slot in an append-only table, when the live-entry count hits zero, at the last position where a pattern can still fit, or at the previous known boundary instead of the beginning of history.
Why it is faster: It turns O(capacity) or O(history) scans into O(high-water mark), O(live entries) or O(delta). Sparse tables and long histories are exactly where the unbounded version hurts most. The extra bookkeeping is a counter or a remembered position.
Applies elsewhere: Data / databases: Retention or compaction that selects files by key or offset range rather than enumerating all of them. • Native / systems: Slab allocators that track a high-water index; probing that stops at an empty bucket. • Web / backend: Pagination cursors that resume from the last id rather than offset-scanning. • Embedded: Config tables that terminate at the first zero entry.
Watch out: Early termination relies on an invariant such as "slots are allocated in order" or "count is accurate". If freed slots can be reused out of order, stopping at the first unused slot misses live entries.
Seen in Aeron: cf67a58800 2018-12-08 The catalog substring search limits its outer loop to `channelLength - fragmentLength`. • cb04b3d889 2020-08-27 Counter lookups (`RecordingPos`, `HeartbeatTimestamp`, cluster counters and others) `break` at the first `RECORD_UNUSED` slot. Counters are allocated in increasing order, so nothing can follow it. 60145defb3 2020-10-07 did the same in C++. • 98f6fb30ff 2023-03-30 The C hash map `remove_if` loops `while (i < capacity && remaining > 0)` and does not advance after a backward-shift delete, which makes it efficient for sparsely populated maps. • 9cb04b5f08 2025-01-17 Purging detached archive segments searches only down to the previous start position (or the minimum parsed from one directory listing) instead of scanning from position 0.

### aeron-009 — Pick the timer mechanism for the timer count: deadline fields, wheel or heap
Lens: algorithms · Source: Aeron
Principle: With a few timers, store a precomputed deadline per object and compare it to the loop's `now`. With many uniformly spaced timeouts, use a hashed timer wheel. When cancellation and arbitrary deadlines dominate, use a binary min-heap with stored indices.
Why it is faster: A deadline field makes the hot check one compare, with no add and no structure. A wheel gives O(1) schedule and expire and only touches the current tick's bucket. A heap gives O(log n) schedule and cancel and O(1) peek, versus O(n) for a sorted array. Using a general timer structure for three timers costs more in scheduling and indirection than it saves.
Applies elsewhere: Web / backend: Store `expiresAt` per connection or cache entry and check it in the loop. Use a wheel (Netty `HashedWheelTimer`) for millions of idle timeouts. • Embedded: Superloops that keep a "next wake tick" per task rather than a timer queue. • Native / systems: Kernel-style timer wheels for TCP retransmit timers; heaps for simulators and schedulers. • Data / databases: TTL expiry with a min-heap keyed by deadline.
Watch out: A heap gives up FIFO order among equal deadlines. A wheel's resolution is its tick size, and a wheel sized far beyond the live timer count wastes cache. Deadline fields only scale while the set of objects checked each cycle is small.

### aeron-010 — Fan out with a single-writer overwriting broadcast buffer
Lens: algorithms · Source: Aeron
Principle: For one-to-many notification, let a single transmitter overwrite a ring without waiting for receivers. Each receiver validates after reading that it was not lapped, and a late joiner jumps straight to the latest record.
Why it is faster: The writer's cost is O(1) whatever the number of receivers, and a slow receiver can never stall it or the other receivers. Readers need no lock: they read, apply a load fence and recheck the sequence, so a lapped read is detected and discarded. Starting late joiners at the latest-message pointer makes their startup O(1) instead of replaying the whole ring.
Applies elsewhere: Native / systems: Market-data or telemetry fan-out to many local processes over shared memory. • Web / backend: Server-sent events or WebSocket fan-out where slow clients skip to the latest state rather than holding back the publisher. • Embedded: A sensor value table updated by one task and read by many, with sequence validation.
Watch out: Receivers can lose messages when lapped, so the protocol must tolerate gaps or make every message self-contained. The writer never sees a slow consumer, so lapping has to be counted to be noticed.
Seen in Aeron: 93423328a0 2014-04-21 and f8a7cbf533 2014-04-22 `BroadcastTransmitter` and `BroadcastReceiver`. The transmitter writes the tail sequence, then the body, then the latest counter, then the ordered tail increment. • 760bb5b5ee 2014-04-24 Added the LoadLoad fence to `validate`, in the style of `StampedLock`. • 3668e7349c 2014-06-25 Used for driver-to-client messaging. 191e34b298 2014-07-31 makes the copying receiver catch up on construction. • ac153e894b 2019-01-14 The C++ `BroadcastReceiver` initialises from the latest-message counter instead of looping `receiveNext()`, "for an O(1) startup".

### aeron-011 — Reassemble out-of-order data by placing it at its offset, then scan one gap at a time
Lens: algorithms · Source: Aeron
Principle: When each packet carries its absolute offset, write it straight into a preallocated buffer at that offset. Track the contiguous prefix (tail) and the furthest byte seen (high-water mark), treat zero regions as gaps, and act on only the first gap per pass.
Why it is faster: No reorder queue, no per-packet node and no sorting: out-of-order arrival costs the same copy as in-order arrival. Gap detection is a linear walk over the region between tail and high-water mark. Handling only the first gap is sufficient because a NAK covers it and later gaps are found on later passes, so the detector keeps one reusable gap record and a few primitive fields instead of a list. Reading the high-water mark before gathering consumer positions fixes the scan range early and keeps it small.
Applies elsewhere: Web / backend: Parallel ranged downloads written with `pwrite` at their offsets, with a contiguous-prefix pointer for streaming to the client. • Native / systems: Selective-repeat ARQ that requests the earliest hole first; torrent piece assembly into a preallocated file. • Data / databases: Replicated-log repair that fixes the lowest missing index first. • Embedded: Firmware-update chunks over a lossy radio, placed by offset into flash with a missing-chunk bitmap.
Watch out: Zero-as-gap needs the buffer to be cleaned ahead of reuse and a frame format in which a valid header is never all zeros. Single-gap scanning recovers multiple losses serially, one per pass, which adds latency when many gaps occur at once.
Seen in Aeron: a1f7671811 2014-04-15 The receiver rebuilds the log by inserting frames at their term offsets. ### aeron-012 — Reassemble fragments per known source with a next-offset check
Lens: algorithms · Source: Aeron
Principle: When the stream source is already known, keep one reassembly buffer for it instead of a map keyed by session. Accept a continuation fragment only if its offset equals the expected next offset. Look up before inserting so that a buffer is constructed only on a miss.
Why it is faster: A per-fragment map lookup is wasted when the poll is already scoped to one source. A single `offset == nextOffset` comparison replaces nested builder-state checks, keeps the common unfragmented path flat, and cheaply rejects fragments that do not continue the stream. `emplace(key, Builder(n))` builds and allocates a temporary even when the key exists, while find-then-emplace allocates only on first use.
Applies elsewhere: Web / backend: HTTP/2 or WebSocket frame reassembly held per stream or connection object, not in a global map. • Native / systems: TCP segment acceptance by expected sequence number; C++17 `try_emplace`. • Data / databases: Multipart upload stitching that validates part offsets. • Embedded: Multi-packet CAN or BLE message reassembly with a single expected-offset counter.
Watch out: A source-scoped assembler is only correct when the poll really is limited to one source. On a multi-source subscription it would interleave sessions.
Seen in Aeron: a483355869 2017-04-01 `ImageFragmentAssembler` holds a single `BufferBuilder` instead of an `Int2ObjectHashMap`, which is "more efficient when polling an individual session". 20b7a3514d 2017-05-10 added `Header.context()` so handlers need no per-image closure. • 1a8e5924bf 2019-10-14 The same image-scoped assemblers in C++. • 40cb68d4b2 2022-07-03 and 98dfd16e78 2022-07-08 "Simplify branching for fragment assembly": a flat BEGIN branch, and an else branch that appends only if `offset == builder.nextTermOffset()`. • 31b7e478b4 2022-07-07 C++ assemblers use a `getBuffer(sessionId)` that finds first and emplaces only on a miss ("Avoid reallocation on fragmented stream").

### aeron-014 — Allocate free ids with one insert-and-test and a bitset, skipping reserved ranges arithmetically
Lens: algorithms · Source: Aeron
Principle: Use an `add()` that reports whether the id was new instead of `contains()` then `add()`. Jump over a known reserved range in one step. Find nearby free ids with a bitset and a find-first-clear operation.
Why it is faster: Contains-then-add hashes and probes twice. Stepping id by id through a reserved block costs a probe per id, while one assignment skips it. A bitset over candidate offsets finds the first free id with word-sized operations instead of repeated set lookups or bounds heuristics.
Applies elsewhere: Native / systems: File-descriptor and port allocators using bitmaps (as the Linux fdtable does). • Web / backend: `putIfAbsent`/`Set.add` return values instead of a separate `has`. • Data / databases: Free-page maps in storage engines. • Embedded: Slot allocation for fixed-size message buffers via a 32- or 64-bit free mask.
Watch out: Bitset search code must handle lengths that are not a multiple of the word size. Aeron needed a follow-up fix for exactly that.

### aeron-017 — Compute values only inside the branch that uses them
Lens: laziness · Source: Aeron · Also: Kafka
Principle: Move loads, clock reads, unit conversions, string decoding, validation and allocation into the branch that consumes the result. Rare cases should be tested only after the common case has failed.
Why it is faster: Work hoisted above a branch is paid on every path, including the hot one that discards it. Moving it inside the branch makes the fast path shorter, frees registers, and keeps cold data out of the cache. Testing a rare condition only after the common check fails removes it from the fast path entirely.
Applies elsewhere: Web / backend: Build log strings behind a level check. Compute ETags only when the response is cacheable. • Data / databases: Decode a column only when a predicate or projection references it. • Native / systems: Allocate subsystems only for enabled features. • Embedded: Read the RTC only on the timeout path.
Watch out: Duplicating a computation into several branches can bloat code. Factor it into a helper rather than copy-pasting it.

### aeron-022 — Consult another thread's state only when your local snapshot runs out
Lens: laziness · Source: Aeron
Principle: Keep a local copy of a remote progress value (producer position, consumer head, last advertised window) and work against it. Re-read the shared, contended value only when the local copy says you are caught up, full or out of window.
Why it is faster: Reading a counter that another core writes costs a coherence miss every time it has changed. Most of the time the local snapshot already allows progress, so the shared read happens once per batch rather than once per item. Validating against a snapshot owned by the current thread also avoids mixing fields written by different threads.
Applies elsewhere: Native / systems: Cached head and tail in any SPSC ring (audio, logging, DPDK `rte_ring`). • Web / backend: Rate limiters that consume from a locally cached token allowance and refresh from the shared store only when it is exhausted. • Data / databases: Readers that check an MVCC snapshot rather than the live transaction table. • Embedded: A UART TX routine that re-reads the hardware FIFO level only when its cached free count hits zero.
Watch out: The snapshot must be conservative (it may under-estimate progress, never over-estimate it), or you will read unpublished data or overrun a consumer.
Seen in Aeron: 3f196a146a 2015-04-05 "Validate packets against flow control window of last SM rather than real time state". 2df6f6714c 2015-04-20 computes the minimum subscriber position on demand, only in the rare `isDrained()`. • 01968ad05c 2015-11-01 "Only check the producer positions if the consumer has not moved". • 819ac26b20 2018-10-03 The receiver keeps `lastSmPosition`/`lastSmWindowLimit` from its own status messages and checks overruns against them, not against conductor-updated fields. • a575b9761d 2018-12-11 Replay re-reads the live recording position only when `replayPosition >= stopPosition`. • f4bda7024b 2019-01-03 C SPSC/MPSC queues rely on a producer-side `head_cache` and re-read the shared head only when the queue looks full. 08399bf419 2019-01-02 fixed a missing cache update. • edbbb53c1c 2020-10-09 Replication checks `image.isClosed()` only when no progress was made.

### aeron-023 — Check that the result can be accepted before doing the expensive work
Lens: laziness · Source: Aeron · Also: jemalloc
Principle: Before encoding, reading from disk or allocating, check that the destination has room (claim space, query the available window, run the acceptance test). Do no more work than the consumer can take.
Why it is faster: If the work is done first and the offer then fails, the CPU spent on it is wasted exactly when the system is overloaded, and the work is repeated on retry. Reserving first turns a full buffer into a near-zero-cost no-op, and sizing reads to the available window avoids reading data that would have to be dropped or read again.
Applies elsewhere: Web / backend: Check the rate limiter or queue capacity before rendering or serialising a response. A proxy reads from upstream only when the client socket is writable. • Data / databases: Check free space on a page before compressing a row into it. Size cursor fetches to the client buffer. • Embedded: Confirm a free TX descriptor before building a packet. • Native / systems: Audio pipelines that pull only as many samples as the ring has room for.
Watch out: A claim must always be committed or aborted, even on error paths, or the reserved region blocks readers. Keep the claim-to-commit window short.

### aeron-024 — Stop consuming once the needed result or end-of-stream is seen

### aeron-025 — Make the common outcome the cheap path: optimistic attempts versus pre-checks
Lens: laziness · Source: Aeron
Principle: If the failure path is expensive (exceptions, stack traces), test cheaply first. Why it is faster: Constructing an exception captures a stack trace and allocates, which costs orders of magnitude more than a branch. Applies elsewhere: Web / backend: `TryParse`-style APIs instead of try/catch. Watch out: Optimistic attempts are only cheap when failure is rare and side-effect free. Counted failures must be exported somewhere visible, or they become silent data loss.

### aeron-029 — Batch naturally: drain what is available, then publish progress or flush once

### aeron-031 — Run secondary work at a lower rate: every Nth cycle, on idle, or on a deadline
Lens: amortization · Source: Aeron

### aeron-036 — Give each thread's hot written fields a cache line of their own

### aeron-037 — Lay out fields by which thread uses them and how often
Lens: memory-layout · Source: Aeron
Principle: Order the fields of a structure so that the fields one code path uses together sit on the same line, fields written by different threads sit in different blocks, and cold configuration and references go to the end.
Why it is faster: A hot path that touches six scattered fields can miss on six lines. Grouped, it misses on one. Separating fields by writer thread also keeps one thread's stores from invalidating lines another thread only reads. Read-mostly fields that a reader needs on every poll belong with that reader, not inside the padded block of a writer. Grouping is free at runtime and costs only care at design time.
Applies elsewhere: Native / systems: Put the key, hash and next pointer first in hash-table entries. Split connection structs into RX-thread and TX-thread blocks. • Data / databases: In buffer-pool descriptors and B-tree node headers, keep the fields checked on every lookup together. Move rarely used metadata into a side structure. • Web / backend: In request objects, keep the parsed method, path pointer and length adjacent. ### aeron-038 — Write shared cache lines only when something actually changed
Lens: memory-layout · Source: Aeron
Principle: A store to a line that other cores read invalidates their copies even when the stored value is identical. Compare before storing, publish thresholds with hysteresis, and publish a loop's result once at the end instead of on every iteration.
Why it is faster: A read of a field a reader already holds is an L1 hit. An unconditional store forces the line into Modified state and makes every reader take a coherence miss on its next read. Testing first keeps the line Shared. Hysteresis ("trip gain") cuts limit updates from once per message to once per fraction of a window. On a GC'd runtime, reference stores also dirty card-table entries, so skipping redundant reference writes saves write-barrier work too. The extra compare is almost always cheaper than the invalidation it avoids.
Applies elsewhere: Native / systems: Test a bit before `set_bit`. Check a reference count before incrementing it for immortal objects. Advance a shared "consumed" cursor only every N KB. • Web / backend: In React, skip `setState` when the value is equal. Skip DOM attribute writes when the value is unchanged. In JVM code, avoid reassigning the same reference to a long-lived object's field in a loop. • Data / databases: Mark a page dirty only when its bytes changed. Skip UPDATEs of unchanged rows to save WAL traffic. Publish a "flushed LSN" only after meaningful progress. • Embedded: Avoid rewriting an unchanged peripheral register or flash cell, which costs bus cycles or wear.
Watch out: Hysteresis delays information to the reader. The trip gain must be small enough that the producer is never starved, so Aeron uses fractions of the window. A compare-before-store on a field only one core ever touches is pure overhead.

### aeron-040 — Flatten pointer chains on hot paths

### aeron-065 — Let a single writer keep derived state locally and update it incrementally

### aeron-066 — Check against a local snapshot of another thread's value, and refresh it only when exhausted
Lens: caching · Source: Aeron

### aeron-073 — Remove layers of indirection on the hot path

### aeron-075 — Choose the cheapest dispatch form for the case count and frequency
Lens: cpu-microopt · Source: Aeron

### aeron-078 — Use branch-free integer idioms: leading-zero counts and wrap-safe comparisons

### aeron-080 — Decide invariant choices once at construction, not on every call
Lens: cpu-microopt · Source: Aeron

### aeron-082 — Account for garbage-collector write barriers on reference stores
Lens: cpu-microopt · Source: Aeron

### aeron-083 — Pick the spin-loop instruction deliberately: PAUSE hint or a true no-op
Lens: cpu-microopt · Source: Aeron
Principle: In a busy-wait loop, a spin hint (x86 `PAUSE`, `Thread.onSpinWait`, ARM `yield`) reduces power, avoids the memory-order pipeline flush when the loop exits and frees resources for a hyperthread sibling. Lens: concurrency · Source: Aeron
Principle: Arrange the design so each counter, index or state field is written by one thread only. The owner can then read it with plain loads and publish it with a release (ordered) store; compare-and-swap, fetch-and-add and locks become unnecessary. Use the multi-writer variant only where producers really are concurrent.
Why it is faster: A locked read-modify-write (LOCK XADD, CAS loop) costs tens of cycles uncontended and much more under contention, because it takes exclusive ownership of the cache line and acts as a full fence. A release store on x86 is a plain `mov`. Single ownership also removes the "in progress" states and retry loops that CAS-based protocols need, and the owner can cache derived state locally. The cost is architectural: you must route all writes for a value through its owner, usually via a queue.
Applies elsewhere: Web / backend: Per-worker metrics counters written only by their worker and summed by a scraper; shard-per-core servers where each connection belongs to one core. • Native / systems: SPSC rings where the producer owns the tail; `std::atomic::store(memory_order_release)` instead of `fetch_add` for owned counters. • Data / databases: One WAL-appender thread fed by queues instead of many sessions contending on a log mutex.
Watch out: The single-writer guarantee must be enforced by structure, not by comment; a second writer introduced later silently loses updates. Aeron documents exclusive publications as not thread-safe and keeps a concurrent variant for genuinely shared producers.

### aeron-089 — Map each ordering requirement to the cheapest instruction on each ISA
Lens: concurrency · Source: Aeron
Principle: Implement acquire, release and full barriers per architecture: compiler barriers only on x86 for acquire/release, a locked add or `xchg` instead of `mfence` for StoreLoad, and real release fences exactly where weakly ordered CPUs need them.
Why it is faster: x86 is TSO: loads already have acquire semantics and stores release semantics, so the fence functions only need to stop compiler reordering; extra dummy loads or stores are wasted instructions. For a full barrier, `lock addl $0,(%rsp)` is cheaper than `mfence`, and `xchg` performs the store and the fence in one instruction. ARM64 needs explicit fences, which on x86 compile to nothing, so adding them costs x86 nothing.
Applies elsewhere: Native / systems: A portable atomics header: no-op plus compiler barrier on x86, `dmb ishld`/`dmb ish` on ARM; benchmark `mfence` against a locked RMW on your CPU. • Embedded: Single-core MCUs need only compiler barriers for ISR-shared variables; device descriptor rings need a write barrier before the doorbell.
Watch out: Hand-rolled barrier code is easy to get subtly wrong; prefer compiler intrinsics or C11/C++11 atomics unless measurements prove a gap, and keep a test suite that runs on ARM.

### aeron-090 — Publish a record by writing its length word last with a release store
Lens: concurrency · Source: Aeron
Principle: Write the payload and the rest of the header with plain stores, then store the length (or the first header word) with release semantics. Readers acquire-load that one word: zero or negative means "not ready". One field signals both readiness and size, with no separate commit flag or lock.
Why it is faster: There is one ordered store per record and no lock. Readers need one acquire load to know a record is complete and how far to skip. Writing a negative length at claim time and the positive one at commit lets scanners distinguish "claimed, in progress" from "empty". Writing the body first and the header word last also lets a writer copy a pre-formed frame from a read-only source without first zeroing and restoring it.
Applies elsewhere: Data / databases: WAL records with the length/CRC word written last; crash recovery stops at the first zero length. • Web / backend: A `SharedArrayBuffer` ring between workers where `Atomics.store(len)` publishes each message. • Embedded: DMA descriptors with an owner/length word written last, followed by a barrier and doorbell.
Watch out: The marker must be a naturally aligned word the CPU writes atomically, and the region must be zeroed before reuse, or readers will see stale lengths. On ARM, a release fence is needed after writing the negative claim marker too.

### aeron-091 — Claim space with one fetch-and-add on a packed word; let the overflowing claimer handle rotation
Lens: concurrency · Source: Aeron
Principle: Multiple producers reserve buffer space with a single atomic add on the tail (no CAS retry loop). Pack related values that must agree (term id and offset) into the same 64-bit word so one atomic reads or claims both. The producer whose claim crosses the end writes padding and triggers rotation; producers that started past the end simply retry on the next buffer.
Why it is faster: Fetch-and-add always succeeds in one instruction, so contention never causes retries and every producer finishes in bounded steps (wait-free claim). Packing two fields into one word means one consistent snapshot without a lock or a second load, even across rotation. Letting the tripping producer pad and rotate avoids records split across the wrap and any lock around rotation. The tail can overshoot capacity, so readers clamp it.
Applies elsewhere: Native / systems: Lock-free bump/arena allocators and per-thread trace buffers using `XADD`; a generation number plus index in one `AtomicU64` for ABA-safe structures. • Data / databases: Multi-writer append-only files where writers reserve offsets with an atomic add and then `pwrite`; segment rolling sealed by the writer that overflows. • Embedded: Circular trace buffers in kernels padded with no-op records at the wrap.
Watch out: Fetch-and-add on a shared tail is still a contended cache line; with a single producer, a plain release store is far cheaper (see the single-writer entry). Packing limits each field's range.

### aeron-092 — Make readers wait-free: stop at the first unpublished record, never spin on a writer
Lens: concurrency · Source: Aeron
Principle: A consumer reads until it meets a record that is not yet committed and then returns, instead of spinning until an in-flight writer finishes. It bounds its scan by buffer capacity, not by a tail that may have run ahead of committed data.
Why it is faster: With fetch-and-add reservations, the tail advances before data is written, and a writer can be descheduled between claim and commit. ### aeron-096 — Move work to the thread that owns the data and keep liveness work off stall-prone threads
Lens: concurrency · Source: Aeron

### aeron-100 — Design inter-thread messaging: copy records by value and match queue type to the producer topology

### aeron-105 — Place threads deliberately: pin hot agents, keep helpers off their cores, stay within one cache domain

### aeron-114 — Use a memory-mapped shared log as the IPC channel
Lens: io · Source: Aeron

Watch out: A shared mapping is a shared failure domain: a crashed writer can leave half-written records, so readers need a commit protocol (length written last) and liveness detection. tmpfs consumes RAM, and the data does not survive reboot.

### aeron-147 — Diagnostics must never back-pressure or disrupt the data path
Lens: observability · Source: Aeron
Principle: If the event buffer is full, drop the event; claim space before encoding so a full buffer costs nothing; and on hot paths count an overflow instead of throwing an exception.
Why it is faster: Spinning until a log ring drains couples application latency to the log reader's speed. Encoding a message and then failing to offer it wastes CPU exactly when the system is overloaded; claiming first makes the full-buffer case free.
