### nginx-001 — Freeze known key sets into a read-only hash built once at startup
Lens: algorithms · Source: nginx
Principle: When the set of keys is fixed before traffic starts (header names, MIME types, server names, variables, filter type lists), build a lookup table once, tuned for lookups only, and never mutate it afterwards.
Why it is faster: A linear list of N strings costs N string compares per lookup; a hash costs one hash plus a short scan. Because the table is never written, the builder can spend time at startup searching for the smallest table size in which every bucket fits a byte budget (one cache line), store elements inline (length, name, value) with no per-element pointers, and lowercase keys in advance. A lookup then touches about one cache line. The tradeoff is build time and a hard failure mode when the budget cannot be met; nginx eventually prefers degrading to a bigger bucket over refusing to start.
Applies elsewhere: Web / backend: replace `Array.includes` allow/deny lists for headers or content types with a frozen `Set`/`Map` built at boot; generate route or keyword tables with gperf or Rust `phf`. • Embedded: string-to-handler dispatch tables generated offline and placed in ROM. • Native / systems: symbol tables and option parsers frozen after load; size buckets to the cache line. • Data / databases: catalog and dictionary lookups in columnar stores that never change after load.
Watch out: only pays when keys are known before lookups start and lookups vastly outnumber rebuilds. The size search can be slow for very large sets, and a hard "cannot fit" error turns a tuning knob into an outage; always have a fallback.

### nginx-002 — One intrusive balanced tree with a shared sentinel and a per-tree insert callback
Lens: algorithms · Source: nginx
Principle: Implement a single balanced search tree whose nodes are embedded in the user's objects, whose empty children all point to one sentinel node, and whose ordering is supplied by a small insert callback per tree.
Why it is faster: Balanced trees give O(log n) insert and delete and cheap access to the minimum, which is what timers, rate-limit tables and caches need. Intrusive nodes mean no allocation per insert and one fewer pointer hop. A shared sentinel removes NULL checks from rotations. A per-tree insert callback lets each user define ordering (wraparound-safe timer compare, hash-then-string) without a generic comparator call on every step. Writing the descent as `p = (key < t->key) ? &t->left : &t->right` folds the mirrored branches into one, so the compiler can use a conditional move.
Applies elsewhere: Native / systems: Linux-style intrusive rbtrees for timers, schedulers and lock managers; one well-tested tree beats many ad hoc ones. • Embedded: RTOS timer and ready queues with intrusive nodes and no heap. • Data / databases: ordered in-memory indexes and expiry queues; plug key ordering in per index. • Web / backend: TTL caches and rate limiters needing "smallest key" plus point lookups.
Watch out: signed-difference compares only work while live keys span less than half the integer range. For pure FIFO timeouts with one fixed duration, a plain queue or timing wheel is O(1) and cheaper.
Seen in nginx: f5003d8a6 2003-12-04 `ngx_rbtree.c` and `ngx_rbtree_min` first appear, used for the event timer tree. • 208eed221 2005-10-07 Timer comparisons use signed difference so 32-bit msec wraparound works (0.3.0). • 8c5f37e7d 2006-11-16 The descend-and-insert loop becomes a per-tree `tree->insert(root, node, sentinel)` callback (`ngx_rbtree_insert_timer_value`). • f4eb01733 2006-11-20 Generic `ngx_rbtree_insert_value()` added, so shm slab zones and limit zones can reuse the same balancing code. • 7912e4ba5 2007-12-17 Branch-light insert via pointer-to-child-pointer in the generic, timer and SSL session inserts; `ngx_rbtree_init()` macro. • baa239c48 2012-04-06 Fixes signed overflows in the timer comparisons (ticket #145). ### nginx-003 — Keep all deadlines ordered and sleep exactly until the earliest one
Lens: algorithms · Source: nginx · Also: NATS
Principle: Store every timeout in a min-ordered structure; the event loop's wait timeout is "earliest deadline minus now", and expiry pops from the minimum end. Nothing ever scans all connections.
Why it is faster: A periodic sweep over N connections costs O(N) per tick even when nothing expires, and also forces wakeups. With an ordered structure, the loop sleeps until something actually expires, and expiring k timers costs O(k log N). The poll call doubles as the timer wait, so there is no separate timer thread or signal.
Applies elsewhere: Web / backend: idle and request timeouts in custom event loops (libuv/libevent heaps follow this design). • Embedded: cooperative schedulers that program a one-shot hardware timer for the next deadline and sleep in between, saving power. • Data / databases: lock-wait and statement timeouts without a sweeper thread.
Watch out: with very many timers that are reset constantly, tree updates dominate; combine with lazy re-arming (see lazy timer updates) or use a hierarchical timing wheel when precision can be coarse.

### nginx-004 — Order a tree by a machine-word hash and compare the full key only on ties
Lens: algorithms · Source: nginx
Principle: When keys are long strings or digests, put a fixed-width hash (or the first word of a cryptographic digest) in the node as the integer key, and fall back to comparing the full key only when two hashes are equal.
Why it is faster: Most tree steps become one register compare instead of a `memcmp` of 16+ bytes, and nodes can drop the bytes already held in the integer key. Correctness depends on a subtle rule: on a hash tie you must keep descending by full-key order, because rebalancing does not keep equal hashes adjacent. Once a hash matches, the full key must still be checked, or collisions (accidental or attacker-made) return the wrong entry.
Applies elsewhere: Data / databases: index a `hash_prefix BIGINT` column and recheck the full hash; abbreviated sort keys (Postgres) use the same idea. • Native / systems: content-addressed stores keyed by the first 8 bytes of a SHA; symbol tables keyed by (hash, string). • Web / backend: shared-memory rate-limit tables keyed by a hash of client identity.
Watch out: the shortcut is only as good as the hash distribution; non-uniform hashes turn into long tie chains. Never skip the full-key verification, and test the collision path explicitly: nginx shipped the broken tie walk for five years.
Seen in nginx: e532b0194 2007-01-11 SSL session cache and limit_zone stop descending at the first equal hash and scan the equal run (also 1279b049b). • 421a3b800 2007-12-25 `ngx_open_file_lookup()` reuses the same pattern. • 52859f2f1 2009-03-23 Proxy cache: the first `sizeof(ngx_rbtree_key_t)` bytes of the 16-byte MD5 become `node.key`; the node stores only the remaining bytes and `memcmp`s them on integer ties. • 7ca6c1ff7 2012-02-27 Fixes lookups in open_file_cache, resolver, SSL session cache, limit_conn, limit_req and file cache: the 2007 "walk equal hashes" loop "incorrectly assumed that nodes with identical keys are linked together"; lookups now descend by string-compare result. • 605a0ab2e 2012-09-03 Matching fix for limit_req insertion on collisions. • ce05841ee 2015-09-11 Cache checks the whole key in addition to hashes, defending against collision attacks.

### nginx-005 — Embed list links in the object so one node can sit in several structures
Lens: algorithms · Source: nginx · Also: Netty, Seastar, Tokio, H2O, Varnish
Principle: Put the link fields inside the object, recover the object with offset arithmetic, and let a single node be in a search tree and an LRU queue at the same time.
Why it is faster: Insert and remove are O(1) with no allocation, and a sentinel head removes empty-list edge cases. An LRU cache needs no separate hash map plus list of wrapper nodes: a hit is a tree lookup, an unlink and a relink at the head; eviction pops the tail. Fewer allocations, fewer pointer hops, better locality.
Applies elsewhere: Native / systems: Linux `list_head`, Boost.Intrusive; buffer-pool page tables in databases. • Embedded: intrusive lists avoid heap use entirely in RTOS code. • Web / backend: in managed languages, JS `Map` delete+set moves an entry to the tail, giving the same O(1) LRU without extra nodes.
Watch out: an object on several lists must be unlinked from all of them before it is freed; intrusive structures make use-after-free bugs easy.

### nginx-006 — Parse with an explicit state machine over the receive buffer, recording tokens as pointers
Lens: algorithms · Source: nginx · Also: Seastar
Principle: Write protocol parsers as a byte-driven `switch(state)` whose state is saved between calls, record token boundaries as pointers into the input instead of copying, and hand the parser whole buffers rather than single characters.
Why it is faster: Each byte is examined once, even when data arrives in fragments: a partial packet resumes where it stopped instead of re-parsing. Tokens are slices of the receive buffer, so there are no copies or allocations. A dense `switch` compiles to a jump table. Feeding whole buffers keeps the inner loop tight; a call per byte pays function overhead and state save/restore on every character.
Applies elsewhere: Web / backend: llhttp/picohttpparser-style HTTP, Redis RESP or streaming JSON parsers that tolerate arbitrary chunking. • Embedded: UART/AT-command decoders fed from an ISR ring buffer; keep the state byte, never buffer whole lines. • Data / databases: CSV and wire-protocol loaders that slice instead of copying fields.
Watch out: pointer tokens are only valid while the buffer lives and is not moved; growing or compacting the buffer must fix up every saved pointer (nginx copies the partial token into a larger buffer for oversized headers).
Seen in nginx: 02f742b45 2005-04-08 By 0.1.28 the header parser keeps `r->state` and pointer fields (`uri_start`, `header_name_start`), and computes a header hash per byte using a 256-entry `lowcase[]` table that also rejects invalid characters. The design dates from the earliest imports. • 0359ba8cc 2006-10-28 The parser source documents "gcc, icc, msvc and others compile these switches as an jump table". • 68d4325de 2021-07-08 HTTP/3 parsers switch from one character per call to whole buffers ("should optimize parsing time and CPU load"), about 1,068 lines added, 870 removed. • Also seen in Seastar (seastar-010): 10695644d7 2014-08-20 "Get rid of regex in http parser. ### nginx-007 — Audit "startup only" code for quadratic algorithms: sort once, merge-sort lists
Lens: algorithms · Source: nginx
Principle: Configuration and table-building paths scale with user input. Replace repeated sorted insertion and insertion sort with append-then-sort-then-dedupe or merge sort, keeping stability where order carries meaning.
Why it is faster: Inserting n items into a sorted array with memmove, or insertion-sorting a list, is O(n²); one O(n log n) sort followed by a linear dedupe pass is dramatically faster at scale. Merge sort on a linked list needs no extra memory and moves no elements, only links. For tiny n, insertion sort is fine and stable, which matters when configured order breaks ties.
Applies elsewhere: Web / backend: route-table and middleware registration in large apps; bulk-build then sort, not sorted insert per route. • Data / databases: bulk-load B-trees from sorted input instead of row-at-a-time inserts. • Native / systems: sort kernel-style intrusive lists by merging. • Embedded: insertion sort stays right for a dozen entries; just do not let n grow unbounded.
Watch out: qsort is not stable; if equal keys must keep config order, use a stable sort. "It only runs at startup" stops being true when users have 20,000 entries or reload often.
Seen in nginx: 35921283d 2007-05-21 `ngx_sort()` "implemented as insertion sort because we need stable sort"; used for locations (c02ed54c4) and upstream weights (7a8e33993, 2007-08-09). • 8634118bc 2008-03-23 Temp element moves from a fixed `buf[256]` to an allocation, removing an element-size cap. • bf7d76b94 2015-03-02 Consistent-hash ring built by linear fill + `ngx_qsort` + in-place dedupe instead of binary search + memmove per point: init for total weight 1000 drops from 5 s to 40 ms. • c93cb45ae 2023-10-18 `ngx_queue_sort()` changes from insertion sort to stable merge sort (split at `ngx_queue_middle()`, `ngx_queue_merge()`): 20k locations start in 0.9 s instead of 8 s.

### nginx-008 — Compile prefix-matching rules into a search tree at configuration time
Lens: algorithms · Source: nginx
Principle: Instead of testing a URI against every prefix rule in turn, sort the rules once and build a balanced tree in which longer prefixes nest under the shorter prefixes they extend.
Why it is faster: Linear matching costs O(N) string compares per request. The compiled tree costs about O(log N + prefix length). Precomputing where different rule kinds begin (for example, the first regex) also removes per-entry type checks from the loop.
Applies elsewhere: Web / backend: radix-tree routers (httprouter, find-my-way) instead of regex-per-route lists. • Native / systems: mount-point resolution, firewall/ACL rule compilation. • Data / databases: prefix lookups in KV stores.
Watch out: only static prefixes compile this way; regex rules still need a separate ordered pass, and the semantics of which rule wins must be preserved exactly.
Seen in nginx: c915106f2 2007-06-05 Precursor: precompute `regex_start` so the regex loop starts at the first regex location without testing `!regex` on each entry. • e55988c06 2008-05-24 "locations tree": `ngx_http_init_static_location_trees()` builds `ngx_http_location_tree_node_t {left, right, tree, exact, inclusive, len, name[1]}` after sorting with `ngx_queue_sort`; `ngx_http_core_find_static_location()` walks it.

### nginx-009 — Longest-prefix match: radix tree, or a direct-index first level plus short range lists
Lens: algorithms · Source: nginx · Also: Envoy
Principle: For IP or CIDR lookups, use a bitwise radix tree (cost bounded by key bits, not entry count), or index directly by the top bits into a table whose slots hold a few ranges over the low bits.
Why it is faster: A radix tree answers in at most 32 (or 128) steps regardless of how many networks are loaded. A two-level table answers in one array index plus a scan of a handful of 16-bit ranges, which is faster still and smaller than a flat table. Preallocating the hot top levels as one contiguous page keeps them cache-dense; storing NULL for empty first-level slots and ending each range list with a sentinel shrinks the index further.
Applies elsewhere: Web / backend: IP allow/deny and GeoIP/ASN lookups in API gateways. • Native / systems: software router FIBs (DIR-24-8 is the same two-level idea), eBPF LPM tries. • Data / databases: Unicode property tables and other two-stage sparse lookups; prefix indexes in KV stores. • Embedded: a two-level table in flash gives constant-time lookup with no pointer chasing.
Watch out: the two-level table wins only when ranges per slot stay short; skewed data can concentrate many ranges into a few slots. Preallocation math is easy to get wrong silently (nginx's was off for years).

### nginx-010 — Match hierarchical wildcards with per-label nested hashes, not regexes
Lens: algorithms · Source: nginx · Also: NATS
Principle: Split a dotted name into labels and look each label up in a nested hash, right to left for `*.example.com` and left to right for `www.example.*`; try exact, then head wildcard, then tail wildcard.
Why it is faster: Each step is an O(1) hash probe, so matching costs O(labels) no matter how many patterns exist; a list of regexes costs O(patterns × name length). Using the two low bits of the aligned value pointer to flag "this is a sub-table" and "the bare domain also matches" avoids a wider node struct. The build step depends on a collation where the separator sorts before every other character, or children get split from their parent.
Applies elsewhere: Web / backend: TLS SNI certificate selection, cookie-domain matching, virtual-host routing. • Native / systems: DNS zone lookups; MQTT `+`/`#` topic routing via per-level tables. • Data / databases: LSM key encodings for hierarchical range scans need the same "separator sorts lowest" rule.
Watch out: pointer tagging requires guaranteed alignment of every stored value. The sort-order bug shows that build-time collation is part of correctness; test sibling names like `domain-some`.

### nginx-011 — Spread weighted picks evenly with smooth weighted round-robin
Lens: algorithms · Source: nginx
Principle: Give each candidate a running score: on each pick add every candidate's weight to its score, choose the highest, and subtract the total weight from the winner. Picks interleave in proportion to weight with no bursts and no precomputed schedule.
Why it is faster: Naive weighted rotation sends consecutive bursts to heavy servers, which spikes their queues and latency. The smooth version needs O(1) state per peer and O(n) work per pick, and an "effective weight" lowered on failures lets a sick peer recover gradually instead of oscillating.
Applies elsewhere: Web / backend: client-side load balancing (gRPC, Envoy), weighted feature rollout or ad-slot interleaving. • Native / systems: weighted packet or queue schedulers. • Embedded: weighted time-slicing of tasks with integer arithmetic only. • Data / databases: read-replica routing by capacity.
Watch out: O(n) per pick is fine for tens of peers, not thousands; it is also blind to actual load, so pair it with load-aware selection when request costs vary.
Seen in nginx: 52327e062 2012-05-14 `ngx_http_upstream_get_peer()` rewritten with `current_weight` and `effective_weight`; weights {5,1,1} now give `a a b a c a a` instead of `c b a a a a a`.

### nginx-012 — Pick the least-loaded backend using cheap counters and a moving average
Lens: algorithms · Source: nginx · Also: H2O
Principle: Route each request to the candidate with the fewest in-flight requests (weighted), or with the lowest exponentially weighted moving average of latency times connections; break ties with round-robin.
Why it is faster: Blind rotation keeps sending work to a slow or overloaded server. A per-peer in-flight counter adapts instantly to uneven request costs; an EWMA (`avg = v*0.05 + avg*0.95`) needs one number per peer, smooths noise, and in-flight counting catches hung servers whose average has not yet moved.

### nginx-013 — Place keys with consistent hashing and a well-mixed hash, and bound the retries
Lens: algorithms · Source: nginx
Principle: Map keys onto a ring of virtual points per server so that adding or removing a server moves only about 1/N of keys; use a hash with good distribution; cap how many points a lookup may try before falling back.
Why it is faster: Keeping a key on the same backend keeps that backend's caches warm, which is worth far more than balancing precision. Poor hash mixing (CRC32 on structured keys) skews splits. When most peers are down, an uncapped walk over ring points degrades badly, so attempts must be bounded and cheap rejections checked first.
Applies elsewhere: Web / backend: sticky routing to cache shards, A/B bucketing with a good hash (Murmur, xxHash). • Data / databases: Dynamo/Cassandra-style partitioning; memcached client sharding. • Native / systems: open-addressing probe limits and bounded rejection sampling follow the same "cap the attempts" rule.
Watch out: placement must be identical on every node (endianness, hash seed, point count), or clients disagree. Too few virtual points gives uneven load; too many makes builds slow.

### nginx-014 — Search text by scanning for a cheap first signal, then confirming; skip ahead with shift tables
Lens: algorithms · Source: nginx · Also: Seastar
Principle: Most positions fail on the first character, so run a tight loop that only looks for the first (case-folded) byte and call the full compare on candidates; for multiple patterns, use Horspool-style shift tables, and in a stream hold back only bytes that could still start a match.
Why it is faster: The confirm step runs rarely, so the average cost approaches one compare per byte, and a `last` bound means the input never has to be copied just to NUL-terminate it. Shift tables let the scan jump by up to the pattern length per mismatch. In streaming filters, holding back a whole chunk "in case" adds latency; checking the tail against pattern prefixes releases bytes that cannot match.
Applies elsewhere: Web / backend: streaming HTML rewriters and log scrubbers; query-parameter scanners that work on slices. • Native / systems: `memchr` for the first byte then `memcmp`, the classic fast grep loop. • Embedded: pattern detection over ring buffers that cannot be NUL-terminated.

### nginx-016 — Rate-limit per key in constant memory with a salted, periodically reset bitmap
Lens: algorithms · Source: nginx

### nginx-017 — Find an unknown limit by doubling until failure, then binary search
Lens: algorithms · Source: nginx

Why it is faster: It converges in O(log n) probes without knowing the upper bound in advance, versus O(n) for linear stepping. Larger packets found this way mean fewer packets and less per-packet CPU.
Applies elsewhere: Web / backend: auto-tune batch sizes or the maximum payload an upstream accepts. • Data / databases: galloping search in merge joins and TimSort. • Embedded: find the largest reliable radio frame or flash write size at runtime.

### nginx-019 — Defer handlers to the end of the loop iteration so many triggers become one call
Lens: amortization · Source: nginx

### nginx-020 — Carry progress across calls instead of restarting from the beginning
Lens: amortization · Source: nginx · Also: PostgreSQL
Principle: Remember where the last call stopped (scan offset, tail pointer, insertion position, already-built key) on the object itself, so repeated or re-entered operations continue in O(new work) rather than O(total).
Why it is faster: Re-scanning a growing buffer for a delimiter on every read is O(n²) overall; remembering the offset makes it O(n). Appending to a chain by walking from the head is O(length); a cached tail is O(1). In a batch whose items all go to the same place in an ordered queue, finding the position once turns O(k·n) into O(n + k). Async handlers re-entered after each I/O completion should not rebuild setup they already did.
Applies elsewhere: Web / backend: line readers and header parsers over sockets; coroutine handlers storing computed values in their state struct. • Native / systems: rope or chunked-buffer builders and TCP reassembly queues with a tail cursor. • Data / databases: bulk loads appending to the same B-tree leaf through a cached cursor. • Embedded: terminal/escape-sequence parsers that keep their offset between UART interrupts.
Watch out: every cached cursor is a second source of truth; any operation that mutates the structure behind it (consume, reorder, free) must invalidate it.

Lens: laziness · Source: nginx

### nginx-034 — Shrink the objects you allocate per request or connection
Lens: memory-layout · Source: nginx · Also: Netty, Seastar
Principle: Any object that exists once per unit of concurrency should be as small as possible. Pack flags into adjacent bit-fields, drop fields you can derive, and move data used by only a few requests into side structures that are allocated only when needed.

Applies elsewhere: Web / backend: Keep request and context objects lean. Watch out: bit-fields cost a mask and shift on every access, and two threads must never write neighbouring bit-fields. Recomputing derived values pays off only if they are rarely read.

### nginx-047 — Keep a cursor past exhausted arena blocks

### nginx-055 — Match the arena to the data's lifetime; use throwaway scratch pools for transient work
Lens: allocation · Source: nginx
Principle: Allocate each piece of data from the arena whose lifetime matches it. Request data goes in the request pool, not the connection pool. ### nginx-058 — Exploit the bump pointer: reset instead of rebuild, grow in place when you are last

### nginx-089 — Put the common case first, and measure what "common" really is
Lens: cpu-microopt · Source: nginx
Principle: Order branches, switch cases and short-circuit conditions so the most frequent and cheapest-to-decide input exits first. Put a cheap exact-match fast path in front of the general slow path. Check your frequency assumptions against real traffic.
Why it is faster: The common input then runs the fewest instructions, and its branch is strongly biased, so the predictor gets it right almost every time. A fixed-length compare such as `strncmp(v, "gzip,", 5)` costs a few cycles. A case-insensitive substring scan costs a loop per byte. In `A || B || C` the right order minimises cost / probability of deciding. If the guess about frequency is wrong, the "optimisation" makes things slower, which nginx learned by backing one out.
Applies elsewhere: Web / backend: check the hottest route, content type or auth scheme with an exact compare before the generic matcher. In JS, order guards so monomorphic fast paths come first. • Embedded: in a protocol decoder, test the common opcode or frame type first. Use `likely()`/`unlikely()` where the compiler can't know the bias. • Native / systems: use profile-guided optimisation (PGO) or branch counters (`perf stat -e branch-misses`) to confirm which order wins. • Data / databases: evaluate the cheap, selective predicate of a hand-written filter first.
Watch out: the frequency that matters is the one at that point in the pipeline, and earlier stages may already have filtered the distribution. Measure first, and expect to revert. Fast paths that skip semantics are bugs, not optimisations (see `d2c0b9a6c` under "Help the compiler").

Watch out: this is endian- and alignment-sensitive, so keep the scalar fallback compiled and tested. For long inputs, real SIMD or a library `memchr`/`memcmp` will beat hand-rolled SWAR.

### nginx-094 — Keep inner loops tight: fuse passes over the same bytes and give the loop whole buffers

### nginx-097 — Pick the lookup-table size by cache footprint and input length
Lens: cpu-microopt · Source: nginx

Use hardware CRC (SSE4.2, ARMv8) when it is available. • Data / databases: per-row checksums on small tuples versus page-level checksums.
Watch out: microbenchmarks in a loop keep the big table hot and hide the effect. Benchmark with realistic interleaving of other work.

### nginx-098 — Detect the real cache-line size and align hot data to it
Lens: cpu-microopt · Source: nginx
Principle: Lay out hot tables, hash buckets and shared slots on cache-line boundaries, using the line size of the CPU you are actually running on (32, 64 or 128 bytes), with a sane compile-time default.
Why it is faster: A bucket that straddles two lines costs two misses instead of one. Data written by different cores on the same line causes false sharing. The right size depends on the CPU: Pentium 4 and Apple Silicon effectively use 128 bytes (the P4 prefetches adjacent line pairs), while most x86 and ARM cores use 64. ### nginx-099 — Prefer idioms that compile to fewer instructions
Lens: cpu-microopt · Source: nginx
Principle: Use native word-sized unsigned integers, count loops down to zero, test against the success value (usually 0), and use a library's own return codes instead of remapping them in a wrapper.
Why it is faster: A 32-bit `int` used as an index on a 64-bit target needs sign extension. A decrement sets the zero flag for free, so `while (n) {...; n--;}` drops an induction variable and a compare. `!= 0` is a `test`, while `== -1` needs an immediate compare, and the success test also catches every unexpected error code. A wrapper that only translates return codes costs a call plus a compare on every match, and as a macro it costs nothing. Each saving is a few bytes or cycles, but these idioms sit on paths executed per byte or per request.
Applies elsewhere: Native / systems: `size_t`/`usize` indices. Check `!= 0` / `if err != nil` style. Mark FFI shims `#[inline]` / `static inline`. • Embedded: count-down loops and native-width loop counters on 32-bit MCUs, where flash size is a hard budget. • Web / backend: in WASM hot loops, avoid mixing `i32` indices with 64-bit pointers.
Watch out: results depend on the ISA and compiler (nginx found `while (n--)` worse on x86). Verify in the generated assembly, and don't sacrifice clarity on cold code.

### nginx-101 — Use a fast keyed hash, not a CSPRNG, for non-secret unique IDs
Lens: cpu-microopt · Source: nginx

### nginx-103 — Tame the thundering herd on shared listen sockets, and hand balancing to the kernel when it can do it
Lens: concurrency · Source: nginx · Also: H2O
Principle: When many workers wait on one listening socket, make sure only one wakes per connection. Start with a user-space lock, then move to per-worker sockets (`SO_REUSEPORT`) or exclusive wakeups (`EPOLLEXCLUSIVE`). Re-measure, and remove the old lock when it starts doing harm.
Why it is faster: Without coordination every worker wakes for every connection. N-1 of them lose the `accept()` race and wasted a context switch, and all contend on the socket's single in-kernel queue lock. A shared-memory trylock means only the holder polls the listen fds. Draining several accepts per wakeup amortises the wakeup. `SO_REUSEPORT` gives each worker its own queue, hashed by the kernel, which removes both the herd and the shared lock. `EPOLLEXCLUSIVE` wakes one waiter. Each kernel mechanism has its own bias, so balance across workers has to be measured, not assumed.
Applies elsewhere: Web / backend: `SO_REUSEPORT` in multi-process Node, Python (gunicorn `--reuse-port`) and Go servers. One UDP socket per core for DNS and QUIC. • Native / systems: `notify_one` instead of `notify_all` on job queues. Each worker gets its own queue instead of all sharing one. • Data / databases: background workers that each claim jobs from their own partition instead of all polling one table.
Watch out: `SO_REUSEPORT` hashing ignores worker load and drops queued connections when a socket closes during a reload. `EPOLLEXCLUSIVE` is biased toward the first waiter. A user-space mutex adds latency. Recheck old serialisation every time the OS improves.

### nginx-105 — Hold shared locks for the minimum: do slow work before or after, and acquire once
Lens: concurrency · Source: nginx
Principle: Inside a cross-worker critical section, do only the shared-state update. Serialisation, syscalls and per-connection setup go outside. Avoid releasing and re-taking the same lock in nested helpers.

### nginx-106 — Spin briefly with test-and-test-and-set and exponential pause, then sleep in the kernel
Lens: concurrency · Source: nginx · Also: jemalloc
Principle: Make the uncontended lock a single CAS. Under contention, first read the lock word plainly and spin with doubling `pause` counts, but only on multi-CPU machines. If it is still held, block on a kernel primitive and wake waiters only when there are any.
Why it is faster: Spinning on CAS writes the cache line and bounces it between cores. A plain read spins in the local cache until the line changes. `pause` saves power, frees resources for the hyperthread sibling and avoids a memory-order flush when the spin exits. Exponential back-off spreads retries. Spinning is pointless on one CPU, because the holder can't run while you spin. `sched_yield()` both burns CPU and gives no wakeup guarantee, while a semaphore sleeps until the lock is released. Counting waiters inside the lock word lets unlock skip the syscall in the common case.
Applies elsewhere: Native / systems: adaptive mutexes (glibc `PTHREAD_MUTEX_ADAPTIVE_NP`, Rust `parking_lot`, WebKit `WTF::Lock`), futex-based locks, spin-then-park in JVM monitors. • Data / databases: InnoDB and Postgres LWLocks spin briefly before waiting. Cross-process locks in shared-memory caches. • Embedded: SMP RTOS mutexes that spin a bounded number of times before blocking. On single-core MCUs, never spin. • Web / backend: any hand-written CAS loop: read first, CAS second.
Watch out: pure spinlocks are dangerous when the holder can be preempted, for example in oversubscribed VMs or containers, so always have the sleep fallback. Tune the spin count to typical hold time: too long wastes CPU, too short pays for syscalls.

### nginx-109 — Get atomics from the compiler where possible, and keep hand-written ones tight
Lens: concurrency · Source: nginx

### nginx-110 — Give each independently written shared counter its own cache line

### nginx-111 — Keep readers lock-free: publish snapshots, and synchronise only when state must change

### nginx-115 — Move bytes kernel-to-kernel, and gather adjacent pieces into one call
Lens: io · Source: nginx · Also: H2O, Netty

Watch out: sendfile blocks on page-cache misses (see async disk I/O below) and does not mix with O_DIRECT. Kernels have quirks: size limits, extra work on empty optional arguments. Read the kernel source or traces before assuming a call is free.

### nginx-116 — Register interest once, and let batching and teardown absorb the rest
Lens: io · Source: nginx · Also: Netty, Tokio

A 1-bit generation tag in the user-data pointer detects events for an fd that an earlier handler in the same batch closed and reused, without any lookup.

Skip per-row deletes before dropping a temp table. • Embedded: keep peripheral interrupt enables armed and track state in flags instead of reprogramming registers on every transition.
Watch out: edge-triggered mode requires draining until EAGAIN (or knowing how much is pending), or the connection hangs forever. Skipping DEL on close is wrong when the fd is `dup()`ed or shared across processes, because epoll tracks the open file description, not the fd number.

### nginx-117 — Let readiness hints decide how many reads to make
Lens: io · Source: nginx
Principle: The poller often already knows how many bytes are pending, whether the peer has half-closed, or that EOF is waiting. Use that to drain fully in one wakeup, to stop as soon as the pending data is consumed, and to skip a read whose only result would be 0 or EAGAIN.
Why it is faster: Without hints, the only way to learn that a socket is empty is a failed `recv()`, which costs one extra syscall per wakeup. Processing one message and returning to the loop costs extra loop iterations, and with edge triggering it can stall the connection. With a pending-bytes count you can read just past it, which re-arms the edge, and yield, so a fast peer cannot monopolize the worker. Ask for the count (FIONREAD) only after a full-buffer read. Small messages, the common case, then pay nothing extra.
Applies elsewhere: Web / backend: drain Node streams until `read()` returns null. Queue consumers can size batches from queue depth. • Embedded: read the UART/SPI FIFO-level register and drain exactly that many bytes, instead of polling byte by byte until empty.
Watch out: TLS and other user-space layers buffer data the kernel cannot see. Account for it, or the "nothing pending" decision is wrong. Querying the hint on every read costs more syscalls than it saves.

### nginx-118 — Bound the work one connection gets per loop turn, and yield without sleeping
Lens: io · Source: nginx · Also: Envoy, memcached
Principle: In a cooperative event loop, a single huge transfer can starve every other client. Cap the bytes moved per call for each connection, then requeue the rest to run after the next poll, not after a timer.
Why it is faster: One `sendfile()` to a fast client can move gigabytes while thousands of other connections wait. A per-call cap bounds tail latency for everyone else. Yielding through a 1 ms timer is not 1 ms: kernel tick granularity rounds it to 4 ms at HZ=250, which throttled links above 2.5 Gbps. Posting the event to run "after the next poll" gives the same fairness with no artificial sleep. Choose the cap from bandwidth-delay arithmetic: 2 MB is about 200 ms on 100 Mbps and 2 ms on 10 Gbps.
Applies elsewhere: Web / backend: in Node, chunk large writes and yield with `setImmediate`, not `setTimeout(0)`. Watch out: a cap that is too small multiplies syscalls and hurts single-stream throughput. Timer-based yields carry hidden granularity costs. Measure on the real kernel tick rate.

### nginx-119 — Never let disk I/O block the event loop
Lens: io · Source: nginx
Principle: Regular-file reads, opens of special files, and sendfile on cold pages can all block. Submit such operations asynchronously, or make the kernel fail fast instead of blocking, and deliver completions through a descriptor the loop already polls, so disk work looks like socket readiness.
Why it is faster: One page-cache miss stalls every connection on the worker for a disk seek (milliseconds). Native AIO signalling an eventfd keeps a single loop with no threads. Reaping up to 64 completions per `io_getevents` amortizes the syscall. With FreeBSD `SF_NODISKIO`, sendfile returns EBUSY instead of blocking. A 1-byte async read pulls the pages into cache, and the retry keeps zero-copy. If the async read completes synchronously, continue inline instead of taking another loop turn. An eventfd counter collapses N completion notifications into one wakeup.
Applies elsewhere: Native / systems: io_uring with a registered eventfd inside an existing epoll loop. IOCP on Windows. Use kernel-native non-blocking paths before reaching for thread-pool emulation. • Web / backend: no synchronous `fs` or DNS calls on the Node/asyncio loop. Warm caches with `posix_fadvise(WILLNEED)` before serving. • Data / databases: async I/O threads or io_uring for page reads. Size AIO and ring reservations to the device, not to "big just in case". • Embedded: have DMA-complete interrupts post to the main-loop queue instead of busy-waiting on flash.
Watch out: Linux native AIO is only truly async with O_DIRECT. Up-front kernel reservations multiply across processes and hit system limits. When the kernel gains a native path, delete the workaround.

### nginx-120 — Detect a capability once, fall back fast, and retry transient failures only a bounded number of times
Lens: io · Source: nginx
Principle: Fast paths (new syscalls, offloads, non-blocking modes) are not always present or working. Remember permanent unavailability in a sticky flag so later calls skip the failing attempt. Treat temporary failure as worth a few retries before degrading, and make risky offloads opt-in when detection is unreliable.
Why it is faster: Without a sticky flag, every call pays one failing syscall (ENOSYS) before the fallback. Falling back on the first transient error (EBUSY, EAGAIN) degrades to the slow synchronous path needlessly. Retrying forever risks livelock. Allowing two or three failures without progress balances the two.
Applies elsewhere: Native / systems: probe `copy_file_range`/`splice`/io_uring once and cache the result. Use cached CPUID for SIMD dispatch. • Web / backend: WebGPU-to-WebGL or HTTP/3-to-HTTP/2 fallback after N failures, remembered per origin. • Data / databases: escalate a lock-free CAS loop to a mutex after N failed attempts. • Embedded: detect optional peripherals at boot and branch once, not on every access.
Watch out: a sticky "unavailable" flag is wrong when the capability can appear later (module load, container migration). Detection can succeed while the feature is broken, so offer a manual off switch.

### nginx-121 — Use the one syscall that does exactly what you need
Lens: io · Source: nginx · Also: Netty
Principle: Many operations are written as two syscalls, or as a heavier call than needed: open where stat would do, accept then fcntl, lseek then write, read-and-buffer where a peek would do. Pick the combined or lighter variant.
Why it is faster: Each avoided syscall saves a kernel crossing. A heavier call also brings side costs: `open()` allocates a descriptor and needs a later `close()`, `lseek`+`writev` races on a shared file offset, and reading bytes you only wanted to inspect forces a buffering shim in front of the real consumer. `readdir` often already returns the entry type, which saves a stat for each entry.
Applies elsewhere: Native / systems: `O_CLOEXEC`/`SOCK_CLOEXEC`/`pipe2`, `pread`/`preadv`, and `getdents64` with `d_type`. • Web / backend: `fs.stat` for try-files probes, `readdir({withFileTypes})`/`os.scandir`, and protocol sniffing with peek on a shared port. • Data / databases: WAL writers using positional vectored writes. DB proxies that peek at the startup packet before handing the socket over. • Embedded: peripheral drivers using combined status-and-data reads where the hardware offers them.
Watch out: combined calls are not portable everywhere (see the fallback entry). `d_type` can be `DT_UNKNOWN`. A peek must be followed by a real consume, or edge-triggered loops stop waking.

### nginx-122 — Tell the kernel how you will use file data: bypass the cache or prefetch
Lens: io · Source: nginx
Principle: The page cache assumes reuse and modest sequential reads. For huge files read once, bypass it so it keeps serving hot small files. For large sequential reads, ask for a bigger read-ahead window. Respect the alignment rules that bypassing requires.
Why it is faster: Streaming a multi-GB video through the page cache evicts thousands of hot small files, and the next requests for them go to disk. O_DIRECT also removes a copy. Read-ahead hints turn many small seeks into fewer large reads. The costs: O_DIRECT needs block-aligned buffers and offsets, so unaligned head and tail parts must be handled separately, and it cannot be combined with sendfile. A hint syscall on a small file costs more than it saves, hence a size threshold.
Applies elsewhere: Data / databases: engines with their own buffer pool use O_DIRECT (InnoDB, ScyllaDB). Full scans use `POSIX_FADV_SEQUENTIAL`, and backups use `POSIX_FADV_DONTNEED`. • Web / backend: media and object servers bypass the cache for big objects. ML data loaders stream shards with read-ahead. • Native / systems: query the device's logical block size (NVMe LBA) instead of hardcoding alignment.
Watch out: O_DIRECT makes repeated reads of the same file slower and every read synchronous. Wrong alignment fails with EINVAL or silently falls back on some filesystems. Hints are advisory and vary by kernel version.

### nginx-124 — Stream data through instead of store-and-forward, and skip the file when there is nothing to store

### nginx-125 — Reuse connections instead of paying a handshake per request

### nginx-126 — Skip or shorten handshakes: Fast Open, 0-RTT, resumable sessions
Lens: networking · Source: nginx · Also: Envoy, curl

### nginx-127 — Control segment boundaries: cork while composing, push at the message end
Lens: networking · Source: nginx
Principle: Small writes become small packets, and Nagle combined with delayed ACK can hold the last small packet for tens of milliseconds. Hold output (cork, or a send threshold) while a response is being assembled so packets go out full. At a logical boundary (end of response, control frame, handshake flight), push explicitly. Cache socket-option state so each option changes only when needed.
Why it is faster: A 200-byte header sent before the file data costs an extra packet, and a lonely tail segment can wait about 40 to 200 ms for an ACK. Corking emits full MSS segments, and setting NODELAY at the boundary flushes the tail at once. `TCP_CORK` and `TCP_NODELAY` are mutually exclusive on Linux, so one must be cleared before the other is set. Remembering the current state avoids a setsockopt per write. The tradeoff: corking adds latency when the next write never comes, so always uncork at boundaries.
Applies elsewhere: Web / backend: RPC frameworks cork (or `MSG_MORE`) while writing a frame and flush at its end. Redis-style servers flush once per pipeline batch. • Native / systems: set NODELAY on request/response sockets, and track socket-option state to avoid redundant setsockopt calls. • Embedded: on cellular or LoRa links, coalesce sensor readings into one segment, since each packet costs radio wake time.

### nginx-129 — Pack several protocol messages into one packet

### nginx-130 — Thin out acknowledgements and piggyback them on data
Lens: networking · Source: nginx

### nginx-131 — Grant flow-control credit ahead of need, and size windows from the bandwidth-delay product

### nginx-132 — Keep the congestion window honest, and probe for bigger packets
Lens: networking · Source: nginx
Principle: A user-space transport owns its own congestion control. Send only while bytes in flight are under the window, requeue frames the socket refused instead of counting them as sent, add no artificial delays, use a modern window-growth law, size thresholds dynamically, and discover the largest packet the path allows. On close, drop queued work and send the terminal signal at once.
Why it is faster: Treating EAGAIN as "sent" triggers spurious retransmits that shrink the window. A fixed reordering threshold of 3 declares false losses on high-BDP paths and collapses throughput. Growing the window while it is underused inflates it with no evidence. CUBIC recovers faster than Reno on long fat links. Bigger packets mean fewer packets and less per-packet CPU: double until the first failure, then binary search, which takes O(log n) probes. Flushing a queue the peer will discard only delays the close.
Applies elsewhere: Native / systems: game netcode, WebRTC and custom UDP file transfer need the same honesty about EAGAIN and in-flight accounting. • Web / backend: adaptive concurrency limiters (AIMD or CUBIC-like) for RPC clients. Probe the largest accepted batch or payload size by doubling then bisecting. • Embedded: radio stacks must requeue on a full TX FIFO, not drop and later retransmit.
Watch out: RFC defaults (reorder threshold 3) are tuned for typical paths, so measure on high-BDP links. MTU probes must neither shrink the window when lost nor be gated by it.

### nginx-141 — Publish files atomically by writing a temp file next to the target and renaming
Lens: storage-engine · Source: nginx

### nginx-142 — Carry warm state across reloads and binary upgrades instead of rebuilding cold

### nginx-143 — Batch durable writes, bound their staleness with a timer, and compress them
Lens: storage-engine · Source: nginx
Principle: Append records to a memory buffer and write it out in large chunks. Arm a timer when the first record enters an empty buffer so no record waits longer than T. Compress each flushed chunk when I/O, not CPU, is the bottleneck. After a disk-full error, skip writes for a while instead of retrying on every record.
Why it is faster: One `write()` per log line costs a syscall per request. A 64 KB buffer amortizes it over hundreds of lines. The timer bounds data loss and staleness on quiet servers. Text logs compress 5 to 10x, which cuts disk bandwidth and storage, and compression works better on large batches. On FreeBSD with softupdates, each write to a full disk can block for a long time, so retrying per request turns one fault into an outage. Compile formats into op arrays and compute line length first, so formatting into the buffer never reallocates. Share one buffer per file across directives.
Applies elsewhere: Web / backend: structured loggers with precompiled templates and async buffered sinks (zap, spdlog), and telemetry exporters with batch size plus linger time. • Data / databases: group commit (flush the WAL every N ms or N bytes), Kafka producer `linger.ms`/`batch.size`, and block compression in RocksDB and InnoDB. • Embedded: write flash in whole pages with a maximum-delay timer, and back off on write errors to save wear.
Watch out: buffered records are lost on crash, up to T seconds' worth, so do not buffer audit logs that must be durable. Concatenated gzip members need readers that support them. Flush on shutdown and on reopen (log rotation).
Seen in nginx: 02025fd6b 2005-01-18 Access-log format compiled into op arrays, with short literals packed into the pointer word and a `getlen()` pass before formatting (first appears in 0.1.14). • 697d1aea0 2005-10-27 `access_log ... buffer=`: flush only when the next line does not fit (first appears in 0.3.7). • 8a2b2fb4f 2006-04-14 `disk_full_time`: after ENOSPC, writes are skipped for the rest of that second. • fcdb4655a 2012-12-23 `flush=time`: a timer is armed when the first record goes into an empty buffer. 70d1a45c7 adds `gzip[=level]`, with each flush written as a separate gzip member. df71cd112 shares one buffer per log file instead of allocating one per directive. • f9b99baed 2014-08-25 The flush timer is cancelable, so it does not delay graceful shutdown.

### nginx-144 — Generate unique temp names from one shared atomic counter, with a random jump on collision
Lens: storage-engine · Source: nginx
Principle: When several processes create temp files in the same directories, per-process counters collide and each collision costs a failed `open(O_EXCL)` and a retry. Draw names from a single `fetch_add` counter in shared memory. On collision, advance by a random step to jump out of a crowded range.
Why it is faster: A lock-free atomic increment gives unique numbers across workers with no lock. Collisions then come only from leftover files (for example after a crash), and a random step seeded from time and pid escapes runs of them in a few tries instead of walking past each one.
Applies elsewhere: Native / systems: ID generation across forked workers, and ring-buffer slot claiming with `fetch_add`. • Data / databases: shard-local sequences plus random jitter for object-store key prefixes, avoiding hot partitions. • Web / backend: upload staging names in shared directories across processes.
Watch out: predictable temp names in world-writable directories are a security risk. Always use `O_EXCL` and private directories.
Seen in nginx: 3a5893593 2009-08-21 `ngx_next_temp_number()` became `ngx_atomic_fetch_add(ngx_temp_number, add)` with `add = collision ? ngx_random_number : 1`. The counter sits in its own cache line of the shared segment, and `ngx_random_number = (msec << 16) + pid`.

### nginx-145 — Treat each optimization as a hypothesis, and revert it when measurement disagrees
Lens: observability · Source: nginx
Principle: An optimization rests on assumptions about frequency, hardware, kernel behaviour or deployment. Recheck them after shipping and as the environment changes. Back out changes that turn out neutral, harmful or incorrect, including long-standing defaults.
Why it is faster: A branch reordered for a case that is rare at that point in the pipeline makes the common path slower. A user-space lock that the kernel has made redundant only adds latency and imbalance. A "faster" clock with 4 ms granularity breaks rate limiting while saving time that is negligible next to the rest of a loop iteration. Shortcuts that break semantics cost more than they save. Reverting restores both performance and correctness.
Applies elsewhere: Web / backend: put performance flags behind config switches so they can be turned off. Re-benchmark old workarounds after runtime upgrades (V8, JVM, Go). • Native / systems: after kernel upgrades, re-test user-space mitigations such as locks, sleeps and pre-reads. • Data / databases: query hints and index choices that were right for last year's data distribution. • Embedded: recheck hand-tuned timing loops when the toolchain or silicon revision changes.
Watch out: reverting on a single benchmark is as risky as adopting on one. Look at distributions and real deployments, and at correctness as well as speed.

### nginx-147 — Derive defaults from production data and arithmetic, not guesses
Lens: observability · Source: nginx · Also: curl
Principle: Defaults are what most deployments run. Set them from real traffic percentiles, from bandwidth-delay arithmetic, from observed allocation counts and from actual hardware needs, and write the reasoning into the change.

### nginx-148 — Expose the right per-request and per-resource metrics as cheap, loggable values
Lens: observability · Source: nginx
Principle: You cannot tune a cache, a network path or an allocator you cannot see. Expose outcomes (cache hit/miss/stale), timings, transport state (RTT, cwnd) and resource usage (free pages) as values computed only when logged, so operators can find the real bottleneck.
Why it is faster: Lazily evaluated variables cost nothing unless a log format uses them. A per-request cache status gives hit ratio and stampede behaviour directly. TCP_INFO separates client-network slowness from server slowness, so the right thing gets tuned. Connection request counters show whether keepalive reuse works. Allocator statistics show whether a shared zone is sized correctly.
Applies elsewhere: Web / backend: `X-Cache` and Server-Timing headers, Prometheus labels for cache outcomes, and TCP_INFO logging in gateways. • Data / databases: per-query buffer-hit statistics, and connection-reuse counters on pool dashboards. • Embedded: heap high-water marks and retry counters exported over a debug channel.
Watch out: high-cardinality labels can blow up metrics backends. Each metric query (a getsockopt call, for example) has a cost, so compute only on demand.

### nginx-149 — Keep diagnostics from becoming the bottleneck
Lens: observability · Source: nginx
Principle: Diagnostics must not change the behaviour they observe or amplify a fault. Log debug output into an in-memory ring buffer instead of disk. Rate-limit repeated error messages. Complain only about anomalies that matter. Make debug-only work (junk fills) opt-in.
Why it is faster: Debug logging to disk changes timing enough to hide heisenbugs and slows the server. A memory ring costs a memcpy and can be extracted from a core dump. When a resource fails (disk full, shm full), logging every failure produces a storm of syscalls and log lines on top of the failure itself. Logging once per minute or once per second keeps the signal and drops the cost.
Applies elsewhere: Web / backend: deduplicate exceptions in Sentry-style reporters, and use sampled debug logging. • Native / systems: flight recorders (JFR, the ftrace ring buffer), and per-thread lock-free trace rings. • Embedded: RAM trace buffers dumped on fault instead of UART printf in timing-critical code.
Watch out: a ring buffer overwrites old entries, so size it to cover the window of interest. Rate-limited logs hide the true error count, so keep a counter as well.

### nginx-150 — Shed load from a cheap, sampled resource metric
Lens: observability · Source: nginx
Principle: Under resource pressure, answer with a cheap response or a close instead of failing badly. Read the pressure metric at most once per time unit and cache it, so the check costs almost nothing per request.
Why it is faster: Out-of-memory failures in the middle of a request waste all the work done so far and can crash a worker. A 204 or a close costs almost nothing. Sampling the metric once per second (when the cached time changes) keeps a potentially costly query off the per-request path.
Applies elsewhere: Web / backend: brownout modes driven by per-tick RSS or GC heap samples, and serving lower-quality images under memory pressure. • Data / databases: reject new queries when buffer-pool free space falls below a watermark, sampled per tick. • Embedded: drop non-critical tasks when the free-heap sample crosses a threshold.
Watch out: `sbrk` does not reflect mmap-based allocators, so pick a metric that tracks the real resource. Sampling lag lets a burst overshoot.
Seen in nginx: 4985109db 2009-11-16 `ngx_http_degradation_module`: `sbrk(0)` heap size is recomputed only when `ngx_time()` changes. Above the threshold the handler returns 204 or 444 (close).
