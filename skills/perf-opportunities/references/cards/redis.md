### redis-001 — Do one lookup per logical operation, not two
Lens: algorithms · Source: Redis
Principle: "Check, then act" sequences (find then delete, add-fails-then-find, exists-then-insert) traverse the index twice. Make the primitive return the slot, entry or insertion link it found so the caller can act on it directly.
Why it is faster: Each lookup hashes the key and walks a chain or a tree path, which means dependent cache misses. Returning the position halves that work. In an incrementally rehashing table it also halves the rehash steps triggered. A further gain: build the stored key object only on the miss path, so updates allocate nothing. Redis measured 3-16% per command from individual fixes, and HSET updates got about 10% faster.
Applies elsewhere: Web / backend: In JS use one `map.get(k)` and branch on `undefined` instead of `has` then `get`. Use Java `computeIfAbsent`/`merge`. • Native / systems: Use C++ `try_emplace`, `insert_or_assign`, `extract()`; Rust `HashMap::entry()` and `raw_entry` with a precomputed hash. • Data / databases: Use `INSERT ... ON CONFLICT DO UPDATE` instead of SELECT then INSERT. A B-tree upsert should return the old value from the same descent.
Watch out: a returned link or position is only valid until the structure is next mutated, and that includes a rehash step or a node split. Use it right away, and never hold it across code that may insert.

### redis-002 — Keep a handle to your container node for O(1) removal
Lens: algorithms · Source: Redis
Principle: When an object belongs to a linked structure, store a pointer to its node in the object at insert time (or embed the links in the object itself). Removal is then an unlink, not a search.
Why it is faster: Removing by value from a list is O(N), and if every one of N members leaves, that is O(N²) in total: think disconnect storms or mass unsubscribes. A stored handle makes removal O(1). Embedding the links (an intrusive list) also saves a node allocation and a pointer hop per membership. The cost is one pointer per membership, plus discipline at every insertion site.
Applies elsewhere: Web / backend: Event emitters and pub/sub registries should return an unsubscribe handle that holds the node. An LRU map should keep a `Map<key, node>`. • Native / systems: Linux `list_head`, Boost.Intrusive, timer structs that embed their wheel links. • Embedded: Intrusive run queues and descriptor lists with no per-membership allocation.
Watch out: handles go stale when the node is freed or moved. Every path that unlinks must clear the handle. An object that sits in many lists pays one pointer per list.

### redis-003 — Replace linear scans with a hashed or sorted index
Lens: algorithms · Source: Redis
Principle: Any lookup by name or membership test that scans a list or array is O(N) per call. Index it once, with a hash or at least a sorted array plus binary search, and the per-call cost becomes O(1) or O(log N).
Why it is faster: These scans hide in dispatch tables, subscriber lists and dedup arrays. They are cheap at first and turn quadratic once both N and the call rate grow. A hash set costs a little memory: 65.4 MB went to 67.7 MB in the pub/sub case below, while a 5000-client teardown went from 23.7 s to 0.29 s. Also compare case-insensitively instead of lowercasing (copying) the input first.
Applies elsewhere: Web / backend: Use router tries or hash maps instead of regex lists. Store WebSocket room membership in a `Set`, not an array with `indexOf`+`splice`. • Embedded: Use perfect hashing (gperf) for fixed keyword or command sets. • Native / systems: Interpreters should intern method and opcode names once and dispatch by integer.
Watch out: for tiny N (under roughly 8-16 items) a contiguous scan beats hashing on cache behaviour. Index once the collection can grow or the call rate is high, not reflexively.
Seen in Redis: bb0b03a3d 2009-04-28 command parsing uses `strcasecmp` instead of `sdstolower()`+`strcmp`. • 1a132bbc9 2010-05-28 the command table is sorted once with qsort and searched with bsearch: O(log N) instead of O(N). 1b1f47c91 2010-11-03 switches to a case-insensitive hash table and caches hot entries (`server.delCommand`). • 2f87cf8b0 2012-12-02 blocking-pop keys are stored directly in a dict instead of an array plus a temporary dedup dict. • b51062497 2023-06-19 `client->pubsub_patterns` goes from a list to a dict, so PSUBSCRIBE/PUNSUBSCRIBE drop from O(N·M) to O(N). • c452e414a 2024-01-08 per-channel subscriber lists become no-value dicts keyed by client. ### redis-004 — Approximate exact policies by sampling: sampled LRU/LFU with a persistent candidate pool
Lens: algorithms · Source: Redis
Principle: Exact LRU needs a linked list that every access updates. Instead, stamp each object with a coarse access clock. At eviction time, sample a few random keys and evict the worst. Keep the best candidates found so far in a small sorted pool, so quality builds up across rounds.
Why it is faster: An access becomes a store into a field the object already has: no pointer updates, no list lock, no extra cache lines. Eviction costs O(samples). The pool makes the effective sample size grow over time, so 5 samples per round approach true LRU on power-law workloads. LFU uses the same machinery with an 8-bit logarithmic (Morris) counter that decays lazily when the key is touched, not in a sweep over all keys.
Applies elsewhere: Web / backend: Big in-process caches can keep a "last used tick" per entry and evict by sampling instead of using `LinkedHashMap`. Use Caffeine-style TinyLFU for frequency. • Data / databases: The CLOCK/second-chance algorithm in buffer pools. G1 picks the emptiest regions from a sample. • Embedded: Few-bit saturating log counters for hot-flow detection in switches and NICs.
Watch out: sampling gives a statistical, not exact, policy. Small sample sizes evict hot keys sometimes. Validate hit rate with a realistic (Zipfian) simulator, as Redis did, before shipping.
Seen in Redis: ef59a8bc9 2010-10-14 `estimateObjectIdleTime()` with a wrapping 22-bit clock. 165346ca2 2010-10-14 volatile/allkeys LRU, random and TTL policies, all sampling `maxmemory_samples` (default 3). a36879293 2010 makes the sample count configurable. • 22c9cfaf5 2014-03-20 adds a 16-entry eviction pool sorted by idle time that persists across calls. f4da796c5 2014-03-20 sets the default samples to 5. • bd128f796 2015-02-09 `redis-cli --lru-test`, a power-law workload simulator for measuring hit rate. • 382991f82 2016-07-11 removes a useless `memmove` from the pool loop. e423f76e7 2016-07-13 makes the pool global, with a `dbid` per entry, so choices span databases. • 5d07984c5 2016-07-15 LFU: a probabilistic log counter plus a 16-bit minutes stamp packed into the existing 24-bit LRU field (`LFU_INIT_VAL 5`). 6416ab19d 2016-07-18 LFU reuses the pool. 2d5eb1f1a 2016-07-20 volatile-ttl goes through the pool too. • 583c31472 2017-10-15 decay is computed on access. 06ca9d683 2017-11-27 decay is a plain decrement, because on a log counter halving popularity means subtracting one.

### redis-005 — Augment ordered indexes with counts for O(log N) rank, count and offset
Lens: algorithms · Source: Redis
Principle: Store at each link or inner node how many elements it skips (span or subtree count). Rank, "the k-th element", "how many in [a,b]" and "skip offset rows" then become one descent rather than a walk.
Why it is faster: Without counts, ZRANGE with a start offset, ZCOUNT and OFFSET-style pagination walk O(k) nodes, and every node is a cache miss. With spans, rank(x) is a sum along the search path: O(log N). Range count is rank(last) − rank(first) + 1. If a hash already points at the node, you can walk up from the node instead of searching from the root, with no key comparisons. Maintaining spans costs a little on every insert or delete.
Applies elsewhere: Web / backend: Leaderboards ("my rank", "page N"), virtualized lists with variable item heights (prefix sums). • Data / databases: Counted B-trees answer `COUNT(*) WHERE x BETWEEN` and OFFSET pagination without scanning. • Native / systems: Ropes in editors for line-number jumps, order-statistic trees with parent pointers.
Watch out: for small offsets a linear walk from the found node beats a rank jump (Redis keeps both). Counts must be updated on every structural change, so bugs show up as silently wrong ranks.
Seen in Redis: 6b47e12ef 2009-10-23 introduces the skiplist for sorted sets. 9d60e6e46 2009-10-26 adds the member as a secondary key in the descent, so delete with M equal scores is O(log N) rather than O(log N)+O(M). • 69d95c3e1 2010-03-03 span arrays and ZRANK. e74825c24 2010-03-04 `zslGetElementByRank()` replaces an O(start) walk in ZRANGE. edb519581 2010-03-04 checks first whether the start is trivially head or tail. • 62d774e5b 2011-10-03 ZCOUNT uses rank arithmetic on `zslFirstInRange`/`zslLastInRange` instead of iterating. • 996a64375 2013-02-25 `countKeysInSlot` uses the same O(log N) trick on the cluster slot→keys skiplist. • b26e8e321 2023-08-31 ZRANGE BYSCORE/BYLEX ... ### redis-006 — Pick the algorithm per call from cheap metadata (cost model, input ratio)
Lens: algorithms · Source: Redis
Principle: When competing algorithms win in different regions of the input space, estimate the cost of each from cardinalities you already know and dispatch per call. A single algorithm is usually terrible at one extreme.
Why it is faster: Choosing k of n elements by repeated random picks is fine for small k but becomes a coupon-collector blowup as k approaches n. In that case it is better to pick the n−k elements to keep. Set difference can check each element of A against the others (O(|A|·M), with early exit) or add-all-then-remove (O(total)), and the winner depends on sizes. A cheap estimate beforehand avoids the worst case at both ends.
Applies elsewhere: Data / databases: Query planners choosing hash vs nested-loop join; when a DELETE removes most rows, copy the survivors to a new table instead. • Web / backend: JS set difference should iterate the smaller side. Choose `filter` vs in-place `splice` by the fraction removed. • Native / systems: Introsort/pdqsort switching, galloping vs linear merge of posting lists by size ratio.
Watch out: each strategy is extra code to test, and the crossover constants are hardware-dependent. Measure them, and make sure every branch keeps the same output distribution (uniformity bugs are easy to introduce).
Seen in Redis: be90c803e 2012-09-19 SRANDMEMBER with a count has four strategies: negative count samples with replacement; count ≥ size returns everything; count near size copies the set and removes randoms; small count samples into a temporary dict. • f50e65845 2012-11-30 SDIFF compares `algo_one_work/2` against `algo_two_work`. With algorithm 1 it sorts the other sets by decreasing size so duplicates are hit sooner. • 288028876 2014-03-11 SPOP with count chooses Knuth selection sampling or Floyd's algorithm by ratio. 9feee428f 2015-02-10 reimplements it in three cases. The third, when most of the set is being popped, builds a new set from the survivors and swaps it in, and 300 lines of special code were deleted. • 62b1f3206 2021-02-07 HRANDFIELD/ZRANDMEMBER on a ziplist (no O(1) random access) use one-pass Algorithm S selection sampling for unique picks instead of repeated random access plus dedup.

### redis-007 — Partition the index along the dimension you query by
Lens: algorithms · Source: Redis
Principle: If a workload constantly asks "all items in partition P" (count, iterate, drop), give each partition its own structure instead of keeping one global index plus a secondary index by partition.
Why it is faster: A secondary index duplicates keys or adds per-entry links: memory, and work on every write. Per-partition tables make iterate, count and flush natural and O(partition), and remove the per-entry overhead. The new cost is aggregate queries over all partitions, which needs O(1) counters and the Fenwick tree described elsewhere. The evolution of Redis Cluster's slot→keys index shows the trade-offs at each step.
Applies elsewhere: Data / databases: Time- or tenant-partitioned tables. Drop a partition instead of running DELETE ... WHERE. • Web / backend: Per-tenant maps in a multi-tenant cache, so evicting a tenant is O(1) to unlink. • Native / systems: Per-core sharded hash maps, which also cut lock contention.
Watch out: many small tables carry fixed per-table overhead and make global operations (random key, total size, full scan) harder. Redis needed O(1) counters, a Fenwick tree and freeing of empty dicts to compensate.

### redis-008 — Index deadlines in time order and pop only the expired prefix
Lens: algorithms · Source: Redis
Principle: Instead of checking every waiter's timeout on each tick (O(N) per tick, limited to tick resolution), keep waiters in a structure ordered by deadline and remove entries from the front until the first one that has not expired.
Why it is faster: Work per tick becomes proportional to the number of expired items, not the population, and timeouts become precise. Encode the key as big-endian deadline + id so byte order equals time order. For millions of TTLs, bucketing by coarse time (about 1 s) with small linked segments per bucket amortizes tree modifications and costs one next-pointer per item. Stale entries can be cleaned up lazily at pop time.
Applies elsewhere: Web / backend: Session/TTL indexes and job schedulers on `(run_at, id)` indexes; Netty/Kafka hierarchical timing wheels. • Embedded: RTOS software-timer lists grouped by tick, so the ISR touches only due timers. • Native / systems: Event-loop timer heaps; Dijkstra with lazy stale-entry skipping.
Watch out: coarse buckets trade precision for amortization, so keep the exact deadline on the item. Lazy cleanup leaves dead entries in the index, which costs memory until they reach the front.
Seen in Redis: 324a8c91d 2020-03-26 precise blocking timeouts: a radix tree keyed by `htonu64(timeout)`+client id, walked from the start in `beforeSleep()`. At first it did no cleanup on unblock; stale entries were detected at expiry. aa9d92d94 2020-03-26 removes the per-client timeout check from `clientsCron`. • 077f96542 2020 returns at once when the tree is empty. 0e22cb268 2020 later removes the entry on unblock. • c18ff0566 2024-04-18 hash-field expiration adds `ebuckets`: a radix tree keyed by ms >> precision bits (about 1 s), with segments of up to `EB_SEG_MAX_ITEMS` per leaf and cyclic lists for O(1) removal. Small sets start as a plain list. It is two-level: fields within a hash, and hashes keyed by their minimum TTL. The exact TTL stays on the item for precise lazy expiry. c115c5230 2024-09-12 adds iteration.

### redis-009 — Accumulate unordered, then order once
Lens: algorithms · Source: Redis
Principle: When merging many keyed inputs into an ordered result, aggregate into a hash map first and build the ordered structure once at the end, pre-sized. Do not keep the ordered index up to date during accumulation.
Why it is faster: Maintaining order per update costs O(log N) with poor locality each time, and probing every other input per element is O(N²). Hash aggregation is O(1) per element. One final ordered build costs O(N log N) once. Storing the aggregate inline in the hash entry (a union with a double) avoids an allocation and a pointer hop per element. Some cases sped up by orders of magnitude.
Applies elsewhere: Data / databases: Hash aggregation for GROUP BY followed by ORDER BY. • Web / backend: Merge arrays into a `Map` and sort once instead of keeping a sorted array with splice inserts. • Native / systems: Log merging and histogram building.
Watch out: if only a few results are needed, a bounded heap or partial sort beats sorting everything. Peak memory holds the whole hash.
Seen in Redis: 119813e96 2014-06-06 ZUNIONSTORE reimplemented. The accumulator dict is pre-expanded to the largest input, scores are aggregated in place, then the dict is converted to a skiplist with the destination pre-sized ("in certain cases by many order of magnitude"). • d1cb6a0fc 2014-06-06 adds `double d` to the `dictEntry` value union for this. • 26ef28467 2024-09-25 ZUNION accumulates directly into the destination zset's dict, which removes the separate accumulator copy.

### redis-010 — Walk the big space once and group by key so expensive work runs once per key
Lens: algorithms · Source: Redis
Principle: "For each owner, scan every slot" or "for each subscriber, match its pattern" repeats work. Invert the loop: walk the large space once and group by owner, or group subscribers by unique pattern and evaluate each pattern once.
Why it is faster: O(owners × slots) becomes O(slots). N pattern matches across M distinct patterns become M matches followed by fan-out. This is the same reasoning as hash join versus nested-loop join.
Applies elsewhere: Web / backend: Webhook routers grouped by route regex, calendar views built by one pass over time slots. • Native / systems: CSS selector matching bucketed by rightmost selector, firewall rule deduplication. • Data / databases: Hash join over nested loops; bucket log lines in one pass into a map.
Watch out: grouping needs a side index that must stay in sync on subscribe and unsubscribe. Worth it only when duplication (N much larger than M) is real.
Seen in Redis: dfb12f062 2018-03-01 PUBLISH keeps `pubsub_patterns_dict` (pattern → clients) and calls `stringmatchlen` once per distinct pattern. • 9cb9f98d2 2021-01-14 CLUSTER NODES checks each slot's owner once instead of once per node. • 5b48d9004 2021-03-12 CLUSTER SLOTS walks `slots[0..16384]` once, emitting a range each time the owner changes.

### redis-011 — Turn per-element edits of packed arrays into one batched pass
Lens: algorithms · Source: Redis
Principle: In a contiguous packed array every insert or resize moves the tail. Doing k edits one at a time costs k tail moves (O(k·n)). Compute the total size change first, resize once, then move each record exactly once, or append a deduplicated batch in one go.
Why it is faster: Quadratic memmove and realloc chains become a single realloc plus linear work. For builds that also deduplicate (each insert scans for an existing key), a temporary hash from key to slot turns an O(n²) build into O(n). Use the batched path only above a measured crossover point, because the setup costs something.
Applies elsewhere: Web / backend: One `splice` with all items instead of repeated inserts. Batch DOM insertion with a DocumentFragment. • Data / databases: Sort and bulk-build an index instead of inserting row by row. Rewrite varint columns in two passes when widths change. • Embedded: Gap-buffer or line-table updates in editors and packed config blobs.
Watch out: batching adds a second code path. For one or two elements the simple path is faster, so gate on measured size.

### redis-012 — Sort only the window you return (partial sort / top-K)
Lens: algorithms · Source: Redis
Principle: When only elements [start, end] of the sorted output are needed, use a partial quicksort or selection that recurses only into partitions overlapping the window.
Why it is faster: Cost drops from O(N log N) to roughly O(N + k log k), which is a big saving when k is much smaller than N (LIMIT, COUNT). Redis saw 5-20% on GEOSEARCH depending on density, and more on SORT ... LIMIT over big inputs.
Applies elsewhere: Web / backend: In JS, take top-k with a bounded heap or quickselect instead of `arr.sort().slice(0,k)`. • Native / systems: C++ `std::partial_sort`/`nth_element`, Rust `select_nth_unstable`. • Data / databases: Top-N heapsort nodes for `ORDER BY ... LIMIT`.
Watch out: quicksort-family partial sorts inherit quicksort's worst cases. Redis had to remove an insertion-sort shortcut from `pqsort` (see the robust worst-case entry).
Seen in Redis: 75fd597da 2009-05-19 adds `pqsort.c`. 5f5b9840c 2009-05-19 SORT uses it when BY and LIMIT are both present. • a3718cde0 2021-02-02 sorted GEORADIUS/GEOSEARCH with COUNT calls `pqsort(..., 0, returned_items-1)` instead of a full qsort.

### redis-013 — Sample from a hash table in contiguous batches, not by independent random probes
Lens: algorithms · Source: Redis
Principle: If you need N samples rather than perfectly uniform independent draws, jump to one random bucket and scan forward to collect N entries. To get fairer single picks, sample a small batch and choose uniformly within it.
Why it is faster: N independent probes cost N random cache misses and N RNG calls, plus wasted probes on empty buckets. A forward scan is sequential and prefetcher-friendly. Because it is cheaper, you can take more samples, which more than makes up for the lost independence. Cap the steps (count×10) and re-jump after long empty runs so sparse tables stay bounded. Separately, picking a random bucket and then a random chain element over-samples short chains, and choosing within a batch of 10-20 smooths that bias.
Applies elsewhere: Data / databases: Block sampling instead of row sampling for planner statistics (Postgres ANALYZE). • Web / backend: Approximate top-K or victim selection in caches; "power of K choices" load balancing. • Native / systems: GC victim selection from a contiguous region.
Watch out: adjacent buckets are correlated, so do not use batch sampling where statistical independence matters (security, unbiased estimates).
Seen in Redis: 5317f5e99 2014-03-20 adds `dictGetRandomKeys()`. c641b670c 2014-03-20 eviction switches to it: quality "degradates a bit" but more samples make it "overall a win". • 5792a217f 2015-02-06 `dictGetSomeKeys()`: duplicates allowed, `maxsteps = count*10`, re-jump after long empty stretches. 8696874d7 2015-02-06 removes the per-key fallback. • 61a01793e 2019-02-18 `dictGetFairRandomKey()` takes a batch via `dictGetSomeKeys` and picks one uniformly. 1613f7a57 2019 and 25b392f90 2019 tune the batch (10, then 20). 35ffbead5 2019 uses it for RANDOMKEY, SRANDMEMBER and SPOP.

### redis-014 — Stateless resumable iteration over a resizable hash table (reverse-binary cursor)
Lens: algorithms · Source: Redis
Principle: With power-of-two tables, a bucket index is `hash & mask`. Incrementing the cursor in bit-reversed order (high bits first) guarantees that growing or shrinking the table between calls never skips an element. The whole iteration state is one integer the client holds.
Why it is faster: Iterating a huge keyspace no longer blocks the server for O(N) (as KEYS did) and needs no server-side cursor memory, snapshot or lock. Each call does bounded work. The trade-off is possible duplicates, so callers must tolerate seeing an element twice.
Applies elsewhere: Web / backend: Paginate a huge in-memory map over an API without server-side cursors. • Native / systems: Resumable heap walks and incremental snapshotting of open-addressing tables. • Data / databases: Resumable crawls over sharded key spaces.
Watch out: after mass deletions a scan step can land on long empty stretches. Cap the empty buckets visited per call (Redis added `maxiterations` in 2014).
Seen in Redis: 7f490b197 2012-07-09 (merged 2013-10-25) `dictScan` and the SCAN command, an algorithm by Pieter Noordhuis. During rehash it iterates the smaller table and visits every expansion of the cursor in the larger one. 34c207227 2013-10-25 documents it. • b4048dfec 2013 and 8fc85a121 2013 return everything at once, with cursor 0, for small compact-encoded objects, where incremental scanning is pointless.

### redis-015 — Use cache-sized blocks of packed elements as nodes (unrolled lists, B+ trees)
Lens: algorithms · Source: Redis
Principle: Pointer-per-element structures (linked lists, skiplists) pay an allocation, pointers and a cache miss per element. Monolithic arrays pay O(n) middle inserts. A tree or list of bounded packed blocks gets locality and few allocations while keeping cheap edits.
Why it is faster: Each node fetch brings in dozens of elements, so you get one miss per block instead of one per element. Bound blocks by bytes rather than count so large elements do not create huge nodes. A purpose-built B+ tree can also delta-pack keys, keep subtree counts for rank, and replace a duplicate hash index with tiny tag-only slots. Node size is a measured space/time dial: smaller nodes speed up range scans, larger nodes save memory.

### redis-016 — Exploit the ordering in your real access pattern
Lens: algorithms · Source: Redis
Principle: Workloads are rarely uniform. Appends usually go to "now", inserts arrive in sorted order, and the newest waiter is most likely to be satisfied. Pick structures and iteration orders that make the common order hit the best case.

Applies elsewhere: Data / databases: Rightmost-leaf fast paths for monotonic keys (Postgres, InnoDB). Watch out: an adversary or an unusual workload can break the assumption. Keep correctness under any order and make sure the slow path is still acceptable.

### redis-025 — Grow capacity geometrically, never by a constant step
Lens: amortization · Source: Redis

### redis-050 — Use invariants to skip regions known to be empty

### redis-085 — Pre-size hash tables and pick the final representation when the size is known

### redis-116 — Break long dependency chains into independent streams
Lens: cpu-microopt · Source: Redis
Principle: If each loop iteration needs the previous iteration's result (one accumulator, one running CRC), the CPU runs one step at a time no matter how wide it is. Split the work into several independent chains, such as multiple accumulators, interleaved buffer segments or paired sums, and combine them at the end.
Why it is faster: An out-of-order core can overlap independent operations, but not dependent ones. With a single chain, throughput is set by the latency of one operation (3-5 cycles for an FP add or a table load). With 2-4 chains it approaches the issue width. It also hides false dependencies such as POPCNT's output-register dependency on some Intel CPUs. Too many chains increase register pressure and front-end load: Redis measured 4 lanes beating 8 on ARM.
Applies elsewhere: Web / backend: Sum, min/max and dot-product loops in JS, Java or C# with 4 accumulators. Hash large uploads in chunks and combine (zlib `crc32_combine`, tree hashes like BLAKE3). • Embedded: DSP filters that process two channels interleaved to fill pipeline slots; slice-by-4 CRC on MCUs without CRC hardware. • Native / systems: Floating-point reductions in kernels and shaders; note that compilers will not reassociate FP sums for you without `-ffast-math`. • Data / databases: Aggregation operators in columnar engines with per-lane partial aggregates.
Watch out: Reassociating floating-point sums changes rounding slightly. Combining step costs (CRC combine math) mean the split only pays above a size cutoff (Redis: 128B for 2-way, 2KB for 3-way). Once the loop is memory-bound, more chains do nothing.

### redis-127 — Over-copy in fixed-size chunks inside a safety margin, then finish exactly
Lens: cpu-microopt · Source: Redis

### redis-135 — Interleave a batch of independent lookups, prefetching each step
Lens: cpu-microopt · Source: Redis
Principle: When you have many independent lookups, don't run them one after another. Turn each into a small state machine (bucket, entry, key, value), issue a prefetch for its next address, and move on to the next lookup in the batch. When you come back, the data has arrived.

This is software pipelining applied to data structures (the "group prefetching"/AMAC idea). It needs a batch: an upstream stage must expose several requests' keys before execution.
Applies elsewhere: Native / systems: `multi_get` on a C++/Rust hash map: hash all keys, prefetch all buckets, then probe in rounds. • Data / databases: Hash-join probe phases and index lookups in batches of 8-32 with group prefetching. • Web / backend: The same shape one level up: DataLoader-style batching resolves all of a request's keys at once instead of one round trip per key.
Watch out: No benefit when the working set fits in L1/L2 or the batch has one element; the state machine then only adds overhead. Too large a batch evicts its own prefetched lines before they are used. Prefetch is a hint: keep it a no-op on compilers or CPUs without it.

### redis-143 — Make shared counters progressively cheaper: atomics, relaxed ordering, per-thread slots, single writers
Lens: concurrency · Source: Redis
Principle: Statistics counters updated on every operation are a hidden contention point once threads exist. Use, in increasing order of payoff: an atomic instead of a mutex; relaxed memory ordering, since stats need no ordering; one slot per thread, summed on read; and plain load-add-store when each slot has a single writer.
Why it is faster: A mutex is two atomic operations plus possible sleeping. A sequentially consistent atomic adds full fences (expensive on POWER/ARM). Even a relaxed atomic RMW on a shared line makes that line bounce between cores. Per-thread slots remove the sharing, and single-writer slots remove the locked instruction. Reads become O(threads), which is fine when reads are rare.

### redis-145 — Hand work between threads in batches and wake the peer only when it is idle

### redis-153 — Buffer in user space so you make one syscall per block, not per field
Lens: io · Source: Redis

### redis-181 — Compact a log without buffering new writes twice

### redis-182 — Stream snapshots straight to the consumer, skipping the disk

### redis-183 — Have the snapshot child release memory it has finished with
Lens: storage-engine · Source: Redis
