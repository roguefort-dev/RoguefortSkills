### kafka-002 — Know the real cost of each collection operation
Lens: algorithms · Source: Kafka
Principle: Library calls that look O(1) or O(n) can be O(n·m) or O(n²) depending on the argument types. Check `removeAll`, `contains`, `size` and iterator removal before putting them in a loop.
Why it is faster: Java's `Set.removeAll(List)` may iterate the set and call `List.contains` for every element: O(n·m). `List.contains` in a loop is O(n·m). `ArrayList` iterator `remove()` shifts the tail each time: O(n²) to drain. `size()` on linked or concurrent structures may walk the whole thing. Replacing these with hash-set arguments, single-pass `removeIf`, a cursor, or `isEmpty()` restores linear or constant cost. The fixes are one-line and the gains are often three orders of magnitude.
Applies elsewhere: Web / backend: `array.includes` inside `array.filter` is O(n·m); build a `Set` first. Repeated `splice` to remove items is quadratic; use one `filter`. • Native / systems: `std::vector::erase` in a loop versus erase-remove idiom; Rust `retain`. Keep a length field on intrusive lists. • Data / databases: `NOT IN (subquery)` versus an anti-join with a hashed probe side; set difference with a hashed side. • Embedded: Ring-buffer read cursors instead of shifting an array after each consumed element.
Watch out: The cost of a call depends on the runtime types of its arguments, so a refactor that changes a `Set` into a `List` can silently reintroduce the quadratic. Benchmark at production cardinality, not with ten elements.

### kafka-003 — Maintain aggregates incrementally instead of recomputing them by scan
Lens: algorithms · Source: Kafka · Also: Pebble
Principle: If a count, sum or "do all items satisfy P?" is queried often, update it on every insert, update and remove. Each query then costs O(1) instead of O(n), and loading n items costs O(n) instead of O(n²).
Why it is faster: A query that scans the collection is fine when called once; when called on every event, heartbeat or metric read it multiplies by the event rate. A delta update on each mutation costs a few instructions. The mutation sites must all be covered, and the delta has to be applied under the same lock that guards the mutation so the counter never drifts.
Applies elsewhere: Web / backend: Keep `doneCount` next to a job list instead of `jobs.every(isDone)` on each poll; maintain a cart total rather than reducing the array on every render. • Native / systems: Per-arena byte counters in allocators; dirty-page counts per checkpoint epoch. • Data / databases: Incrementally maintained materialized views and per-partition row counts. • Embedded: Running sums for sensor averages instead of re-summing the sample buffer.
Watch out: One missed mutation path makes the counter wrong forever, so centralize mutations. When the underlying structure already has an O(1) size, drop the duplicate: 769882d910 2021-10-07 removed a manual size counter once the store used a `TreeMap`.
Seen in Kafka: c42726cdaf 2012-10-04 Caches `events.size` because `ListBuffer.size` "is a O(n) operation". • d97e63b260 2018-01-30 `InFlightRequests` keeps an `AtomicInteger` total instead of summing all per-node deques. • b01f8fb668 2018-08-06 `GroupMetadata` keeps `numMembersAwaitingJoin` and a supported-protocol count map, so `hasAllMembersJoined` and `candidateProtocols` no longer scan or intersect over all members on every JoinGroup. • 5b25d823af 2018-08-21 The offline-partition count is updated on state transitions instead of counted on every metric read. • f8078f3803 2019-08-13 `InMemoryKeyValueStore` tracks its own size because `ConcurrentSkipListMap.size()` walks the list. • 7867c24a40 2020-06-05 `preferredReplicaImbalanceCount` is updated from (previous, new) on each assignment or leadership change instead of a pass over all partitions after each controller event. • 96b1db510a 2022-12-07 Streams `ThreadCache` keeps an `AtomicLong sizeInBytes` adjusted by `new - old` inside each sub-cache's lock; every `put` used to sum over all sub-caches and slowed down as tasks were added. • a88fd01e74 2025-07-08 The Streams sticky assignor's `ProcessState` computes collections and aggregates at insertion time, making most accessors O(1): about 14x lower runtime on worst-case benchmarks. • c52095ac83 2026-11-11 Consumer and streams groups keep `numStableMembersByEpoch`; the group is reconciling when the count at the assignment epoch is below the member count. ### kafka-006 — Check, register on all keys, check again (not once per key)
Lens: algorithms · Source: Kafka
Principle: For an operation that waits on K keys, try to complete it once, register it on all K keys, then try once more. Rechecking after each registration costs O(K²); the two checks close the same race at O(K).
Why it is faster: The completion check usually scans all keys, so calling it after each of K registrations is quadratic. The race the per-key checks guard against (the condition becoming true between the first check and registration) is closed just as well by one final check after every registration is in place.
Applies elsewhere: Web / backend: Subscribing a waiter to many pub/sub channels or futures: subscribe to all, then recheck state once. • Native / systems: Multi-condition wait/notify and futex-style protocols (register, then re-test the predicate before sleeping).
Watch out: The final check is mandatory; dropping it reintroduces lost wake-ups.
Seen in Kafka: f5684366ef 2015-02-18 KAFKA-1952 "High CPU Usage in 0.8.2": `tryCompleteElseWatch` becomes `tryComplete()`, `watch` on all keys, `tryComplete()` again. The comment notes tryComplete's cost "is typically proportional to the number of keys".

### kafka-007 — Scan for expired items only when the earliest deadline could have passed
Lens: algorithms · Source: Kafka
Principle: Track the minimum expiry time (or keep items in expiry order) and look at candidates only once that minimum is due. An expiry check then costs O(1) per loop instead of a scan of everything.
Why it is faster: Naive expiry inspects every item on every tick or every input. If items are kept in access or time order, only the oldest can be expired, and if the earliest possible expiry is in the future, nothing at all needs checking. Rate-limiting the sweep adds a further bound when each check opens expensive resources such as storage iterators.
Applies elsewhere: Web / backend: Session or cache TTL sweeps that sleep until the soonest expiry instead of scanning every N ms. • Native / systems: Keep-alive timeouts in proxies with an LRU list; only the head can be stale. • Data / databases: Trigger tombstone compaction only when the oldest tombstone may be past the horizon.
Watch out: The tracked minimum must be updated when the oldest item is touched or removed, or the gate either fires constantly or never.
Seen in Kafka: 8eac7d789f 2014-09-20 Idle-connection reaping keeps an access-ordered `LinkedHashMap` plus `nextIdleCloseCheckTime`; `maybeCloseOldestConnection` examines only the first entry. • a095e1fd8c 2021-07-01 Stream-stream outer joins track `minTime` and `nextTimeToEmit` (1 s default interval) and open RocksDB iterators to emit non-joined records only when they may be old enough. Excessive iterator creation had made throughput very low.

### kafka-008 — Least-loaded selection: sort once for a single pass, use a heap for repeated picks
Lens: algorithms · Source: Kafka
Principle: Pick the structure by access pattern. If bins are filled in one pass, sort them once and walk the array. If the minimum must be re-picked after each load change, use a heap (pop, update, push) instead of a linear scan per pick.
Why it is faster: A scan for the minimum is O(n) per pick, O(n·k) for k picks. A heap makes each pick O(log n). But a balanced tree or heap maintained on every insertion costs a log factor plus node allocation per step, which a single sort followed by a linear walk avoids. Ordering the work so the heap stays valid (place sticky items first, then build the heap) lets it work even with exclusion constraints. Dropping a heuristic that kept global pair sets made room for the asymptotically better structure.
Applies elsewhere: Web / backend: Least-connections load balancing and job dispatch to the least-busy worker with a heap. • Native / systems: Schedulers and bin-packing (containers onto nodes); Dijkstra with a binary heap. • Data / databases: Shard rebalancing, assigning ranges to the least-loaded node.
Watch out: A heap is only correct if every load change re-sifts the affected entry; changing a load in place without reinserting corrupts the order. Always add an early exit for the already-balanced case.
Seen in Kafka: 017da21099 2024-10-17 Heterogeneous assignor: instead of TreeSets for least-loaded subscribers, sort an `ArrayList` once per topic and fill in order; the commit says this tested faster than priority queues. It also caps iterative rebalancing at a fixed number of rounds. • 29cf97b9ad 2025-07-14 Removes the global "task pairs" collection consulted on every standby placement, preparing the heap rewrite. • 6247fd9eb3 2025-09-03 Streams sticky task assignor uses a load-ordered heap; standbys go to previous owners first, then up to `NumStandbyReplicas` heap entries are popped to skip processes that already own the task. • 8628d74c49 2025-09-15 Adds a per-process heap of members, kept valid while only the top member's load changes: about another 2x on the worst benchmark. • b35ed0ec91 2026-10-16 uniform2 balancing: a max-heap of givers, parking givers with no current receiver; termination is guaranteed because each move lowers the sum of squares, and the step returns before building any state when sizes are already within one.

### kafka-009 — Closed-form quota assignment with a fast path for the homogeneous case
Lens: algorithms · Source: Kafka
Principle: When distributing P items over C owners, compute quotas directly (minQuota = P / C, extras = P mod C) and fill them in one pass, and detect the common case where every owner is eligible for the same items instead of running the general algorithm.
Why it is faster: General assignment algorithms that handle arbitrary eligibility and track every move can be super-linear. When all owners subscribe to the same items, a direct quota computation is linear and sticky enough (keep owned items up to quota, hand out the rest). Recomputing from a closed form can also beat incrementally maintaining move bookkeeping.
Applies elsewhere: Web / backend: Spreading jobs or shards over identical workers with a modulo/quota formula instead of a general matcher. • Native / systems: Static work partitioning across equal threads (OpenMP static schedule). • Data / databases: Range partitioning splits computed arithmetically; consistent-hash fast path when all nodes have equal weight.
Watch out: The fast path must be selected by an exact predicate; a heterogeneous input that slips through gets an invalid assignment.
Seen in Kafka: c6633a157e 2020-06-01 `AbstractStickyAssignor`: `allSubscriptionsEqual()` routes to `constrainedAssign`. 2000 consumers over 200 topics of 2000 partitions finish in seconds; trunk took 2 minutes on a problem 100x smaller. • 79225504ed 2021-05-06 `constrainedAssign` rewritten around minQuota/maxQuota counters and a sorted assigned list: the 1M-partition test went from about 2,600 ms to 1,400 ms. • 42f267a853 2024-07-04 Server-side `RangeAssignor` recomputes the target assignment each time from per-topic `minQuota`/`extraPartitions`; stickiness comes from static member ids. 10k members × 1000 topics: 37.9 ms.

### kafka-010 — Store per-group facts at the group, not per member
Lens: algorithms · Source: Kafka
Principle: If every member of a group shares the same attribute (all partitions of a topic share eligible consumers, all members with identical subscriptions behave the same), store it once per group and do the work once per group.
Why it is faster: Per-member copies of a group-level fact cost O(members × facts) memory and the same in time to build and update. Collapsing them to the group level divides both by the group size, which can be the difference between finishing and running out of memory.
Applies elsewhere: Web / backend: Role-based permissions instead of per-user copies of the same grants; per-room rather than per-socket fan-out lists. • Data / databases: Per-shard routing metadata instead of per-key; dictionary-encode repeated attribute sets. • Native / systems: Flyweight objects for shared configuration.
Watch out: When a member diverges from its group it must be split out cleanly, so keep the grouping key explicit.
Seen in Kafka: 6db51e4663 2021-06-03 `generalAssign` replaces `partition2AllPotentialConsumers` with `topic2AllPotentialConsumers`. 50 topics × 800 partitions × 800 consumers: 10 s to 100-200 ms; 1M partitions with 2,000 consumers no longer runs out of memory and finishes in 4-5 s. • 394688481c 2026-10-13 uniform2 groups members with identical subscriptions into "cohorts" so work is done once per cohort.

### kafka-011 — Sort once, then sweep or two-pointer walk
Lens: algorithms · Source: Kafka
Principle: Set differences and overlapping-interval merges become linear after one sort: walk two sorted lists with two pointers, or turn intervals into begin/end events and sweep them in order.
Why it is faster: Repeated set removals, or repeatedly searching for overlapping pairs and reinserting merged intervals, can be quadratic. An O(n log n) sort followed by an O(n) walk bounds the total, allocates little, and touches memory sequentially.
Applies elsewhere: Web / backend: Calendar free/busy merging; diffing two sorted id lists in a sync engine. • Native / systems: Coalescing byte-range locks or HTTP range requests. • Data / databases: Merge joins; building a skyline of overlapping range tombstones.
Watch out: End events at `last + 1` (half-open intervals) avoid off-by-one gaps; mixing closed and half-open ranges is the usual bug.
Seen in Kafka: 6db51e4663 2021-06-03 `getUnassignedPartitions` becomes a two-pointer walk over two sorted partition lists instead of set removals. • 46b4636d68 2026-06-15 `PersisterStateBatchCombiner` replaces TreeSet candidate-pair merging (worst-case quadratic) with (firstOffset, BEGIN)/(lastOffset+1, END) events, a counted TreeMap of active priorities, and coalescing of equal adjacent slices: O((n+k) log p).

### kafka-012 — Minimal-movement (sticky) assignment that reports "unchanged"
Lens: algorithms · Source: Kafka
Principle: When reassigning stateful work, keep each item with its previous owner whenever quotas allow and move only the excess. Return a flag when nothing moved so callers can reuse their existing output.
Why it is faster: Moving stateful work costs far more than computing a slightly less balanced assignment: state must be rebuilt or transferred. Minimizing movement minimizes that downstream cost. An explicit "unchanged" result also lets callers skip rebuilding maps and sets for members that did not change.
Applies elsewhere: Web / backend: Sticky sessions and consistent hashing so a scale event moves only 1/n of keys. • Data / databases: Shard relocation that prefers nodes holding a replica (Elasticsearch-style). • Native / systems: Thread or IRQ affinity kept across rebalances to preserve warm caches.
Watch out: Stickiness fights balance; cap how much imbalance stickiness may preserve, or skew accumulates over many rebalances.
Seen in Kafka: 0b48ea1c81 2017-01-31 Streams `StickyTaskAssignor`: prefer the previous owner, then a standby replica, then the least-loaded client. 0fba529608 2017-03-01 adds a rolling-bounce optimization. • d18f93f985 2026-10-22 `PartitionPlacement.place` keeps each owner's lowest-id partitions up to quota and returns false when every partition stays. • 9a61f5711c 2026-10-28 The uniform2 result reuses the maps and sets of members that do not change.

### kafka-013 — Remember a failed search and resume from a cursor
Lens: algorithms · Source: Kafka
Principle: In a placement loop that scans candidates for each item, cache "nothing matched at key K" together with a resume cursor, and rescan only when the selection key changes.
Why it is faster: Repeated full scans that are known to fail waste O(items × candidates). Remembering the negative result reduces the work to O(distinct keys × candidates).
Applies elsewhere: Native / systems: Next-fit allocators that remember the last free slot; schedulers caching "no runnable task at this priority". • Web / backend: Round-robin balancers that skip saturated backends without rescanning from the start.
Watch out: Invalidate the cached negative result whenever anything that could make a candidate eligible changes.
Seen in Kafka: 34753857d0 2026-11-18 `AssignRemainingExtraPartitions.nextMember` caches `lowestExtraPartitionsWithoutTopic` and `cursorWithoutTopic` per cohort, scanning twice per distinct count instead of twice per extra partition. 5,000 members / 10,000 partitions: 3.64 ms to 0.86 ms.

### kafka-014 — Fair, load-aware selection: weighted random over a cumulative table, per-destination cursors
Lens: algorithms · Source: Kafka
Principle: Choose the next target by weighted random selection where weights reflect inverse load (binary search over a cumulative-frequency array), and keep a separate round-robin cursor per destination so no item is starved.
Why it is faster: Plain round-robin ignores slow destinations and keeps feeding them. Weighting by queue depth steers load away from them. Building the cumulative table can piggyback on a loop that already visits every target, and the O(log N) pick happens rarely. A single shared start index over destinations with different list lengths can repeatedly skip the same items; per-destination cursors guarantee rotation.
Applies elsewhere: Web / backend: Load balancers picking backends by weighted random over inverse queue length; per-tenant round-robin in API gateways. • Native / systems: Per-worker cursors in work-stealing schedulers; disk striping weighted by device latency.
Watch out: Stale load stats cause herding onto the same "idle" target; refresh them at the same cadence as selection.
Seen in Kafka: f7db6031b8 2022-05-06 KIP-794 `BuiltInPartitioner.nextPartition()` does `Arrays.binarySearch` over a `cumulativeFrequencyTable` built from per-partition queue sizes collected inside `RecordAccumulator.ready()`, which already loops over all partitions; partitions with longer queues are picked less often. • 252e09501d 2022-04-21 A global `drainIndex` becomes `Map<String,Integer> nodesDrainIndex`, a cursor per node.

### kafka-015 — Match the access path to the question: point get, bounded range, range clear
Lens: algorithms · Source: Kafka
Principle: Use a point lookup when the exact key is known, clamp range scans to keys that exist, iterate a sorted range instead of doing a lookup per key, and remove a key range with one range operation.
Why it is faster: Range iterators carry setup and per-step overhead far above a single get. Probing a hash map for ids that cannot exist wastes lookups. Removing a sorted range key by key pays O(log n) per key, while clearing the submap view or issuing one range tombstone removes it in one operation.
Applies elsewhere: Web / backend: `GET` instead of `SCAN` in Redis when the key is known; delete by prefix through key design. • Data / databases: `DELETE ... WHERE k BETWEEN` and RocksDB `DeleteRange`; partition pruning bounded to partitions that exist. • Native / systems: Rust `BTreeMap::split_off`/`range` instead of per-key operations.
Watch out: Range bounds must be inclusive/exclusive exactly as intended; an off-by-one on a range clear silently deletes or keeps one extra entry.
Seen in Kafka: 146edd530a 2017-03-07 `Segments.segments(from, to)` clamps the id range to `[minSegmentId, maxSegmentId]` instead of probing a hash map for non-existent segments. • eb449fe7c5 2018-03-01 Adds `WindowStore.fetch(key, windowStart)`; window aggregates do one point fetch per matched window instead of a range iterator. 34a1f7099b 2018-04-25 uses it on cache flush. • 538bd7eddf 2019-03-19 Iterates `subMap(...).entrySet()` instead of a `get()` per key. • c116354908 2025-01-06 `SharePartition`: `cachedState.subMap(first, true, last, true).clear()` replaces a loop of `remove(key)`.

### kafka-017 — Size and resize hash tables correctly
Lens: algorithms · Source: Kafka
Principle: Compute capacity as `ceil(n / loadFactor)` rounded up to a power of two, start growing maps at a sensible minimum, and rehash by walking the old table into a new array rather than removing and reinserting.
Why it is faster: Capacity is not entry count: `new HashMap(n)` still rehashes before n entries. A sizing bug yields tables that are too small (long probe chains) or too large. In open addressing, removing each element from the old table during resize triggers backward-shift reseating of its probe run, which with clustered hashes makes resize quadratic; copying straight into the new array is linear.
Applies elsewhere: Native / systems: Custom open-addressing maps in game engines and embedded caches; Rust `HashMap::with_capacity`, Go `make(map[K]V, n)`. • Data / databases: Size hash-join tables from cardinality estimates; resize by sequential migration. • Embedded: Fixed power-of-two tables sized at build time from the maximum element count.
Watch out: Presizing from an untrusted or overestimated count wastes memory; cap it and let the table grow.
Seen in Kafka: f6884cc6dd 2021-03-18 `BaseHashTable.expectedSizeToCapacity` returned a log2 exponent instead of a capacity; it now rounds with `1L << -Long.numberOfLeadingZeros(i - 1)`. • 8ed535f41c 2026-10-06 Adds `Utils.newHashMap/newHashSet` with `ceil(n / 0.75)`; 3655d7c19c 2026-10-28 uses `max(size, 12)` for maps that start empty but will grow. • 5f17770e11 2026-11-11 `ImplicitLinkedHashCollection.changeCapacity` follows insertion links into the new array without `iter.remove()`: 100,000 consecutive int keys took about 17 s before and about 5 ms after.

### kafka-018 — Bound worst-case complexity before doing exact work on untrusted input
Lens: algorithms · Source: Kafka
Principle: Before running an algorithm whose cost depends on input shape (regex backtracking, arbitrary-precision conversion), add a cheap guard that caps the worst case.
Why it is faster: Average-case fast operations can be exponential or memory-explosive on crafted input: nested quantifiers over alternations backtrack exponentially, and converting `1e1000000000` to an exact integer materializes a gigantic number. Possessive quantifiers never give back characters, and a magnitude check rejects impossible values before exact arithmetic.
Applies elsewhere: Web / backend: ReDoS-safe validators (atomic groups, RE2); cap JSON bigint and number-string lengths before `BigInt`. • Native / systems: Check image dimensions or decompressed sizes before allocating. • Data / databases: Guard numeric casts in query engines against huge exponents.
Watch out: Possessive quantifiers change which strings match; re-test valid inputs, especially where a later token needed backtracking.
Seen in Kafka: d001b47093 2025-01-27 Connect `Values`: an `abs.compareTo(1e19)` guard returns before `toBigIntegerExact`, and whole-number detection uses scale checks instead of comparing scaled ceiling and floor. • b65cb2cac2 2026-11-12 SCRAM and OAuth patterns switch to possessive `++`/`*+` and a lookahead, bounding match time.

### kafka-019 — Integer, overflow-safe midpoint in binary search, with invariants preserved
Lens: algorithms · Source: Kafka
Principle: Compute the midpoint as `(lo + hi) >>> 1` (or `lo + ((hi - lo) >> 1)`): one add and one shift, no floating point, no overflow.
Why it is faster: Floating-point midpoints with `ceil` cost conversions on a hot path that runs on every index lookup. The unsigned shift handles the sum overflowing a signed int. Changing rounding direction, however, interacts with loop termination.
Applies elsewhere: Web / backend: JS binary searches with `(lo + hi) >>> 1`. • Embedded: Bisection over sorted tables in firmware without an FPU.
Watch out: A search that needs the upper midpoint (when `lo = mid`) must use `(lo + hi + 1) >>> 1`, or it never terminates.
Seen in Kafka: cf84f244e5 2019-11-16 `AbstractIndex`: `ceil(hi/2.0 + lo/2.0).toInt` becomes `(lo + hi) >>> 1`. ca7a5eae89 2019-11-17 fixes the infinite loop the new rounding direction caused in `indexSlotRangeFor`.

### kafka-023 — Stream, don't materialize, and stop as soon as the answer is known
Lens: laziness · Source: Kafka
Principle: Decompress, convert and iterate one record at a time through a streaming iterator, and close it once the search, budget or limit is satisfied instead of building the full result first.
Why it is faster: Materializing a whole decompressed batch or converted response costs peak memory proportional to its size and does all the work even when the consumer needs the first match. A streaming iterator holds one element, lets the caller stop early, and lets conversion overlap with sending.
Applies elsewhere: Web / backend: Pipe `zlib.createGunzip()` instead of `gunzipSync`; streaming JSON-to-CSV exports; generators for pagination. • Data / databases: Cursors instead of `fetchall()`; `LIMIT` pushed into the scan; top-k early termination. • Native / systems: Rust iterators instead of collecting a `Vec` between stages.
Watch out: Memoizing lazy sequences are not streams: b5f5be69ea 2015-12-08 replaced Scala `Stream.continually`, which retained every polled element, with `Iterator.continually`. Streaming iterators over native decompressors must be closed even on early exit.
Seen in Kafka: d2f50fc388 2015-03-26 `decompress()`, which built a whole message set, becomes `deepIterator` reading one record at a time from the codec stream. • a0b8e435c9 2017-03-28 The consumer walks batches with `streamingIterator` instead of first parsing every record into an `ArrayList`. • 90da94c384 2017-11-23 Down-conversion drops a `toList` pre-pass used only to check emptiness. 837f31dd18 2018-05-30 KIP-283 converts lazily in chunks during the network send, converting only the first batch up front to learn the size; this prevented broker OOMs. • 47888630a0 2019-03-06 In-memory window store fetch returns an iterator over `subMap(...)` instead of copying results into a list. • 0e46dd4a1d 2020-04-16 The log cleaner's offset-map build uses a streaming iterator. • fb529d8966 2024-04-22 Tiered-storage timestamp lookup uses a streaming iterator in try-with-resources and returns on the first matching record. • 71312a111e 2026-10-23 Share fetch computes the remaining record budget from data already fetched and skips the second log read when it is zero.

### kafka-024 — Pass bytes through untouched when nothing needs to change
Lens: laziness · Source: Kafka
Principle: If an intermediary does not need to alter a payload (same codec, offsets already assigned, no records removed), forward or rewrite only the envelope and copy the original bytes as-is, never decompressing and recompressing.
Why it is faster: Decompress-validate-recompress is the most expensive thing a broker can do per byte. Followers that trust leader-assigned offsets, brokers that keep the producer's codec, mirrors that forward compressed wrappers, and cleaners that copy a batch through when nothing was removed all avoid it, and preserve the original compression ratio too.
Applies elsewhere: Web / backend: CDNs and proxies forwarding origin `Content-Encoding`; image proxies skipping re-encode when format and size already match. • Data / databases: Replicas applying primary LSNs as-is; Parquet compaction copying unchanged row groups byte-for-byte. • Native / systems: Routers rewriting only TTL/checksum fields; delta sync skipping unchanged chunks.
Watch out: Passthrough means trusting the upstream: validation that is skipped must be guaranteed elsewhere (replication protocol, checksums at the outer level).

### kafka-027 — Skip no-op writes, empty items and repeated transitions; scope follow-up work to what changed

### kafka-053 — Send stored bytes without copying them through the application, and keep that path when adding layers

### kafka-058 — Size buffers to actual use: allocate lazily, grow in chunks, and shrink back after bursts
Lens: allocation · Source: Kafka
Principle: Do not reserve the worst-case size for every entity up front. Allocate on first real use, start small and grow, or chain fixed-size chunks. After a burst, give oversized buffers back instead of keeping them at peak size.

Applies elsewhere: Web / backend: Defer per-WebSocket or per-session state until the first message. Watch out: Growth costs copies, and chunked buffers complicate contiguous access and zero-copy sends. Lazy allocation moves the allocation cost, and any failure, to first use. Shrink thresholds need hysteresis, or steady workloads reallocate constantly.

### kafka-075 — Index append-only data sparsely: one small entry per N bytes, binary search, then a short forward scan
Lens: caching · Source: Kafka
Principle: Do not index every record. Add an entry only after every N bytes of data, store it compactly in a preallocated, memory-mapped file, binary-search it, then scan forward a bounded distance. Why it is faster: A sparse index is orders of magnitude smaller than the data, so it stays resident in memory and binary search touches few pages. ### kafka-076 — Carry the resolved physical position alongside a logical position, so later checks skip the lookup
Lens: caching · Source: Kafka

### kafka-078 — Make binary search cache-friendly when lookups cluster at the tail

Applies elsewhere: Web / backend: API gateway rate limits that return `Retry-After` computed from the deficit. • Native / systems: Traffic shaping; job admission control.
Watch out: A large burst allowance lets many clients spike together; size it against server capacity, not per client alone.
Seen in Kafka: b5f90daf13 2020-08-06 KIP-599 adds a `TokenBucket` stat for controller mutation quotas, with burst = samples x window x quota.

### kafka-171 — Keep log calls out of per-item loops: demote, hoist, log on transitions only
Lens: observability · Source: Kafka · Also: Envoy
Principle: Move logs that fire per request or per partition to TRACE or remove them, hoist level checks out of inner loops, log a state only when it changes, and do not print stack traces for expected retries.
Why it is faster: Even a disabled level check costs tens of nanoseconds and can walk filter chains; repeated per partition it adds up. Enabled INFO logs that print large structures on a heartbeat path cost real CPU at scale. A steady-state branch that logs every cycle produces both CPU cost and log noise.
Applies elsewhere: Web / backend: Edge-triggered alerts instead of level-triggered; sampled request logs instead of per-request INFO. • Embedded: Log state changes of a peripheral, not every poll of it. • Data / databases: Per-query debug logging behind a session flag rather than a global level.
Watch out: Demoting logs removes evidence during incidents; keep a cheap counter or metric for anything you demote.

### kafka-172 — Look up loggers once, never per request or per object
Lens: observability · Source: Kafka
Principle: Use static per-class loggers or create a logger once and pass it to the objects that need it.
Why it is faster: Logger factories (log4j2 in particular) perform context lookups and synchronization on each call. Calling them per fetch response, per handler instance or several times per method puts that cost on the hot path.
Applies elsewhere: Web / backend: Python `logging.getLogger(__name__)` at module scope; Node pino child loggers created once per module, not per request. • Native / systems: Build the zap or slog logger once in Go and pass it down.
Watch out: Per-request context (request ids) belongs in structured fields or MDC, not in a freshly created logger.

### kafka-173 — Make metric recording one cheap branch: check enablement once, reuse a timestamp, skip empty sensors and unused quota checks
Lens: observability · Source: Kafka
Principle: On hot paths, decide once whether a sensor records at all, pass one "now" down instead of reading the clock per record, skip sensors with no metrics, and bypass quota evaluation for sensors that never carry a quota.
Why it is faster: A generic `record()` that rechecks the recording level at each layer, reads the clock and evaluates quotas costs nanoseconds per call, multiplied by records per second. Most sensors have no quota and many have no metrics attached. Removing that work leaves the counter update itself.
Applies elsewhere: Web / backend: Cache `performance.now()` per tick; skip rate-limit evaluation for routes without limits; StatsD sampling. • Embedded: Compile out disabled counters; read the cycle counter once per loop. • Data / databases: Skip resource-governor checks for system queries.
Watch out: A reused timestamp is slightly stale; fine for rates and averages, not for latency of the individual operation.

### kafka-174 — Keep metric registries and hot counters free of contention and O(n) inserts
Lens: observability · Source: Kafka
Principle: Back a growing metric registry with a concurrent hash map, not copy-on-write; do get-or-create without a lock on the hit path; and use striped counters for metrics updated by many threads.
Why it is faster: Copy-on-write makes every new metric O(registry size), which becomes quadratic at tens of thousands of sensors. A synchronized getter serializes every reader forever, though creation is rare. A single atomic counter hammered by many threads bounces one cache line between cores.
Applies elsewhere: Web / backend: Prometheus client label children cached in concurrent maps; per-key counter creation without a global lock. • Native / systems: Per-CPU counters in kernels; sharded counters in Go metrics libraries.
Watch out: Striped counters make reads more expensive and slightly non-atomic; fine for metrics, wrong for counters that drive control decisions.
Seen in Kafka: 217eb90444 2015-10-29 KAFKA-2664: `Metrics.sensors`, `metrics` and `childrenSensors` move from `CopyOnWriteMap` to `ConcurrentHashMap`; afterwards 100k sensors register in 1.5 s and 500k in 14 s. • d9ee9c96dd 2024-05-25 Streams metered stores count open iterators with `LongAdder` instead of `AtomicInteger`, so query threads do not contend on a metric. • 8ae35c08fa 2026-04-18 `RequestMetrics.getOrCreateMeter` becomes double-checked. • 282eef9d05 2026-04-20 `Metrics.sensor(...)` overloads are no longer synchronized; the lock and re-check happen only on a miss.

### kafka-175 — Build descriptive metric metadata lazily, and do not create metrics for disabled features
Lens: observability · Source: Kafka

### kafka-176 — Bound the memory of metrics: expire idle sensors, shrink buffers, share strings
Lens: observability · Source: Kafka
Principle: Expire per-entity sensors after inactivity, size histogram buffers to the precision actually needed, and compute per-connection metric names once instead of per instance.
Why it is faster: Per-client or per-topic sensors accumulate without bound as entities come and go. Fixed-size histogram buffers and duplicated strings multiply by the number of instances. Smaller metric state means less heap, less GC and faster scrapes.
Applies elsewhere: Web / backend: Label-cardinality hygiene in Prometheus; TTL eviction of per-user rate-limiter state. • Embedded: Fixed small histograms with a few buckets instead of full latency arrays.
Watch out: Expiring a sensor resets its history; dashboards that read cumulative values see a drop when an entity returns.

### kafka-177 — Build a microbenchmark harness, and make sure benchmarks and load tools measure the system, not themselves
Lens: observability · Source: Kafka · Also: NATS
Principle: Give the project a standard benchmark module, keep setup work (key generation, payload creation) out of the timed loop, and check that the load generator is not the bottleneck.

### kafka-179 — Instrument the performance mechanisms you add
Lens: observability · Source: Kafka
Principle: When you add a buffer cache, a batching linger, an admission limit or a slow background step, expose its effect (effective linger, flush rate, blocked time, cache size, discards, duration) as a metric or log.
Why it is faster: Adaptive and bounded mechanisms behave differently under each load; without visibility operators cannot tell whether a limit is hit or a linger is helping, and tuning becomes guesswork. Cheap counters next to the mechanism turn later tuning into measurement.
Applies elsewhere: Web / backend: Export pool wait time, cache hit and eviction counts, and batch sizes alongside the features. • Data / databases: Report group-commit size and checkpoint duration. • Embedded: Keep overflow and drop counters for every bounded queue.
Watch out: The instrumentation itself must follow the rules above: no per-event allocation, no lookups on the hot path.
