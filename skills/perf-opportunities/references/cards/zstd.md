### zstd-001 — Replace search with a single-probe hash index
Lens: algorithms · Source: zstd
Principle: To find an earlier occurrence of the data at the cursor, hash a fixed-width prefix into a table that remembers only the last position per slot. One multiply, one load and one store replace any search.
Why it is faster: Cost per position becomes O(1) and branch-light: load N bytes as one word, multiply by a large odd constant, keep the top bits. Recall is lost (only the latest candidate per bucket survives, and collisions evict good entries), so this suits the fastest tiers. The key width N is the main knob: longer keys give fewer, better candidates and more misses on short repeats. zstd benchmarked 4 to 8 byte variants and made N a parameter.
Applies elsewhere: Web / backend: a "seen recently?" check in front of a cache or dedup step, keyed by a hash of the first bytes of a payload. • Data / databases: rsync-style chunk lookup or duplicate-substring detection during log ingestion. • Native / systems: JS or CSS minifiers detecting repeated tokens with a fixed-size table instead of a map of all occurrences.
Watch out: the table is lossy by design. Always verify a hit against the real data, and expect ratio to drop when the table is too small for the input.
Seen in zstd: 4856a00164 2015-01-24 Initial release: `ZSTD_hashPtr` hashes 7 bytes as `(read64(p) * prime7bytes) >> (56-HASH_LOG)`; commented-out 5/6/8-byte and Knuth 4-byte variants show the choice was measured. • 1f44b3f778 2015-11-05 Key width became a parameter (`hash4Ptr` to `hash7Ptr`). • 45dc35628c 2016-07-12 Added an 8-byte hash with its own prime for the long table of doubleFast.

### zstd-002 — Try the most recently successful answers before searching
Lens: algorithms · Source: zstd
Principle: Structured data repeats at the same distance or key again and again. Check the last few winning answers with one cheap compare each before running the general search, and let a hit raise the bar the search must beat.
Why it is faster: A hit costs one load and compare instead of a hash probe plus chain walk, and in zstd it is also cheaper to encode (no offset bits). Checking at `ip+1` catches the very common "one literal, then same distance" pattern. When the recent-answer check is folded into the main search, its best length becomes the threshold, so the expensive walk records fewer, longer candidates and can return immediately on a long hit.
Applies elsewhere: Web / backend: a router or authorization check that tries the last matched route or rule before scanning the full table. • Data / databases: delta encoding of time series that tries the previous delta first; column-aware compression of fixed-width records. • Native / systems: stride prediction in prefetchers; a tiny MRU memo in front of an expensive lookup, also used to prune branch-and-bound search.
Watch out: the recent-answer list must be updated exactly as the decoder or consumer updates it, or results diverge. Keep it very short; past 3-4 entries the extra compares cost more than they find.

### zstd-003 — Stop searching when the answer is good enough
Lens: algorithms · Source: zstd
Principle: Define a "sufficient" result and stop the search the moment a candidate reaches it. In a candidate loop ordered best-first, stop at the first candidate that fails to improve the result.
Why it is faster: Long matches are both easy to find and nearly impossible to beat meaningfully, so further search on them is wasted. A threshold bounds worst-case work on easy data while leaving hard data the full budget. Breaking on the first non-improvement turns a scan of all lengths into a scan of a few, trading a tiny quality loss for a large speed gain. Exposed as a parameter (`targetLength`), the threshold becomes a speed/ratio knob.
Applies elsewhere: Web / backend: fuzzy search or autocomplete that stops at a score threshold instead of ranking every candidate. • Data / databases: query optimizers that stop enumerating plans once one is under a cost bound. • Native / systems: beam search or motion estimation that exits when the residual is below a target.
Watch out: set the threshold per effort level. A fixed low threshold quietly caps quality at high levels, and "first non-improvement" assumes candidates are ordered so that later ones are unlikely to win.

### zstd-005 — Delay commitment by one step and compare estimated gain
Lens: algorithms · Source: zstd
Principle: Don't take the first acceptable candidate. Also evaluate the next one or two positions and keep the later choice if its estimated net gain is larger, using a cost formula that includes how expensive the choice is to encode.
Why it is faster: A greedy choice can block a better one that starts a byte later. One step of lookahead recovers most of that loss for roughly 2x the search work, far cheaper than a full optimal parse. The gain is scored with an integer approximation such as `5*length - log2(offset)`, so a slightly shorter match with a much nearer offset can win. One generic routine with a depth parameter serves greedy, lazy and lazy2.
Applies elsewhere: Web / backend: greedy tokenizers (BPE, longest-prefix routing) that check whether the next merge or route beats the current best. • Data / databases: schedulers that delay committing a job to a slot if the next slot scores better. • Native / systems: video motion search and edit-distance heuristics with one-step lookahead.
Watch out: compare measured quantities, not a speculative candidate's assumed length; zstd's doubleFast lost ratio until it measured both sides. The bias constants interact with the encoder's real costs and need re-tuning when the format or cost model changes.
Seen in zstd: be2010ea1b 2015-10-31 "Lazy strategy" compares the next match against `matchLength - highbit(offset)/4`. • 9b11b46f8a 2015-11-01 Switched to integer `ml*5 - highbit(offset)`; 3564487614 added a second lookahead step with a stronger bias. • 7a23179779 2015-11-21 Greedy, lazy and lazy2 merged into `ZSTD_compressBlock_lazy_generic(..., searchMethod, depth)`; b241e9deb7 applied the same cost test inside the binary-tree search. • 6326775166 2024-10-16 doubleFast: the short match's real length is computed first, and the long candidate at `ip+1` is taken only if it is actually longer. This saved about 75 KB on silesia.tar at level 3 for 0 to -1% speed; c2abfc5ba4 folded the range check into the same condition.

### zstd-006 — Forward dynamic programming over approximate prices, pruned hard
Lens: algorithms · Source: zstd
Principle: For the highest quality tier, treat parsing as a shortest path: relax `cost[pos+len] = min(cost[pos] + price(choice))` over every candidate at every position, then backtrack. Keep it affordable by pruning and by storing only back-pointers until a node is final.
Why it is faster: The DP finds better parses than any greedy rule, and the engineering makes it practical. The window is bounded (`ZSTD_OPT_NUM`), long matches end the window early, and derived per-node state (zstd's repeat-offset history) is computed once when a node becomes current instead of copied at every relaxation. Each copy at relaxation is per candidate edge; computing on arrival is per node. Representing nodes as "stretches" (literal count plus last match) lets non-monotone costs be handled exactly.
Applies elsewhere: Web / backend: text line breaking (Knuth-Plass) and tokenization that minimizes total encoded length (Viterbi). • Data / databases: optimal batching of writes or cost-based join ordering with an early cutoff. • Native / systems: Dijkstra or A* that stores parent pointers and rebuilds derived path state only for settled nodes.
Watch out: DP cost scales with candidates per position. Without a bounded window and an early exit on long matches, pathological inputs blow up. Prices are approximate, so a "more exact" DP can lose ratio when the price model is off.
Seen in zstd: c71568fd44 2016-01-30 First optimal parser, `ZSTD_compressBlock_opt_generic`: `opt[]`/`matches[]` arrays, repcodes probed first. • 87d4f3daa4 2016-03-02 The 4K-entry DP arrays moved from the stack into the context workspace. • 81fda0419e 2020-03-04 "Only update repcodes upon arrival": removed `ZSTD_updateRep` plus memcpy from the inner match loops and computes `opt[cur].rep` from its predecessor when `cur` is visited; 0f9882deb9 stopped recomputing repcodes while emitting, and 5f49578be7 stopped recomputing the initial literal price. • 4683667785 2024-01-31 Nodes stored as stretches with tables sized `ZSTD_OPT_NUM+2`, after exploratory versions de10f56be2 and 0166b2ba80 hurt some corpora. • d31018e223 2024-02-03 When a 1-literal run is priced below a 0-literal run, also evaluate "previous match + exactly 1 literal" (btultra only). A big win on regular 32-bit arrays and noise elsewhere; 8168a451e5 simplified it and 0055ce7a02 simplified backtracking.

### zstd-007 — Fix the cost model instead of compensating with heuristics
Lens: algorithms · Source: zstd
Principle: An optimizing search is only as good as its price function. Make prices reflect how the output will actually be encoded and consumed, then delete the fudge factors that were hiding modeling errors.
Why it is faster: A heuristic that hides a modeling error breaks whenever anything else changes, and it blocks further tuning. A correct model makes the search stable. It also lets the search skip work that the real encoding makes pointless: if literals will be stored raw, there is no need to maintain literal statistics at all.
Applies elsewhere: Data / databases: query optimizers whose cost model must know the real storage format (compressed vs uncompressed pages) instead of carrying per-query fudge factors. • Native / systems: compilers costing instruction selection per real target; rate-distortion optimization in encoders. • Web / backend: layout engines measuring text with the real font instead of corrected estimates.
Watch out: a more correct model can still lose on some corpora, since prices are estimates. Validate across a broad benchmark set before removing the old heuristic.
Seen in zstd: 0a0a212934 2017-11-28 Literal cost is now compared against match cost plus the cost of the implied zero-length literal run, which allowed removing a heuristic that "was actually compensating". Ratio moved within ±0.01, better on calgary and enwik7. • 3d7377b874 2019-02-15 `ZSTD_compressedLiterals()` gates literal-frequency updates and base prices on whether literals will be entropy-coded.

### zstd-008 — Bias the producer toward output that is cheap to consume
Lens: algorithms · Source: zstd
Principle: When data is produced once and consumed many times, add the consumer's cost to the producer's objective. Among near-equal choices, prefer the one that decodes faster, and relax the bias only in max-quality modes.
Why it is faster: Far references miss cache on decode, many short tokens cost per-token overhead, and barely compressed blocks cost decode time for almost no saving. Small price penalties on those choices barely change output size but cut consumer time and energy for every future read.
Applies elsewhere: Web / backend: CDN asset compression choosing settings by decode cost on client devices; bundlers preferring chunk splits that avoid extra round trips. • Data / databases: page formats favoring cheap-to-decode encodings for hot tables; delta chains preferring nearer base versions. • Embedded: encoders limiting features weak decoders handle slowly.
Watch out: only worth it when reads outnumber writes. For write-once, read-rarely data (backups), spend nothing on consumer bias.
Seen in zstd: e6da37c430 2017-11-19 `ZSTD_getPrice` adds `(offCode-19)*2` for large offset codes when `optLevel<2`, "favors small offset for decompression speed (improved cache efficiency)"; only btultra disables it. • e2c0e3d437 2018-05-25 Every match gets `BITCOST_MULTIPLIER / 5` extra to "favor less sequences, faster decompression speed". • 5f177f1c53 2018-05-25 `ZSTD_minGain()` keeps a block raw unless it saves about 1.5%, lowered to about 0.8% only for btultra. • a7fdceeccd 2018-05-25 With 4489daec09: the sequence count at which predefined entropy tables give way to dynamic ones depends on symbol type and strategy, so fast levels favor faster compression and decompression.

### zstd-009 — Hoist invariant cost terms and price incrementally
Lens: algorithms · Source: zstd
Principle: In a scoring function called millions of times, factor out terms that don't change, compute them once per batch or outer iteration, and extend partial sums instead of recomputing them. Keep such caches explicit and owned by the caller, or store values directly in the DP table.
Why it is faster: `Σ(log2 total - log2 f_i)` equals `n*log2 total - Σ log2 f_i`, so the log of the total is computed once instead of per symbol. The literal-run cost does not depend on the match length being tried, so it is computed once per position, not per length. A hidden cache inside a "get price" helper only works if callers ask in one order, which constrains later algorithm changes; storing the value in the DP cell is simpler and computes each cell once.
Applies elsewhere: Web / backend: search ranking with precomputed IDF (BM25) and per-query constants hoisted out of per-document scoring; pricing engines hoisting per-customer factors out of per-item loops. • Data / databases: DP kernels such as affine-gap edit distance keeping costs in-row instead of in a side memo. • Native / systems: text layout caching the width of a growing run; shader uniforms computed once on the CPU.
Watch out: implicit caches that depend on call order go stale silently when the algorithm changes. Prefer explicit state, and re-verify output after every refactor of the pricing code.
Seen in zstd: 0068be94d8 2016-02-15 Literal cost became `litLength * highbit(litSum)` minus per-literal terms. • b5a519f43c 2016-03-09 `log2litSum`, `log2litLengthSum` and so on cached once per statistics update. • f7d210b2e9 2016-04-11 Literal-run prices cached and extended by only the additional bytes. • 03f30d9dcb 2017-11-28 With b71405dc51: costs split into raw-literal, literal-length and match parts; `basePrice` computed once per position. b71405dc51 also replaced the hidden order-dependent cache with a caller-held `cachedLitPrice`, because the old design "forbids future parser with skipping capabilities". • e9d1987fd7 2017-11-27 The first fill of fresh DP slots assigns unconditionally, since "new < stored" always holds there. • 463a0fe38b 2018-05-29 Removed `cachedLiteralPrice_t` entirely; prices live in the optimal table. Slightly faster and, surprisingly, better ratio.

### zstd-010 — Start adaptive statistics from good priors, or from a throwaway first pass
Lens: algorithms · Source: zstd
Principle: An adaptive model that starts flat makes poor early decisions, and on small inputs it never converges. Seed it from known statistics (a dictionary, typical distributions), or run a quick discarded pass to gather them when quality matters most.
Why it is faster: Better early decisions mean better output at the same search effort. Seeding costs almost nothing. A two-pass approach doubles CPU on the first chunk, so it is gated to the top tier and to inputs large enough for statistics to matter; below a size threshold, predefined tables are used anyway and the first pass is skipped.
Applies elsewhere: Web / backend: warm-start recommendation or A/B estimators from a cohort prior; JIT tiering from persisted profiles. • Data / databases: sample a partition before choosing a join or external-sort splitters; seed a cache's frequency sketch from the previous run. • Native / systems: two-pass video encoding at the top preset only.
Watch out: a strong prior can mislead on data unlike the training set; renormalize it toward a modest weight so real statistics take over quickly. A full second pass is rarely worth it below the highest tier.
Seen in zstd: 338f738c24 2018-05-08 With 6a3c34aa58: dictionary entropy tables passed to the optimal parser; 1a26ec6e8d initializes frequencies from Huffman/FSE bit costs. • 2c26df0e13 2018-05-14 Removed static pricing: "always better to use dynamic prices albeit initialised from dictionary". • 134388ba6b 2018-05-17 Experimented with two passes on the first block (2.142 to 2.153 ratio on enwik7 level 20, CPU doubled), disabled in a8ddf1d370. • e9448cdf4c 2018-12-06 Shipped it as strategy btultra2 (`ZSTD_initStats_ultra()` rewinds and redoes the first block); 635783da12 disables it for inputs of 1024 bytes or less. • 27a8bbe265 2021-09-03 Baseline literal-length frequencies, then 23a9368c45 (offset codes) and 08ceda3dfc (`ZSTD_scaleStats` toward a target sum); 9e1b4828e5 floors literal price at 1 bit; 5434de01e2 handles small alphabets, giving the optimal 29-byte result for issue #3328.

### zstd-011 — Bound search effort with data-driven parameter tables
Lens: algorithms · Source: zstd
Principle: Cap worst-case work explicitly (candidates per position, table sizes, window) and keep the caps in tables indexed by effort level and input size class, so tuning is data rather than code. Enforce the search window exactly.
Why it is faster: A cap such as `1 << searchLog` candidates bounds per-position time on any input. Small inputs need different trade-offs than large ones, so a second index by size class picks smaller tables and shallower search. Computing the exact lowest valid index per position stops work on references that can never be used, which also improves ratio when the window is small.
Applies elsewhere: Web / backend: image or video encoder presets; search engines capping postings scanned per query. • Data / databases: vacuum or compaction aggressiveness tiers; query planners with effort budgets by query size. • Native / systems: sliding-window rate limiters that compute the exact cutoff instead of trusting bucket rotation.
Watch out: parameter tables go stale when the engine gets faster. Re-run the tuner after algorithm changes, or levels will no longer be monotone in speed and ratio.
Seen in zstd: be2010ea1b 2015-10-31 Introduced rows of `{windowLog, chainLog, hashLog, searchLog, searchLength, strategy}` and `maxSearches = 1 << searchLog`; paramgrill (fd9d6b8e2f) automated the parameter search. • a308259afa 2015-12-02 Extra tables for inputs of 128 KB or less and 16 KB or less; 0dbf2874ee is one of many retuning commits. • bc601bdc6d 2019-05-31 With 58adb1059f: `lowLimit = max(valid, current - maxDistance)` per position in btopt and greedy/lazy; enwik7 level 19 ratio improved 7.5-9.4% at windowLog 13-17. facbe8b2c2 centralized it as `ZSTD_getLowestMatchIndex()`.

### zstd-012 — Use several indexes at different key lengths
Lens: algorithms · Source: zstd
Principle: A long-key index gives few, high-quality candidates; a short-key index catches what the long one misses. Probe the long one first and fall back to the short one. Give very short keys their own small, short-range table instead of letting them pollute the main ones.
Why it is faster: Two single-probe lookups give most of the quality of a deeper search at close to single-probe cost. Short matches (3 bytes) only pay off at short distances, so indexing them in a small separate table avoids growing every table and keeps the main probes focused. Allocate the small table only when the configuration can use it.
Applies elsewhere: Web / backend: two-level caches (exact key, then prefix key); n-gram plagiarism detection (8-gram first, 4-gram fallback). • Data / databases: separate small indexes for short tokens (stop words, 2-grams) in search engines. • Native / systems: multi-resolution spatial hashing; size-class special cases for small objects in allocators.
Watch out: every extra table costs memory and an insert per position. Check that the fallback actually finds enough extra matches to pay for its maintenance.
Seen in zstd: 45dc35628c 2016-07-12 doubleFast: `hashLong` (8-byte keys) and `hashSmall` (4-6 byte keys), both updated each step, long table probed first. • cc52a97214 2016-02-19 `hashLog3`: a separate 3-byte hash table; 4ab9c913a5 reads 4 bytes and shifts off one so a 3-byte compare is one load; e74215e3c7 allocates it only when `searchLength==3`. • 6326775166 2024-10-16 Measure the short candidate's real length before switching to a long-table candidate at the next position.

### zstd-013 — Estimate once, then partition proportionally
Lens: algorithms · Source: zstd
Principle: Re-running a cost estimator after every added element is quadratic. Estimate the whole unit once, derive average costs per element type, and pack greedily with those averages when the size contract is approximate anyway.
Why it is faster: One O(n) estimate replaces O(n) estimates of growing prefixes. Carrying any leftover budget from one part to the next keeps part sizes regular. Pick the target part size from what the consumer needs, such as one network frame, so each part is useful on arrival.
Applies elsewhere: Web / backend: pagination or response chunking by byte budget using average row size; WebSocket or QUIC message sizing to the MTU. • Data / databases: splitting a bulk insert into transactions of about N MB; batching rows into Kafka batches of a target size. • Embedded: packing telemetry into fixed radio frames from a per-field average.
Watch out: averages fail on very skewed units. Use this only where the size target is soft; keep exact accounting where a hard limit applies.
Seen in zstd: cc4530924b 2024-02-23 `ZSTD_compressSubBlock_multi` replaced per-sequence `ZSTD_estimateSubBlockSize` calls with one full-block estimate and `nbSubBlocks = ceil(est/target)`, fixing a `targetCBlockSize` speed regression. • 038a8a906b 2024-02-25 `sizeBlockSequences()` uses fixed-point `avgLitCost`/`avgSeqCost`, budgets the entropy header into the first sub-block and carries over `blockBudgetSupp`. • f8372191f5 2024-02-24 Minimum target lowered to 1300 bytes "to match the transport layer size, such as Ethernet and 4G"; 3613448fb8 made `ZSTD_c_targetCBlockSize` stable API.

### zstd-015 — Hash chains in a window-sized ring, inserted lazily
Lens: algorithms · Source: zstd
Principle: Keep a head table (hash to latest position) plus a `next[pos & mask]` chain array the size of the window, so old entries are overwritten for free. Insert positions in a catch-up loop just before each search, and store absolute positions rather than deltas.
Why it is faster: Walking a chain visits many candidates per bucket for a bounded cost, giving more recall than single-probe hashing. The ring needs no deletion or aging. Catch-up insertion indexes positions skipped by matches only when a later search needs them. Absolute positions remove an arithmetic step and the clamp that delta storage needed.
Applies elsewhere: Web / backend: sliding-window rate limiters or dedup windows keyed by hash. • Data / databases: time-windowed join buffers in stream processors. • Embedded: packet reassembly or dedup with a fixed ring and hash heads, with no allocation.
Watch out: chains through a circular buffer can alias entries that were overwritten; validate each candidate's position against the window before using it, and cap chain length.
Seen in zstd: f3eca25322 2015-10-22 First `zstdhc.c`: `ZSTD_HC_insert` loops `idx < target`, filling chain entries up to the cursor. • eeb8ba18d1 2015-10-22 Window size decoupled from chain size; a 16-bit chain is masked by a cast. • d55a7e0e4d 2015-10-27 "Simplified chain": `NEXT_IN_CHAIN(idx) = hashTable[h]` replaced clamped deltas.

### zstd-016 — Fixed-size bucket rows filtered by small fingerprints
Lens: algorithms · Source: zstd
Principle: Instead of following a pointer chain (one dependent miss per candidate), keep each bucket's candidates in a fixed-size row with a parallel array of 1-byte fingerprints. Compare all fingerprints at once, then load and verify only the matching candidates.
Why it is faster: Work per lookup becomes bounded and cache-line aligned, and few full comparisons are wasted. The row works as a ring: insertion decrements a stored head index so nothing shifts, and recency order is recovered by rotating the match bitmask by the head instead of moving data. The result is a match finder between hash chains and single-probe hashing in both speed and quality. Its per-row comparison is SIMD-friendly, with portable fallbacks.
Applies elsewhere: Native / systems: Swiss-table or F14-style hash maps (control bytes plus group probe). • Data / databases: in-memory index buckets holding 16 fingerprints per cache line; dedup engines pre-filtering chunk fingerprints before comparing full keys. • Web / backend: fixed-size per-bucket LRU sets in CDN or DNS caches.
Watch out: rows evict the oldest candidate unconditionally, so very repetitive data loses distant matches a chain would keep. Selecting the algorithm by detected hardware makes output machine-dependent; zstd chose a platform-independent rule.
Seen in zstd: 4694423c4f 2020-11-02 Row-based match finder (merged in PR #2494): rows of 16/32 indices plus a tag row; the tag compare gives a mask iterated with `ctz` and `m &= m-1`; insertion via `ZSTD_row_nextIndex`, ordering via `ZSTD_VecMask_rotateRight`. • e411040ea1 2021-06-03 Added 64-entry rows with a 64-bit mask. • dd4f6aa9e6 2021-06-09 Flattened the mask computation and aligned tag rows. • d88651e604 2025-01-03 The row finder is enabled for `windowLog > 14` on every platform, so output no longer depends on SIMD availability; 68dfd14a8c raised the bound to 17 only for the Linux kernel build, which has no SIMD and many 128 KB blocks.

### zstd-017 — Binary search tree of suffixes with tracked common-prefix lengths
Lens: algorithms · Source: zstd
Principle: Per hash bucket, keep earlier positions in a binary tree ordered by their following bytes, and insert and search in the same descent. Track the prefix length already known to match on each side, and start each comparison at the smaller of the two.
Why it is faster: A sorted tree finds the longest earlier match without walking every candidate. Starting compares at `min(commonLengthSmaller, commonLengthLarger)` instead of 0 keeps total compare work near-linear, the same idea as LCP-aware string merging.
Applies elsewhere: Data / databases: suffix-array or LCP-style search in full-text indexes. • Native / systems: trie or radix inserts that skip known prefixes; LCP-merge string sort. • Web / backend: longest-prefix lookups over URL or path sets without a full trie.
Watch out: highly repetitive input makes every insert compare very long equal prefixes. Pair it with skip rules for long matches (see the laziness section).
Seen in zstd: 96b9f0ba4d 2015-11-04 btlazy2: `ZSTD_HC_insertBt1` / `ZSTD_HC_insertBtAndFindBestMatch` with `matchLength = MIN(commonLengthSmaller, commonLengthLarger)` then `ZSTD_count` from there; stops when a match reaches the input end, "to guarantee consistency".

### zstd-018 — Predict this step's outcome from the previous position
Lens: algorithms · Source: zstd
Principle: Adjacent positions have almost identical suffixes, so if position `p-1`'s neighbour in the tree was `c`, position `p`'s is very likely `c+1`. When the candidate equals the prediction, take the branch without comparing any bytes.
Why it is faster: Each correct prediction removes a full byte comparison from the tree descent. The prediction costs one table read and one integer compare.
Applies elsewhere: Data / databases: B-tree "last leaf" hints for sequential inserts; incremental sort of nearly sorted streams starting from the last insert point. • Native / systems: skip-list finger search; incremental parsers reusing the last parse state.
Watch out: only valid when consecutive queries really are related. Use the prediction as a shortcut to a known result, never as an unchecked assumption.
Seen in zstd: a87278a4f0 2016-01-17 `ZSTD_insertBt1`: `predictedSmall = bt[2*((current-1)&btMask)] + 1` and the same for the larger side; on a hit it links directly, "no need to check length, result known".

### zstd-019 — Content-defined sampling with a cheap rolling hash for long-range repeats
Lens: algorithms · Source: zstd
Principle: To find repeats far beyond the main window, roll a cheap hash over a long minimum length and index only positions whose hash bits hit a mask, about 1 in 2^k. Compute the strong hash only at those points, keep small round-robin buckets with a checksum, and feed the results into the main search as candidates.
Why it is faster: Sampling by content (not by offset) keeps memory small and stays aligned across shifted copies, since the same bytes produce the same sample points. A checksum from spare hash bits rejects false candidates without touching their data. Batching candidates lets all their buckets be fetched together. Running long-range search as a separate producer of candidate sequences lets the optimal parser weigh them against local matches, and its density can grow with the effort level.
Applies elsewhere: Data / databases: content-defined chunking for backup and dedup (FastCDC, restic-style). • Web / backend: rsync-style delta sync; near-duplicate detection over crawled pages. • Native / systems: container-layer dedup; WAN optimizers.
Watch out: runs and short periodic patterns hit the sampling condition at every repetition. Detect self-overlap and jump (see the laziness section), and validate derived parameters against degenerate inputs.

### zstd-021 — Accelerate through barren regions
Lens: laziness · Source: zstd
Principle: When a search keeps failing, step forward faster: let the stride grow with the distance since the last success, and once the stride is large, stop indexing the skipped positions too. Reset on the next hit.

### zstd-089 — Do not hoist loads you do not need yet: sink them to cut register pressure
Lens: cpu-microopt · Source: zstd
Principle: Read a field at the point where it is consumed, and keep variable scopes narrow. A value loaded early has to stay in a register until it is used. Under pressure the compiler spills it to the stack and reloads it, turning one L1 hit into a load, a spill store and a reload.
Why it is faster: Hoisting all the fields of a struct to the top of a hot block looks free, but it lengthens live ranges. In a loop that is already short of registers this forces spills. Reading at the use site from a cache line that is already hot costs one load, with no spill or reload around it.
Applies elsewhere: Native / systems: Interpreter dispatch loops that load operands per opcode rather than all up front. Wide-struct decoders. • Data / databases: Row decoders and JIT-generated operators. Check the generated code for `rsp`-relative spills in the inner loop. • Embedded: Register-poor targets (32-bit x86, Cortex-M), where every extra live value spills.
Watch out: This is the counterweight to the previous entry. Hoisting helps when it removes aliasing reloads and hurts when it only lengthens live ranges. Inspect the assembly instead of guessing.
Seen in zstd: 1e7fa242f4 2024-10-07 The hot variables in `zstd_fast.c` (`mvalAddr`, `mval`) get narrower scopes. • bd38fc2c5f 2025-06-20 Once register pressure stopped being the limit, AArch64 decodes stream 3 in the regular 4-way order (`HUF_4X2_4WAY`). • cc10195987 2026-09-07 `ZSTD_decodeSequence` stops hoisting the six `nextState`/`nbBits` values and reads them inside the state-update calls. ### zstd-096 — Filter a bucket of candidates with one vector compare of 1-byte fingerprints
Lens: simd · Source: zstd
Principle: Store each hash bucket as a fixed row of candidates plus a parallel row of 1-byte secondary hashes ("tags"). ### zstd-109 — Prefetch per cache line, at the right cache level, and far enough ahead
Lens: cpu-microopt · Source: zstd
Principle: Issue one prefetch per 64-byte line, not per byte. Use L2-level hints for bulk or near-future data and L1 hints for data needed immediately. On cores with weak hardware prefetchers, add a stream-ahead prefetch a fixed distance in front of forward-scanning pointers. Prefer compiler builtins to inline asm.
Why it is faster: A prefetch fetches a whole cache line, so issuing one per byte wastes issue bandwidth. Bulk data pulled into L1 too early evicts the working set, while imminent data should go straight to L1. Some cores (here aarch64) do not ramp up sequential prefetching fast enough, and a prefetch 256 bytes ahead closes the gap. A builtin lets the compiler schedule the prefetch, which an asm block blocks.
Applies elsewhere: Native / systems: Manual prefetch loops in C, C++ or Rust: stride by cache line and choose the hint level deliberately. Checksum or encryption over large buffers on mobile CPUs. • Data / databases: Columnar scans in embedded databases on ARM. ### zstd-149 — Instrument waits and progress so both humans and control loops can see the bottleneck

### zstd-153 — Provide compile-time switches that keep exactly one implementation of each multi-variant function
Lens: cpu-microopt · Source: zstd
Principle: When a library ships several implementations of one function for different regimes, add macros that force a single one, disable inlining and strip descriptive strings. Restructure dispatch code so the unused variants drop out of the binary entirely.
Why it is faster: Runtime selection between variants means every variant is linked in, even if a target only ever uses one. On size-constrained targets (bootloaders, kernels, WASM, firmware) the extra decoders, inlined copies and error strings can be most of the binary. A macro that hard-wires one variant turns dispatch into a constant, so the compiler removes the rest. Dispatch must be written so that variants can actually be compiled out. Nested ternaries that mention every variant defeat this.
Applies elsewhere: Embedded: firmware feature flags that keep one codec path and drop error strings. • Web / backend: tree-shakable JS or WASM builds where each codec is a separate import, not a runtime switch. • Native / systems: Rust cargo features or CMake options for optional algorithms; `-Os` builds without SIMD paths.
Watch out: every switch combination is a build to test. Add the minimal configurations to CI, or they will rot.
