### seastar-001 — Use a power-of-two ring buffer as the default queue
Lens: algorithms · Source: Seastar
Principle: A growable circular array with power-of-two capacity, indexed with `i & (cap-1)`, gives O(1) push/pop at both ends with contiguous storage and no per-element allocation. It is the right default for FIFOs and task queues.
Why it is faster: Linked queues and `std::deque` pay a pointer chase or a two-level index per access and allocate nodes or blocks. A ring keeps elements adjacent (prefetch-friendly), and masking replaces wrap-around compare-and-branch. With masking, the head and tail can grow forever, so no slot is sacrificed to tell full from empty. The cost: growth copies the whole array, and very large rings need one big contiguous allocation (see chunked containers).
Applies elsewhere: Web / backend: In JS, a power-of-two array ring beats `Array.prototype.shift()`, which is O(n) on large arrays, for job queues. • Embedded: UART/DMA buffers and audio FIFOs with a mask instead of a modulo. • Native / systems: Log and telemetry rings, work-stealing deques, event queues. • Data / databases: WAL record queues and replication backlogs.
Watch out: doubling copies every element, and a queue that can hold hundreds of thousands of entries needs one huge contiguous block. Under memory fragmentation, switch to a chunked structure.

### seastar-002 — Segment big containers into fixed-size chunks to bound contiguous allocation
Lens: algorithms · Source: Seastar · Also: Varnish
Principle: When a container can grow large, store it as a linked list of fixed-size arrays (chunked FIFO, deque, unrolled list). No single allocation then exceeds one chunk, while iteration stays almost as fast as an array.
Why it is faster: In a long-running process with a fragmented heap (especially a per-core allocator with a fixed memory budget), a multi-megabyte contiguous request can fail, force cache eviction or stall in reclaim. Chunks are always satisfiable and growth never copies existing elements. The trade-off is a small iteration and erase penalty (10–20% measured), plus a chunk-sized minimum footprint, which needs care when there are many nearly empty instances.
Applies elsewhere: Web / backend: Chunked buffer lists for HTTP bodies instead of concatenating into one huge Buffer; avoid giant JS arrays that land in large-object space. • Embedded: Pools of fixed-size blocks instead of one growable heap array. • Native / systems: Unrolled linked lists or ropes in editors and network stacks. • Data / databases: Paged row buffers and segmented WAL buffers.
Watch out: if a structure usually holds 0–1 items, a 32 KB first chunk wastes memory. Pair this with an inline first slot (see inline-capacity containers) and decide explicitly whether to cache freed chunks.

### seastar-003 — Store the common small case inline (small and fixed-capacity containers)
Lens: algorithms · Source: Seastar
Principle: When the element count is usually small or has a hard upper bound, keep the elements inside the owning object and spill to the heap only past that size.
Why it is faster: It removes a heap allocation and free per container, a pointer indirection per access, and a cache miss, because the data shares lines with its owner. With a known bound, the "can it grow" logic also disappears. The cost: the owner gets bigger, and moving the container copies its inline elements.
Applies elsewhere: Web / backend: Preallocated small arrays for typical-arity argument or header lists; small-string optimization in parsers. • Embedded: Fixed-size arrays for bounded queues, with no heap at all. • Native / systems: `SmallVec` / `absl::InlinedVector` / `boost::static_vector`. • Data / databases: Inline storage for the first few columns or keys of a tuple or index node.
Watch out: choose the inline size from measured distributions. Too large bloats every instance and its moves; too small rarely hits.

### seastar-005 — Use a good hash, store it in the node, and compute it once for every purpose
Lens: algorithms · Source: Seastar
Principle: Pick a well-distributed hash function, keep the computed hash next to the key, and reuse that one value for every decision that needs it (shard selection, bucket index, equality pre-check).
Why it is faster: A weak hash creates long collision chains, so lookups degrade toward linear scans. A stored hash makes rehashing free and rejects most unequal keys with one integer compare before a full key compare. Computing the hash once for both sharding and per-shard lookup halves hashing work on the request path.
Applies elsewhere: Web / backend: Route requests to workers and look up per-worker caches with the same precomputed key hash. • Native / systems: xxHash/wyhash instead of ad-hoc string hashes; store hash bits in Swiss-table control bytes. • Data / databases: Hash joins and GROUP BY that keep hashes with rows for partitioning and probing; Redis Cluster slot reuse.
Watch out: a stored hash costs 4–8 bytes per entry; skip it for tiny keys where comparing is already cheap. Untrusted keys need a seeded or keyed hash against flooding.

### seastar-006 — Tune the hash table's load factor and presize it
Lens: algorithms · Source: Seastar
Principle: For chained hash tables that grow large, raise the maximum load factor and reserve buckets up front, so the bucket array stays small and never rehashes in bursts.
Why it is faster: A load factor of 1 doubles the bucket array at every power of two. That means a full rehash storm on the hot path and bucket arrays big enough to cross large-allocation thresholds. A higher load factor trades slightly longer chains for a compact, stable bucket array.
Applies elsewhere: Web / backend: Java `HashMap` initial capacity and load factor for per-connection maps. JS `Map` cannot be presized, so pool and reuse maps instead. • Data / databases: Presize hash-join tables from cardinality estimates. • Embedded: Fixed bucket arrays sized for the worst case at build time.
Watch out: high load factors hurt open-addressing tables badly. This applies to chained tables, or to tables whose lookups are rare compared with their churn.
Seen in Seastar: d17a4f2be2 2026-06-16 The RPC client's `_outstanding` map uses `max_load_factor(8)` and `reserve(4096)`, keeping the bucket array at about 32 KB instead of crossing 128 KB at around 16K entries.

### seastar-008 — Key aggregations by one flat serialized key, and build derived objects only on first sight
Lens: algorithms · Source: Seastar
Principle: When grouping by a set of fields, encode them into a single delimited string or byte key for the hash lookup. Construct the heavyweight per-group object only when a new group is actually created.
Why it is faster: Nested maps or map-valued keys allocate, compare field by field and chase pointers on every lookup. A flat key is one hash and one memcmp. Building the stripped or derived structure only on insertion moves most of the work off the common "group already exists" path.
Applies elsewhere: Web / backend: In JS, a `Map` keyed by `a + '\n' + b` instead of nested maps or `JSON.stringify` of objects. • Data / databases: GROUP BY on a normalized serialized key (as vectorized engines do). • Native / systems: Packed integer keys (`(a<<32)|b`) for two-field lookups.
Watch out: the delimiter must not occur in the fields, or escape them. Otherwise distinct groups collide.
Seen in Seastar: f99ec4d210 2025-10-22 Prometheus aggregation uses a newline-delimited string key instead of a `std::map` of labels, and builds the label map only for new groups: large_families_int_aggr went from 154.7 to 65.7 ns, allocations from 8.16 to 0.16, and instructions from 2449 to 1007.

### seastar-012 — Stream output and input incrementally instead of materializing it whole
Lens: algorithms · Source: Seastar
Principle: Produce and consume data piece by piece (per record, per metric, per line), so memory stays O(1) or O(chunk) and long jobs can yield between pieces.
Why it is faster: Building a full response or loading a full file needs memory proportional to its size: large allocations, cache misses and GC or reclaim pressure. It also produces one long uninterruptible computation. Streaming bounds memory, starts output sooner, and creates natural points to yield to other work.
Applies elsewhere: Web / backend: Stream large JSON arrays and CSV exports with chunked transfer; Node `readline` instead of `readFileSync().split()`. • Data / databases: Cursor-based exports; operators that pipeline rows instead of materializing intermediate tables. • Embedded: Process sensor logs block by block from flash.
Watch out: very fine-grained streaming adds per-piece overhead (syscalls, continuations). Stream in reasonably sized batches, and make sure partial output on error is acceptable.

### seastar-013 — Make bulk operations work per chunk, not per element
Lens: algorithms · Source: Seastar
Principle: When elements need no per-element cleanup, implement bulk pop, truncate and clear as operations on whole storage blocks, so the cost is proportional to the number of chunks, not elements.
Why it is faster: Popping n trivially destructible elements one at a time does n bounds checks and index updates for nothing. Dropping whole chunks touches only the chunk headers.
Applies elsewhere: Native / systems: Ring buffers that advance the head by n in one step; `Vec::truncate` of `Copy` types. • Data / databases: Dropping whole log segments or pages instead of deleting record by record. • Embedded: Discarding consumed DMA blocks wholesale.
Watch out: keep a per-element path for types with destructors or side effects, and select it at compile time.
Seen in Seastar: f91df6862a 2024-07-19 `chunked_fifo::pop_front_n` does O(chunks) work for trivially destructible `T`. e8905c68b6 2024-07-19 implements `clear()` on top of it.

### seastar-014 — Turn every event source into a poller checked by one loop
Lens: scheduling · Source: Seastar
Principle: On a dedicated core, check each event source (I/O completions, timers, signals, cross-thread queues, helper-thread results) by reading memory or making a zero-timeout call once per loop iteration, instead of being woken through notification machinery. Each poller reports whether it made progress.
Why it is faster: Wakeup mechanisms (eventfd write plus read, signalfd, timerfd, signals) cost syscalls, interrupts and context switches per event. Checking a memory word or a ring index costs a few nanoseconds. "Did any poller do work?" also tells the loop exactly when it may sleep. The cost is a core that spins while the system is busy.
Applies elsewhere: Embedded: Super-loops that poll peripheral status registers at high event rates instead of taking an interrupt per event. • Native / systems: DPDK/SPDK poll-mode drivers; io_uring SQPOLL; game loops polling input, network and audio each frame. • Web / backend: Workers that drain completion queues once per event-loop tick instead of being notified per item. • Data / databases: Executor threads polling a lock-free completion queue filled by background I/O threads.
Watch out: pure polling burns a whole core when idle, and on shared hosts it steals CPU from neighbors and kernel helpers. It must be paired with a sleep strategy.

### seastar-015 — Poll while busy, then switch sources to wake-up mode and sleep when idle
Lens: scheduling · Source: Seastar
Principle: After a short idle period, ask every event source to arm a wake-capable notification (any source can veto if work raced in), then block. On wake, return to polling. Make the idle threshold configurable, and fall back to blocking when spinning harms the system.
Why it is faster: It keeps polling's low latency under load and gets the efficiency of interrupts when idle. Arming notifications only on the rare transition to sleep keeps their cost off the hot path. The threshold matters: too short causes constant arm/disarm churn, too long wastes CPU. A spin loop can also starve kernel threads that complete your own I/O.
Applies elsewhere: Native / systems: Adaptive spin-then-park mutexes; Linux NAPI (interrupt, then poll); DPDK interrupt mode at low load. • Web / backend: Clients that long-poll or spin briefly after activity, then fall back to push or backoff. • Embedded: Poll at high event rates, then enter low-power sleep with an interrupt armed. • Data / databases: Compute the next wake time from token-bucket math rather than polling a shared counter.
Watch out: the sleep handshake needs correct memory ordering (a lost wakeup means a hang). Make sure the threshold isn't accidentally tiny, and test on shared and virtualized hosts.

### seastar-016 — Bound cooperative run time with a time quota, not a task count
Lens: scheduling · Source: Seastar
Principle: A cooperative scheduler should yield to I/O polling when a fixed time slice has elapsed, measured by a timer that sets a flag, rather than after N tasks or continuations.
Why it is faster: Task counts are a poor proxy for time. Tiny tasks yield too often (wasted polls) and huge tasks overrun (latency). A timer-set flag costs nothing per task, gives a precise latency bound, and lets the slice be tuned (2 ms down to 500 µs) once checking is cheap. The clock source matters: a thread-CPU-time clock had 1/HZ (4 ms) resolution, which is coarser than the quota.
Applies elsewhere: Web / backend: React's scheduler and `scheduler.yield()` loops yield on a `performance.now()` deadline (about 5 ms), not an item count. • Data / databases: Long scans that check a timer-set interrupt flag every page. • Embedded: Run-to-completion loops with a SysTick-set "slice over" flag.
Watch out: a timer source coarser than the quota silently breaks the bound. Disable the tick while sleeping to avoid spurious wakeups.

### seastar-017 — Make the "time to yield" flag nearly free to set and to check
Lens: scheduling · Source: Seastar
Principle: Have the time-slice signal land as a plain memory write that hot code polls with a relaxed load, ideally written by the kernel or hardware directly, so neither setting nor checking it needs signals, wakeups or context switches.
Why it is faster: The check runs in every loop and every continuation chain, so it must be a single predictable load. Setting it via POSIX signals takes a process-wide kernel lock that doesn't scale with core count. A helper thread blocking on timerfd scales but costs a context switch per tick. Pointing the flag at a kernel-written AIO completion ring (head != tail) makes a timer completion the preemption signal at zero user-space cost, which in turn allows a shorter quota.
Applies elsewhere: Native / systems: Poll the CQ tail of an io_uring that holds a timeout SQE; prefer eventfd/futex over signals for inter-thread wakeups on many-core boxes. • Web / backend: Check a `SharedArrayBuffer` word written by a timer worker instead of awaiting a message. • Embedded: Have a hardware timer DMA a counter into a polled RAM word instead of taking an interrupt.
Watch out: relying on a kernel ABI layout is fragile. Keep a portable fallback and gate the trick on detected support.

### seastar-018 — Check for preemption once per loop iteration or await, not at every step
Lens: scheduling · Source: Seastar
Principle: Put the yield check at loop back-edges and suspension points, which is enough to bound latency. Long synchronous operations get explicit yield points or async variants.
Why it is faster: A check on every continuation link adds a load and a branch everywhere and blocks inlining. A loop that never checks can monopolize the core for milliseconds, or forever if every future is already ready. One check per iteration gives both: cheap chains and a bounded run time.
Applies elsewhere: Web / backend: `await scheduler.yield()` every N items or on a deadline in batch loops; chunked zlib with `setImmediate` between chunks. • Native / systems: Interpreters that check interrupts only on back-edges; budgeted cooperative tasks (Tokio coop). • Data / databases: Check cancellation per page, not per row. • Embedded: Check the tick flag once per pass of the main loop.
Watch out: any loop that can spin on ready work without passing a check point is a latency bug waiting to happen. Debug modes that force yields help find them.

### seastar-019 — Keep the yield machinery itself from dominating under backlog
Lens: scheduling · Source: Seastar
Principle: When the system is forced to keep running (large backlog) or forced to yield often (test modes), make sure the "preempted" slow mode doesn't become the steady state. Clear the flag to regain the fast inline path, cap the backlog, and rate-limit expensive polls.
Why it is faster: With the preempt flag set, every `.then()` stops inlining and every loop becomes at least one task, so throughput collapses exactly when there is the most work. Bounding the backlog by not polling for new work keeps memory in check, and decoupling "loops must yield" from "scheduler must poll I/O" keeps a cheap action from triggering an expensive one.
Applies elsewhere: Web / backend: Admission control: stop accepting (skip `accept`/reads) while draining a backlog. • Native / systems: Async runtimes that disable "yield every N" heuristics while draining; test-mode yield injection that doesn't also force expensive polls. • Data / databases: Pause intake of new queries when the run queue exceeds a threshold.
Watch out: clearing the flag delays I/O polling. Bound how long the backlog mode may last, or latency for new events suffers.
Seen in Seastar: 9d1db3f2b8 2016-07-20 Task backlog limited to 1000 by skipping pollers until it drains (700,000 queued tasks had once filled memory). • 7d073eb0e7 2018-07-01 When `tasks.size() > _max_task_backlog`, set `g_need_preempt = false` instead of staying in a mode where "even .then() chains cannot execute their inline branch". • e0d515b6cf 2023-12-19 `scheduler_need_preempt()` is split from the loop-yield predicate. ### seastar-020 — Schedule task groups by proportional share with virtual runtime
Lens: scheduling · Source: Seastar
Principle: Give each class of work (foreground, compaction, streaming) its own queue with a share. Always run the queue with the lowest virtual runtime (runtime / shares), and clamp the vruntime of queues that wake from idle.
Why it is faster: Without isolation, background work steals latency from foreground work, or is starved entirely. vruntime gives each group its proportional slice of a core over any window. A precomputed reciprocal (232/shares) makes accounting a multiply-and-shift instead of a divide. Clamping stops a newly active queue from monopolizing the core to "catch up".
Applies elsewhere: Web / backend: Weighted fair queuing per tenant in request schedulers; idle-callback budgets for background work in browsers. • Data / databases: Compaction and repair throttled relative to queries; resource groups. • Native / systems: CFS-style schedulers in userspace thread pools; cgroup `cpu.weight`/`cpu.max`.
Watch out: measurement errors (charging the wrong group, overflow in fixed point) silently skew shares. Test with adversarial mixes of groups.
Seen in Seastar: 6c97dcf4bd 2015-09-10 `thread_scheduling_group(period, usage)`: "a 20% limit with a period of 1ms will limit the thread ... to using 200usec of cpu time in any 1ms period". • 98630451a2 2017-07-25 Task queues ordered by `_vruntime`, computed as `(runtime * _reciprocal_shares_times_2_power_32) >> 32`; sleepers clamped to `_last_vruntime - to_vruntime(task_quota)`. 9c5f06f4a9 2017-10-13 widened the reciprocal to avoid overflow. • 21badbda93 2018-02-02 Uses the vruntime from before the group ran as the baseline, which fixed a low-share group over-running about 450 µs and letting others dominate. 70ad3254a2 2018-03-13 stopped charging pollers' time to the first group.

### seastar-021 — Give urgent and just-readied work a front-of-queue lane
Lens: scheduling · Source: Seastar · Also: Kafka
Principle: Let urgent work (memory reclaim, the continuation of a value that just became ready) jump to the head of the run queue, and give yields a forced poll so that yielding is actually fair.
Why it is faster: Running the next step of a chain immediately keeps its data hot in cache and removes extra deferral points: flat `.then()` chains had been slower than nested ones. Urgent system tasks that also end the current quota make loops break quickly when memory is scarce. A `later()` that forces a poll stops "yield" from just re-running the same task ahead of I/O.
Applies elsewhere: Web / backend: Microtasks versus macrotasks in JS event loops. • Native / systems: The LIFO slot in Tokio and Go schedulers (run the just-woken task next); softirq versus normal work in kernels. • Data / databases: Continue an operator on the batch it just produced while it's in cache.
Watch out: an always-front lane can starve the tail. Bound how many urgent tasks run consecutively, or pair the lane with the quota.

### seastar-044 — Reduce the common allocation to a free-list pop, and let the rare cases fail into the slow path
Lens: allocation · Source: Seastar

### seastar-045 — Use segregated size classes that keep internal waste bounded
Lens: allocation · Source: Seastar · Also: jemalloc, memcached
Principle: Serve small objects from per-size-class pools whose classes are spaced finely enough that rounding up wastes a bounded fraction, with a branch-free mapping from size to class. Do not pad requests past what alignment rules actually require.
Why it is faster: Segregated pools give O(1) alloc and free with no per-object header. The class spacing sets the worst-case waste: power-of-two classes waste up to 50%, while four linear steps per octave cap it near 20%, and the index stays a log2 plus a couple of fraction bits. A single extra byte (a NUL terminator, over-alignment) can push an object into the next class and double its cost.
Applies elsewhere: Web / backend: Size buffer pools in classes (4K, 5K, 6K, 7K, 8K...) rather than one size. Avoid +1 sizing that crosses a class boundary. • Embedded: Use a few fixed-block pools sized to the actual message types instead of a general heap. • Native / systems: Use jemalloc/mimalloc-style classes, and HdrHistogram-style sub-buckets for anything bucketed by size. • Data / databases: Use slab classes for cache items (as memcached does) and page-size classes for variable-length records.
Watch out: More classes mean more partially empty pools, so external fragmentation grows as internal waste shrinks. Alignment below what the compiler assumes (16 on x86-64) breaks vectorized moves.

### seastar-047 — Allocate large blocks from buddy spans, shrink in place, and fall back before failing
Lens: allocation · Source: Seastar
Principle: Use power-of-two buddy spans for large allocations to get O(log n) allocation, natural alignment and cheap coalescing. Shrink by releasing the tail rather than copying, and try an exhaustive search before declaring failure.
Why it is faster: First-fit extent allocators are dense, but large aligned requests can cost a scan over all memory. A buddy system finds a block in O(log n), and finding a block's partner is an XOR. The price is up to 100% internal waste for sizes just above a power of two. A shrinking realloc that frees the tail avoids allocate-copy-free entirely.
Applies elsewhere: Embedded: Use buddy heaps for DMA buffers that need natural alignment. • Native / systems: This is the design of Linux's page allocator and of GPU memory pools. `vector::shrink_to_fit` can release in place when the allocator supports it. • Web / backend: WebAssembly allocators often use buddy schemes for large linear-memory blocks.
Watch out: Buddy waste is severe for sizes like 2^n+1. Pair it with a size-class layer for small objects and avoid odd large sizes, which is one reason Seastar dropped NUL terminators.

### seastar-049 — Tag the pool, not each object
Lens: allocation · Source: Seastar

### seastar-051 — Build output as a list of fragments that reference the data, but batch them

### seastar-059 — Cap the size of any single allocation
Lens: allocation · Source: Seastar

### seastar-060 — Decide explicitly whether freed memory is kept or returned
Lens: allocation · Source: Seastar
Principle: Caching a freed chunk or object speeds up churn but pins memory in idle structures. Make retention a deliberate, tunable choice with hysteresis, and drop reserves as soon as a structure is known to be done.
Why it is faster: Retained free memory avoids allocator round-trips when a structure oscillates around a boundary. But with many mostly idle instances, every retained chunk is memory that nobody else can use, and that leads to OOMs. Hysteresis (separate low and high watermarks) prevents thrashing between keeping and releasing.
Applies elsewhere: Web / backend: Trim idle connection pools and object pools down to a low-water mark, and release large per-request buffers back after spikes. • Embedded: Return blocks to the global pool once a task's burst is over, so other tasks are not starved. • Native / systems: Call `shrink_to_fit` after bulk loads, and tune `malloc_trim` or arena decay. • Data / databases: Bound per-connection caches and statement buffers and release them on idle.
Watch out: Releasing too eagerly shows up as allocator churn in microbenchmarks. Seastar chose memory safety over the microbenchmark, and that trade-off should be made consciously.

### seastar-063 — Pay page-fault and locking costs before latency-critical code runs

### seastar-105 — Partition state per core and communicate only by explicit messages
Lens: concurrency · Source: Seastar
Principle: Give each core (or worker) exclusive ownership of its data, memory and queues, and route any operation on foreign data as a message to its owner. No locks, no shared mutable state, no cache-line ping-pong on the hot path.

Applies elsewhere: Web / backend: Worker-per-core servers (Node cluster, one event loop per core) that hash sessions or tenants to a fixed worker instead of sharing an in-process cache under a mutex. • Data / databases: Partition the keyspace per core (as ScyllaDB does) and forward requests to the owning core rather than locking shared B-trees. • Embedded: One task per core with mailbox queues between them instead of shared globals guarded by spinlocks. • Native / systems: Actor-style ownership; return objects to their owning thread for destruction.
Watch out: skewed keys overload one partition while others idle, and memory is split statically. Every cross-partition operation becomes asynchronous, which complicates code that used to be a simple lock.

### seastar-106 — Batch cross-core messages so one index write publishes many items
Lens: concurrency · Source: Seastar

Watch out: without a flush at idle or end of loop, a partial batch can wait indefinitely. Very large batches increase tail latency and can hide back-pressure.

### seastar-107 — Separate data written by different cores onto different cache lines

### seastar-110 — One single-producer/single-consumer ring per pair of cores
Lens: concurrency · Source: Seastar

### seastar-112 — Asymmetric memory barriers: keep the frequent side fence-free
Lens: concurrency · Source: Seastar
Principle: When a handshake needs a full fence on both sides but one side runs millions of times and the other rarely, move the whole cost to the rare side with a system-wide barrier, and let the hot side use plain relaxed accesses.

Watch out: the expensive side costs microseconds and IPIs every CPU; if it becomes frequent (or many threads issue it concurrently) it is far worse than plain fences.
