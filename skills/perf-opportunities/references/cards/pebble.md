# Pebble — technique cards (113)

Each card is exactly 7 lines. Fetch one with: grep -A 6 "^### pebble-NNN " pebble.md

### pebble-003 — Share unchanged structure between versions (copy-on-write, persistent trees)
Lens: algorithms · Source: Pebble
Principle: When you build a new version of a large collection from a small edit, reuse the parts that did not change and copy only the modified path.
Why it is faster: Copying a flat sorted array to apply one edit costs O(n) time and memory per version. Sharing untouched sub-arrays makes most of that work free. A persistent B-tree goes further and makes each edit O(log n) for any level size. Where an edit adds many items to a sorted list, merging two sorted lists beats re-sorting. The price is reference counting on shared nodes, and node recycling becomes unsafe, because another version may still point at the node.
Applies elsewhere: Web / backend: Immutable state trees (Redux, Immer) and versioned config snapshots handed to request handlers. • Data / databases: MVCC catalogs, copy-on-write B+trees (LMDB-style) for snapshot isolation, and undo history. • Native / systems: HAMTs and persistent vectors for routing tables that change rarely but are read by many threads.
Watch out: Shared nodes rule out in-place mutation and naive pooling. Old versions held by slow readers keep their whole structure alive, so drop any derived indexes they do not need.
Seen in Pebble: 0cddafd4c8 2019-05-02 Version-edit application reuses `base.files[level]` for levels that have no adds or deletes. A typical edit touches 2 of 7 levels. • 1acac2061f 2019-09-26 `BulkVersionEdit.Apply` merges the sorted current files with the sorted added files for levels > 0 instead of re-sorting. • e7d2ee42b1 2020-08-10 Added a copy-on-write B-tree. df33a42107 2020-10-22 rebuilt `LevelMetadata` on top of it, "allowing logarithmic applications of version edits". • 255915dc5f 2020-09-21 Removed `sync.Pool` recycling of tree nodes, because shared nodes made recycling unsafe. • b62f766154 2021-04-23 A version that is no longer the newest drops its large derived `L0Sublevels` structure. Readers keep a shallow copy of what they need, so long-lived old versions do not pin the bulk of memory.

### pebble-006 — Normalize overlapping intervals into a sorted, disjoint array
Lens: algorithms · Source: Pebble
Principle: Turn a set of overlapping ranges into non-overlapping fragments sorted by start, computed once. Then each point query is a binary search, or a forward cursor for sorted queries, over a flat array.
Why it is faster: With raw overlapping intervals, each query must check every interval or walk an interval tree. After normalization, the "which ranges cover x" answer for each fragment is precomputed, so a lookup costs O(log n) over contiguous memory with no pointers. Queries that arrive in sorted order can advance a cursor and pay amortized O(1). Normalization costs O(n log n) once and is shared by all queries. The fragments can also be served from storage as they are, and converted once before caching when they arrive in a legacy shape.
Applies elsewhere: Web / backend: Merge a calendar's busy intervals once before answering availability queries. Coalesce IP allow and deny ranges before firewall or rate-limit lookups. • Data / databases: Deletion ranges, lock ranges and partition coverage maps. Precomputed covered-page ranges for vacuum or GC. • Embedded: Memory-protection or flash-sector maps kept as a sorted array of disjoint regions in ROM. • Native / systems: Coverage maps in profilers and debuggers. Address-to-symbol maps.
Watch out: Fragmentation can multiply the number of entries when many ranges overlap heavily. The array must be rebuilt, or patched carefully, when the input ranges change.
Seen in Pebble: ff149b6b4d 2018-11-23 Range-deletion fragmenter: tombstones become non-overlapping fragments that carry their seqnums. 2fb597ced2 2018-11-24 binary-searches them in `SeekGE` and `SeekLT`. • 13d77b01cb 2019-05-25 Unfragmented RocksDB v1 range-deletion blocks are fragmented on load by a pre-cache hook, so the cache holds the form that is ready to serve. • b6ff1735c9 2020-01-14 Tombstone elision during compaction used to walk all file metadata below the compaction for each key, a cost that grew with LSM size. It now consults a flattened slice of disjoint "in-use" key ranges. • edcfca5432 2021-05-20 L0's in-use ranges are computed from the already sorted sublevel intervals, skipping covered stretches. e45797baeb 2021-05-25 merges level by level and seeks lower levels straight to the end of the range accumulated so far. • ff149b6b4d 2018-11-23 Range-tombstone fragmenter package. 2fb597ced2 2018-11-24 uses binary search in `rangedel.Iter.{SeekGE,SeekLT}`. 3941850989 compresses the range-del block.

### pebble-007 — Pack overlapping items into non-overlapping layers (interval layering), built by line sweep
Lens: algorithms · Source: Pebble
Principle: When many sorted runs overlap, assign them to the fewest possible "layers" in which runs do not overlap. Each layer can then be searched with one binary-searchable cursor instead of one cursor per run. Build the layering with a single sorted sweep of the endpoints, and patch it incrementally when items are only added.
Why it is faster: Read cost scales with the number of independent sources a query must merge. With N overlapping files that is N cursors, but with layering it is the number of layers, usually far fewer. The same structure shows where overlap is deepest, which guides where to split new output and what to compact. Sorting all endpoints once and assigning each item's interval indices during the sweep replaces a binary search per item. An add-only incremental update avoids a full rebuild.
Applies elsewhere: Data / databases: Group overlapping time-series chunks or segments into non-overlapping runs so a query merges fewer streams. • Web / backend: Calendar UIs that lay overlapping events into columns. Gantt and timeline rendering. • Native / systems: Register allocation by interval-graph coloring. Layering overlapping map tiles or sprites.
Watch out: The structure is derived state that must stay consistent with the item set. Keep a full-rebuild path and cross-check incremental results against it, sampled in test builds.
Seen in Pebble: 6a43207910 2020-04-21 Added the `L0Sublevels` structure. 43f8d507aa 2020-04-22 gives the merging iterator and point lookups one level iterator per sublevel instead of one per L0 file. • 00ded19fe8 2020-05-05 and 48a267ca24 2020-05-20 pick base and intra-L0 compactions from the sublevel structure. 32a5180fe1 2020-11-24 made it the default. • 8440f2908c 2022-02-01 `sortAndSweep` assigns each file's min and max interval index during the dedup sweep instead of binary-searching per file: L0SublevelsInit went from 9.44 ms to 7.30 ms (-22.7%). • b7b78b1ce0 2022-02-07 Incremental L0Sublevels generation when files are only added to L0.

### pebble-008 — Binary-search sorted metadata and return sub-slices instead of scanning
Lens: algorithms · Source: Pebble
Principle: When a list is sorted and its entries do not overlap, find the matching range with two binary searches and return a view (sub-slice) of the original. Narrow each search with any bound you already know.
Why it is faster: The scan goes from O(n) to O(log n) comparisons, and returning a sub-slice allocates nothing. Starting a search at an index you already know (the lower end of a range found earlier) prunes it further. For data that does overlap, tracking which items were already selected avoids rechecking them when the query range grows.
Applies elsewhere: Data / databases: Find the shards or segments overlapping a time range in a sorted segment list (Kafka offset index, time-series shards). • Web / backend: Range filters over sorted in-memory arrays, such as price or date windows, with the slice returned as a view. • Embedded: Lookup in sorted calibration or breakpoint tables.
Watch out: Binary search needs both sortedness and non-overlap. Items that overlap need either a separate path or a layering step (see the entry above).
Seen in Pebble: a9fa61e18f 2018-11-11 Uses binary search to find the range of overlapping files in levels > 0, whose files are sorted and disjoint. • 86edff699f 2019-09-13 L0 files can overlap. The overlap expansion now tracks the indices already selected so they are not rechecked, which cuts string comparisons. • 2da62788ee 2020-11-23 The upper-bound search starts at the lower bound that was already found.

### pebble-009 — Pick the hash table design for the real table size; re-measure as designs improve
Lens: algorithms · Source: Pebble
Principle: General-purpose maps leave speed on the table. An open-addressing table with flat memory beats a chained or bucketed map, and the right variant depends on the actual size range. Benchmark again when better designs appear.
Why it is faster: Open addressing keeps probes in adjacent cache lines and avoids per-bucket pointers. Robin Hood displacement bounds probe length, and Fibonacci (multiplicative) hashing replaces modulo. Swiss tables go further: they probe a group of control bytes in parallel, so most lookups resolve with one group read. Which design wins depends on table size, and Pebble measured that Robin Hood beat Swiss only above about 1M entries, larger than any of its cache shards.
Applies elsewhere: Native / systems: absl `flat_hash_map` or Rust hashbrown for hot symbol, connection or session tables. • Web / backend: In JS, a typed-array open-addressing table for numeric keys can beat `Map` holding millions of entries. • Data / databases: Buffer-pool page tables and hash-join build sides. • Embedded: A fixed-size open-addressing table in static memory, with no allocation and a bounded probe length.
Watch out: Benchmark at your real sizes and load factors. Designs swap places as tables grow. Tombstone-free deletion and probe caps add code complexity.
Seen in Pebble: 0f2704f939 2020-02-12 A pointer-free Robin Hood map in manually allocated memory replaced Go maps for the cache's `shard.blocks` and `shard.files`. It uses linear probing, a probe-distance cap that triggers a resize, a sentinel slot that ends loops without a bounds check, backward-shift deletion, and Fibonacci hashing. Insert went from 144 to 101 ns (-30%), hit lookup from 137 to 47 ns (-66%), and miss lookup from 90 to 49 ns (-46%). • af1fcbbe80 2024-03-04 Replaced the Robin Hood map with a Swiss table. Insert was 75% faster (31.5 to 7.8 ns), hit lookup 38% faster, and miss lookup 20% faster.

### pebble-010 — Design the ordered in-memory index for its workload: arena offsets, truncated towers, single-writer variant
Lens: algorithms · Source: Pebble
Principle: An ordered in-memory index should store nodes contiguously and link them by small integer offsets. Each node should be sized to its actual height, and the level distribution should be drawn with one random number. Keep a separate lock-free variant for the concurrent case and a plain one for single-owner use.
Why it is faster: Offsets into one arena halve link size compared with pointers and give the garbage collector nothing to scan. They also keep nodes close together, and freeing the index means dropping one buffer. Most skiplist nodes are short, so allocating only `height` link slots shrinks the average node a lot. Choosing p = 1/e minimizes expected search cost, and a precomputed threshold table turns height selection into one random draw plus comparisons. A structure owned by one writer pays nothing for atomics or CAS.
Applies elsewhere: Web / backend: In GC languages (Go, Java, JS), index structures stored in typed arrays or byte slices with integer links avoid GC scanning of millions of nodes. • Embedded: Fixed memory pools with 16- or 32-bit node indices instead of pointers. • Native / systems: Variable-fanout nodes (tries, B-tree leaves) sized with a flexible array member to their actual fanout. • Data / databases: Memtables, and per-transaction write buffers that use the cheaper single-owner variant.
Watch out: Arena memory is freed only all at once, so long-lived arenas with deletes waste space. 32-bit offsets cap the arena at 4 GB. Two variants of the same structure double the maintenance work.
Seen in Pebble: 61d267b43d 2011-09-14 In golang/leveldb, memdb nodes became offsets into an `[]int` plus a `[]byte` instead of pointer structs. Mallocs in the test fell from about 22,000 to about 20,000. • 737e51ba0f 2018-06-14 Imported `arenaskl`: an atomic bump allocator, 32-bit offsets with offset 0 meaning nil, towers updated by CAS, and `newNode` allocating `MaxNodeSize-(maxHeight-height)*linksSize`. README numbers: concurrent ReadWrite at 8x parallelism costs about 250-470 ns/op, and IterNext/IterPrev about 4 ns. 02d46c2b81 2018-06-15 switched the memtable to it. • 32c1e970e1 2018-06-15 Forked `batchskl` for single-writer batches: no atomics, a growable node buffer, keys kept outside nodes as offsets into the batch, and a `probabilities[maxHeight]` table with p = 1/e. • 75fc5f684c 2019-11-04 batchskl nodes store the record offset plus key start and end offsets, so fetching a key needs no varint decode. The node array is reused across pool reuse.

### pebble-011 — Track many thresholds with a min-heap "frontier" instead of checking each one per item
Lens: algorithms · Source: Pebble
Principle: When many observers each need a callback once a sorted stream passes their key, keep their thresholds in a min-heap. Compare each element against the heap top only, and fire callbacks when it is crossed.
Why it is faster: Checking N thresholds per element costs O(N) comparisons per element. With a heap it costs one comparison per element plus O(log N) per threshold crossed, and crossings are rare. The structure also removes ad-hoc per-key checks spread across code, such as "has the current range tombstone ended yet?".
Applies elsewhere: Web / backend: Many per-subscription deadlines or watermarks in a stream processor. Rate-limit windows that expire. • Native / systems: Timer heaps or wheels instead of per-event deadline checks in an event loop. • Embedded: Distance- or time-triggered events along a path, keeping only the nearest threshold "armed".
Watch out: With only one or two thresholds, a plain comparison is simpler and as fast. Callback ordering must be defined when several thresholds are crossed by the same element.
Seen in Pebble: 2f086b741e 2023-02-08 Added a `frontiers` type, with heap code adapted from the merging iterator, and used it for compaction-output splitters (L0 flush split keys, grandparent limits). • 7cdb5eedf2 2024-05-28 The compaction iterator registers the current range tombstone's end key as a frontier. The per-key `cmp(key, span.End)` in `tombstoneCovers` is gone, because a callback resets the span when its end is passed.

### pebble-012 — Search from where you already are before searching from scratch
Lens: laziness · Source: Pebble
Principle: When successive operations target nearby positions, first check the current position and take a few cheap steps forward. Fall back to a full logarithmic search only if that fails. Let callers declare monotonicity so the shortcut is safe.
Why it is faster: A full seek descends every layer (file list, index block, data block) at O(log n) comparisons each, plus block loads. When the target is usually within a few entries, a handful of `Next` calls or one "still in this file?" check is far cheaper. Capping the probe (around 4 steps) bounds the worst case to "probe plus normal seek". The same idea applies to inserts: a remembered splice point makes sorted insertion amortized O(1).
Applies elsewhere: Data / databases: Cursor-hinted B-tree seeks for sorted multi-gets. Galloping search in merge joins. Time-series index scans that resume from the last position. • Web / backend: Virtual-list "scroll to row" that walks from the current row when the target is close. A KV client that sorts batch keys and reuses the cursor. • Native / systems: `insert(hint, value)` on ordered maps for sorted appends. Timsort-style galloping. • Embedded: Lookup in a sorted table that starts from the last index used, for monotonic sensor readings.
Watch out: The monotonicity hint is a contract. A caller that lies about it gets wrong results, not just slow ones, and Pebble had to revert and fix its first attempt. Cap the linear probe, and randomly disable the fast path in test builds so both paths stay correct.
Seen in Pebble: 4ebbec0531 2018-12-16 `arenaskl.Inserter` caches the per-level splice from the last insert and checks it before searching from the head. 741b7335ce 2018-12-16 uses it in `memTable.apply`: "3-4x faster insertion if the data is ordered". be607977ba 2019-11-04 added an in-order fast path to batchskl: OrderedWrite went from 145 ns to 74 ns (-48.9%). • a24bc6c830 2020-08-17 First version of seek-using-next in sstables, reverted in d3f98730b0 2020-09-08 and re-landed as d1b2f64e9e 2020-10-21. MergingIterSeqSeekGEWithBounds went from 3.64 µs to 0.73 µs (-80%). • a516e691fb 2021-02-05 `SeekPrefixGE(..., trySeekUsingNext)` for sorted batches of point lookups tries a few Next calls first. ### pebble-013 — Remember the last answer and turn repeated operations into no-ops
Lens: laziness · Source: Pebble
Principle: Keep the inputs and result of the last positioning or lookup call. If the next call provably has the same answer (same or later target, already positioned past it, unchanged bounds, target still inside the cached range), return immediately.
Why it is faster: Callers often repeat a seek or move it slightly, for example re-seeking to the same key after skipping deleted entries, or setting identical bounds. Without memory, each repeat walks the same tombstones, re-seeks span iterators and invalidates lower layers. With a small saved state the repeat costs a comparison. In the worst case Pebble measured, this turned a scan over a run of deleted keys from tens of milliseconds into microseconds.
Applies elsewhere: Web / backend: Memoized selectors and `React.memo` on owned copies of props. Paginated API clients that skip a refetch when the cursor is unchanged. • Native / systems: GPU state caches that skip redundant uniform or texture binds. Last-hit caches for IP-range or symbol lookups. • Data / databases: Lock-table or index cursors kept positioned across successive lookups. Log readers that skip re-seeking at an unchanged offset. • Embedded: Skip reprogramming a peripheral register when the new value equals the cached one.
Watch out: The cache must be invalidated whenever the underlying data changes (batch refresh, file swap). Its key must be owned memory, not a caller buffer that can change. A missed invalidation is a correctness bug, so test it explicitly.
Seen in Pebble: 4e31372216 2018-11-09 `memTableIter` caches its positioned key and validity. 09d995f892 2018-12-10 caches validity instead of calling `Valid()` repeatedly. • 2fdc9f37cf 2020-01-11 Each merging-iterator level caches the result of its last range-tombstone seek, so later key checks do not repeat the seek. • 959663f8cc 2021-02-19 `lastPositioningOp` plus a saved seek key make a repeated seek a no-op when the iterator already sits at or past the new target. ScanAllIntentDeleted went from 51.7 ms to about 5 µs. 560af6e14c 2021-02-22 fixed a bug in it and added tests. • 7c5f0cbb26 2022-05-13 Iterator bounds are copied into two pooled buffers (current and previous), so "bounds unchanged" can be detected and lower layers are not invalidated. • 04f9100f89 2022-08-02 The interleaving iterator keeps the current range-key span when it still covers the seek key: CombinedIteratorSeek went from 29.7 µs to 9.1 µs (-69%). 9f3e421646 2022-08-02 stopped buffering empty spans on seeks (batch seeks 17% faster). • 2722c6eb16 2026-05-22 Documents the cached-span fast path in the new interleaving iterator and adds `InvalidateCachedSpan()`, called whenever the underlying batch view is refreshed.

### pebble-014 — Keep your current position and loaded state after a negative or same-place answer
Lens: laziness · Source: Pebble
Principle: A "not here" answer from a filter, or a seek that lands on the block already loaded, does not make the loaded state stale. Keep the current file, block and decoded position so the next nearby operation can reuse them.
Why it is faster: Throwing away a loaded block forces a cache lookup, a refcount bump and a decode on the next nearby seek. Moving to the next file after a filter miss opens a file that may never be needed, and it also breaks the "search from the current position" shortcut for the next sorted lookup. Keeping the state costs nothing on the miss path.
Applies elsewhere: Data / databases: In filter-guarded multi-segment lookups (search segments, Parquet row groups), stay on the current segment while its range still covers the key. • Web / backend: Image tile and map viewers that keep the current tile when the viewport moves within it. • Native / systems: Decompression streams that keep the current frame, and B-tree cursors that keep their leaf after a negative probe.
Watch out: Keeping state after a "not found" means the iterator is in an unusual position. Document that calling Next is not allowed afterwards and enforce it with assertions, as Pebble did.
Seen in Pebble: 92fbeeabfd 2021-03-19 On a bloom-filter miss, `levelIter` stays on the current file when that file's range extends past the prefix. IteratorSeqSeekPrefixGENotFound went from 3.73 µs to 0.82 µs (-78%) and from 5.07 µs to 0.82 µs (-84%). This was traced to about half of the lock-table seek overhead in TPC-C. • 3d0ff924d1 2022-01-12 `loadBlock` returns early when the target block handle equals the loaded one and the block is valid: `if i.dataBH == bhp.BlockHandle && i.data.Valid() { i.initBounds(); return loadBlockOK }`. • c27a208c0f 2025-09-12 The `!mayContain` path in `seekPrefixGE` no longer invalidates the loaded data block; invalidation now happens only on error. An invariants-only flag checks that callers do not call Next after a nil prefix seek.

### pebble-015 — Stop as soon as the answer cannot change (exhaustion, prefix and bound short-circuits)
Lens: laziness · Source: Pebble
Principle: Check early whether any further work could still produce a result. Examples are an iterator already past its bound, a key past the sought prefix, or a file whose smallest key sorts after the prefix. Return immediately instead of loading or scanning more.
Why it is faster: Without these checks a prefix lookup can wade through large deleted regions, or open the next file only to discard it and reopen it on the next seek. A seek on an already exhausted iterator can reload index blocks for nothing. Each check is one comparison against a key already in hand, and the work it saves can be a whole I/O, or a scan proportional to the number of tombstones. Filtering before the merge heap also keeps the heap small.
Applies elsewhere: Data / databases: Stop a `LIKE 'abc%'` index scan at `'abd'`. Partition pruning by min/max before opening files. • Web / backend: Autocomplete over a trie that stops at the subtree boundary. A paginated client that caches "no more pages". • Native / systems: Merge readers over sharded files that stop at the query bound instead of opening the next shard. • Embedded: Log scans over flash pages that stop when timestamps pass the window.
Watch out: Short-circuits depend on exact bound semantics (inclusive or exclusive, prefix successor). An off-by-one returns wrong data. Iterators left in an "exhausted" state need clear rules for what a later seek may assume.
Seen in Pebble: 8248df4418 2020-01-06 Two-level iterators stop skipping forward or backward at the upper or lower bound. • 7a40f6bea6 2020-01-13 `SeekPrefixGE` notices a prefix mismatch while stuck in tombstones and stops: ycsb/F +50%, p95 -45%. 00685e9c29 2021-03-08 gives `mergingIter` a split function so it returns as soon as the prefix stops matching while skipping range-deleted keys. • a69a94e1b0 2020-09-29 `levelIter` stops at the iteration bound instead of loading the next file, and skips synthetic boundary keys from files with no tombstones. For narrow monotonic bounds, LevelIterSeqSeekGEWithBounds went from 892 to 661 ns (-26%). • f4b082db8b 2022-08-12 Added `Comparer.ImmediateSuccessor` and limited range-key defragmentation to the prefix: CombinedIteratorSeekPrefix went from 2.53 ms to 0.10 ms (-96%), and allocations from 17.0k to 0.4k. • 8dc60b62eb 2022-11-04 A two-level iterator that is already exhausted returns immediately on a monotonic seek: 319 ns to 4 ns (-98.7%). • 1f7e8ee45c 2024-03-06 Prefix filtering pushed into the merging iterator: non-matching levels leave the heap before more fix-ups. • c4b8017ec2 2024-05-13 stops stepping `levelIter` beyond the iteration prefix. 255087f92a 2024-05-15 returns `noFileLoaded` when a file's smallest point key prefix already sorts after the sought prefix, so no I/O, filter or index load happens. ### pebble-016 — Build optional machinery only when the data actually needs it
Lens: laziness · Source: Pebble
Principle: Start with the minimal pipeline for the common case. Switch to the expensive general mode only when the input shows it is needed, and use cheap metadata to know where that switch point is.
Why it is faster: Rare features (range keys here) need extra iterator stacks, block loads and per-key interleaving. Building that for every read makes everyone pay for a feature few use. Deferring it until a file or key region with range keys is reached removes the setup cost, the I/O and the per-key overhead for the common case. An incrementally maintained index of "regions that may contain the feature" lets the switch happen exactly where it is needed.
Applies elsewhere: Web / backend: Code splitting and lazy modules. Turning on row-level-security or ACL evaluation only for partitions flagged as needing it. • Data / databases: Lazy join materialization. Switching a scan to a slow path only in segments flagged "has deletes" or "has nulls". • Native / systems: Allocate the slow-path state of a parser only when an escape or extension is first seen.
Watch out: The switch from cheap mode to full mode must preserve iterator position and ordering exactly. Metadata flags must be conservative: a false "may contain" is fine, a false "does not contain" is a correctness bug.
Seen in Pebble: 89b7bc729b 2022-07-22 `lazyCombinedIter` starts with only the point-key stack and builds the range-key stack when a `levelIter` reaches a file that has range keys. • babd592d23 2023-10-20 L0 range-key blocks are no longer loaded during iterator construction. • 9b9b8110d1 2026-04-22 A conservative per-table `RangeKeyKinds` flag, so table statistics are not needed to decide. 7ba7d544eb 2026-04-22 maintains a region tree of key ranges that contain range-key sets inside version-edit application. • 8ad53fcedf 2026-05-08 `TriggerIter` emits a synthetic boundary at the first such region and switches modes there. 56eeba0e1b 2026-05-08 makes it the first merge level, armed or disarmed by `Reset`, so the same iterator survives option changes.

### pebble-017 — Open and load per-file components only when a query touches them, and never twice
Lens: laziness · Source: Pebble
Principle: Constructing a reader should do no I/O. Load each sub-component (index block, range-deletion iterator) at the first operation that needs it. Share one opened component between consumers instead of opening duplicates.
Why it is faster: Many iterators are created and then rejected cheaply, for example by a bloom filter on a prefix seek. If construction already loaded the index, that I/O and decode were wasted. Opening a range-deletion iterator for a file that has none, or opening it twice, doubles block reads. A guard at each entry point costs a branch per call.
Applies elsewhere: Data / databases: Parse Parquet footers and row-group indexes on first read. Open delete-vector or sidecar files only when metadata says they are not empty. • Web / backend: ORM lazy relations. Lazy decoding of JSON or protobuf sub-messages. Sharing one parsed config or index between a validator and a reader. • Native / systems: File handles that open on first read. Font and glyph tables loaded per page.
Watch out: Lazy state machines multiply the number of states. Pebble's first lazy-index attempt corrupted data under stress and had to be redone. Sharing a component between consumers fails when they need different views of it (here, truncated versus full spans).
Seen in Pebble: dbdcab4ff1 2024-04-23 The range-deletion iterator is opened only when the caller asks for it. 8e556e810d 2024-05-13 fixed a YCSB regression in which it was opened a second time even after the file was known to have none. • 527eebf448 2025-06-27 First attempt at lazy index loading, reverted after stress-test corruption. bbfc14bdad and 1ba33f5129 2025-09-03 reimplemented it with stricter state handling: construction no longer reads the top-level index, and `ensureIndexLoaded()` guards every seek, first and last entry point. Bloom-filter rejections now skip the index load entirely. • d46b095199 2026-01-14 The level checker reuses `levelIter.getTombstone()` instead of opening its own iterator on the same range-deletion block. Extending this to the merging iterator (658c3ce08b 2026-02-10) was reverted in b1991e0a11 2026-02-23, because under prefix seeks the shared span is truncated and the merging iterator needs the full span.

### pebble-018 — Return a cheap placeholder and resolve it only if it wins
Lens: laziness · Source: Pebble
Principle: In a merge, an input only needs an exact position when it reaches the top. If metadata proves the true answer sorts at or after some key K, report K without doing I/O, and do the real work only if K becomes the minimum. Likewise, advance only the inputs that are still active.
Why it is faster: Most levels in a merge never produce the winning key for a given seek. Seeking all of them pays block reads and filter probes that are then discarded. A placeholder costs a metadata comparison, and an input that never wins costs nothing more. Deferring the advance of inputs that may turn out to be covered by a range deletion similarly avoids opening files that would be skipped anyway.
Applies elsewhere: Data / databases: Block-max WAND in search engines (use the block's maximum score as a stand-in until it matters). Time-series merges using per-chunk maximum timestamps. • Web / backend: Merging pages from remote partitions: do not fetch the next page of a partition whose lower bound cannot win yet. • Native / systems: Demand-driven stream pulls, and lazy evaluation of union branches.
Watch out: A placeholder key must never escape to the user. Every operation has to resolve it or step past it, and Pebble needed several follow-up fixes. Placeholders can disable other shortcuts, so measure the net effect.
Seen in Pebble: ca74226f0d 2025-09-11 When a prefix seek falls strictly inside a table's bounds and the seek suffix is below the table's max-suffix property, the sstable iterator returns a synthetic key (prefix plus max suffix) with no I/O, and resolves it on Next. The trade-off is that `TrySeekUsingNext` is disabled after a synthetic key. 5e3f0383f6 2025-09-18 supplies the max-suffix property for CockroachDB keys. fd959dd096 and 9d1f319b34 2025-09-18 fixed correctness issues. • d71b0c7d6c 2026-04-15 When several merge inputs sit at a boundary, they are marked "at boundary" and only the inputs not parked under a covering tombstone are advanced. Parked inputs never pay for the step, which could mean opening an sstable. `anyLevelParked()` also avoids needless key copies.

### pebble-019 — Hand out lazy handles; let the consumer decide what to materialize
Lens: laziness · Source: Pebble
Principle: Return a cheap handle (location plus length plus a few attribute bits) instead of the value, and fetch the value only when the consumer actually reads it. In the same spirit, compute derived metadata only for consumers that need it, and let primitives return raw results so callers filter only when they care.
Why it is faster: Many consumers never read the value. A key scan, a length check, a tombstone test, or a compaction that drops the key because a newer tombstone covers it all fall in this group. Eager fetching pays I/O, decompression and copying for nothing. Putting the length and a short attribute in the handle answers common questions without a fetch. A primitive that loops until it finds a "visible" entry does work the caller may not want.
Applies elsewhere: Web / backend: APIs that return heavy fields (blobs, rendered HTML, large JSON) as links or lazy loaders. GraphQL resolvers that fetch only the requested fields. • Data / databases: TOAST-style out-of-line values. WiscKey value logs. ETL pipelines that filter rows before reading blob columns. • Native / systems: Lazy string or length caching. Memory-mapped records decoded only on access.
Watch out: The handle must keep its backing resource alive (or be refcounted) until it is resolved. Many lazy fetches in a loop can cost more than one eager batched read, so batch them or prefetch for sequential access.

### pebble-020 — Skip comparisons whose answer an invariant already implies
Lens: laziness · Source: Pebble
Principle: Before calling an expensive comparator, check whether the sort order, a sentinel value, or object identity already determines the result.
Why it is faster: Variable-length key comparisons dominate the inner loops of sorted structures. Entries ordered by (key ascending, sequence number descending) imply that a non-decreasing trailer means a new key. A zero sequence number proves "last version of this key". In a skiplist, a node already compared at level h+1 that reappears at level h gives the same answer, which a pointer-equality check detects. Each shortcut replaces a memcmp over long keys with an integer or pointer test.
Applies elsewhere: Data / databases: Merging versioned records, where a monotonic secondary field proves a primary-key change. MVCC stores that strip version metadata from frozen rows. • Native / systems: B-tree or trie descent that remembers comparison results by node identity. Redis-style skiplists. • Web / backend: Diffing with identity checks (`===`) before deep equality.
Watch out: The shortcut is only as safe as the invariant. Ingested files, seqnum zeroing and snapshots all bend sort-order assumptions. Where the saving is small, prefer an assertion over a shortcut, as Pebble did for compactions.

### pebble-021 — Ask the cheapest question that suffices: equality over ordering, prefix proxies, dominant field first
Lens: laziness · Source: Pebble
Principle: If you only need to know whether keys are equal, test equality instead of computing a three-way order. Decide most comparisons with a cheap fixed-width proxy (an 8-byte order-preserving prefix) or with the dominant field taken from raw bytes, and fall back to the full comparison only on ties.
Why it is faster: An equality test can stop at a length mismatch and use memcmp, with no splitting or decoding. A three-way compare often has to decode or split keys. An abbreviated key stored in the node sits on the same cache line as the links, so most seek comparisons are one integer compare and need no extra cache miss to fetch the full key. Comparing the user key straight from the arena, and tie-breaking on the trailer only when keys are equal, skips building a decoded struct for every node visited.
Applies elsewhere: Data / databases: Sort operators with 8-byte normalized key prefixes. Group-by over sorted rows using equality to detect group changes. • Web / backend: Sorting objects in JS by a precomputed numeric key instead of a string comparator. Change detection in CDC streams with hash or equality checks. • Native / systems: Composite-key compares that check the dominant field from raw bytes first. Hash tables that compare stored hashes before keys.
Watch out: The proxy must preserve the comparator's order exactly, including custom comparators, so let the comparator define it. Equality and comparison must agree, or structures that mix them break.

### pebble-022 — Replace per-item checks with one coarse check that covers the whole group
Lens: laziness · Source: Pebble
Principle: If one test shows that an entire block or input lies inside the bound or range, every per-item check in that group is known to pass. Turn them off for that group.
Why it is faster: Bound and membership checks run per key, often two comparisons each. One comparison against the block's first key and index separator (or against a covering range) removes thousands of them, and the branch in the inner loop becomes a nil check that predicts well. Pushing bounds down to the leaf iterators puts the check where this elision is possible.
Applies elsewhere: Data / databases: Zone-map elision: skip per-row predicate evaluation for pages whose min/max lie fully inside the predicate. • Web / backend: Permission checks: if the user owns the folder, skip per-file ACL checks. • Native / systems: Hoisting bounds checks out of loops. Geofencing when a bounding box lies fully inside a region. • Embedded: Skip per-sample range clamping when a block's min and max are already in range.
Watch out: The coarse summary must be exact or conservative. Separator keys may not be real keys, so reason carefully about inclusive and exclusive bounds.

### pebble-023 — Update incrementally, and skip a rebuild when a cheap check shows nothing relevant changed
Lens: laziness · Source: Pebble
Principle: After a small local step, rewrite only the parts of derived state that changed. Use a conservative change detector (false alarms allowed, misses never) to prove that a full rebuild can be skipped.
Why it is faster: Rebuilding a key from scratch at each step, or recomputing per-level visibility state at each boundary, costs O(size) or O(levels) even when only one byte or one input moved. Checking the delta is O(1). A detector that snapshots a few fields can prove "unchanged" cheaply, and when it cannot, it falls back to the full rebuild, so correctness does not depend on it being clever.
Applies elsewhere: Web / backend: UI layout invalidation that re-lays out only when a size actually changed. Memoized derived state with cheap dirty checks. • Data / databases: Delta checks before refreshing a materialized aggregate. Skipping a re-sort when only the top element moved and still beats the runner-up. • Native / systems: Incremental path or string building while walking sorted lists. Front-coded dictionary decoders.
Watch out: The change detector must never miss a real change. Test the full-rebuild path heavily, because the fast path hides its bugs.

### pebble-025 — Let callers give an operation a work limit
Lens: laziness · Source: Pebble
Principle: Add a soft limit to iteration or search calls so the callee can stop at the limit and report "paused here" instead of walking an unbounded run of invisible entries.
Why it is faster: Coordinated scans over data full of deleted entries can go quadratic. Each call skips the same long deleted run only to discover it has gone past what the caller wanted. A per-call limit caps the work per call and lets the caller interleave other sources, so the total cost becomes linear.
Applies elsewhere: Data / databases: Tombstone-heavy scans with a scan budget (Cassandra-style). Cursor APIs that return "paused at bound". • Web / backend: Budgeted iteration in request handlers and schedulers, yielding after N items or N ms. • Embedded: Cooperative tasks that process at most N items per tick.
Watch out: Callers must handle the extra "at limit" state correctly and resume from it, which complicates the API contract.

### pebble-026 — Group commit: one durable sync for many writers
Lens: amortization · Source: Pebble · Also: Kafka
Principle: Writers append to a shared log buffer and wait on a handle. A dedicated flusher writes and syncs once, then wakes every waiter whose data is now durable.
Why it is faster: An fsync costs about the same for 1 KB as for 100 KB, and it is the dominant cost of a durable commit. With one sync per commit, throughput is capped at the device's sync rate. When syncs are shared, throughput scales with the number of concurrent writers, while each writer's latency stays about one sync. A lock-free queue of waiters and a condition variable signalled without holding its lock keep the coordination itself cheap. Enough concurrent waiter slots are needed so writers do not queue on a semaphore before they can join a group.
Applies elsewhere: Data / databases: WAL group commit in any database. Journaling in embedded KV stores. • Web / backend: Batch audit-log or event writes from many request handlers into one flush. Coalesce network flushes in RPC frameworks. • Embedded: Gather several log records per flash page program instead of programming per record. • Native / systems: Journaling filesystems. Message brokers acking producers after one segment fsync.
Watch out: With a single writer there is nothing to share, and the hand-off adds latency. Waking waiters must be cheap, so wake all of them in one pass rather than chaining wake-ups.
Seen in Pebble: 5d49ef61a4 2019-05-11 Added `LogWriter.SyncRecord`: records join a lock-free SPSC `syncQueue`, and the flusher goroutine syncs once and pops, calling `Done()` on every waiting `WaitGroup`. ### pebble-027 — Wait a little on purpose so more work can join the batch
Lens: amortization · Source: Pebble
Principle: When sync or flush requests arrive faster than a threshold, delay the next one by a small fixed interval so more requests arrive to share it.
Why it is faster: Group commit only batches the requests that happen to be waiting. On fast devices the flusher can run so often that each batch holds one or two requests, which wastes IOPS. A short deliberate delay (hundreds of microseconds) grows batches and cuts operations per second at the device, with little throughput cost. It trades a bounded amount of latency for efficiency.
Applies elsewhere: Web / backend: Kafka producer `linger.ms`. Debounced autosave or IndexedDB persistence in browser apps. Batching outbound webhooks. • Data / databases: Commit delay settings in database WALs. Micro-batching in stream sinks. • Embedded: Coalesce radio transmissions or flash writes within a short window to save power.
Watch out: Under light load the delay is pure added latency. Apply it only when requests are frequent, and keep it well below the latency budget.

### pebble-029 — Batch updates per lock acquisition, with a bounded batch size
Lens: amortization · Source: Pebble
Principle: Instead of taking an exclusive lock for every small update, buffer the updates and apply them in groups under one acquisition. For long bulk operations, do the opposite: cap the work done per acquisition and release the lock between batches.
Why it is faster: Exclusive lock acquisition under contention costs far more than the update it protects. Recording LRU hits in a per-thread buffer and applying 64 at a time divides that cost by 64. An approximate policy loses nothing important when a buffer is occasionally dropped. For bulk eviction, a small fixed batch per acquisition followed by a yield bounds how long any other thread waits, while still amortizing the lock.
Applies elsewhere: Web / backend: Buffered access recording in in-process caches (Caffeine-style read buffers). Batched metrics counters flushed periodically. • Data / databases: Batch deletes that commit every N rows, so other transactions get a turn. • Native / systems: Per-thread free lists returned to a global allocator in chunks. Incremental cleanup sweeps in game loops.
Watch out: Buffered updates are applied late or occasionally lost. That is fine for approximate policies like LRU and wrong for exact accounting. Batches that are too large bring back long lock holds.

### pebble-030 — Hand large or conflicting bulk inputs over as whole immutable units instead of copying or flushing first
Lens: amortization · Source: Pebble
Principle: When a write is too large for the in-memory buffer, or an ingest overlaps buffered data, queue it as its own immutable unit in the flush pipeline. Do not copy it into the buffer or force a synchronous flush first.
Why it is faster: Copying a batch larger than the memtable into a skiplist pays per-key insertion for data that will be flushed right away. Forcing a memtable flush before an overlapping ingest stalls all writers for the flush. Deferring dependent work (such as an excise) to flush time, and waiting only on real conflicts, removes more stalls.
Applies elsewhere: Data / databases: Bulk inserts that write segment files directly (columnar stores) instead of going through the row buffer. Watch out: Queued units must keep the correct sequence-number order relative to the memtables around them. Many small staged units can raise read amplification until they are flushed.

### pebble-032 — Accumulate operands and combine once at the end
Lens: amortization · Source: Pebble

### pebble-033 — Amortize full snapshots against accumulated deltas
Lens: amortization · Source: Pebble
Principle: For a log of edits that is periodically compacted into a fresh snapshot, trigger the rewrite when the accumulated edit volume is comparable to the snapshot size. A fixed size threshold is the wrong trigger.

Watch out: Recovery time grows with the allowed delta volume, so cap it absolutely as well as relatively when startup latency matters.

### pebble-037 — Frame-of-reference integers: one base plus the narrowest fixed-width deltas

### pebble-152 — Store large or cold values apart from keys, and read them lazily
Lens: io · Source: Pebble
Principle: Keep the frequently scanned part (keys and small values) dense. Move large values, and old versions that are probably garbage, into separate blocks or files. Readers get a lazy handle that fetches the value only on demand.

### pebble-171 — Cache decoded entries to iterate backward over forward-only encodings
Lens: storage-engine · Source: Pebble
Principle: Delta- or prefix-encoded data decodes only forward. To step backward, jump to the previous restart point, decode forward once, and cache the decoded entries compactly so later Prev calls pop from the cache.
Why it is faster: Without a cache, each Prev re-decodes from the restart point, so iterating backward through a block of n entries costs O(n^2). Caching makes it O(n). Storing cache entries as small integer offsets rather than slices keeps the cache in L1, and filling it only when needed avoids paying for forward-only use.
Applies elsewhere: Web / backend: backward scrolling over delta-encoded logs or chat histories. • Native / systems: reverse iteration over UTF-8 or varint streams, and undo stacks over compressed edit logs. • Data / databases: `ORDER BY ... DESC` scans over prefix-compressed index pages.
Watch out: the cache costs memory per iterator. Size it to one restart interval and reuse it.

### pebble-172 — Randomly disable fast paths in test builds
Lens: observability · Source: Pebble
Principle: Under invariant or test builds, take the slow path at random even when the fast path applies. Randomized and metamorphic tests then exercise and cross-check both.
Why it is faster: This does not speed anything up directly. It is what makes aggressive fast paths safe to ship. A fast path that almost always fires leaves the general path untested, and a bug in either one can hide behind the other. Random bypass gives both coverage at no production cost.
Applies elsewhere: Web / backend: randomly bypass caches or memoization in test builds and compare results. • Native / systems: fuzz flags that switch off SIMD or specialized kernels, and chaos toggles for connection reuse. • Data / databases: randomly disable plan shortcuts such as index-only scans or constant folding in test runs.
Watch out: the randomization has to be compiled out of production builds, and seeded so failures can be reproduced.

### pebble-173 — Use the cheapest clock that answers the question
Lens: observability · Source: Pebble
Principle: For durations and latency measurements, read a raw monotonic counter rather than the full wall clock.
Why it is faster: A wall-clock read that also captures a monotonic component does more work than a single monotonic nanosecond read. Instrumented hot paths may read the clock several times per operation, so halving that cost matters.
Applies elsewhere: Web / backend: use `performance.now()` or `process.hrtime` instead of `Date` in JS timing. • Native / systems: `CLOCK_MONOTONIC(_COARSE)` or TSC reads for histograms, and `Instant` in Rust. • Embedded: a free-running hardware timer counter instead of an RTC read.
Watch out: a monotonic value cannot be converted to wall time for logs. Coarse clocks lose resolution for very short intervals.
Seen in Pebble: ddcd530162 2024-11-04 `time.Now` was replaced with `crtime.NowMono` across production code. It is about 2x faster.

### pebble-174 — Benchmark the whole path, keep benchmarks quiet, and revert on evidence
Lens: observability · Source: Pebble
Principle: Measure end to end, including FFI and wrapper costs, not just the function you changed. Keep assertion helpers out of timed loops, and remove mechanisms whose benefit does not show up in workload-level numbers.
Why it is faster: Micro-level reasoning misleads. A "cheaper" C call can go through a more expensive wrapper, and test helpers inside benchmark loops add noise larger than the effect being measured. Workload benchmarks catch regressions that unit benchmarks miss, and they justify removing complexity.
Applies elsewhere: Web / backend: load-test the full request path before adopting a micro-optimized serializer, and keep assertions and logging out of timed regions. • Native / systems: benchmark across the FFI or JNI boundary, not just the native function. • Data / databases: back each tuning mechanism with a workload benchmark, and delete mechanisms that do not pay.
Watch out: workload benchmarks are noisy too. Use repeated runs and statistical comparison (benchstat-style) before you accept or revert a change.
