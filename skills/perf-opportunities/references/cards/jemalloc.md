### jemalloc-001 — Replace one ordered container with an array of per-class buckets, a non-empty bitmap and cached minima
Lens: algorithms · Source: jemalloc
Principle: When searches are "smallest adequate item", keep one small container per size class, mark non-empty classes in a bitmap, and cache each bucket's minimum key in a flat array, so a search is a bit-scan plus a contiguous array walk instead of a tree descent.
Why it is faster: A single tree keyed by (size class, address) recomputes the class on every comparison and dereferences a node per level. Bucketing classifies once on insert/remove, the bitmap skips empty classes with one find-first-set, and the cached minimum turns "inspect the root of each candidate heap" (one cache miss per class) into a sequential scan of a dense array. The bucket count must be bounded and small (page-size classes here).
Applies elsewhere: Web / backend: Priority job queues with a fixed number of priority levels: an array of FIFOs plus a bitmap of non-empty levels gives O(1) dequeue. • Embedded: RTOS ready queues (a priority bitmap plus `clz`), TLSF-style real-time allocators. • Native / systems: Segregated free lists in any allocator; timer wheels caching each slot's earliest deadline. • Data / databases: Free-space maps by size class; per-partition min/max summaries (zone maps) scanned before touching partitions.
Watch out: only pays when the key space quantizes into a small fixed number of classes; cached minima must be kept exact on every insert/remove or searches silently pick the wrong bucket.

### jemalloc-002 — Track free slots with word-wide bit scans; add summary levels only when the bitmap is large
Lens: algorithms · Source: jemalloc · Also: TigerBeetle
Principle: A bitmap plus a hardware find-first-set instruction finds the lowest free slot in one instruction per machine word; a hierarchical summary is only worth its extra writes when the bitmap spans many words.
Why it is faster: Bitmaps are dense (one bit per slot), naturally prefer low addresses, and `ffs`/`clz` process 64 slots per instruction. Summary levels make search O(levels) but every set/clear must propagate upward, doubling writes. For a few words a linear scan wins; flat bitmaps with range operations (set/clear runs, iterate runs, longest run, and/or/not) cover more uses with simpler code.
Applies elsewhere: Web / backend: Slot tables for fixed-size connection or session pools. • Embedded: Free-block maps in flash file systems; slot occupancy in static object pools with no heap. • Native / systems: Page and inode allocation maps; FD tables (lowest free descriptor). • Data / databases: Null bitmaps and selection vectors in columnar engines; free-page maps that also need "longest free run".
Watch out: a linear scan degrades on very large, mostly-full bitmaps; keep a start hint or cursor, or add one summary level only after measuring.

### jemalloc-003 — Drain many free slots per bitmap word, searching and propagating once per word
Lens: algorithms · Source: jemalloc
Principle: When you need N free slots, find a non-empty word once, take all its set bits with popcount and clear-lowest-set-bit, and write back counters and summary state once per word rather than once per slot.
Why it is faster: Allocating bits one at a time repeats the search from the root (or from word 0) and the upward fullness propagation for every slot. Working per word hoists base/stride loads out of the loop, uses `popcount` to know how many slots the word yields, and lets a forward cursor skip the already-exhausted prefix on the next word.
Applies elsewhere: Web / backend: Reserving N free seats/slots from a bitset in a booking or quota service. • Native / systems: Allocating runs of blocks or inodes from file-system bitmaps; GPU slab allocators claiming a warp's slots from one word. • Data / databases: Iterating set bits in Roaring/bitset indexes and selection vectors word by word.
Watch out: a cursor that skips "exhausted" words is only valid while something (a lock, single ownership) guarantees those words cannot regain free bits during the batch.
Seen in jemalloc: 4b82872ebf 2018-10-18 `arena_slab_reg_alloc_batch` fills several thread-cache slots per slab visit. • 13c237c7ef 2018-10-29 17aa470760 2018-10-29 Walk bitmap groups, take `popcount_lu(g)` slots from each with `cfs_lu` (clear first set), and update the slab's free count once. • 8487209a9c 2026-10-02 29a4539e52 2026-10-02 For hierarchical bitmaps, find the first non-full leaf group once (`bitmap_ffu_group`), drain it with bit operations, then store and propagate once. • 0d9d5d553e 2026-10-08 The linear variant keeps a forward cursor so later groups do not rescan the exhausted prefix (safe because the bin lock prevents earlier groups from refilling).

### jemalloc-004 — Use a pairing heap when you only need insert, delete and find-min
Lens: algorithms · Source: jemalloc
Principle: If you never iterate in order or search for neighbours, a pairing heap gives O(1) insert and cheap first() with far fewer memory touches than a balanced tree; keep its lazy merge work bounded and done by the thread whose cache is warm.
Why it is faster: A red-black tree rebalances (touching several cold nodes) on every insert and delete. A pairing heap just links the new node; work is deferred to the next delete-min, amortized O(log n). Sibling merging must be FIFO multipass to avoid degenerate chains and deep recursion. A purely lazy aux list can make one delete-min do a huge merge while holding a lock, so pre-merging a little on each insert bounds worst-case hold time.
Applies elsewhere: Web / backend: Timer and timeout queues in event loops; delayed-job schedulers. • Native / systems: Scheduler run queues; Dijkstra/A* open sets with decrease-key. • Data / databases: Free-space maps ordered by size; merge queues for k-way merges.
Watch out: no ordered iteration or nearest-key search; naive LIFO merging can go quadratic; very lazy variants move cost into rare long pauses unless you pre-merge.
Seen in jemalloc: 6bafa6678f 2016-02-29 Two-pass pairing heap with an aux list ("much faster first(), delete(), and insert()"); an array heap was rejected because of cold-cache loads. • 4a0dbb5ac8 2016-02-29 Available runs moved to it: "a 1% cpu win, and 2% latency win ... large free()s, and small bin frees are now O(1)". 613cdc80f6 2016-03-08 fc0372a15e 2016-05-17 Bin runs and extent size/address trees followed. • c6a2c39404 2016-03-26 FIFO (not LIFO) multipass sibling merging fixes degenerate merges and deep recursion; per-node parent pointers removed (parent inferred from the leftmost sibling's prev link). • 7c6c99b829 2017-09-26 The available-extent set switched from a red-black tree to a pairing heap that reuses the existing heap link. • 40d53e007c 2021-07-26 After the N-th insert do `ffs(N)` pairwise aux merges, keeping the aux list O(log N) and moving work to the cache-warm inserter; dae24589bc 2021-07-26 a node smaller than the root simply becomes the root; 08a4cc0969 2021-07-19 macros became force-inlined functions with no profile change.

### jemalloc-005 — Map addresses to metadata with a shallow, fixed-depth radix tree shaped to the real key width
Lens: algorithms · Source: jemalloc
Principle: For pointer-to-metadata lookups, use a radix tree with wide nodes whose depth is fixed at compile time from the number of significant address bits, so a lookup is a couple of dependent loads with no comparisons.
Why it is faster: Each tree level is a dependent load (a potential cache miss). User-space addresses use only ~47-48 bits and the low page bits are irrelevant, so dropping both and using wide nodes cuts depth to 1-3 levels. Fixed depth lets the walk be unrolled and indexes become compile-time constants. Leaves sized to what is stored, and nodes sized per level, keep memory proportional to use, and nodes allocated from demand-zero memory only consume RAM where written.
Applies elsewhere: Web / backend: Sparse ID-to-record maps where IDs are dense at the low end. • Embedded: Address-to-handler maps for memory-mapped peripherals; emulator memory maps. • Native / systems: Page-to-owner lookup in GCs and JITs; IP longest-prefix tries with wide strides. • Data / databases: Page-id to buffer-frame maps; bulk range updates in shadow page tables.
Watch out: the significant-bit assumption is platform-specific (5-level paging, tagged pointers); wide nodes waste memory unless backed by lazily committed pages.
Seen in jemalloc: b954bc5d3a 2014-01-02 rtree leaves store a `uint8_t` (membership only) instead of a pointer and nodes grow to 64 KiB: depth "from 13 to 3 on 64-bit systems". • 8d0e04d42f 2015-01-30 A `start_level[lg_floor(key) >> ...]` table starts lookups below the root, "skipping the root node on x64 (possible because the top 16 bits are all 0 in practice)". • f500a10b2e 2015-01-30 Large sparse nodes are carved from demand-zeroed virtual memory, so untouched parts cost no RAM and need no memset. • dc553d52d8 2016-10-28 Allocate child nodes with the correct per-level fanout, so leaves are 2^4 elements, not 2^16. • f5cf9b19c8 2017-02-06 Levels become a `static const` table chosen from `LG_VADDR` (1-3 levels, insignificant high and low bits dropped), so key splitting no longer reads runtime fields. • ce41ab0c57 2017-03-22 The root array is embedded in the tree struct: "avoids one atomic operation per tree access". • 7c964b0352 2021-03-17 Writing one value over a key range looks up the leaf only when crossing a leaf boundary and encodes the value once outside the loop (the interior-registration path "became noticeable in perf profiles").

### jemalloc-006 — Put a tiny per-thread lookup cache in front of a large index: direct-mapped L1 plus a small LRU victim cache
Lens: algorithms · Source: jemalloc
Principle: Successive lookups by one thread hit nearby keys, so cache recent results thread-locally: a direct-mapped table answers most hits with one index and one compare, and a small victim list catches conflict misses before falling back to the full walk.
Why it is faster: Even a two-level radix walk is several dependent loads. A direct-mapped cache hit is one tag compare on data already in L1. Direct mapping suffers conflicts, so a tiny LRU behind it catches them: on an L2 hit swap the entry into L1, on a full miss demote the L1 entry. Moving a hit only one slot toward the front ("bubble up by one") converges to the same hot set without a memmove.
Applies elsewhere: Web / backend: Per-worker memo of the last few route or tenant resolutions in front of a shared map. • Embedded: Software TLBs in emulators and MMU-less systems. • Native / systems: Inline caches with a megamorphic fallback in VMs; filesystem path-lookup caches. • Data / databases: Page-id to frame cache in a buffer manager; B-tree "finger" for sequential inserts.
Watch out: per-thread caches must be invalidated when the underlying mapping changes; with random access the extra compare is pure overhead.
Seen in jemalloc: 6f29a83924 2016-06-02 Per-thread `rtree_ctx` caches the last key and traversal path; `lg_floor(key ^ cached)` finds the deepest shared level: "~3 CPU cycles per metadata lookup ... versus ~11 cycles prior". • 4a346f5593 2017-02-03 Replaced the path cache with an LRU of leaf pointers ("logically much simpler, slightly faster"). • af3d737a9a 2017-03-27 "Only bubble up the cache hit element by 1" instead of memmove-to-front on the free fast path. • 3c9c41edb2 2017-04-14 Final shape: 16-entry direct-mapped L1 indexed by leaf-key bits plus 8-entry LRU L2, with swap-on-L2-hit and demote-on-miss. • 2fee33d292 2026-09-25 Only the L1 hit is inlined; the miss path calls an out-of-line `rtree_read_slow`.

### jemalloc-007 — Find mergeable neighbours by direct address lookup instead of an address-ordered tree
Lens: algorithms · Source: jemalloc
Principle: Register each free region's first and last unit in an address-indexed map; on free, look up the unit just before and just after to find neighbours in O(1), and keep their state in the map entry so they can be checked without touching them.
Why it is faster: An address-ordered tree costs O(log n) per insert and remove just to support neighbour queries. Boundary entries in a map you already maintain make neighbour discovery a lookup. Storing a few state bits next to the pointer (in alignment-freed low bits) lets a thread validate a neighbour with one atomic load before locking or dereferencing it, which can replace a separate lock table.
Applies elsewhere: Native / systems: Boundary-tag and buddy allocators; GPU heap interval merging. • Data / databases: File-system and DB free-extent coalescing via a block-to-extent map. • Web / backend: Merging adjacent time slots in calendar/reservation services keyed by slot index.
Watch out: boundary entries must be updated atomically with splits and merges; racy reads need a state protocol and re-validation after locking.
Seen in jemalloc: b2a9fae886 2016-03-27 ffa45a5331 2016-05-16 Set rtree entries for each extent's last page and "use rtree rather than [sz]ad trees for chunk split/coalesce", deleting the address-ordered tree. • 47613afc34 2016-05-24 Register every page of slabs (interior entries) in the rtree. • 70d1541c5b 2021-02-26 4d8c22f9a5 2021-02-26 Track `is_head` and a 3-bit extent state in the leaf (metadata aligned to 128 B to free the bits). • 1784939688 2021-03-04 7dc77527ba 2021-03-25 Rtree-tracked states (with transitional `updating`/`merging`) protect neighbours outside the cache locks, so the address-hashed mutex pool was deleted.

### jemalloc-008 — Update a derived summary or ordering only when the change can affect it
Lens: algorithms · Source: jemalloc
Principle: Before recomputing a maximum, a minimum or a priority position after an update, check cheaply whether the update could have changed it, and stop the recomputation as soon as the old value is re-established.
Why it is faster: Most updates leave a summary unchanged: allocating from a run shorter than the longest free run cannot change "longest free run", and an item whose sort key and bucket did not change need not leave its heap. Remove-plus-reinsert and full rescans pay O(log n) or O(n) for a no-op.
Applies elsewhere: Web / backend: Leaderboards that move an entry only when its score bucket changes. • Native / systems: Schedulers doing decrease-key only if the deadline bucket changed; timer wheels skipping same-slot moves. • Data / databases: Heap-only-tuple style updates that skip index maintenance when no indexed column changed; largest-free-extent tracking.
Watch out: the "can it change?" test must be exact; a wrong shortcut corrupts ordering silently, so keep debug assertions that recompute and compare.
Seen in jemalloc: 271a676dcd 2021-02-06 `hpdata_reserve_alloc` rescans for the longest free range only when the allocation came from a range of that length, and breaks as soon as another equal-length range is found. • e1d2e5ee34 2026-10-29 The pageslab set snapshots the key before an update and keeps the heap link if the slab stays eligible with the same bucket and age. • 192c83c047 2026-10-30 Old and new bucket indices are computed once per update and reused for stats and container operations.

### jemalloc-009 — When you need an ordered tree, pick the variant with the lowest height and cheapest fixups, and drop sentinel nodes
Lens: algorithms · Source: jemalloc
Principle: Among balanced trees, prefer a variant with a tighter height bound and lazy (bottom-up) rebalancing, and use NULL leaves rather than a sentinel node the size of a full element.
Why it is faster: Height bounds the number of dependent loads per operation; fixups done on the way back up avoid speculative transformations on the way down. A sentinel "nil" node is as large as an element, which wastes memory and cache when elements are big.
Applies elsewhere: Embedded: Intrusive ordered maps in RTOS timers with no allocation. • Native / systems: Kernel interval trees; free-extent trees in file systems. • Data / databases: In-memory ordered indexes in embedded databases.
Watch out: if you only need min/insert/delete, a heap (above) beats any balanced tree.
Seen in jemalloc: f3ff75289b 2010-02-28 Left-leaning 2-3 red-black trees instead of 2-3-4 cut maximum height from 3 lg n to 2 lg n; lazy balance fixup "improves insert/remove speed by ~30%". • 2b1fc90b7b 2016-02-17 Removed `rbt_nil`, which "is the whole size of the node and can be quite large" (~100 bytes for the map element).

### jemalloc-010 — Derive several independent hashes from one wide hash call
Lens: algorithms · Source: jemalloc
Principle: A hash function that emits 128 bits in one call yields two independent 64-bit hashes at no extra cost, which is all cuckoo or double hashing needs.
Why it is faster: Multi-probe schemes need k independent hash values; computing k separate hashes repeats the expensive mixing. One wide hash amortizes it.
Applies elsewhere: Web / backend: Bloom filters deriving k probes from two halves (Kirsch-Mitzenmacher). • Data / databases: Cuckoo filters; consistent hashing with multiple probes.
Watch out: the two halves must be well mixed; a weak wide hash correlates them and inflates collision rates.
Seen in jemalloc: ae03bf6a57 2013-01-22 Moved from MurmurHash2 to MurmurHash3 "because the latter generates 128 bits in a single call for no extra cost", simplifying the cuckoo hash table (`ckh`).

### jemalloc-011 — Use a cheap LCG for non-cryptographic randomness: take high bits, reject to stay unbiased
Lens: algorithms · Source: jemalloc
Principle: For jitter, offsets and sampling, an LCG is enough if you take its top bits (low bits are weak) and get an unbiased value in [0, range) by retrying when a power-of-two draw exceeds the range.
Why it is faster: One multiply-add per draw, no division (modulo) and no bias; rejection needs fewer than two tries on average.
Applies elsewhere: Web / backend: Load-balancer random choice; retry jitter. • Embedded: Randomized backoff on MCUs without an FPU or hardware RNG. • Native / systems: Skip-list level generation; game effects RNG.
Watch out: never for security; correlated seeds across processes run in lockstep, so seed from something per-instance.
Seen in jemalloc: 34676d3369 2016-02-09 `prng_lg_range()` returns `ret >> (64 - lg_range)`; `prng_range()` uses repeated trials. • 5d6cb6eb66 2016-11-07 Word-sized (`u32`/`size_t`) variants avoid emulated 64-bit atomics on 32-bit platforms.

### jemalloc-012 — Order pointer writes so an existing field serves as the temporary
Lens: algorithms · Source: jemalloc
Principle: In linked-structure splices, reorder the writes so a field you are about to overwrite holds the intermediate value, removing temporaries and type parameters.
Why it is faster: Fewer live values and writes in a tiny hot primitive; in concurrent variants fewer writes also shrink the race window.
Applies elsewhere: Native / systems: Intrusive list libraries, kernel `list_splice`. • Embedded: Ring-list primitives in RTOS queues.
Watch out: micro-level; only worth it in primitives used everywhere, and needs tests for self-splice cases.
Seen in jemalloc: c9d56cddf2 2020-04-01 `qr_meld` swaps the prev pointers first, then fixes `->next`, dropping a temporary.

### jemalloc-013 — Let callers supply what they know, and encode rare cases so a cheap test can rule them out without a lookup
Lens: laziness · Source: jemalloc
Principle: Accept facts the caller already holds (the object's size), and arrange for the exceptional cases to be recognizable by a property you can test for free (pointer alignment), so the common case never consults the metadata index.
Why it is faster: Mapping pointer to size class is a radix-tree walk plus decode. With a caller-supplied size it is a table lookup on a value already in a register. The size alone is not enough if a few objects are special (sampled allocations stored differently); forcing those to a distinctive alignment means one mask test separates them, so the trust in the caller's size stays safe.
Applies elsewhere: Web / backend: APIs that accept a known content length or precomputed ETag instead of re-scanning the body. • Embedded: Pool `free(ptr, size)` APIs that need no per-block header. • Native / systems: C++14 sized `operator delete`; tagged pointers whose low bits mark special objects. • Data / databases: Pass the known row length or page type into decoders instead of re-reading headers.
Watch out: a caller passing a wrong size corrupts state silently; keep a debug check, and remember the alignment trick costs padding for the special objects.
Seen in jemalloc: 4cfe55166e 2014-08-28 `sdallocx()`: sized deallocation uses `small_size2bin(size)` with no map read, "~10%" on an alloc/free microbenchmark. • 665769357c 2013-12-15 5fbad0902b 2013-12-15 Pass usize to the profiling setter instead of reading the page map, delaying the read "until it's unavoidable"; 594c759f37 2015-09-02 decide from `usize` and the value in hand "to avoid reading run metadata". • 1ab2ab294c 2017-07-31 A non-page-aligned pointer cannot be a sampled allocation, so sized free uses the caller's size and skips the rtree. • 88d9eca848 2020-01-28 Sampled allocations are forced page-aligned "so that sampled allocations can be identified w/o metadata lookup", making sized free usable in every configuration. • cdb2c0e02f 2023-07-14 Added C23 `free_sized`/`free_aligned_sized` so more callers reach the sized path.

### jemalloc-015 — Skip checks and preparation the source already guarantees or the next step will overwrite
Lens: laziness · Source: jemalloc
Principle: Do not validate memory whose state is guaranteed by its source, and do not prepare (purge, zero, fill) memory that the very next step rewrites.
Why it is faster: Debug validation of freshly mapped, known-zero memory touches every page, ruining startup time and RSS. Purging memory that will be junk-filled immediately pays a syscall and a refault for nothing. Validation only belongs where state is uncertain (recycled memory), and only as much as needed.
Applies elsewhere: Web / backend: Do not re-validate input already validated at the trust boundary. • Embedded: Skip clearing a buffer that a DMA transfer will fully overwrite. • Native / systems: Skip zeroing buffers about to be filled by `read()`; avoid clearing render targets fully covered by a draw. • Data / databases: Do not checksum freshly allocated pages before the first write.
Watch out: "the source guarantees it" must really hold (hooks or custom backends may hand back dirty memory).
Seen in jemalloc: 14a2c6a698 2013-01-21 Zeroed-page validation moved from `chunk_alloc()` to `chunk_recycle()`; it "can make a big difference to application startup time and overall system usage". • 6e62984ef6 2013-12-15 "Don't junk-fill reallocations unless usize changes"; 58799f6d1c 2014-08-26 removed redundant junk filling in tcache flush. • 4a2a3c9a6e 2015-08-28 When shrinking with junk filling on, purging the chunk first "is just a waste of time". • 57553c3b1a 2018-11-12 The debug zero-check touches only the first page instead of paging in the whole extent.

### jemalloc-017 — Create expensive state on first real need, but promote callers stuck on the slow path
Lens: laziness · Source: jemalloc
Principle: Allocate heavy per-thread or per-feature state only when an event actually needs it, and gather costly data only for sampled items; if lazy setup leaves some callers permanently on a slow path, promote them after a bounded number of slow calls.
Why it is faster: Most threads never reach a sample point, so creating profiling state on the first allocation wastes memory and time. Resolving symbols or reading clocks only when needed trims startup and per-event cost. Laziness has a failure mode: a role that never triggers full initialization (a thread that only frees) stays slow forever, so a counter-based promotion bounds the penalty.
Applies elsewhere: Web / backend: Allocate tracing spans only for sampled requests; create per-connection TLS buffers on first write. • Embedded: Power up and configure peripherals on first use. • Native / systems: Lazy plugin loading in CLI tools; JIT tier-up after N calls as the promotion rule. • Data / databases: Create per-session sort or hash workspaces on first query that needs them.
Watch out: the "initialized?" check itself must not land on the fast path; fold it into an existing slow-path condition.

### jemalloc-018 — Remove items from an index lazily when they tend to come back
Lens: laziness · Source: jemalloc
Principle: If an item often re-enters a set soon after leaving, leave it in place with a staleness flag and clean it up when the index is next consumed.
Why it is faster: Eager removal and reinsertion each cost a tree operation; with frequent oscillation, most of those operations cancel out. Lazy removal pays only when the consumer encounters a stale entry.
Applies elsewhere: Web / backend: Tombstones in timer heaps when timeouts are frequently reset. • Native / systems: CLOCK-style lazy LRU promotion. • Data / databases: Deferred index cleanup (vacuum) instead of synchronous removal.
Watch out: stale entries cost memory and consumer time; if items rarely return, eager removal is cheaper.
Seen in jemalloc: 45c128d1a9 2009-12-29 "Reduce chunks_dirty red-black tree operations via lazy updating": removal is lazy, so `dirtied && ndirty == 0` is a legal state.

### jemalloc-021 — Move items between private and shared pools in batches, one lock per batch
Lens: amortization · Source: jemalloc
Principle: Keep a private per-thread stash; on a miss take many items from the shared pool under one lock, on overflow return many at once, and organize the returned batch (by owner) before taking any lock.
Why it is faster: Lock acquisition and the shared cache-line transfer are a fixed cost per acquisition; spreading them over N items divides them by N. The batch must be large enough to amortize (hence a capacity floor). When a returned batch belongs to several owners, partitioning it first means each owner's lock is taken once and held only for a contiguous run, with no scanning while locked.
Applies elsewhere: Web / backend: Fetch ID ranges from a sequence service; bulk-dequeue jobs from a shared queue; group outgoing writes by shard before taking per-shard locks. • Embedded: Refill a per-ISR buffer ring from a shared pool in chunks. • Native / systems: Per-CPU slab magazines; batched remote frees sorted by NUMA node. • Data / databases: Group commit; bulk insert grouped by partition.
Watch out: batches hoard memory in private caches; pair them with GC or adaptive sizing (below).

### jemalloc-048 — Bound per-thread caches: a floor for amortization, a cap for footprint, a flush on idle
Lens: allocation · Source: jemalloc

### jemalloc-082 — Use the closed-form formula when the input is a compile-time constant
Lens: cpu-microopt · Source: jemalloc

### jemalloc-122 — Return memory in stages: cheapest reversible hint first, hard release later
Lens: io · Source: jemalloc
Principle: Release unused pages with the cheapest primitive that lets the kernel reclaim them under pressure, and escalate to an eager or irreversible release only after a second delay.
Why it is faster: `MADV_FREE` only marks pages reclaimable: if the program touches them again before the kernel needs them, reuse costs nothing. `MADV_DONTNEED`, decommit or `munmap` free the page immediately, so reuse always pays a fault and zero-fill. Staging (dirty, then lazily freed "muzzy", then clean), each stage with its own timer, pool and lock, gets most of the RSS win cheaply while keeping the expensive step rare. Applies elsewhere: Web / backend: Mark cache entries evictable (soft) before deleting them, so a re-request inside the window is free. • Native / systems: In a language runtime's scavenger, use `MADV_FREE` for recently freed spans and `MADV_DONTNEED` only for long-idle ones. • Data / databases: Use soft delete then physical purge in storage; drop file pages with `fadvise` before truncating.
Watch out: Lazily freed pages still count in RSS until the kernel reclaims them, which confuses monitoring and container limits; that is why jemalloc later made the muzzy stage opt-in.

### jemalloc-123 — Make each release syscall cover as much memory as possible
Lens: io · Source: jemalloc
Principle: Merge adjacent ranges, extend ranges across already-released gaps, and pass many ranges in one vectored call, so the number of syscalls and TLB shootdowns is minimal.

Applies elsewhere: Data / databases: Coalesce adjacent `fallocate(PUNCH_HOLE)` or TRIM ranges, and fsync contiguous dirty ranges together. • Native / systems: Use `writev`, `sendmmsg`, `io_uring` or batched `munmap` instead of one call per buffer. • Embedded: Erase or invalidate flash and cache lines in maximal contiguous blocks rather than per sector.

### jemalloc-124 — Keep address space mapped and recycle it instead of unmapping

### jemalloc-125 — Track which memory is already zero and never zero or check it twice
Lens: io · Source: jemalloc

Watch out: A raw pointer becomes part of the API: its lifetime and memory ordering must be documented and stable.
