### libuv-002 — Pick the priority structure that makes the hottest query O(1)
Lens: algorithms · Source: libuv
Principle: If one query ("what is the earliest deadline?") runs every iteration and inserts and removes are rarer, choose the structure that makes that query constant time. A binary min-heap does this for timers. A balanced tree does not.
Why it is faster: An event loop must know the next timer deadline to compute its poll timeout on every turn. A red-black tree answers that in O(log n) and touches several nodes. A min-heap keeps the minimum at the root (O(1)) and still inserts and removes in O(log n). An intrusive, pointer-based heap (left/right/parent stored inside the timer) needs no array resize and no allocation. A monotonic sequence number as tie-breaker gives FIFO order among equal deadlines with a cheap comparator.
Applies elsewhere: Web / backend: idle-connection and request-timeout tracking. Delayed-job queues. TTL expiry in caches. • Embedded: a software timer list as a heap in a fixed array, giving an O(1) "next wakeup" for tickless sleep. • Native / systems: scheduler run queues. Discrete-event simulators. TCP retransmission timers. • Data / databases: top-k and k-way merge in sort operators. Lease expiry.
Watch out: heaps are poor at ordered iteration and range queries. Keep a tree if you need those. With very many timers that are mostly cancelled before firing, a hierarchical timer wheel can beat both structures.
Seen in libuv: 34f69db83a 2011-04-12 Early Windows timers sit in an RB-tree (`RB_HEAD(uv_timer_tree_s, ...)`). • c9396dd57e 2012-05-31 Unix timers move from libev to libuv's own RB-tree keyed by (deadline, address). `RB_MIN` supplies the next timeout, and pointer comparison breaks ties without a counter. 0ae026dc84 2012-06-09 adds a "lots-of-timers" (million timers) benchmark. • f17c535b73 2013-09-12 Unix replaces the tree with an intrusive binary min-heap (`src/heap-inl.h`). `uv__next_timeout` becomes `heap_min`, the message argues O(log n) → O(1), and ties break by `start_id`. The insertion path is derived from the binary digits of `nelts+1`. Removal fixes followed in d4f904b0e7 2014-02-23 and e002340e50 2014-05-13. • 95c5bf8db1 2018-06-14 Windows and Unix merge into one `src/timer.c` on the heap, replacing Windows' tree "for generally better performance". • 0fd993195f 2020-04-16 The comparator shrinks to deadline, then `return a->start_id < b->start_id;`, dropping two branches.

### libuv-003 — Replace linear lists with intrusive balanced trees for keyed lookups
Lens: algorithms · Source: libuv
Principle: A keyed lookup on a linked list is O(n). An intrusive red-black tree, with its node embedded in the object, gives O(log n) lookup, insert and remove with no allocation, and supports "find all entries with key k" through ordered iteration.
Why it is faster: Lookup cost stops growing linearly with the number of watchers. Embedding the node in the owning struct means insert and remove never call the allocator and never fail. Ordered iteration (`RB_NFIND` + `RB_NEXT`) lets several entries share one key and be visited together. Static generation of the tree functions keeps calls direct and inlinable.
Applies elsewhere: Web / backend: socket-to-session or subscription-id-to-listeners maps that need ordered scans. • Embedded: intrusive trees (no heap) for ordered registries in RTOS kernels. • Data / databases: in-memory ordered indexes. Interval or range lookups.
Watch out: for exact-match lookups on dense integer keys, a direct array (above) is faster still. With a handful of entries, a list may beat the tree's constant factors.
Seen in libuv: dfda5009c2 2012-03-16 c-ares socket handles are stored "in a binary tree... not a linked list". • d3efefb043 2012-02-22 inotify watchers are kept in an RB-tree on the loop, keyed by watch descriptor, so an event finds its watchers in O(log n). • 1e32cb01b5 2012-10-16 Signal watchers live in a global RB-tree keyed by signum. The signal handler finds every watcher for a signal with `RB_NFIND` + `RB_NEXT`. • 87151c8a7b 2012-03-16 Tree code is generated static (`RB_GENERATE_STATIC`).

### libuv-004 — Hash with chunked buckets whose first chunk is static, and size it to what is touched
Lens: algorithms · Source: libuv
Principle: For a map keyed by mostly sequential integers, hash with a cheap modulo and store each bucket as a linked list of small arrays. Allocate the first array of every bucket statically, so typical use never allocates. Size static storage to what is actually accessed.
Why it is faster: `key % 256` spreads sequential fds evenly at almost no cost. Arrays of 16 entries scan contiguous memory rather than chasing a pointer per entry. A static first chunk means no allocation or allocation failure in the common case. Static space is still memory: over-reserving bloats BSS and touched RSS without speeding up the lookup.
Applies elsewhere: Embedded: a static first segment for tables that rarely grow, with heap overflow chunks only when needed. • Native / systems: per-fd metadata in proxies. Unrolled linked lists for cache-friendly chaining. • Data / databases: buffer-pool hash chains in blocks. Right-sizing a map's initial capacity to the observed working set.
Watch out: modulo hashing only works while keys stay roughly sequential. Adversarial or clustered keys degrade to long chains. Audit static tables: an indexing bug can silently reserve far more than is used.
Seen in libuv: 2c279504f9 2019-05-09 The Windows fd hash (`src/win/fs-fd-hash-inl.h`, for `UV_FS_O_FILEMAP`) uses `UV__FD_HASH_SIZE 256`, `UV__FD_HASH_GROUP_SIZE 16` and a static `uv__fd_hash_entry_initial[]`, "a single linked list of arrays is kept to minimize allocations". • 12fbd34475 2025-08-24 The static initial table reserved SIZE×GROUP_SIZE entries, but only every 16th was used. Shrinking it to SIZE cut it from about 2592k to 162k (16x). Search, insert and delete timings were logged to confirm no regression.

### libuv-005 — Keep a counter instead of a container when only the size is asked
Lens: algorithms · Source: libuv
Principle: If a collection is only ever checked for emptiness or size, replace it with an integer count.
Why it is faster: Each element no longer carries link pointers, and insert and remove become one increment or decrement instead of relinking nodes. The liveness check becomes a compare against zero. The structure was paying full container costs for a question a counter answers.
Applies elsewhere: Web / backend: an in-flight request count for graceful shutdown instead of a set of request objects. • Embedded: outstanding-DMA counters in drivers. • Data / databases: pin counts instead of pin lists on buffer pages.
Watch out: you lose the ability to enumerate or cancel the items. Make sure no debug, cancel-all or leak-report path needs the list. A counter shared across threads must become atomic, so measure that cost.
Seen in libuv: 88c2af0e65 2017-11-14 `loop->active_reqs` changes from an intrusive queue to `union { void* unused[2]; unsigned int count; }`. `uv_req_t.active_queue[2]` becomes reserved and `uv__has_active_reqs()` is `count > 0`. The body calls the queue "unnecessary extra space and work". The union keeps the ABI size. • 3e0b846bdb 2023-03-28 A `loop_alive` benchmark (200M `uv_loop_alive()` calls) was added to measure making that counter atomic.

### libuv-006 — Stop scanning once the known number of hits is found
Lens: algorithms · Source: libuv
Principle: When an API tells you how many items are ready (poll's return value, a popcount, a completion count), stop the scan as soon as you have found that many. Hoist special cases out of the per-item loop.
Why it is faster: A scan of a large pollfd array where a few fds are ready otherwise visits every slot. Ending at the reported count makes the cost proportional to the work, not the table size. Copying result bits directly instead of translating them bit by bit and moving invariant checks out of the loop cut per-element instructions further.
Applies elsewhere: Native / systems: `select`/`poll` fallbacks in portable reactors. Bitmap scans that stop when the popcount is reached. • Embedded: DMA descriptor rings that stop at the hardware completion count. • Data / databases: `LIMIT k` early termination. Bloom or bitmap index scans that stop at a known match count.
Watch out: the count must be exact. If one slot can contribute more than one hit, or the count includes items you skip, an early stop drops events.
Seen in libuv: cbac5f1693 2017-05-31 The z/OS `epoll_wait` emulation (`os390-syscalls.c`) adds `reventcount < pollret` to the loop condition, returns early on `pollret <= 0`, copies `revents` directly, and drops a mutex lock/unlock pair from the hot path ("improve loop_count benchmark performance"). • 7d988e0763 2020-03-15 "move mq check out of loop to save cpu cycles": the message-queue slot test is hoisted out of the per-fd loop.

### libuv-007 — Sort with a byte-wise comparator unless humans read the order
Lens: algorithms · Source: libuv
Principle: Locale-aware collation is expensive and environment-dependent. For internal ordering, compare bytes.
Why it is faster: `strcoll()` builds collation weights through locale tables for every comparison, and a sort makes O(n log n) comparisons. `strcmp` is a tight, often vectorized byte loop. The order also stops depending on the user's locale, so results are reproducible.
Applies elsewhere: Web / backend: plain `<` for internal JS sorts, and `Intl.Collator` only for UI lists. • Data / databases: binary (`C`) collation for keys and indexes that never face users. • Native / systems: byte-order map keys. Deterministic build and file listings.
Watch out: users expect locale order in visible lists ("é" next to "e", case-insensitive). Changing a public API's order is a behaviour change.
Seen in libuv: e7bc260c42 2016-09-12 `uv__fs_scandir()` replaces `scandir(..., alphasort)`, which uses `strcoll()` in glibc and musl, with `uv__fs_scandir_sort` built on `strcmp`.

### libuv-010 — Report synchronous completions through a pending phase, not on the caller's stack
Lens: scheduling · Source: libuv
Principle: When an async operation finishes immediately, queue its completion for a dedicated "pending" phase of the loop instead of invoking the callback inline. A callback that may complete synchronously stays asynchronous.
Why it is faster: Inline callbacks re-enter user code while the library is mid-operation, which grows the stack and forces defensive state checks. A pending queue runs several completions in one pass, before the next poll, with no kernel round trip. Execution order is the same whether the kernel answered at once or later.
Applies elsewhere: Web / backend: promise resolution through a microtask queue (never "Zalgo"). Batched ack callbacks. • Data / databases: storage engines that complete cached reads through the same completion queue as disk reads. • Native / systems: `ValueTask`-style APIs that still defer continuations.
Watch out: deferral adds one phase of latency. The loop must also treat a non-empty pending queue as "do not block" (see the entry above) or the deferred callback waits for an unrelated event.
Seen in libuv: 9b49e4c359 2011-06-22 "unix: sync writes": completed write requests go to `write_completed_queue` and an event is fed with `ev_feed_event`. • 1282d64868 2012-08-23 With libev removed, this becomes `uv__io_feed()` plus `loop->pending_queue`, run by `uv__run_pending` before polling.

### libuv-011 — Order loop phases deliberately and do each one once per turn
Lens: scheduling · Source: libuv
Principle: Decide once where each class of work runs in an iteration (I/O, then special watchers, then timers) and avoid running a phase twice per turn. Defer special events until after the ordinary batch they relate to.
Why it is faster: Running timers before and after polling costs an extra clock read and an extra heap scan per iteration with no benefit. Handling a "child exited" signal before that child's final stdout bytes reverses the user-visible order and forces another poll. Recording "seen" during dispatch and running the special watcher once at the end fixes the order and removes an extra non-blocking poll.
Applies elsewhere: Web / backend: run layout/paint once per frame after all input handlers (React batching, `requestAnimationFrame`). • Embedded: process I/O ISR flags first and housekeeping/watchdog flags last in the superloop. • Data / databases: run checkpoint triggers after the batch of user requests in a cycle, not interleaved.
Watch out: phase order is observable behaviour. Users may depend on timers firing before I/O in the first iteration. Document it and change it only with tests for ordering.
Seen in libuv: 4a5b3f982e 2015-11-07 In every backend's `uv__io_poll()`, the signal pipe watcher is only flagged (`have_signals = 1`) during dispatch. After the batch its callback runs once and the poll returns instead of polling again, so child output arrives before the exit event. • 6600954906 2023-03-20 Unix and Windows `uv_run`: the top-of-loop `update_time` + `run_timers` becomes a single pre-loop call for `UV_RUN_DEFAULT`. Inside the loop, time is updated and timers run once, after poll. • 24d1d0802d 2023-06-14 The pre-loop timer pass is skipped when the loop is stopped or unref'd.

### libuv-012 — Expose the loop's wait handle and timeout so another loop can drive it
Lens: scheduling · Source: libuv
Principle: Hand out the single kernel object the loop waits on (epoll/kqueue/port fd) plus the computed next timeout. A host loop can then wait on it and run one non-blocking iteration when it fires.
Why it is faster: Without this, combining two event systems needs a second thread that polls and wakes the first, with cross-thread wakeups and locking on every event, or nested blocking calls that stall one loop. With one fd and one timeout, the host does a single wait for both.
Applies elsewhere: Native / systems: integrate a DB client's socket into GLib or Qt loops. Embed a JS runtime in a game engine's frame loop. • Web / backend: drive an async HTTP client from an existing reactor instead of a helper thread.
Watch out: the timeout must account for all queued work (see "Block only when nothing is runnable"), or the host sleeps while callbacks wait.
Seen in libuv: 09a7f85b70 2012-11-26 Adds `uv_backend_fd()` and `uv_backend_timeout()`, "Useful for embedding libuv's event loop in another event loop".

### libuv-016 — Defer cleanup until it matters, but not when stale state can resurface
Lens: laziness · Source: libuv
Principle: On stop, clear only the cheap userspace record and skip the kernel deregistration. If the kernel later reports an event for an entry with no owner, clean it up then. Make cleanup eager where a deferred delete can act on a reused identity or keep firing forever.
Why it is faster: Watchers that stop and restart in the same tick, which is common, pay no syscalls at all. Only entries that actually fire again pay for their deletion. Lazy deletion is unsafe when the kernel object outlives your view of it. epoll tracks file descriptions, so a dup'ed or inherited fd keeps reporting events you can no longer deregister. A batched delete may run after the fd number was reused. Those cases need immediate deletion.
Applies elsewhere: Data / databases: tombstones in hash tables and LSM trees, purged at compaction. • Native / systems: lazy deletion in priority queues (mark cancelled, skip on pop). • Web / backend: deferred unsubscription in pub/sub. Write-behind caches that defer inserts but invalidate synchronously.
Watch out: deferred deletion is only safe if the identity cannot be reused or duplicated in the meantime, and if a stale event is harmless. With level triggering, a stale registration nobody consumes is a CPU spin.
Seen in libuv: 1282d64868 2012-08-23 `uv__io_stop` sets `loop->watchers[fd] = NULL` without touching epoll. In `uv__io_poll`, an event with `w == NULL` triggers `EPOLL_CTL_DEL` ("File descriptor that we've stopped watching, disarm it"). On re-add, `EEXIST` from ADD is retried as MOD. Same scheme with EV_DELETE in kqueue. • 84f305915f 2014-02-05 / 780d8ad8e5 2014-02-05 `uv__platform_invalidate_fd` always does `EPOLL_CTL_DEL` on close, because forked children holding the description caused "spurious events that cause the event loop to spin repeatedly". • ce56a85b19 2017-08-08 `uv__poll_stop()` also invalidates eagerly; the symptom was "no directly observable behavior, only increased CPU usage". 1ce6393a57 2019-02-10 skips it when `fd == -1`. • 3ecce91410 2024-03-21 When epoll_ctl was batched through io_uring, `EPOLL_CTL_DEL` went back to a direct syscall, and the batch now asserts ADD/MOD only, so a delete can never hit a reused fd.

### libuv-017 — Ask only for the data you will use
Lens: laziness · Source: libuv
Principle: When an API can return optional outputs (peer address, extra metadata), pass NULL or pick the narrowest variant, so the provider never computes or copies them.
Why it is faster: Every optional output costs work on the other side: a copy across the kernel boundary, extra internal queries, a larger stack frame. A narrower variant can mean one kernel query instead of two.
Applies elsewhere: Data / databases: `SELECT` only the needed columns. Covering indexes. • Native / systems: `recvfrom` with a NULL address on connected sockets. `statx` with a narrow mask. • Web / backend: GraphQL field selection or sparse fieldsets instead of full objects.
Watch out: if a later code path needs the field after all, fetching it separately costs more than having asked once.
Seen in libuv: 752ac30ec8 2012-05-24 "unix: don't pass sockaddr to accept()... Shaves a few nanoseconds off the accept() syscall". The stack `sockaddr_storage` locals were removed too. • ada5131840 2025-12-11 Windows `fs__unlink_rmdir` uses `GetFileInformationByHandleEx(FileBasicInfo)` instead of `GetFileInformationByHandle`: "one syscall, instead of two".

### libuv-018 — Stream results in caller-sized batches instead of materializing everything
Lens: laziness · Source: libuv
Principle: Instead of an API that reads, allocates and sorts every result before returning, offer an iterator that fills a caller-provided array of N entries per call. Carry along cheap metadata that saves follow-up calls.
Why it is faster: Memory becomes proportional to N rather than the result size, so a huge directory no longer means a huge allocation. The first results arrive sooner, and the caller can stop early without paying for the rest. Returning the entry type from `readdir`'s `d_type` spares a `stat` per entry.
Applies elsewhere: Web / backend: paginated or cursor-based listing APIs (S3 ListObjects). Streaming JSON responses. • Data / databases: server-side cursors with fetch size instead of loading full result sets. • Native / systems: filesystem walkers using `d_type` (ripgrep, fd).
Watch out: batched iteration gives up global ordering (scandir sorted everything) and sees concurrent modifications. Tiny batches add per-call overhead.
Seen in libuv: 99440bb673 2015-01-30 Adds `uv_fs_opendir`/`uv_fs_readdir`/`uv_fs_closedir` alongside `scandir`. `uv__fs_readdir()` fills `dir->dirents[0..nentries)` and sets `dirent->type = uv__fs_get_dirent_type(res)`.

### libuv-020 — Store booleans as bits in one flags word, and overlap bits whose meanings are mutually exclusive
Lens: memory-layout · Source: libuv
Principle: Represent each boolean state as a bit in a shared flags integer; when the word fills up, let bits that only apply to one subtype reuse the same positions across subtypes.
Why it is faster: A separate `int` boolean costs 4 bytes plus padding; a bit costs nothing once the flags word exists, and tests become a single AND. Because an object is only ever one subtype, TCP-only and pipe-only flags can never be set on the same object, so they can share bit positions and the word never has to grow.
Applies elsewhere: Native / systems: bitflags enums (C, Rust `bitflags`) instead of struct-of-bools; subtype-specific bit ranges in kernel-style objects. • Data / databases: packed status bits in page and tuple headers; null bitmaps instead of per-column null bytes. • Embedded: status registers in RAM-constrained firmware; one byte of flags per sensor channel. • Web / backend: permission sets and feature toggles as integer bitmasks in caches and tokens.
Watch out: Overlapping bits are only safe if the subtype is fixed for the object's life and code always checks the type first; bitfields shared between threads need atomic updates, since writing one bit rewrites the whole word.
Seen in libuv: 6c3205557b 2011-08-06 Helper functions around handle state replaced by direct bit operations on `flags`. • 7d45cca12a 2012-04-25 "we're out of handle flags": Windows flags re-laid out as shared bits for all handles, stream bits in 0x100-0x100000, and type-specific bits overlapping from 0x01000000 up. • e71495c84a 2012-05-23 `stream->blocking` turned into a flag bit, saving 4 bytes per stream.

### libuv-024 — Lay out your public buffer type to be binary-identical to the OS structure
Lens: memory-layout · Source: libuv
Principle: Define the library's buffer or descriptor type with exactly the field order and types of the native scatter/gather struct on each platform, so arrays can be handed to the kernel without conversion.
Why it is faster: If `uv_buf_t[]` is layout-compatible with `struct iovec[]` on Unix and `WSABUF[]` on Windows (which order the fields differently), `writev`/`WSASend` take the user's array directly: no per-call allocation and copy into a temporary iovec array, and partial writes are resumed by adjusting base/len in place.
Applies elsewhere: Native / systems: FFI structs that match C ABI layout so arrays cross language boundaries without marshalling. • Data / databases: Arrow-style columnar buffers shared across processes and languages without conversion. • Embedded: message structs laid out exactly like the DMA descriptor or wire header. • Web / backend: pass `Buffer`/`ArrayBuffer` slices straight to native writev bindings instead of concatenating.
Watch out: Field order differs per platform, so the public type becomes platform-conditional; any field added later breaks the cast, so guard it with static size and offset checks.
Seen in libuv: 5917f8b273 2011-03-30 "It should be possible to cast ol_buf[] to WSABUF[]": the Windows buffer type follows WSABUF's field order. • 9539443905 2011-04-26 On Unix the buffer is cast to `iovec` ("We had to have our own oio_buf instead of iovec because Windows's WSABUF is not an iovec"); the header notes "May be cast to struct iovec".

### libuv-025 — Remove an index table whose mapping is always the identity
Lens: memory-layout · Source: libuv
Principle: If an indirection array maps slot i to entry i, fill it once at setup or eliminate it entirely, instead of rewriting or reading through it on every operation.
Why it is faster: An identity map costs memory and a dependent load on the consumer side for every entry, and rewriting it per submission costs stores. Filling it once at init removes the per-operation stores; a mode that drops it removes the memory and the load.
Applies elsewhere: Data / databases: skip the selection vector when it is dense; drop row-id maps that are just positions. • Native / systems: ring buffers whose slot map is identity can index entries directly. • Embedded: DMA descriptor rings indexed directly instead of through a remap table. • Web / backend: in JS, avoid index arrays that mirror array positions; iterate the data directly.
Watch out: Only valid while the identity actually holds; if you later need reordering (priorities, out-of-order submission) the indirection comes back.
Seen in libuv: 6e073ef5da 2023-05-01 The io_uring `sqarray[i] = i` identity fill moved from every submission to ring initialization. • bcc6d1c1fc 2024-09-30 On Linux 6.6+ the ring is created with `IORING_SETUP_NO_SQARRAY`, removing the array entirely: about 1 KiB per ring and one level of indirection in the kernel.

### libuv-026 — Size static tables to what is actually accessed
Lens: memory-layout · Source: libuv
Principle: Audit statically allocated tables: reserve only the entries the access pattern touches, and keep a static first segment for the common case rather than the worst case.
Why it is faster: Static arrays live in BSS: they cost no allocation calls, but oversized ones inflate the binary's memory image and the pages touched. A table that reserved M×N entries while only every Nth was used wasted 15/16 of its space.
Applies elsewhere: Embedded: BSS audits with the linker map; every oversized static array is RAM lost. • Native / systems: right-size initial hash-map capacities and per-thread static pools. • Web / backend: initial capacity of caches and maps per worker multiplies by worker count. • Data / databases: size static lock or latch tables to real concurrency, not theoretical maxima.
Watch out: Shrinking a static table moves more workloads onto the slower heap-overflow path; measure the hit rate of the static part before cutting it.
Seen in libuv: 2c279504f9 2019-05-09 The Windows fd hash was introduced with 256 buckets of 16-entry groups and a statically allocated first group per bucket, so typical use needs no heap allocation. • 12fbd34475 2025-08-24 `uv__fd_hash_entry_initial` was resized from `SIZE * GROUP_SIZE` to `SIZE`: about 2592k down to 162k (16x), with search/insert/delete timings logged to confirm no regression.

### libuv-029 — Allocate I/O buffers only when data is known to be ready, and let the consumer supply them
Lens: allocation · Source: libuv
Principle: Ask the consumer for a buffer through a callback right before a read that will succeed; on completion-based APIs, wait for readiness with a zero-byte operation instead of posting a full buffer per idle connection.
Why it is faster: Posting a 64 KB buffer per socket pins memory proportional to connections, most of which are idle. Calling an allocation callback only after readiness means idle sockets hold nothing and the consumer can hand out pooled or slab buffers. Sizing the request to the bytes available avoids both oversized buffers and extra mode-switching syscalls.
Applies elsewhere: Web / backend: Netty's `RecvByteBufAllocator`; .NET pipelines with zero-byte `ReceiveAsync` and pooled buffers. • Native / systems: io_uring provided-buffer rings; rent buffers from a pool on EPOLLIN only. • Embedded: attach DMA buffers to a peripheral only when its FIFO signals data. • Data / databases: allocate result buffers after the row count is known (`FIONREAD`-style sizing).
Watch out: The extra readiness step costs a round trip per read burst, which is why low-connection-count servers may prefer pre-posted buffers; a shared sliced buffer needs an explicit release signal.
Seen in libuv: 1a76881cb0 2011-05-03 "Yet another oio_read api": `oio_alloc_cb(handle, suggested_size)` with `read_start/read_stop`. • 5a56c90af9 2011-05-03 Windows posts `WSARecv` with a zero-length buffer; the real buffer is allocated and read synchronously when it completes. • 7770b1a1f6 2011-06-01 `alloc_cb` moved to `uv_read_start()`, so buffer policy is chosen per read session. • 2765509430 2011-07-18 Named pipes ask `PeekNamedPipe` how much is available and call `alloc_cb(handle, avail)`, replacing two `SetNamedPipeHandleState` mode switches per read. • 422c139306 2011-08-15 Hybrid: real 64 KB buffers are pre-posted while fewer than 50 TCP streams are active (`uv_active_tcp_streams_threshold`), zero reads above that. • 51e9dbc2bb 2011-10-20 Zero reads extended to UDP. • 3d7136639a 2015-07-08 recvmmsg path asks the allocator for one large buffer and slices it into 64 KB per-datagram iovecs; later commits (`d9cd7d43`, `ea17e1cf`) add a final callback and `UV_UDP_MMSG_FREE` so the consumer knows when the shared buffer can be released. • 2b4b293ebb 2022-11-04 The long-disabled preallocation path was removed: TCP and UDP on Windows always use the 0-byte / `MSG_PEEK` read.

### libuv-030 — Borrow the caller's memory for synchronous calls; copy only when the operation outlives the call
Lens: allocation · Source: libuv
Principle: When the same request type serves synchronous and asynchronous calls, keep pointers to the caller's arguments in the synchronous case and copy only for asynchronous execution.
Why it is faster: An async request must own copies of paths and buffer arrays because the caller's stack frame may be gone when it runs. A synchronous request completes before returning, so the caller's data stays valid: the strdup/memcpy and the later free are pure overhead.
Applies elsewhere: Web / backend: Node-style sync/async API pairs sharing request structs; DB drivers copying bind params only for deferred execution. • Native / systems: take `std::span` / Rust slices in synchronous paths, owned buffers only in async ones. • Data / databases: zero-copy parsing with string views when the result is consumed before the input buffer is released.
Watch out: The cleanup code must know which mode created the request; any path that mutates borrowed data (as libuv's write iterator does) silently corrupts the caller's state.
Seen in libuv: e19764f75a 2015-08-14 fs `PATH`/`PATH2` macros: when `cb == NULL`, `req->path = path` without `uv__strdup`; cleanup frees only if `req->cb != NULL`. • 13148457a9 2023-10-12 Synchronous `uv_fs_read` points `req->bufs` at the caller's array; the copy into `bufsml` or a malloc happens only for async reads. Not applied to write, whose iterator mutates the list.

### libuv-032 — Read small system data into a stack buffer with raw calls instead of allocating library layers
Lens: allocation · Source: libuv
Principle: For small, bounded inputs (pseudo-files, kernel records), read once into a stack buffer and parse in place, rather than going through stdio or heavyweight libraries that allocate and buffer.
Why it is faster: `fopen` allocates a FILE and an I/O buffer (on glibc it even mmaps, changing the RSS being measured); `kvm_open` opens a kernel-memory interface and allocates. One `open` + `read` into a 1-4 KB stack array, or one `sysctl` into a stack struct, gets the same data with no heap use, no fd beyond the call, and fewer syscalls.
Applies elsewhere: Native / systems: metrics agents scraping `/proc` and cgroup files without stdio. • Embedded: allocation-free sysfs or config parsing, usable from interrupt or signal context. • Web / backend: read small config or secret files in one call into a reusable buffer. • Data / databases: parse fixed-size control files in place rather than through generic readers.
Watch out: Fixed stack buffers truncate if the file grows (e.g. `/proc/meminfo` on future kernels); check the read length and fail or fall back rather than parsing a partial record.

### libuv-044 — Read before you write atomically, and use exchange when there is no retry loop
Lens: cpu-microopt · Source: libuv

Applies elsewhere: Native / systems: Test-and-test-and-set spinlocks. "Already initialised?" flags. Watch out: A relaxed pre-read gives no ordering. If the flag publishes other data, the fast path needs acquire semantics, or callers must fence. libuv eventually gave up the fast path for that reason. Measure under contention: without contention the gain is small.

### libuv-045 — Use the compiler's atomics and the ISA's native CAS instead of hand-written or emulated ones
Lens: cpu-microopt · Source: libuv
Principle: Express atomics through the language's standard atomics or compiler intrinsics, and let the compiler emit the instruction the target does best. Remove hand-written inline assembly and emulations built from weaker primitives.
Why it is faster: Inline assembly with a `"memory"` clobber is opaque to the optimiser. It acts as a full compiler barrier and cannot be adapted to the target, for example LSE atomics on newer ARM. ### libuv-050 — Keep read-mostly globals off cache lines that get written (tried, then reverted)
Lens: cpu-microopt · Source: libuv

### libuv-052 — One wakeup channel per loop, built on the cheapest kernel doorbell available
Lens: concurrency · Source: libuv
Principle: Give each consumer one wakeup object shared by all its producers and handles, and implement it with the lightest primitive the OS offers: a counter fd, a user event filter or a completion post rather than a pipe.
Why it is faster: An fd per signalling handle grows the poll set and the kernel object count with the number of handles. A single fd per loop, followed by a sweep of pending flags, keeps both O(1). A pipe needs two fds, buffers bytes, and has to be drained with reads. An eventfd is a single 8-byte counter: writes coalesce and one read drains any number of signals. Edge-triggered registration removes even that read. kqueue's `EVFILT_USER` wakes `kevent` directly with no fd I/O at all. Each step removes a syscall or an fd from every wakeup.
Applies elsewhere: Native / systems: One eventfd (Linux), `EVFILT_USER` (BSD/macOS) or `PostQueuedCompletionStatus` (Windows) per reactor thread, not a socketpair per subsystem. • Web / backend: Runtimes embedding a loop (Node addons, Python asyncio `call_soon_threadsafe`): route every cross-thread call through one doorbell plus a queue. • Data / databases: Background workers signalling a coordinator: one notification channel with per-task flags, instead of one per task. • Embedded: One event group or notification word per task, with a bit per source, rather than a queue per source.
Watch out: Edge-triggered doorbells break when another component expects level semantics (libuv's EPOLLET change was reverted for two years). Native user-event filters may exist but not work, so probe them at runtime. Writing per-item data into the channel to skip the sweep can create lifetime bugs.

### libuv-057 — Cap a slow work class to a fraction of the pool so it cannot starve fast work

### libuv-063 — Make asynchronous signals ordinary loop events, and keep them from interrupting sleeps
Lens: concurrency · Source: libuv
Principle: Have the signal handler do almost nothing (write a small record to a pipe and bump a counter) and handle everything in the event loop. Mask signals the loop doesn't need during the blocking wait, and apply the mask atomically inside the wait syscall.
Why it is faster: Code in a signal handler is restricted to async-signal-safe calls and races with the interrupted thread. Turning signals into fd events serialises them with all other I/O at no extra cost. A sampling profiler's SIGPROF, though, interrupts every sleeping `epoll_wait` with EINTR. The loop then recomputes timeouts, reads the clock and goes round again: wasted wakeups. Blocking that signal during the wait removes them. `epoll_pwait` swaps the mask inside the syscall, which saves the two `pthread_sigmask` calls per poll and closes the race window.
Applies elsewhere: Native / systems: Use `signalfd`, kqueue `EVFILT_SIGNAL` or the self-pipe trick. Use `ppoll`/`pselect`/`epoll_pwait` so timer and profiler signals don't break sleeps. • Web / backend: Servers shutting down gracefully on SIGTERM: set a flag or write a byte, and do the shutdown in the loop. • Embedded: Top-half/bottom-half interrupt handling: the ISR records the event, a task handles it. • Data / databases: Database processes that are profiled in production: mask SIGPROF in I/O threads during waits.
Watch out: A signal pipe can fill up under a signal storm, so coalesce with counters. Masking a signal delays its delivery, so mask only signals whose latency doesn't matter during the wait (profiling ticks, not SIGTERM).

### libuv-064 — Create helper threads lazily, with explicit stacks reserved rather than committed
Lens: concurrency · Source: libuv
Principle: Don't start a thread until its feature is used. When you do, give it an explicit, page-rounded stack size, let the OS commit stack pages only as they are touched, and pass the entry function straight to the thread API.
Why it is faster: Each thread costs stack address space, commit charge, a scheduler entry and startup synchronisation. Starting helpers at init makes every process pay for them, even processes that never use the feature. Default stack sizes differ per platform (macOS secondary threads are small, musl defaults to 80 KB). An explicit size, rounded to a page with a floor for signal frames, is predictable. A reserve-only stack lets an 8 MB nominal stack cost only what is used. Passing the user's entry point directly removes a heap-allocated trampoline context per thread.
Applies elsewhere: Web / backend: Start background flushers, metrics exporters and watchdogs lazily. Pass small stacks to I/O worker threads to reduce RSS in high-thread-count servers. • Embedded: RTOS task stacks sized from measured high-water marks plus a guard margin. ### libuv-066 — Try the best OS primitive, detect "unsupported" at runtime, and fall back per request
Lens: platform · Source: libuv
Principle: Ship one binary that calls the newest, fastest mechanism. If the kernel, filesystem or environment rejects it, fall back to the older path for that request and remember global unsupported-ness. Callers never see the difference.
Why it is faster: Compile-time selection forces the slowest common denominator on every user of a portable binary. Probing at runtime gives modern systems the fast path (an atomic-flag syscall, a kernel copy, a native metadata call, a completion ring) and keeps old or unusual systems working. The detail that matters is how errors are classified. "Never works here" errors (ENOSYS, EPERM from seccomp, a probe failing at init) disable the path globally. "Doesn't work for this object" errors (ENOTSUP on one filesystem, EOPNOTSUPP for one opcode, EINVAL for a non-regular file) fall back only for that request.
Applies elsewhere: Native / systems: CPU-feature dispatch (AVX2/NEON kernels with a scalar fallback). Zero-copy send falling back to a copy. `renameat2` falling back to rename. • Web / backend: HTTP clients trying HTTP/2 or compression and remembering per-host refusals. Feature detection in browsers with polyfill fallback. • Data / databases: Try `RETURNING`, `MERGE` or a bulk-load protocol, fall back per server version. Use `O_DIRECT` where the filesystem allows it. • Embedded: Use a DMA or hardware accelerator if the peripheral is present at boot, otherwise a software loop.
Watch out: If you classify a per-object error as global, one odd filesystem disables the fast path for the whole process. If you classify a global error as per-object, every call pays for a failing syscall first. Make sure the fallback really is exercised in CI, or it will rot.

### libuv-068 — Completion-port I/O: handle inline successes inline and suppress packets nobody will dequeue

### libuv-077 — Pick the cheapest flush primitive that still gives the durability or ordering you promised
Lens: platform · Source: libuv

### libuv-078 — Offer a memory-mapped read/write path where the OS makes buffered calls expensive

### libuv-108 — Accept one connection per readiness notification
Lens: networking · Source: libuv
Principle: On a level-triggered listener, accept once and return to the loop; the poller will report the socket again if more connections are pending. Use a kernel-reported backlog count when available rather than calling until EAGAIN.
Why it is faster: An accept-until-EAGAIN loop almost always ends with a failing call. libuv measured that "99.9% of the time the second accept() call fails with EAGAIN". Accepting one also leaves connections for sibling processes sharing the socket.
Applies elsewhere: Web / backend: Prefork servers sharing listen sockets; any level-triggered acceptor. • Native / systems: Use readiness metadata (FIONREAD, kevent data) to size work exactly instead of probing to EAGAIN. • Data / databases: Connection acceptors in DB servers under connection storms.
Watch out: Under edge-triggered polling, accepting one per event loses connections; this relies on level triggering.

### libuv-110 — Keep a spare descriptor to shed load at the fd limit
Lens: networking · Source: libuv
Principle: Hold one spare fd open. On EMFILE, close it, accept and immediately close every pending connection, then reopen the spare.
Why it is faster: When accept fails with EMFILE the connection stays in the backlog and a level-triggered poller reports it forever: a 100% CPU spin with clients hanging. The trick turns that into fast resets for clients and an idle loop.
Applies elsewhere: Web / backend: Any acceptor on level-triggered epoll (nginx and HAProxy throttle accepts similarly). • Native / systems: Reserved memory ballast released under OOM pressure to allow a clean shutdown path. • Data / databases: Reserved connections kept for administrators.
Watch out: Another thread can grab the freed fd between close and accept; the trick only sheds load, it does not fix the limit.

### libuv-111 — Keep several accepts outstanding on completion-based APIs
Lens: networking · Source: libuv
Principle: Post many accept operations with pre-created sockets so bursts of connections never wait for the server to re-arm, with a switch back to one for fairness across processes.
Why it is faster: With one pending accept, each new connection waits for the previous completion to be processed and a new accept to be posted. Several outstanding accepts absorb bursts in the kernel.
Applies elsewhere: Native / systems: io_uring multishot accept; pre-posted receive buffers in RDMA. • Web / backend: IOCP-based servers under connection storms. • Data / databases: Connection-pool front ends that must absorb login bursts.
Watch out: Each outstanding accept holds a pre-created socket; in shared-socket multi-process setups, many outstanding accepts in one process starve the others.

### libuv-112 — Measure event-loop idle time without perturbing the loop
Lens: networking · Source: libuv
Principle: Timestamp just before a blocking wait and accumulate idle time at the first callback dispatch, polling with a zero timeout first so non-blocking polls are not counted as idle.
Why it is faster: Loop utilisation (busy versus idle) is the key capacity signal for event-driven servers. Measuring at the wait boundary costs two clock reads per blocking wait and needs no sampling thread.
Applies elsewhere: Web / backend: Node.js event-loop utilisation (ELU) is built on this; autoscale on loop utilisation rather than CPU. • Native / systems: Thread-pool saturation metrics in Java or Go executors. • Embedded: Accumulate MCU sleep time for power budgets.
Watch out: The extra zero-timeout poll costs a syscall per iteration, so it is opt-in.
Seen in libuv: e8effd4556 2020-03-26 `uv_metrics_idle_time()`: with `UV_METRICS_IDLE_TIME`, each backend's `uv__io_poll` first polls with `timeout = 0`, records the entry time only when it will block, and updates idle time before the first callback.
