### curl-001 — Size hash tables to the population they will actually hold
Lens: algorithms · Source: curl
Principle: The bucket count should follow the expected number of entries in each context. Too few buckets turns a hash into a linked-list scan; too many wastes memory and allocations for tiny users.
Why it is faster: Average chain length is entries/buckets. At 7 buckets and 7,000 entries every lookup walks about 1,000 nodes; at 911 it walks about 8. In the other direction, preallocating hundreds of bucket heads for a table that holds one entry costs mallocs and cache lines at every init. A single global constant is wrong at both ends, so the size has to be picked per use site (small for a lone handle, larger for a shared pool) or exposed as a build-time knob. Prime counts help when the hash is weak, such as `fd % slots`.
Applies elsewhere: Web / backend: pass capacity hints (Java `HashMap(n)`, Go `make(map[K]V, n)`, Rust `with_capacity`); use small maps for per-request scratch and large ones for process-wide caches. • Embedded: choose table sizes per build profile with a `#define`, so a small device does not pay for a server-sized table. • Data / databases: size hash-join and aggregation tables from the cardinality estimate rather than a fixed default.
Watch out: a table sized for the common case can still degrade when one deployment is unusual; either grow on load factor or let integrators override the size. Measure chain length, not just total memory.
Seen in curl: 686d90745b 2006-04-10 First socket hash for `curl_multi_socket()`. Tests at 7,000 and 9,000 connections showed the 7-slot hash was a bottleneck (about 1,000 nodes per chain). Raising it to 97 slots gave "a significant speed increase", under 10 µs per call at 9,000 connections. • 62f0f5571d 2007-06-26 Socket hash grown from 97 to 911 buckets (a prime), costing about 3 KB against 45-50 KB per handle; "greatly enhance[s] speed when very many connections are added". • 6420672879 2013-04-26 The implicit multi handle behind `curl_easy_perform` gets tiny socket and connection hashes. Test 40 went from 1,142 mallocs to 138, and peak memory from 118,969 to 78,805 bytes. • 3340b456a5 2017-10-11 `CURL_CONNECTION_HASH_SIZE` and the socket hash size can be overridden at build time. • 7632c0d25a 2022-08-27 DNS cache: 7 buckets for an easy handle, 23 for a share handle, 71 for a multi handle, "to scale and perform better when used with _many_ host names". 61275672b4 cut the cookie hash from 256 to 63 buckets, saving 1.5 KB per instance.

### curl-002 — Specialize the hash function and key comparison to the key type
Lens: algorithms · Source: curl
Principle: A generic byte-string hash with function-pointer callbacks is the slowest way to hash an integer. Choose the hash and compare by key type, reject mismatches with the cheapest test first, and build composite keys as compact binary rather than formatted text.
Why it is faster: Integer keys (file descriptors, IDs) can be hashed with one modulo and compared with one instruction; running a string hash over their bytes wastes cycles and needs a key copy. For string keys, a simple multiply-xor hash and a length-equality test before `memcmp` reject most mismatches cheaply. Formatting a key with `printf` costs a format-string parse and often a heap allocation per lookup; writing a type byte, two port bytes and the name directly costs a few stores. Doing "find, then delete" hashes and probes twice when delete already handles a miss.
Applies elsewhere: Web / backend: use numeric or tuple keys instead of string-concatenated cache keys (``${user}:${id}``); use `map.delete(k)` without a preceding `has(k)`. • Native / systems: fd-indexed tables in event loops; integer-keyed flat maps for IDs; shift away pointer alignment bits before hashing. • Data / databases: compare stored hash and length before key bytes in hash indexes; encode composite index keys as fixed binary.
Watch out: weak hashes such as `fd % n` or first-and-last-byte only behave when keys are well distributed or the table is small; adversarial string keys need a seeded hash.
Seen in curl: 9ebcfe9dff 2002-04-12 "Speed up the hash code considerably": PJW/ELF hash and typed-key macros replaced by DJB (`h=5381; h += h<<5; h ^= c`), and compare checks length and first byte before `memcmp`. • 62f0f5571d 2007-06-26 `Curl_hash_init` gains pluggable hash and compare functions; the socket hash uses `fd % slots`. • b2ea1bfcd6 2015-04-28 String key compare reduced to `len == len && !memcmp`, since the extra first-byte branch bought nothing once lengths match. 8eaf884417 2016-03-14 drops a `Curl_hash_pick` before `Curl_hash_delete` and skips lookups for `CURL_SOCKET_BAD`. • 1aa69221be 2025-02-23 A dedicated hash for `curl_off_t` keys: "smaller memory footprint and faster lookups as we do not need to deal with variable key lengths". • d08d16cac3 2024-09-26 Pointer-keyed hash uses `(key[len-1] ^ key[0]) % slots`, the bytes most likely to vary, and avoids an unaligned type-punned read. • 7c0c7ca57b 2026-09-04 `Curl_hash` stores a `uint8_t` key type (bytes or socket) instead of two function pointers, so socket keys hash by modulo through shared code. • 3ddbd522b9 2026-09-10 DNS cache keys become `[type][port_hi][port_lo][lowercased name]` instead of `msnprintf("%s:%u")`.

### curl-003 — Partition a flat collection by the key every lookup already knows
Lens: algorithms · Source: curl
Principle: When every lookup carries some component of the key (destination host, stream ID, request ID, domain), bucket entries by that component so a lookup scans only its own bucket.
Why it is faster: Lookup cost drops from O(all entries) to O(entries in the matching partition). For connection reuse, the search becomes "connections to this host" instead of "every cached connection"; for frame routing, a stream-ID hash replaces a walk over all streams. The partition key must be cheap to derive and present in every query.
Applies elsewhere: Web / backend: per-origin connection pools; route tables bucketed by first path segment; permission stores keyed by eTLD+1. • Native / systems: request-ID maps in RPC multiplexers; DNS transaction-ID tables; QUIC connection-ID tables. • Data / databases: per-tenant or per-shard indexes; partitioned lock tables.
Watch out: a skewed key (one host holding most connections, one domain holding most cookies) puts the whole population back in one bucket; check the distribution.
Seen in curl: 23f5d145ec 2007-09-29 Bundled c-ares: outstanding queries indexed by `queries_by_qid[2048]`, `queries_by_timeout[1024]` and per-server lists. Timeout batches had been O(n²) and response dispatch O(n); "most important operations are now O(1)", at about 100 kB of memory. • d021f2e8a0 2012-12-06 Connection cache becomes a hash of per-host "bundles": "Faster search for connections to reuse, since the hash lookup only finds connections to the host in question." • 77f1029ecd 2015-04-28 HTTP/2 streams indexed by stream ID; 2c238ea1fc 2015-04-29 moves per-stream state into the stream object and routes incoming frames through the hash. • c990eadd12 2018-03-30 Cookies stored in buckets hashed by the top two domain labels, making libcurl "handle thousands of cookies much better and speedier". 82dfdac5f7 simplified label extraction to one `memrchr` pass.

### curl-004 — Keep items in per-state lists so the hot loop touches only active work
Lens: algorithms · Source: curl
Principle: Instead of scanning every item to find the few that are done, pending or idle, move items between dedicated lists (or queues) as they change state. Each consumer walks only the set it cares about.
Why it is faster: A poll for "which items finished?" becomes a queue pop (O(1)) instead of a full scan (O(n)). A main loop that iterates all handles every tick spends most of its time skipping idle ones; parking pending and completed handles elsewhere makes each tick proportional to active work. The producer pays an O(1) list move at the state transition, which it was already handling.
Applies elsewhere: Web / backend: runnable versus blocked queues in job schedulers; active versus idle connection lists in servers. • Native / systems: a completion queue beside a worker pool (the IOCP or io_uring CQ pattern) instead of polling each task. • Data / databases: dirty-page and free-page lists in buffer pools instead of scanning all frames. • Embedded: ready lists in an RTOS scheduler.
Watch out: every state transition must move the item, or it is lost from processing; curl's first version of the PENDING split was reverted and re-landed. Removing an item must be O(1) too (see the next entries).
Seen in curl: 4d53dc5d80 2010-08-09 `curl_multi_info_read` reads a `msglist` filled at completion instead of looping over all handles: "We MUST make this function as fast as possible as it will be polled frequently... fully O(1)." • 3c8c873252 2014-09-02 A `multi->pending` list holds handles waiting for a connection slot, which "avoids a rather hefty slow-down especially notable if you add many handles". • 843b3baa3e 2023-03-26 PENDING and MSGSENT handles leave the main list: "the main loop does not need to iterate over these handles. A performance improvement." • 0d1e43af8d 2025-03-07 QUIC backends stop iterating `multi->process` (646ffb591a, 469c037fcf for quiche and OpenSSL-QUIC). 73c0180cb6 2026-09-02 later replaces the completion list with a `msgsent` bitset (see the ID-and-bitset entry).

### curl-005 — Maintain counts, totals and minimums incrementally
Lens: algorithms · Source: curl
Principle: If a value is an aggregate over a collection (count of live items, buffered bytes, earliest expiry), update it at insert and remove time instead of recomputing it with a walk on every query.
Why it is faster: The query becomes O(1). The maintenance cost is a constant-time update at transitions the code already handles. A next-expiry watermark is the minimum case: a sweep for expired entries can return immediately while that time is still in the future, which makes speculative, frequent sweeps affordable. When only the count of a set is ever used, the set itself can shrink to a counter.
Applies elsewhere: Web / backend: session stores that track the soonest expiry; queue length gauges kept on enqueue and dequeue. • Data / databases: maintained counts or materialized aggregates; min-heap or watermark for TTL eviction. • Embedded: byte counters in ring buffers instead of computing fill level from scans.
Watch out: every mutation path must update the aggregate, including error and teardown paths. A minimum watermark can only be lowered cheaply; on removal let it go stale (conservatively early) and correct it during the next scan.
Seen in curl: 159834171e 2006-08-02 `num_alive` incremented on add and decremented on completion; `*running_handles = multi->num_alive` replaces a per-call loop. • 1bd4b3f4e2 2021-06-08 Cookie jar keeps `next_expiration`, and `remove_expired()` returns early when `now < next_expiration`: removal "needs to be a fast operation since we want to be able to perform it often and speculatively". • 89ca8fe80a 2026-09-09 The client writer keeps a running total of buffered bytes plus a tail pointer instead of rescanning its chunk list. • d7928029fc 2025-12-04 A per-connection sparse bitset of attached transfers became a `uint32_t` counter once nothing traversed it.

### curl-006 — Make removal O(1): back-pointers, intrusive nodes, stored keys
Lens: algorithms · Source: curl
Principle: An element that knows where it lives (its list node, its tree node, its hash key) can be removed without a search. Store that position inside the element.
Why it is faster: Removal by value in a list or by "find the entry whose pointer equals X" in a hash is O(n). With the node embedded in the owning object, unlinking is a few pointer writes; with the key stored in the value, deletion is a single hash probe. Embedding also removes the separate node allocation, so insertion cannot fail.
Applies elsewhere: Native / systems: Linux-style `list_head`; intrusive LRU entries; heap index stored in the element for O(log n) priority-queue removal. • Web / backend: keep the map key on the object so cleanup does not search; DOM-like trees with parent pointers. • Data / databases: keep the primary key on cached rows so identity-map eviction is a direct delete.
Watch out: an embedded node lets an object sit in only as many containers as it has nodes, and a stale back-pointer after the container changes corrupts memory; keep ownership rules explicit.
Seen in curl: c2edf42567 2006-04-12 The timer splay tree uses a node embedded in each transfer; 686d90745b 2006-04-10 removes timers with `Curl_splayremovebyaddr`, refined in 405d98ee63. • 6c6e4710b5 2007-04-01 Each easy handle stores a pointer to its multi-list node, so `curl_multi_remove_handle` no longer loops: "a lot faster when many easy handles are added". • 09b9fc9009 2013-08-02 The per-handle tracking struct is merged into the handle itself, giving an intrusive list with a tail pointer. cbae73e1dd 2017-04-20 makes the generic list intrusive (caller supplies the node), removing 16.6% of tiny mallocs in a simple transfer and making insert infallible. • 335d325708 2024-10-14 Removing a connection bundle uses `Curl_hash_delete(&dest2bundle, bundle->dest, ...)` instead of iterating the hash looking for the pointer.

### curl-007 — Keep a tail pointer so appends never walk the list
Lens: algorithms · Source: curl
Principle: Appending to a singly linked list by walking from the head is O(n) per append and O(n²) to build. Track the last node (or the address of the last `next` field).
Why it is faster: Each append becomes O(1). The cost is one extra pointer per list and one update per append and removal. The same fix applies to "next fill position" cursors, where a builder rescans from the start to find the first empty slot.
Applies elsewhere: Web / backend: queue implementations; middleware chains built at startup from long lists. • Native / systems: linked queues in kernels and allocators; WAL segment lists. • Data / databases: building linked result sets in executors.
Watch out: every removal of the last element must reset the tail; an O(1) append with a dangling tail is worse than an O(n) one.
Seen in curl: ee8016b3de 2017-11-04 The curl tool keeps `url_get`, `url_out` and `url_ul` cursors instead of rescanning the URL list for each `-o` or `-T`: speedup of "several magnitudes on 100K URLs". • 09b9fc9009 2013-08-02 The multi's handle list gains a tail pointer `easylp`. • 55ecaa52b7 2026-09-12 The pause writer appends at the tail and consumes from the head; its flush had been O(N²). • 2cb089c698 2026-10-11 `Curl_slist_duplicate` and `cookie_list()` build with a tail pointer; 2910040880 2026-10-10 tool header buffering switches to a list with a cached tail; 3341da7dc2 2026-09-09 happy eyeballs gets a tail pointer.

### curl-008 — Hunt down hidden O(n²) and exponential paths
Lens: algorithms · Source: curl
Principle: Look for loops that restart from the beginning on every step: a "next item" API that recounts from the head, a trim that rescans after each removal, a hand-written bubble sort, a pattern matcher that recurses on every star.
Why it is faster: These code paths are invisible at small n and dominate at large n. Fixes are usually small: cache the cursor from the previous call, walk back once from the end, call the library `qsort`, or normalize the pattern so the matcher tries each suffix once.
Applies elsewhere: Web / backend: gitignore and route wildcard matchers; offset-based pagination that re-reads from row 0 (use a cursor). • Data / databases: LIKE pattern evaluation; iterators over B-tree leaves that keep their position. • Embedded: replace hand-rolled sorts in config canonicalization with a library sort.
Watch out: a cached cursor must be invalidated whenever the underlying collection changes; matchers on untrusted patterns also need hard caps, not just a better algorithm.
Seen in curl: a0984eae14 2018-02-07 fnmatch: runs of `*` and `?` are regrouped (`*?*?*` is `??*`), `?` consumes a character immediately, and the star suffix is tried once per position instead of exponentially. 2a1b2b4ef5 and 404c8850da cap the number of star sections. • a15c4a7f8c 2026-09-09 `curl_easy_nextheader()` caches name, origin, index and count from the previous call, so full enumeration is linear; it falls back to a scan only if the call pattern breaks. • dfdae2ee34 2026-10-26 AWS SigV4 canonical header sorting: bubble sort replaced by `qsort`. • ded4c00884 2026-10-14 Trailing `/` and `\` removal walks back once instead of calling `strrchr` after each removed character.

### curl-009 — Never rescan for a length or value you already have
Lens: algorithms · Source: curl
Principle: Carry `(pointer, length)` pairs through the code, take literal lengths from `sizeof`, reuse the end position a scan already returned, and use a known value instead of re-parsing text the program generated itself.
Why it is faster: `strlen` and friends are O(n) passes; when the length was known a moment ago, each call is a second pass over the same bytes. Passing a length of 0 or -1 to "let the callee measure" pushes the scan into the callee. Re-parsing a header the code just wrote (case-insensitive name compare plus digit loop) duplicates both work and failure modes.
Applies elsewhere: Native / systems: `string_view`, Rust `&str`, Go slices; pass byte lengths across FFI (N-API, JNI) instead of NUL-scanning. • Web / backend: carry `Content-Length` with generated payloads instead of measuring again; keep parsed metadata through a pipeline. • Data / databases: store lengths beside strings in row formats; drivers that bind parameters with explicit lengths.
Watch out: a stale length is a memory-safety bug; when lengths travel separately from the bytes, keep them in one struct.
Seen in curl: 03bb481598 2016-09-05 HTTP/2 send drops the per-header `content-length` scan and uses `state.infilesize` directly. • f4b85d24b2 2021-04-24 Callers of `Curl_client_write` pass the length instead of 0, which had triggered a `strlen`. • b807219292 2022-02-07 `STRCONST()` turns `Curl_dyn_add(lit)` into `Curl_dyn_addn(lit, sizeof(lit)-1)`; 9fff7feb82 does the same for `checkprefix`. • 186340c9cd 2022-02-10 mprintf skips `strlen` on empty strings, 24 such calls "alone when doing a simple GET from https://curl.se". 8f384577b8 2022-10-24 cookies reuse the `strcspn()` result; 458c70db6a 2023-08-27 tests `*endptr == '\0'` instead of comparing with `str+strlen(str)`. • 6694a42aa0 2025-12-01 Windows IDN conversion reuses the length returned by the UTF-8 to wide conversion and passes it to `WideCharToMultiByte()`, "saving length calculations within that API too". • aad438d535 2026-09-21 mprintf: unbounded `%s` passes the known length to the run writer instead of rescanning for the terminator.

### curl-010 — Scan once, search with `memchr`, and anchor matches where they must be
Lens: algorithms · Source: curl
Principle: Merge scattered validation passes into one up-front scan, locate special bytes with `memchr` rather than per-byte loops, search forward when any hit will do, and compare at the fixed offset when a token can only appear there.
Why it is faster: libc `memchr` checks 16-32 bytes per step with SIMD, so a few `memchr` calls beat one hand-written per-byte switch. Each separate validation pass touches every byte again. `strstr` over a whole string when the token can only be a suffix is both slower and wrong on earlier matches; `strrchr` scans to the end even when the first hit would answer the question.
Applies elsewhere: Web / backend: `endsWith` instead of `includes` for extensions; Node `Buffer.indexOf` for delimiters; single-pass request validation. • Embedded: one sanity-check pass over each received packet. • Data / databases: CSV and log ingestion that locates delimiters with vectorized search.
Watch out: `memchr` wins on long inputs; for very short strings a simple loop can be just as fast. Suffix compares need an explicit length check first.
Seen in curl: 64fa3b8d64 2016-02-04 NSS nickname: `strrchr` to `strchr`, "wasteful to search it backwards if we look for _any_ slash". • 4cfa5bcc9a 2023-04-11 URL parser: `junkscan()` once at the start instead of scattered, more `memchr`, fewer `strlen`, normalize directly into the output buffer: "~41% faster" than 7.88.1. 44deccf907 2025-02-12 later reduces `junkscan()` to one range-test loop replacing `strcspn` plus `strchr`. • f228410f77 2026-09-24 "verify headers in fewer passes": one scan instead of up to three. 1f0346f060 2026-10-23 `Curl_verify_header` uses three `memchr` calls (NUL, CR, colon) instead of a per-byte switch, and the colon search only runs for lines that need it. • 9441127394 2025-10-14 ftp-via-proxy check: `!memcmp(&path[len-7], ";type=", 6)` instead of `strstr(path, ";type=")`, "faster" and no false match; 5ac3541cb4 2025-10-15 same in ftp.c.

### curl-011 — Dispatch closed keyword sets by length, first byte or packed integer
Lens: algorithms · Source: curl
Principle: When the set of keywords is fixed at build time, replace a linear chain of string compares with a structure that rules out almost every candidate in one integer operation: a perfect hash, a `switch` on length or first character, or a `switch` on the keyword packed into a 32-bit integer.
Why it is faster: A linear scan costs up to N string compares. A switch on length or first byte is one integer compare that leaves one or two candidates; a perfect hash leaves exactly one. Packing a 2-4 character name into a `uint32_t` and switching on constants built by the same macro lets the compiler emit a jump table or binary search with no table and no loop. When a linear scan must remain, ordering by hit frequency shortens the average case.
Applies elsewhere: Web / backend: HTTP method and header-name recognition; in JS, switch on `str.length` or `charCodeAt(0)` before full compares. • Embedded: AT-command and NMEA sentence dispatch with packed-integer switches. • Data / databases: SQL keyword recognition in tokenizers (gperf-style perfect hashing).
Watch out: generated tables and packed constants must be regenerated when the set changes; case-insensitive packing needs care for characters that alias under `| 0x20`. curl went through three designs before settling, so benchmark each step.
Seen in curl: db8866fad9 2020-05-11 The `protocols[]` table reordered by survey popularity (HTTPS, HTTP, FTP...); the author notes the gain is not measurable but the least likely matches now come last. • b2d8f3f7f9 2023-11-17 Scheme lookup becomes a perfect hash generated by d6447b1bd2 (`scripts/schemetable.c`), one scheme per slot. • 522ea5420f 2024-03-18 "save cpu cycles": `http_header()` checks length with `sizeof` before compare and switches on `hd[0]` instead of a long if/else chain. 93e91e965e 2025-10-08 HTTP/2 `on_header()` checks name length before `strncmp`. • 2687751471 2026-08-24 Scheme lookup: generated mod-59 hash plus confirm replaced by length dispatch and character compares, 31% faster; 23d2782bee 2026-11-17 finishes with a per-length `MKPROT(a,b,c,d)` switch. • 283db12e05 2026-04-08 Time-zone names: linear search to bsearch over 69 entries; e7f76c782b 2026-09-17 weekday, month and zone names found "without loops", dateparser test "almost twice as fast"; 2c4d103bac 2026-11-03 removes the tables and bsearch for a `switch` on `MKNAME3` packed values. • d9ab46a9ce 2026-11-09 Cookie attribute names matched by `switch(nlen)` first, then at most one or two `strncasecmp`; cookierecv test 10-13% faster.

### curl-012 — Sort read-only lookup tables and binary-search them
Lens: algorithms · Source: curl
Principle: A table of names that grows over time should be kept sorted and searched with binary search, or indexed directly when keys are single characters.
Why it is faster: Linear lookup costs O(n) string compares per query; binary search costs O(log n), and a direct array index for single-byte keys costs one load. A sorted static array also beats a hash map for read-only data: no allocation, no hashing, compact in cache.
Applies elsewhere: Web / backend: CLI parsers; static route tables; MIME-type lookups. • Embedded: sorted const tables in flash instead of a RAM hash map. • Data / databases: sorted arrays for small read-only dictionaries.
Watch out: the table must stay sorted under the same comparison used at lookup time; add a unit test that checks ordering.
Seen in curl: 07dd60c05b 2024-01-08 Tool long options sorted alphabetically and found with `bsearch`; short options through a 96-entry table indexed by ASCII. Lookup is "a lot faster". • 4464c9f2c6 2024-06-10 `-w` variable names via bsearch, "as the list of variable names grows, doing a simple loop ... get increasingly worse". • eb9166dc66 2024-03-04 The docs generator no longer loops over every option for each replacement.

### curl-013 — Replace general-purpose parsers with narrow, in-place ones
Lens: algorithms · Source: curl
Principle: For a narrow grammar (dates, host:port pairs, attribute lists), a small hand-written cursor parser over the original bytes beats a generated parser, `sscanf`, or `strtok` on a writable copy.
Why it is faster: Generated parsers carry general machinery and size. `sscanf` interprets its format string on every call, handles locale and copies into temporary buffers. `strtok` needs a writable copy (malloc plus strdup). A cursor-based parser over a const span does one pass, no allocation, and has bounded behaviour on bad input.
Applies elsewhere: Web / backend: HTTP date and header parsing without regex or `split()`; span-based parsing in C# and Rust (nom, zero-copy). • Embedded: NMEA/GPS and config-file parsing without a scanf implementation linked in. • Data / databases: log-line ingestion with hand-rolled field scanners.
Watch out: hand parsers are where security bugs live; fuzz them and keep the grammar narrow.
Seen in curl: f6433211ae 2004-09-11 "getdate replacement code. smaller, slicker, faster": a 329-line table-driven date parser; f71b3f48a1 2004-09-15 deletes the yacc grammar, 3,681 lines, "No more yacc/bison needed." • 220776de6b 2012-06-15 RTSP CSeq: `strdup` + uppercase + `sscanf` + `free` replaced by one `sscanf` at the already-matched offset. • 788c6b3864 2023-02-24 `CURLOPT_RESOLVE` parsing: `sscanf("%255[^:]:%d")` into a 256-byte buffer replaced by `strchr` + `strtoul` in place ("avoid sscanf and extra buffer copies"). 5cc09a8479 2023-02-17 parsedate time fields, 3b15ee1e34 2023-02-24 RTSP and 5ed7417d2f 2023-02-24 krb5 likewise. • d5c738c608 2024-12-06 adds the `Curl_str_*` span helpers; 676de7f580 2025-02-17 replaces `strtok_r()` across 26 files, which "helps avoid extra mallocs"; 9be5c68492 2026-09-04 digest auth parses with spans instead of copying values into local buffers.

### curl-014 — Exit as soon as the answer is known, and try the likely answer first
Lens: algorithms · Source: curl
Principle: Return on the first mismatch, stop searching when an invariant says no further match can exist, stop formatting once the sink refuses output, and test the cheap exact-match case before the expensive general comparison.
Why it is faster: Work after the answer is decided is pure overhead. When most comparisons are between identical values, `strcmp` (platform-optimized) settles them before a case-insensitive or semantic compare runs. With a uniqueness invariant, a matching-but-unusable entry means "miss", so there is no reason to keep scanning.
Applies elsewhere: Web / backend: pointer or reference equality before deep equals; `Array.find`/`some` instead of `filter`/`reduce` for existence. • Data / databases: unique-index lookups stop at the first hit; collation compares with a memcmp prefix check. • Native / systems: truncating log formatters that stop once the buffer is full.
Watch out: early exit based on an invariant ("keys are unique") silently breaks when the invariant does; assert it in debug builds.
Seen in curl: 9b6545c479 2001-11-01 `ConnectionExists` returns on a matching-but-dead connection instead of continuing, "because we only store one connection for each unique set of identifiers". • 1d7ce36791 2004-05-12 `OUTCHAR()` returns once the output stream fails: "return faster when we 'hit a wall' while printfing". • b12c2b91df 2022-05-18 `Curl_strcasecompare`: the mismatch path returns directly, and the tail check is `!*first == !*second`; with lookup tables, 1.6-1.7x faster overall. • 35b0490aab 2026-09-11 `Curl_peer_same_destination()` tries `strcmp()` first and falls back to `curl_strequal()` only when needed; d9ab46a9ce 2026-11-09 adds a fast exit to `Curl_host_is_ipnum()`.

### curl-015 — Small integer IDs, ID-indexed tables and bitsets instead of pointer lists
Lens: algorithms · Source: curl
Principle: Give each object a dense integer ID, store objects in an array indexed by ID, and track membership in sets (pending, dirty, done, attached to this connection) as bitsets over those IDs.
Why it is faster: Lookup is one array index. A bitset costs one bit per object, add and remove are O(1), counting and scanning go 64 bits at a time, and modifying the set while iterating it is safe, so there are no dangling-pointer hazards. No per-membership nodes are allocated. A "first non-empty word" hint stops scans of leading zero words, and a resume cursor gives round-robin order for free.
Applies elsewhere: Native / systems: entity-component systems (entity ID plus component masks); connection IDs in servers; free-slot bitmaps in object pools. • Data / databases: lock tables tracking holders by transaction-ID bitmaps; dirty-page bitmaps. • Embedded: RTOS ready-priority bitmaps with a lowest-set-bit hint.
Watch out: IDs must be dense or the bitsets get sparse and large (hence curl's sparse variant); recycled IDs need a generation check if stale references can exist.

### curl-016 — Timer bookkeeping: one global node per owner, fixed slots per timer kind
Lens: algorithms · Source: curl

### curl-021 — Register exactly the readiness the operation can act on
Lens: scheduling · Source: curl
Principle: Wait for readable only when you will read, for writable only when you have something you are allowed to send, and for nothing while paused or throttled. Let each layer adjust the interest.

### curl-101 — Write byte assembly in a form the compiler turns into one instruction
Lens: cpu-microopt · Source: curl

### curl-103 — Never block the event loop on a blocking call: async API, helper thread, pool, native async
Lens: concurrency · Source: curl
Principle: Move each unavoidable blocking call (here `getaddrinfo`) off the thread that drives I/O. Prefer an OS async API. Otherwise use a reusable thread pool rather than a thread per call, and let waiters leave as soon as a shared result makes the call unnecessary.
Why it is faster: A blocking resolve stalls every transfer multiplexed on the thread, for as long as the slowest DNS server takes. An async resolver folds its sockets into the main poll set. A helper thread keeps the loop free but costs thread creation, a stack and a join per call. A pool amortizes those costs, and native async (completion callbacks) removes the thread entirely. A shared cache lets a waiter abandon a stuck lookup the moment another request has resolved the same name.
Applies elsewhere: Web / backend: libuv's threadpool for fs/dns, async DB drivers instead of a blocking pool, and single-flight so concurrent callers share one in-flight lookup. • Native / systems: io_uring or IOCP instead of a thread per file operation. `getaddrinfo_a` or c-ares for DNS. • Embedded: A fixed pool of worker tasks fed by a queue, instead of creating an RTOS task per request.
Watch out: Abandoned threads still hold resources until the blocking call returns, so cap the pool (`RESOLVE_THREADS_MAX`). Skipping joins at exit is only safe when the process is ending. Signal-based escapes (`siglongjmp`) are not thread-safe and were superseded.

### curl-104 — Hold shared locks only around shared data, never across slow work
Lens: concurrency · Source: curl
Principle: Take a cross-thread lock only for the read or write of the shared structure. Release it before slow operations such as network lookups or freeing memory, and don't take it at all when the feature using it is off.
Why it is faster: A lock held across a DNS resolve serializes every thread on the slowest lookup. A lock that guards a disabled feature costs an atomic operation for nothing.
Applies elsewhere: Web / backend: Cache-aside: never hold the cache mutex during the backend fetch. Watch out: After re-locking, re-check state, because another thread may have inserted the same key. The "duplicate work" trade-off can become a thundering herd on a popular key.

### curl-105 — Do check, modify and clean-up in one critical section
Lens: concurrency · Source: curl
Principle: When an operation needs several steps on shared state (look up, check staleness, take a reference, enforce limits, prune), do them in one lock acquisition instead of several lock/unlock pairs.

Applies elsewhere: Web / backend: Use `computeIfAbsent`-style get-or-insert in concurrent caches instead of get, then lock, then put. • Data / databases: Pin and look up a buffer-pool page in one latch acquisition. • Native / systems: Allocator slow paths that refill and allocate under one lock.
Watch out: Merging steps lengthens the critical section. Keep slow work (I/O, frees) out of it, as in the previous technique.

### curl-122 — Assemble a message in user space, then write it in one call

### curl-135 — Wake event loops through a descriptor, using the lightest primitive available
Lens: io · Source: curl
Principle: When another thread needs to interrupt an event loop, give the loop a readable descriptor to watch. Pick the cheapest kind: eventfd over pipe, and pipe over socketpair.
Why it is faster: Polling a worker's completion on a timer either adds latency or burns CPU on wakeups. A descriptor lets the kernel wake the loop exactly when needed. A wakeup carries one bit of information: eventfd is a single descriptor holding a counter, a pipe needs two descriptors and a byte stream, and an AF_UNIX socketpair goes through the full socket layer.
Applies elsewhere: Native / systems: Thread-pool completion into epoll via eventfd. `EVFILT_USER` on BSD. libuv's `uv_async_send` works this way. • Data / databases: Background I/O completion notifying the query thread. • Embedded: RTOS task notifications instead of queues for single-bit signals.

### curl-136 — Block on readiness with a real timeout, never sleep-poll or zero-poll

### curl-138 — Keep exactly one buffering layer on file output

### curl-140 — Keep connections open and reuse them whenever the protocol allows
Lens: networking · Source: curl

### curl-145 — Size flow-control windows to the bandwidth-delay product

Why it is faster: A "may I send?" handshake protects bandwidth when the body would be rejected, but it always costs an RTT, plus a server-timeout stall if the server ignores it. Watch out: The threshold depends on RTT and the rejection rate. On a server that often rejects large uploads, the handshake is worth it.

### curl-152 — Stop waiting for what you don't need, and tell the peer at once
Lens: networking · Source: curl
Principle: Treat a transfer as complete as soon as all the data you need has arrived. Skip polite goodbyes on connections already known to be broken. Flush stream resets immediately, so the peer stops sending useless data.
Why it is faster: Waiting for a close, a trailing end-of-stream marker, or a QUIT reply on a broken connection adds tail latency, and sometimes hangs. A reset left sitting in a send buffer lets the server keep streaming data that will be thrown away.
Applies elsewhere: Web / backend: gRPC cancellation that flushes RST. Video players that cancel range requests promptly. • Data / databases: Close cursors early once LIMIT is reached. Skip the ROLLBACK round trip when the socket is already dead. • Native / systems: Abort instead of a graceful TLS `close_notify` on errored sockets.
Watch out: Ending early on a stream may abort a connection that could have been reused (HTTP/1). Only do it when reuse isn't possible or the rest is truly unwanted.

### curl-154 — Put the first payload in the SYN (TCP Fast Open)

### curl-155 — Tune socket send buffers per platform, guided by the OS
Lens: networking · Source: curl
Principle: Where the OS default send buffer limits throughput, size `SO_SNDBUF` above the application's write size, or to the OS's ideal backlog for the current path. Never shrink a buffer that is already larger, and apply the change only on platforms where it helps.

Applies elsewhere: Native / systems: Size send and receive buffers from measured RTT × bandwidth for bulk senders on long-fat networks. • Data / databases: Backup and replication tools matching write chunk size to socket buffer size.

### curl-157 — Jitter retry timeouts to avoid synchronized storms
Lens: networking · Source: curl
Principle: Randomize retry and timeout intervals so requests that started together don't retry together.
Why it is faster: Identical timeouts line clients up. Every retry then hits the server or network in the same instant, causing loss and further retries. A random spread smooths the load at no cost to average latency.
Applies elsewhere: Web / backend: Exponential backoff with full jitter in HTTP and SDK retry policies. • Data / databases: Randomized lease renewal and leader-election timeouts (Raft does this). • Embedded: Randomized reconnect delays for device fleets after an outage.
Watch out: Jitter lowers the minimum delay, so keep a floor that respects server back-off hints such as Retry-After.
