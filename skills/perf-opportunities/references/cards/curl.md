### curl-001 — Size hash tables to the population they will actually hold
Lens: algorithms · Source: curl
Principle: The bucket count should follow the expected number of entries in each context. Too few buckets turns a hash into a linked-list scan; too many wastes memory and allocations for tiny users.
Why it is faster: Average chain length is entries/buckets. At 7 buckets and 7,000 entries every lookup walks about 1,000 nodes; at 911 it walks about 8. In the other direction, preallocating hundreds of bucket heads for a table that holds one entry costs mallocs and cache lines at every init. A single global constant is wrong at both ends, so the size has to be picked per use site (small for a lone handle, larger for a shared pool) or exposed as a build-time knob. Prime counts help when the hash is weak, such as `fd % slots`.
Applies elsewhere: Web / backend: pass capacity hints (Java `HashMap(n)`, Go `make(map[K]V, n)`, Rust `with_capacity`); use small maps for per-request scratch and large ones for process-wide caches. • Embedded: choose table sizes per build profile with a `#define`, so a small device does not pay for a server-sized table. • Data / databases: size hash-join and aggregation tables from the cardinality estimate rather than a fixed default.
Watch out: a table sized for the common case can still degrade when one deployment is unusual; either grow on load factor or let integrators override the size. Measure chain length, not just total memory.
Seen in curl: 686d90745b 2006-04-10 First socket hash for `curl_multi_socket()`. Tests at 7,000 and 9,000 connections showed the 7-slot hash was a bottleneck (about 1,000 nodes per chain). Raising it to 97 slots gave "a significant speed increase", under 10 µs per call at 9,000 connections. • 62f0f5571d 2007-06-26 Socket hash grown from 97 to 911 buckets (a prime), costing about 3 KB against 45-50 KB per handle; "greatly enhance[s] speed when very many connections are added". • 6420672879 2013-04-26 The implicit multi handle behind `curl_easy_perform` gets tiny socket and connection hashes. Test 40 went from 1,142 mallocs to 138, and peak memory from 118,969 to 78,805 bytes. • 3340b456a5 2017-10-11 `CURL_CONNECTION_HASH_SIZE` and the socket hash size can be overridden at build time. • 7632c0d25a 2022-08-27 DNS cache: 7 buckets for an easy handle, 23 for a share handle, 71 for a multi handle, "to scale and perform better when used with _many_ host names". 61275672b4 cut the cookie hash from 256 to 63 buckets, saving 1.5 KB per instance.

### curl-002 — Specialize the hash function and key comparison to the key type
Lens: algorithms · Source: curl
Principle: A generic byte-string hash with function-pointer callbacks is the slowest way to hash an integer. Choose the hash and compare by key type, reject mismatches with the cheapest test first, and build composite keys as compact binary rather than formatted text.
Why it is faster: Integer keys (file descriptors, IDs) can be hashed with one modulo and compared with one instruction; running a string hash over their bytes wastes cycles and needs a key copy. For string keys, a simple multiply-xor hash and a length-equality test before `memcmp` reject most mismatches cheaply. Formatting a key with `printf` costs a format-string parse and often a heap allocation per lookup; writing a type byte, two port bytes and the name directly costs a few stores. Doing "find, then delete" hashes and probes twice when delete already handles a miss.
Applies elsewhere: Web / backend: use numeric or tuple keys instead of string-concatenated cache keys (``${user}:${id}``); use `map.delete(k)` without a preceding `has(k)`. • Native / systems: fd-indexed tables in event loops; integer-keyed flat maps for IDs; shift away pointer alignment bits before hashing. • Data / databases: compare stored hash and length before key bytes in hash indexes; encode composite index keys as fixed binary.
Watch out: weak hashes such as `fd % n` or first-and-last-byte only behave when keys are well distributed or the table is small; adversarial string keys need a seeded hash.
Seen in curl: 9ebcfe9dff 2002-04-12 "Speed up the hash code considerably": PJW/ELF hash and typed-key macros replaced by DJB (`h=5381; h += h<<5; h ^= c`), and compare checks length and first byte before `memcmp`. • 62f0f5571d 2007-06-26 `Curl_hash_init` gains pluggable hash and compare functions; the socket hash uses `fd % slots`. • b2ea1bfcd6 2015-04-28 String key compare reduced to `len == len && !memcmp`, since the extra first-byte branch bought nothing once lengths match. 8eaf884417 2016-03-14 drops a `Curl_hash_pick` before `Curl_hash_delete` and skips lookups for `CURL_SOCKET_BAD`. • 1aa69221be 2025-02-23 A dedicated hash for `curl_off_t` keys: "smaller memory footprint and faster lookups as we do not need to deal with variable key lengths". • d08d16cac3 2024-09-26 Pointer-keyed hash uses `(key[len-1] ^ key[0]) % slots`, the bytes most likely to vary, and avoids an unaligned type-punned read. • 7c0c7ca57b 2026-09-04 `Curl_hash` stores a `uint8_t` key type (bytes or socket) instead of two function pointers, so socket keys hash by modulo through shared code. • 3ddbd522b9 2026-09-10 DNS cache keys become `[type][port_hi][port_lo][lowercased name]` instead of `msnprintf("%s:%u")`.

### curl-010 — Scan once, search with `memchr`, and anchor matches where they must be
Lens: algorithms · Source: curl
Principle: Merge scattered validation passes into one up-front scan, locate special bytes with `memchr` rather than per-byte loops, search forward when any hit will do, and compare at the fixed offset when a token can only appear there.
Why it is faster: libc `memchr` checks 16-32 bytes per step with SIMD, so a few `memchr` calls beat one hand-written per-byte switch. Each separate validation pass touches every byte again. `strstr` over a whole string when the token can only be a suffix is both slower and wrong on earlier matches; `strrchr` scans to the end even when the first hit would answer the question.
Applies elsewhere: Web / backend: `endsWith` instead of `includes` for extensions; Node `Buffer.indexOf` for delimiters; single-pass request validation. • Embedded: one sanity-check pass over each received packet. • Data / databases: CSV and log ingestion that locates delimiters with vectorized search.
Watch out: `memchr` wins on long inputs; for very short strings a simple loop can be just as fast. Suffix compares need an explicit length check first.
Seen in curl: 64fa3b8d64 2016-02-04 NSS nickname: `strrchr` to `strchr`, "wasteful to search it backwards if we look for _any_ slash". • 4cfa5bcc9a 2023-04-11 URL parser: `junkscan()` once at the start instead of scattered, more `memchr`, fewer `strlen`, normalize directly into the output buffer: "~41% faster" than 7.88.1. 44deccf907 2025-02-12 later reduces `junkscan()` to one range-test loop replacing `strcspn` plus `strchr`. • f228410f77 2026-09-24 "verify headers in fewer passes": one scan instead of up to three. 1f0346f060 2026-10-23 `Curl_verify_header` uses three `memchr` calls (NUL, CR, colon) instead of a per-byte switch, and the colon search only runs for lines that need it. • 9441127394 2025-10-14 ftp-via-proxy check: `!memcmp(&path[len-7], ";type=", 6)` instead of `strstr(path, ";type=")`, "faster" and no false match; 5ac3541cb4 2025-10-15 same in ftp.c.

### curl-012 — Sort read-only lookup tables and binary-search them
Lens: algorithms · Source: curl
Principle: A table of names that grows over time should be kept sorted and searched with binary search, or indexed directly when keys are single characters.
Why it is faster: Linear lookup costs O(n) string compares per query; binary search costs O(log n), and a direct array index for single-byte keys costs one load. A sorted static array also beats a hash map for read-only data: no allocation, no hashing, compact in cache.
Applies elsewhere: Web / backend: CLI parsers; static route tables; MIME-type lookups. • Embedded: sorted const tables in flash instead of a RAM hash map. • Data / databases: sorted arrays for small read-only dictionaries.
Watch out: the table must stay sorted under the same comparison used at lookup time; add a unit test that checks ordering.
Seen in curl: 07dd60c05b 2024-01-08 Tool long options sorted alphabetically and found with `bsearch`; short options through a 96-entry table indexed by ASCII. Lookup is "a lot faster". • 4464c9f2c6 2024-06-10 `-w` variable names via bsearch, "as the list of variable names grows, doing a simple loop ... get increasingly worse". • eb9166dc66 2024-03-04 The docs generator no longer loops over every option for each replacement.

### curl-014 — Exit as soon as the answer is known, and try the likely answer first
Lens: algorithms · Source: curl
Principle: Return on the first mismatch, stop searching when an invariant says no further match can exist, stop formatting once the sink refuses output, and test the cheap exact-match case before the expensive general comparison.
Why it is faster: Work after the answer is decided is pure overhead. When most comparisons are between identical values, `strcmp` (platform-optimized) settles them before a case-insensitive or semantic compare runs. With a uniqueness invariant, a matching-but-unusable entry means "miss", so there is no reason to keep scanning.
Applies elsewhere: Web / backend: pointer or reference equality before deep equals; `Array.find`/`some` instead of `filter`/`reduce` for existence. • Data / databases: unique-index lookups stop at the first hit; collation compares with a memcmp prefix check. • Native / systems: truncating log formatters that stop once the buffer is full.
Watch out: early exit based on an invariant ("keys are unique") silently breaks when the invariant does; assert it in debug builds.
Seen in curl: 9b6545c479 2001-11-01 `ConnectionExists` returns on a matching-but-dead connection instead of continuing, "because we only store one connection for each unique set of identifiers". • 1d7ce36791 2004-05-12 `OUTCHAR()` returns once the output stream fails: "return faster when we 'hit a wall' while printfing". • b12c2b91df 2022-05-18 `Curl_strcasecompare`: the mismatch path returns directly, and the tail check is `!*first == !*second`; with lookup tables, 1.6-1.7x faster overall. • 35b0490aab 2026-09-11 `Curl_peer_same_destination()` tries `strcmp()` first and falls back to `curl_strequal()` only when needed; d9ab46a9ce 2026-11-09 adds a fast exit to `Curl_host_is_ipnum()`.

### curl-015 — Small integer IDs, ID-indexed tables and bitsets instead of pointer lists
Lens: algorithms · Source: curl
Principle: Give each object a dense integer ID, store objects in an array indexed by ID, and track membership in sets (pending, dirty, done, attached to this connection) as bitsets over those IDs.
Why it is faster: Lookup is one array index. A bitset costs one bit per object, add and remove are O(1), counting and scanning go 64 bits at a time, and modifying the set while iterating it is safe, so there are no dangling-pointer hazards. No per-membership nodes are allocated. A "first non-empty word" hint stops scans of leading zero words, and a resume cursor gives round-robin order for free.
Applies elsewhere: Native / systems: entity-component systems (entity ID plus component masks); connection IDs in servers; free-slot bitmaps in object pools. • Data / databases: lock tables tracking holders by transaction-ID bitmaps; dirty-page bitmaps. • Embedded: RTOS ready-priority bitmaps with a lowest-set-bit hint.
Watch out: IDs must be dense or the bitsets get sparse and large (hence curl's sparse variant); recycled IDs need a generation check if stale references can exist.
Seen in curl: 909af1a43b 2025-03-25 "multi: do transfer book keeping using mid": adds `uint_tbl`, `uint_bset`, a sparse bitset of 256-bit chunks for "few IDs per socket", and `uint_hash`, replacing the multi's lists across 41 files. The internals doc gives 1,000 entries in one 8 KB array and a 40,000-transfer bitset in 5 KB. • e80c893254 2025-06-24 `first_slot_used` hint: `add()` lowers it, `count()` and `first()` start there; it "avoids slot scans on empty sets". e26f6e408a applies it to counting; c5fd5eb55a 2026-07-17 sparse bitsets reuse empty chunks instead of only growing. • 73c0180cb6 2026-09-02 The completion message list is replaced by scanning a `msgsent` bitset, removing a list node from every easy handle. • 082503f1f6 2026-09-23 The connection pool moves from linked lists to a `uint32_tbl` plus bitsets keyed by a new `cpid`, with `last_cpid` for a fast lookup of the transfer's previous connection. 4701a6d2ae switched the sets to `uint32_t`.

### curl-016 — Timer bookkeeping: one global node per owner, fixed slots per timer kind
Lens: algorithms · Source: curl
Principle: Keep the global "next deadline" structure small: each owner contributes only its earliest deadline, and each owner keeps its other deadlines in a fixed, enum-indexed slot array so a timer of the same kind replaces the previous one instead of piling up.
Why it is faster: A self-adjusting tree (or heap) gives the next expiring deadline in O(log n). If every pending timeout of every transfer went into it, n would be the number of timeouts, not transfers, and stale duplicates would fire "in vain". A per-owner sorted list with only its head in the global tree keeps n equal to the number of owners. Fixed slots per timer kind remove a malloc per timer and make re-arming idempotent. Compact index arrays (`time[]`, `next[]`) replace pointer nodes when the key space is a small enum.
Applies elsewhere: Native / systems: one heap entry per connection with idle, keepalive and request deadlines held locally; TCP stacks with fixed retransmit, keepalive and delayed-ACK slots. • Web / backend: a component keeping one `setTimeout` handle per purpose and clearing it before re-arming. • Embedded: static RTOS timer tables indexed by purpose.
Watch out: promoting the next local deadline into the global structure must happen on every fire and every cancel, or deadlines are silently lost (the bug the per-handle list originally fixed).
Seen in curl: d774730f83 2006-04-12 A splay tree for timers is added; 686d90745b 2006-04-10 `multi_socket` pops expired timers with `Curl_splaygetbest`. • 232ad6549a 2010-08-10 Each handle keeps `state.timeoutlist`; only the nearest timer sits in the global splay tree, and the next is promoted when it fires. • e9fd794a61 2017-05-09 Every `Curl_expire()` takes an `expire_id`, and the previous timer with that ID is removed first: "reduces the timeout lists drastically". 31b39c40cf 2017-05-09 stores `expires[EXPIRE_LAST]` in the handle instead of malloc'ing nodes ("faster, easier and reduces memory overhead"). • 874a54de5d 2026-08-03 Per-transfer timers become `struct expire_timers { time[], next[], first }`; 787cbd2033 2026-08-15 shrinks indices to `uint8_t`. 3d6d93a6be 2026-08-14 the splay tree's same-key list becomes singly linked ("we almost never have duplicate keys") and stores the transfer ID instead of a pointer.

### curl-017 — Lean hash layouts: singly linked chains, then open addressing
Lens: algorithms · Source: curl
Principle: A chained hash whose chains are only walked forward does not need doubly linked nodes; for small integer keys, open addressing in one structure-of-arrays block removes per-entry nodes entirely.
Why it is faster: Dropping the prev pointer and per-slot head/tail pointers shrinks every entry and slot; a pointer-to-pointer anchor still unlinks in O(1). Open addressing with power-of-two masking keeps probes in contiguous memory. Robin Hood displacement keeps probe sequences short and lets a miss stop as soon as the stored probe length is shorter than the current one.
Applies elsewhere: Native / systems: stream-ID maps in HTTP/2 and QUIC servers; next-only chains in kernel hash tables. • Data / databases: open-addressing hash joins and aggregation tables. • Embedded: fixed-capacity open-addressing tables with no allocator.
Watch out: open addressing needs deletion handling (tombstones or backward shift) and degrades sharply at high load factor; keep it below about 0.8.
Seen in curl: 069f9d066e 2025-02-16 Hash entries moved from the generic doubly linked list to an internal singly linked chain, saving 3 pointers per entry plus 3 per slot. • 01eff554af 2026-09-17 `u32_ptrset` replaces `uint-hash` for mapping transfer IDs to HTTP/2 and QUIC streams ("leaner and faster"): `ids[]`, `data[]` and `psl[]` arrays in a single `calloc`, and lookup stops when `psl > set->psl[i]`.

### curl-018 — Sliding-window rates from a ring of timestamped samples
Lens: algorithms · Source: curl
Principle: Compute a "current rate" from a small circular array of (amount, time) samples, using the real elapsed time between the oldest and newest sample.
Why it is faster: Each update is O(1): overwrite the oldest slot. Using actual timestamps instead of assuming one sample per second keeps the result correct when samples arrive irregularly, with no need for a larger history.
Applies elsewhere: Web / backend: moving-window throughput meters in load balancers; FPS counters. • Embedded: sensor rate estimation with a fixed-size sample ring.
Watch out: with very few samples or near-zero spans the rate is noisy; clamp the minimum span.
Seen in curl: ef48c73783 2001-10-12 The progress meter adds `speeder_time[]` next to `speeder[]` and computes the span in ms: "'current speed' is now more accurate since it is based on actual spent time".

### curl-019 — Turn recursive state machines into loops
Lens: algorithms · Source: curl
Principle: A state machine that calls itself to advance to the next state should loop instead, so stack use is bounded regardless of input.
Why it is faster: A loop avoids call and frame setup per transition and cannot overflow the stack on long or hostile inputs. Where recursion stays, shrinking the frame and making the call a tail call lets compilers reuse the frame.
Applies elsewhere: Native / systems: parser and VM dispatch loops; directory walkers with an explicit stack. • Web / backend: JSON decoders and tree walkers that may see deeply nested input. • Embedded: small task stacks where recursion depth cannot be bounded.
Watch out: do not rely on tail-call optimization being applied; C compilers are not required to do it, especially at `-O0`.
Seen in curl: 59f07ddf28 2010-10-20 FTP `wc_statemach`: locals moved into case scopes and `return wc_statemach(conn)` "to help compilers to perform tail call recursion optimization". • 69a358f218 2020-11-28 The same state machine becomes a loop (CVE-2020-8285), bounding stack use.

### curl-020 — Drive many operations from one thread with resumable state machines
Lens: scheduling · Source: curl
Principle: Write each protocol step as a state that returns "would block" instead of blocking, so a single thread can multiplex many operations over one readiness wait.
Why it is faster: A thread per transfer costs a stack, a context switch per wakeup and lock traffic. Non-blocking state machines let one thread service thousands of transfers, enforce timeouts uniformly and overlap all their network waits. The cost is that every blocking step (connect, TLS handshake, multi-step protocol exchanges, retries) must be split into states.
Applies elsewhere: Web / backend: async/await or futures over a single event loop; `Promise.all` with a concurrency limit instead of serial fetches. • Embedded: super-loop firmware where each protocol driver is a state machine fed by non-blocking UART or SPI. • Data / databases: drivers with async handshakes and pipelined queries over one connection.
Watch out: any one step that still blocks (a synchronous DNS call, a sleep) stalls every transfer on the loop; audit for them.

### curl-021 — Register exactly the readiness the operation can act on
Lens: scheduling · Source: curl
Principle: Wait for readable only when you will read, for writable only when you have something you are allowed to send, and for nothing while paused or throttled. Let each layer adjust the interest.
Why it is faster: A socket is almost always writable; registering POLLOUT while flow control forbids sending makes poll return immediately, forever, and the loop burns 100% CPU. Registering read interest while paused does the same once data is waiting. The opposite error, missing interest, stalls the transfer until some timeout: an upload that never asks for POLLOUT crawls at one chunk per second. Error flags such as POLLHUP must be mapped so callers see them, or they spin too.
Applies elsewhere: Web / backend: toggle EPOLLOUT only while the output queue is non-empty; Node `stream.pause()` and Netty `autoRead=false` under backpressure. • Native / systems: honour TLS WANT_READ/WANT_WRITE exactly; check all `revents` bits, not only the requested ones. • Embedded: enable the TX-empty interrupt only while the transmit buffer has data.
Watch out: removing interest is as dangerous as adding it: drop read interest while data is still buffered above the socket and the transfer stalls. Busy loops often show up only as CPU usage, not as slower transfers.
Seen in curl: 3ce43764be 2006-12-05 POLLHUP treated as an error to stop a 100% CPU spin when poll returned only POLLHUP; f7690db37d 2009-09-15 maps POLLHUP to POLLIN and POLLERR to IN|OUT. • 53a8a6e5a6 2008-11-24 SSH uses libssh2's block directions: "(much) less busy-loop situations and thus less CPU usage with no speed loss" (07416b61e3); 66fcebdc9e 2009-09-26 a protocol-independent `conn->waitfor` fixes 100% CPU during SFTP upload; 0510759bc4 2008-05-09 after sending a proxy CONNECT, wait only for read. • c175d184a2 2015-05-20 HTTP/2 upload resumes nghttp2 data so it wants to write; before, uploads ran at "16k something per 1 second". ea45b4334f 2016-08-05 always keeps read interest on HTTP/2, since frames can arrive while uploading. • c7f95fa0cc 2020-12-22 No read interest while the HTTP/2 transfer is paused; 1fed8feaf1 2021-10-11 no write interest when the remote window is 0; 4fee6c644f 2021-08-27 proxy CONNECT waits for writable only while the request is still being sent. • 47f5b1a37f 2023-09-04 `adjust_pollset()` lets each connection filter add or remove POLLIN and POLLOUT; d1c2bb3d8d 2023-11-30 rate-limited transfers report no sockets, avoiding "much more CPU work and updates than necessary". • 5e4e62962c 2026-05-19 Sockets of paused transfers are no longer added to pollsets (endless POLLIN); 6c7468718e 2026-09-21 blocking connect without a timeout polls with 1000 ms instead of 0, as does 39088cd295 2026-09-19 for SSH; 68b5e60138 2026-08-13 DICT waits for writability between retries.

### curl-022 — Keep running the state machine until it would actually block
Lens: scheduling · Source: curl
Principle: After a transition that needed no I/O, run the next state immediately in the same call. Returning to the event loop for a state that is ready now costs a full poll cycle, and sometimes the whole poll timeout.
Why it is faster: Transient states (DONE, protocol init after TLS, DO_DONE on a file transfer) have nothing to wait for. Bouncing through the poller adds at least one syscall and, if no socket is registered, a sleep until the timeout, which in curl's case was often a full second. Looping internally until a step reports "would block" removes that latency.
Applies elsewhere: Web / backend: resolve promise chains synchronously when data is already available; parsers that loop while input remains. • Native / systems: coroutine schedulers that keep running a task that is still ready; non-blocking TLS handshakes that loop until WANT_*. • Data / databases: executors that run CPU-only plan steps without yielding to the I/O scheduler.
Watch out: this must be bounded by "would block", not by "has more data", or one transfer monopolizes the loop (see the fairness entry).
Seen in curl: d17416190b 2010-01-11 SSH state machine wraps its switch in a loop "to perform as much as possible in one go, as long as it doesn't block"; 2158e234aa 2010-01-11 returns CALL_MULTI_PERFORM after a confirmed TCP connect "so that we can act faster". • 55f1e787f3 2010-02-01 Every call site loops on `multi_runsingle` while it returns CALL_MULTI_PERFORM; e04ccbd506 2014-11-18 moves that loop inside `multi_runsingle`. • 22adb46a32 2013-08-21 STATE_DONE, "highly transient", always continues; 5c14a7f068 2013-09-10 IMAP, POP3 and SMTP continue straight into protocol init after TLS instead of waiting "(usually 1 second)"; 2715d7f948 2013-12-22 DO_DONE goes straight to DONE when no socket needs I/O. • 07008ee8ac 2023-10-07 Sets CALL_MULTI_PERFORM on transitions that had relied on a spurious timer, after that timer was removed.

### curl-024 — Arm timers only when they change, can matter, and are not for yourself
Lens: scheduling · Source: curl
Principle: Notify the application's timer only when the earliest deadline actually changes, keep a "check again in X" only if it is earlier than what is already pending, never arm a wakeup for the task that is currently running, and do not schedule timers whose handler will find nothing to do. Do arm explicit deadlines for checks that would otherwise never run in an idle event-driven loop.
Why it is faster: Each redundant timer costs a tree or heap operation, possibly a timer syscall in the application, and a wakeup that does nothing. Re-arming the running handle for every incoming chunk adds a pass through the scheduler per chunk. On the other side, an event-driven loop only evaluates time-based conditions when something wakes it, so low-speed checks and throttle expiry need their own deadline.
Applies elsewhere: Web / backend: call `timerfd_settime` or reset a `setTimeout` only when the deadline moves; skip `setImmediate` when the consumer is already running. • Native / systems: per-connection idle timers set once, not on every packet; timer slack and coalescing. • Embedded: watchdog and lease timers armed explicitly rather than relying on traffic to trigger checks.
Watch out: when a timer is removed because it "never mattered", any state transition that silently depended on its wakeup stalls; curl had to add explicit CALL_MULTI_PERFORM returns afterwards.

### curl-025 — Match timer precision to what the loop can act on
Lens: scheduling · Source: curl
Principle: Round waits up, never report 0 ms for a deadline that is still in the future, return 0 at once when the deadline has passed, keep only the slack the OS clock really needs, and clamp the caller's wait to the next internal deadline.
Why it is faster: Truncating 0.7 ms to 0 makes the caller poll with no timeout, find nothing due and loop: a short busy spin per deadline. Rounding up avoids that. Firing early by a large margin (to tolerate a coarse clock) makes work run too soon, re-arm, and run again. A wait longer than the next internal deadline turns internal latency into the caller's timeout.
Applies elsewhere: Web / backend: epoll timeout = `ceil(min(user timeout, next timer))`; libuv-style timers that round up. • Embedded: RTOS tick conversion that rounds up so a task never wakes one tick early. • Native / systems: game loops that sleep in timer-resolution units and correct drift.
Watch out: rounding up adds up to one tick of latency per timer; for sub-millisecond deadlines use a higher-resolution wait rather than spinning.
Seen in curl: eb68aa38e3 2008-05-07 Splay tree keys changed from seconds to `struct timeval`. • ffd08df863 2008-12-19 `curl_multi_timeout` returns 1, not 0, when less than 1 ms remains: 0 "may cause short bursts of busyloops on fast processors". 2c72732ebf 2010-06-01 adds 40 ms slack for Windows' 16 ms tick. • 29bf0598aa 2013-06-03 `curl_multi_wait` shortens the caller's timeout to the internal one. • 21091549c0 2013-06-10 Early-fire margin cut from 40 ms to 3 ms outside Windows; 980659a2ca 2014-01-08 re-tells the application the timeout when a timer call finds nothing due; 3b183df9cc 2014-01-05 removes the inaccuracy constant and refreshes `now` after socket handling. • 913b80d5fd 2022-04-05 "ngtcp2: make curl 1ms faster": pass 0 for an already expired timer; d39863d27a 2023-09-25 `Curl_timediff_ceil()` "so we will never ask the platform to wake up too early".

### curl-026 — Report only changes in socket interest, combined per socket
Lens: scheduling · Source: curl
Principle: Instead of rebuilding a full descriptor set every iteration, keep the last interest per socket, compare, and tell the event loop only about differences. When several logical streams share one socket, register the union of their needs.
Why it is faster: Rebuilding and scanning an fd set is O(n) per wakeup; an epoll or kqueue registration only needs O(changes). Identical state means no callback at all. With multiplexing, one stream's "not interested" must not hide another's "interested", or transfers stall.
Applies elsewhere: Native / systems: `EPOLL_CTL_MOD` only on interest change; per-fd reference counts of interested parties. • Web / backend: the same diff-and-patch idea as UI reconciliation: emit deltas, not full state. • Data / databases: a shared connection serving pipelined queries must combine their read and write needs.
Watch out: the cached "previous state" must be updated on every path, including socket close and reuse of the same fd number, or the loop and the library disagree.

### curl-027 — Consume data buffered above the socket before waiting on the socket

### curl-028 — When there is nothing to wait on, sleep sensibly instead of spinning
Lens: scheduling · Source: curl
Principle: A wait call with no descriptors returns immediately, so naive loops spin. Skip the empty poll and its allocations, and make the wait API itself sleep for the next deadline; if that is impossible, back off exponentially from a tiny delay to a cap.
Why it is faster: Spinning burns a core; a fixed long sleep adds latency. Sleeping until the next known deadline is exact. Exponential backoff picks up fast results quickly and costs few wakeups for slow ones. Putting the sleep inside the library means callers cannot forget it.
Applies elsewhere: Web / backend: blocking queue `take()` rather than `poll()` in a loop; job-status polling with exponential backoff. • Native / systems: spin-then-park locks; event loops that never return zero events instantly unless asked. • Embedded: enter low-power sleep until the next timer instead of looping on an empty event set.

### curl-060 — Retain capacity across uses; release on idle only when memory, not CPU, is the constraint
Lens: allocation · Source: curl · Also: simdjson

Lens: cpu-microopt · Source: curl

### curl-123 — Trust readiness: read until EAGAIN instead of probing before each read
Lens: io · Source: curl
Principle: If an outer event loop already said a descriptor is ready, read from it until it reports would-block. Don't ask the kernel "is there data?" before every read.
Why it is faster: A zero-timeout `poll()`, `select()` or `FIONREAD` before each `read()` doubles the syscalls per iteration and tells you nothing that the read's own `EAGAIN` wouldn't. Looping until `EAGAIN` also drains several packets per wakeup instead of paying one full event-loop pass per packet. The limit is fairness: a fast source drained without bound starves other connections and timers, so the loop needs an iteration or byte budget.
Applies elsewhere: Native / systems: In epoll servers, don't call `ioctl(FIONREAD)` or `poll()` before `read()`. Don't poll the hardware status register before every byte.
Watch out: curl went back and forth on this: it looped in 2002 and stopped looping reads in 2003 (5ddc260fc2) because one transfer could monopolize the loop. Always pair the drain with a budget. Also check that data buffered in an upper layer (TLS, decompressor) still causes a wakeup.

### curl-125 — Fill the caller's buffer instead of returning one record per call
Lens: io · Source: curl
Principle: A layer that decodes framed input should keep decoding until the caller's buffer is nearly full or the source would block. On would-block after partial data, return the partial success.

### curl-126 — Make every socket operation non-blocking

Why it is faster: `select()` has a hard `FD_SETSIZE` limit (often 1024), and its cost grows with the highest descriptor number, not the number of descriptors watched. `poll()` scales with entry count, so merging read and write interest for one socket into a single entry and dropping duplicates shrinks the kernel's scan. Per-socket probe calls before the wait can usually be folded into the one multiplexed wait.
Applies elsewhere: Native / systems: Replace `select` in legacy servers. Use epoll or kqueue for large sets. Check all `revents` bits, or you get busy loops. • Web / backend: In Python, register a selector once per fd with combined events. • Embedded: Keep poll tables compact, with one slot per peripheral.
Watch out: Some platforms have broken `poll()` corner cases (for example zero descriptors as a sleep), so keep a narrow fallback. Unhandled `POLLHUP`/`POLLERR` results make a poll loop spin.

### curl-135 — Wake event loops through a descriptor, using the lightest primitive available
Lens: io · Source: curl
Principle: When another thread needs to interrupt an event loop, give the loop a readable descriptor to watch. Pick the cheapest kind: eventfd over pipe, and pipe over socketpair.

### curl-155 — Tune socket send buffers per platform, guided by the OS
Lens: networking · Source: curl · Also: libuv
Principle: Where the OS default send buffer limits throughput, size `SO_SNDBUF` above the application's write size, or to the OS's ideal backlog for the current path. Never shrink a buffer that is already larger, and apply the change only on platforms where it helps.
Why it is faster: On some stacks, a send buffer no larger than one application write makes the sender wait for an ACK before it can queue the next write, which halves upload speed. An OS-provided ideal backlog query follows the path's bandwidth-delay product. The same knob can hurt on newer OS versions with autotuning.
Applies elsewhere: Native / systems: Size send and receive buffers from measured RTT × bandwidth for bulk senders on long-fat networks. • Data / databases: Backup and replication tools matching write chunk size to socket buffer size.
Watch out: Fixed socket-buffer values can disable kernel autotuning (Linux) and make things worse. Gate the change by platform and version, and re-measure on each OS release.

### curl-157 — Jitter retry timeouts to avoid synchronized storms
Lens: networking · Source: curl
Principle: Randomize retry and timeout intervals so requests that started together don't retry together.
Why it is faster: Identical timeouts line clients up. Every retry then hits the server or network in the same instant, causing loss and further retries. A random spread smooths the load at no cost to average latency.
Applies elsewhere: Web / backend: Exponential backoff with full jitter in HTTP and SDK retry policies. • Data / databases: Randomized lease renewal and leader-election timeouts (Raft does this). • Embedded: Randomized reconnect delays for device fleets after an outage.
Watch out: Jitter lowers the minimum delay, so keep a floor that respects server back-off hints such as Retry-After.

### curl-159 — Measure each micro-step separately, and on several architectures
Lens: observability · Source: curl
Principle: When rewriting a hot routine, apply the changes one at a time and record the delta of each. Repeat the measurement on CPUs of different classes (desktop, in-order ARM, embedded PowerPC) before deciding.
Why it is faster: Bundled rewrites hide which part helped and which part hurt. Per-step numbers let you keep the wins and drop the neutral or harmful steps. Gains vary a lot between out-of-order x86 and small in-order cores, so a change tuned on one machine can be neutral or negative on another.
Applies elsewhere: Native / systems: One commit per micro-change with a benchmark line in the message. Test on ARM servers and low-end mobile, not just a dev laptop. • Web / backend: Benchmark JS hot paths in several engines (V8, JSC, SpiderMonkey). They optimize differently. • Embedded: Measure on the slowest supported MCU, where branch and memory costs differ most.
Watch out: Gains of a few nanoseconds are close to noise. Use many iterations and report medians. Interactions mean the steps don't always add up, so re-measure the final combination.

### curl-165 — Measure with a high-resolution monotonic clock in integer units
Lens: observability · Source: curl
Principle: Time intervals with a monotonic, high-resolution counter, and store them as integer microseconds (or as offsets from one base time) rather than floating-point seconds.
Why it is faster: Coarse clocks (10-16 ms ticks) make short timeouts, rate limiting and speed figures wrong: transfers that finish within one tick show infinite or zero speed. Integer microseconds give exact arithmetic and comparisons. Offsets from one base time take less memory than full timestamps.
Applies elsewhere: Web / backend: `performance.now()` or `process.hrtime.bigint()`, not `Date.now()`, for latency metrics. • Native / systems: `CLOCK_MONOTONIC` and `std::chrono::steady_clock`, stored as int64 ns or µs. • Data / databases: Delta-encode timestamps against a base in time-series storage.
Watch out: High-resolution counters can be slower to read on some platforms. Read once and pass the value down. Wall-clock time is still needed for display and for absolute expiry dates.

### curl-166 — Decouple progress reporting from state updates and rate-limit it
Lens: observability · Source: curl
Principle: Update counters on every event, but render progress or emit statistics at a fixed low rate, and only when the displayed value changes.
Why it is faster: On fast links, progress callbacks fire thousands of times per second. Redrawing a terminal line or emitting a metric each time can cost more than the transfer itself. Rendering once per second, and only on visible change, makes reporting cost independent of throughput.
