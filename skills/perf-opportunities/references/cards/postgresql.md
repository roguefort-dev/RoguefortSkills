### postgresql-002 — Keep O(1) handles: tail pointers, stored lengths and back links
Lens: algorithms · Source: PostgreSQL
Principle: Store whatever lets the common container operations run in constant time: a tail pointer for appends, a cached length, and a back pointer for unlinking. Append in the natural direction instead of prepending into an array.
Why it is faster: A singly linked list with only a head pointer makes append and length O(N), so N appends cost O(N²). Unlinking from a singly linked list needs a predecessor search, so freeing many nodes in arbitrary order is quadratic. Prepending into an array-backed list memmoves every element. One extra word per header or node removes all of these.
Applies elsewhere: Web / backend: Avoid `array.unshift` or `array.shift` in a loop; use push plus reverse, an index cursor, or a deque. • Native / systems: Track the tail and length in intrusive list headers; use doubly linked lists for LRU and timer wheels where removal is arbitrary. • Embedded: Ring buffers with head and tail indices instead of shifting arrays.
Watch out: Each extra pointer costs memory per node; for lists that are always short or freed all at once (arena reset), the bookkeeping may not pay.

### postgresql-004 — Make recursive rewrites visit each node once
Lens: algorithms · Source: PostgreSQL
Principle: Recursive transforms must reuse the results they have already computed for a subtree and must not re-walk regions they did not change. Visiting a child twice per level makes cost exponential in depth.
Why it is faster: If each level of a recursive simplifier re-evaluates the original arguments instead of the simplified ones, a constant at depth N is evaluated N times, and visiting the same child twice per level doubles work per level. Restricting a rewrite pass to the affected region turns "for each of N items, walk all N" into a linear pass.
Applies elsewhere: Web / backend: AST transforms in bundlers and template compilers: build parents from already-transformed children; memoize selectors. • Native / systems: Compiler passes and graph rewriters should track a changed-region worklist instead of re-walking the whole tree after each local change. • Data / databases: Recursive JSON or XML transformers: one visit per node, results passed upward.
Watch out: Memoizing every subtree costs memory; prefer restructuring so the recursion naturally returns the transformed child.
Seen in PostgreSQL: 8759f175db0 1999-09-07 cnfify removed "exponential space consumption"; a 10,000-arm OR query now plans in about 20MB. • 1879175b182 2000-03-12 The constant folder evaluated operators on the original arguments, so "A constant subexpression at depth N got evaluated N times"; it now builds the new node from simplified arguments. ef3386affeb stopped calling `fireRIRonSubselect` twice per subselect, "an exponential amount of wasted effort". • 8685c472235 2005-11-18 `exprTypmod()` recursed twice on the first COALESCE argument, which was exponential for deep FULL JOIN nests. • 5ec81aceec8 2016-10-30 tsquery rewriting replaced an O(2^N) subset matcher with a single merge-style scan over sorted operands. • 64919aaab45 2021-07-06 Clearing a flattened view's subquery pointer immediately cut planning for nested views from O(N³) to O(N²). • e42e3124302 2022-12-22 Pulling up a UNION ALL leaf now mutates only that leaf's AppendRelInfo instead of the whole query, which was O(N²) for N leaves. • 6d8fd5a8818 2026-07-15 JSON_TABLE NESTED PATH was re-evaluated several times per parent row; now resets only mark state and the path is evaluated once per parent row.

### postgresql-006 — Prefer contiguous arrays and direct indexing over linked structures and searches
Lens: algorithms · Source: PostgreSQL
Principle: Store sequences in growable arrays, and when keys come from a dense bounded domain, index an array by key instead of searching a list, a tree or a sorted table.
Why it is faster: Linked cons cells cost one allocation and pointer per element, scatter data across memory and make positional access O(N). An array scans in cache order and gives O(1) `nth`. A dense key turns binary search or list walks into one load. The trade-off is that prepend and delete-first become O(N), so callers must append and delete from the end.
Applies elsewhere: Web / backend: Index objects by numeric ID in arrays or typed arrays; avoid linked lists and Array.shift loops. • Native / systems: Opcode, file-descriptor and per-shard tables indexed directly; bound scans by a high-water mark. • Embedded: Enum-indexed lookup tables instead of switch chains or search loops.
Watch out: Direct indexing wastes memory when the key domain is sparse; arrays make middle insertion and deletion O(N).

### postgresql-007 — Engineer the hash table: a well-mixing hash, power-of-two buckets, open addressing
Lens: algorithms · Source: PostgreSQL
Principle: Use a hash function that mixes all input bits, size tables as powers of two so bucket selection is a mask, and for hot paths use a flat open-addressing table specialized at compile time for the key type.
Why it is faster: With a good mixer, prime bucket counts add nothing and division is slow, so `hash & (n-1)` replaces modulo. Word-at-a-time hashing beats byte loops; integer keys need only a cheap finalizer. Chained tables pay pointer chasing and indirect hash/compare calls; linear probing over a flat array with inlined key handling is far more cache- and branch-friendly, and Robin Hood displacement keeps probe lengths short.
Applies elsewhere: Web / backend: Use the runtime's flat hash maps (`Map` keyed by small ints) and avoid string-keying numeric IDs. • Native / systems: Prefer SwissTable/hashbrown/Robin Hood maps over chained `std::unordered_map`; pass precomputed hashes through APIs that reuse them. • Data / databases: Store each row's hash with spilled data so repartitioning does not rehash; check bucket distribution of custom hashers.
Watch out: Power-of-two masking only works with a hash that mixes low bits well; identity hashing on structured keys clusters badly. Open addressing needs a load-factor cap and care with deletion.

### postgresql-011 — Make each sort comparison cheap
Lens: algorithms · Source: PostgreSQL
Principle: Comparisons dominate sorting, so shrink their cost: use a three-way comparator, cache the leading key next to the pointer, compare a fixed-width proxy key first, and specialize the sort so the comparator is inlined.
Why it is faster: A less-than-only sort needs two calls to distinguish equality. Extracting the first key from the tuple on every comparison chases pointers. An 8-byte abbreviated key (a strxfrm prefix or encoded numeric, byte-swapped so one integer compare matches memcmp) resolves most comparisons in a register, with the full collation-aware compare only on ties. A HyperLogLog estimate of proxy distinctness stops abbreviation when it stops discriminating. A templated sort removes one indirect call per comparison.
Applies elsewhere: Web / backend: Sort by a precomputed numeric or string prefix key (decorate-sort-undecorate); use `TypedArray.prototype.sort` instead of comparator callbacks. • Data / databases: Normalized fixed-width key prefixes in sort buffers; pack composite keys (shard, id) into one 64-bit integer. • Native / systems: Templates or generics instead of `qsort` with a function pointer; byte-swap keys once so integer compare equals lexicographic order.
Watch out: Abbreviation adds a conversion pass and wastes it on low-cardinality prefixes; keep an abort heuristic. Specialized sorts multiply code size per instantiation.
Seen in PostgreSQL: f905d65ee35 2001-05-07 Tuplesort finds a btree three-way comparator for the sort operator instead of calling `<` twice; 8cb624262ab had btree call the comparator directly, a "nice speedup in CREATE INDEX". • 909ca1407c4 2006-02-26 SortTuple stores the first key (`datum1`/`isnull1`) directly in the sort array. • 337b6f5ecf0 2012-02-15 Generated SortTuple-specialized quicksorts, one with the single-key comparator inlined; 5ea86e6e65d spread SortSupport (comparators without fmgr overhead) to btree builds. • e246b3d6eac 2014-09-19 memcmp before strcoll for equal-length strings "speeds up sorts containing many equal strings significantly"; 0e57b4d8bd9 caches the previous strxfrm and strcoll results. • 4ea51cdfe85 2015-01-19 Abbreviated keys for text with HyperLogLog-driven abort; abd94bcac45 added numeric and 78efd5c1edb datum sorts. • bfb54ff15a4 2015-10-09 The packed text key is byte-swapped to native order once, so `memcmp` becomes a single integer compare. • b648b70342f 2015-12-16 TIDs are encoded as int8 for the CREATE INDEX CONCURRENTLY sort, making comparison one instruction and pass-by-value. • 1b88b8908e7 2021-03-12 The checkpointer's buffer sort was specialized via the new `sort_template.h` (0a1f1d3cac6); one large-buffer-pool case went from 1.4 s to 0.6 s. • 6974924347c 2022-04-02 Tuplesort gained `qsort_tuple_unsigned/signed/int32` from a sort template with always-inline comparators, usually 10-20% faster. • 9f3755ea07a 2026-04-07 pg_trgm uses a templated sort plus an equality-only comparator for deduplication, which is cheaper than three-way comparison.

### postgresql-015 — Shape B-tree pages for the insert pattern to avoid splits
Lens: algorithms · Source: PostgreSQL
Principle: Decide how full pages are, where they split, and what keys they store based on how data arrives: leave headroom on bulk builds, split ascending inserts near the new item, merge duplicates into posting lists only when a split looms, and keep only the key prefix internal pages need.
Why it is faster: A 100%-full page splits on the first insert, and splits cascade upward. A 50/50 split under locally ascending inserts leaves pages half empty forever. Deduplicating only at split time amortizes the cost like a split and keeps ordinary inserts cheap. Truncated internal keys make the tree shallower. Remembering the rightmost leaf skips the root-to-leaf descent for monotonically increasing keys.
Applies elsewhere: Data / databases: Fillfactor and split-point heuristics in any B-tree engine; time-ordered composite keys benefit most from right-biased splits. • Native / systems: Rope or array-chunk splits in editors that adapt to append patterns. • Embedded: Flash-friendly KV stores leaving slack in pages to avoid rewrite cascades.
Watch out: Heuristics tuned for ascending inserts waste space for random inserts; deduplication costs a little on unique keys. Keep the detection cheap and conservative.
Seen in PostgreSQL: 421f0baaffd 2000-07-21 Bulk btree builds fill leaves to 90% and upper pages to 70%, and do not store the unneeded leftmost keys on internal pages. • 40549e9cb5a 2000-08-25 When inserting among many equal keys, the search moves right with probability 0.99 rather than always, spreading inserts across the run; it "does an excellent job of preventing O(N^2) behavior with many equal keys". • d04c8ed9044 2015-03-26 GiST gained index-only scans through a `fetch` method, skipping the heap when the index can reconstruct the value. • 2b272734353 2018-03-26 Inserts of increasing keys cache the rightmost leaf and insert there after a try-lock, skipping the descent; if the try-lock fails it falls back, since failure signals contention. • 8224de4f42c 2018-04-07 INCLUDE columns are carried in leaves for index-only reads but truncated from pivot tuples. • f21668f328c 2019-03-25 "Split after new tuple" detects locally ascending inserts; pg_depend indexes got more than 20% smaller and TPC-C indexes about 40% smaller. • 0d861bbb702 2020-02-26 Deduplication merges equal keys into a key plus TID list only when a page would otherwise split: indexes with 10-15 rows per key became 2.5-4x smaller, at about a 2% regression for append-only unique-ish workloads; 2903f1404df enabled it for catalog indexes. • d168b666823 2021-01-13 Bottom-up deletion removes dead duplicate versions locally when version churn is about to split a page.

### postgresql-016 — End and narrow ordered scans using page-level proofs
Lens: algorithms · Source: PostgreSQL
Principle: In an ordered index scan, prove facts once per page (the high key ends the range, the first and last items both satisfy the keys) and use them to stop early or skip per-item checks; also mark entries known to be dead so later scans skip them.
Why it is faster: Per-tuple key evaluation and sibling-page visits dominate range scans. If a page's high key already exceeds the bound, there is nothing to the right. If the first and last tuples satisfy a key prefix, every tuple between does too, so the comparator runs once instead of per item. Hint bits on index entries turn repeated heap fetches into a bit test.
Applies elsewhere: Data / databases: Zone maps per block: skip predicate evaluation when the block's min/max lies entirely inside the predicate range. • Web / backend: Paginated range queries that stop at the first page whose upper bound passes the limit. • Native / systems: Skip lists and SSTables with per-block max keys for early termination.
Watch out: Page-level proofs must account for concurrent splits and NULL ordering; skip the precheck on the first page if it slows point lookups.
Seen in PostgreSQL: 3f4d4880227 2002-05-24 Index scans set "killed" hints when a heap tuple is dead to everyone, and equality on all columns of a unique key stops after the first hit, which "Saves repeated heap_fetch operations on frequently-updated rows". • 606c0123d62 2014-11-18 The first `<`/`>` key satisfied by the initial position is marked matched, skipping per-tuple rechecks; 1a77f8b63d1 uses an implied NOT NULL to position past leading nulls. • 3ca930fc39c 2017-09-07 A new snapshot type lets planner probes at index ends kill recently-dead entries so later probes skip them cheaply. • 29b64d1de7c 2019-03-23 nbtree checks the high key before stepping to the right sibling and ends the scan when no match can follow. • e0b1ee17dc3 2023-10-06 A per-page precheck of the last item lets per-tuple checks skip direction-required keys; 8a510275dd6 generalized it to a page-level "startikey" proof and 7d9cd2df5ff extended it to row comparisons. • c9c0589fda0 2023-12-08 "goback" descent lands `<` backward scans directly on the page holding the answer, reading 1 leaf instead of 2 for a LIMIT 1 query. • 1bd4bc85cac 2024-10-18 Backward scans stash the left-sibling link and follow it without relocking, about 12% on parallel index-only backward scans; 2ed5b87f96d dropped leaf pins early and one content lock per page step.

### postgresql-017 — Seek instead of scan: skip scan and skip-ahead intersection
Lens: algorithms · Source: PostgreSQL · Also: TigerBeetle
Principle: When the leading key is unconstrained or one input is far sparser than another, jump to the next possible match rather than reading everything in between.
Why it is faster: A multi-column index with no condition on its first column can still be used by iterating each distinct leading value and re-descending, which is orders of magnitude cheaper than a full scan when that column has few values. For "rare AND frequent", iterating the rare list and advancing the frequent list's cursor to each candidate avoids materializing the frequent list. A tri-state (TRUE/FALSE/MAYBE) consistency check tells the engine which terms are required.
Applies elsewhere: Data / databases: Loose index scans; galloping intersection of posting lists; seek per prefix in KV stores. • Web / backend: Tag filtering by intersecting sorted ID lists, driving from the rarest tag. • Native / systems: Skip pointers in compressed posting lists.
Watch out: Skipping pays only when distinct leading values are few; with high cardinality each re-descent costs more than scanning.
Seen in PostgreSQL: 25b1dafab63 2014-01-29 GIN skips decoding posting-list segments whose TIDs are all below the skip target. • dbc649fd773 2014-02-07 GIN tri-state consistent functions "greatly speed up 'rare & frequent' type queries"; 97f3014647a added a native one for pg_trgm and 626a120656a optimized multi-key searches. • 25bfa7efd03 2015-12-25 pg_trgm uses a tighter similarity upper bound to prune candidates. • 92fe23d93aa 2025-04-04 nbtree skip scan generates `a = ANY(all)` arrays procedurally, "multiple orders of magnitude faster" with a low-cardinality prefix; b3f1a13f22f rewrites `a > 5` to `a >= 6` so the first descent can apply later keys. • Also seen in TigerBeetle (tigerbeetle-015): 424d9f69a6 2024-04-23 `ZigZagMergeIteratorType` with `stream_peek/pop/probe`. `ScanTreeLevel.probe` keeps the level iterator "without reading the index block again" when the key is still ahead in the buffer, and copies only the matching sub-range of a block. • 6a5fdba519 2024-04-23 Short-circuits a repeated probe with the same key. • 15bb188fb0 2026-02-23 A `pending` bitset skips already-pending streams during tours and probes them once at the end: "stream_peek/stream_probe are ... virtual functions, so its best to avoid calling them needlessly."

### postgresql-018 — Rule work out with small lossy summaries
Lens: algorithms · Source: PostgreSQL
Principle: Keep a compact summary that can answer "definitely not here" (min/max per block range, a Bloom filter, a stored hash, a bounds check) and consult it before the expensive lookup.
Why it is faster: A summary that fits in cache can skip disk blocks or long scans for the common negative case. Bloom filters have false positives but no false negatives. Storing a 32-bit hash instead of a wide key makes an equality index far smaller and confines expensive comparisons to hash matches. Checking a sorted array's min and max answers out-of-range probes in two compares before any binary search.
Applies elsewhere: Data / databases: Parquet row-group min/max stats; SSTable Bloom filters; content-addressed dedup indexes keyed by fingerprint. • Web / backend: Bloom filter of known IDs before a slow remote lookup; "seen URL" filters in crawlers. • Embedded: Per-page summaries on flash to avoid reading pages that cannot match.
Watch out: Summaries only help when values cluster (BRIN) or negatives are common; on random data they add a lookup without pruning anything.
Seen in PostgreSQL: 4adc2f72a4c 2008-09-15 Hash indexes store only the hash code, sorted within a page for binary search; "the gain in index compactness outweighs this when the indexed values are wide". • 7516f525941 2014-11-07 BRIN stores only min/max per block range "to accelerate scans of very large tables, without the maintenance overhead of btrees". • 51bc271790e 2018-03-31 A generic Bloom filter for amcheck; 9ee014fc899 added a Bloom-signature index for queries filtering on many columns; d365ae70540 puts a Bloom filter in front of a long role-membership list. • bbaf315309e 2021-03-10 `lazy_tid_reaped()` returns early when the probe TID is below the first or above the last dead TID, before `bsearch()`, on a path run for every index tuple during VACUUM.

### postgresql-019 — Store large sorted ID sets compactly with deltas and adaptive nodes
Lens: algorithms · Source: PostgreSQL
Principle: Sorted integer sets (row pointers, dead tuples) compress well as variable-length deltas or in adaptive radix trees whose node size follows fan-out; choose an encoding where removing an item never grows the data.
Why it is faster: Absolute 6-byte pointers waste space when IDs cluster. Delta plus varbyte encoding stores most gaps in one byte, and because deletion never lengthens the encoding, in-place updates stay simple. An adaptive radix tree has good locality for clustered keys, ordered iteration, and can embed small values in child slots. Smaller sets mean more fits in memory and lookups touch fewer cache lines.
Applies elsewhere: Data / databases: Inverted indexes and compressed bitmaps (Roaring, Lucene postings). • Native / systems: IP routing tables and page tables as radix trees. • Embedded: Delta-encoded timestamp lists for telemetry on microcontrollers.
Watch out: Compressed sets cost decode time per access; for small sets a plain sorted array is simpler and faster.
Seen in PostgreSQL: 36a35c550ac 2014-01-22 GIN posting lists encode 43-bit TIDs as varbyte deltas, making GIN indexes smaller. • df816f6ad53 2019-03-22 `integerset.c` stores 64-bit integers in a B-tree whose leaves are Simple-8b-encoded deltas. • ee1b30f128d 2024-03-07 An adaptive radix tree template; 30e144287a7 built TidStore on it and f35bd9bf359 embedded small values in child slots. • 667e65aac35 2024-04-02 VACUUM's dead-TID store became a TidStore: memory often "smaller by an order of magnitude", the 1 GB limit removed, and lookups "several times faster" than binary search over an array.

### postgresql-021 — Use sublinear, byte-wise and backtrack-free text algorithms
Lens: algorithms · Source: PostgreSQL
Principle: Pick string algorithms that skip input (Boyer-Moore-Horspool), avoid decoding (byte-wise matching on UTF-8), never back up (DFA lexers without backtracking states), and prune before expensive recursion.
Why it is faster: BMH's skip table lets mismatches jump ahead by up to the pattern length, so the average case is sublinear. UTF-8 continuation bytes never look like ASCII, so most matching can compare bytes without decoding characters. A lexer with no backup states runs a tight DFA loop. Running a cheap DFA before recursive backtracking rejects impossible split points early, and bounded edit distance stops once the bound is exceeded.
Applies elsewhere: Web / backend: Router path matching and log grep on UTF-8 bytes without decoding to UTF-16. • Native / systems: Check generated lexers with `flex -b` in CI; use banded edit distance for fuzzy search. • Embedded: Packet signature scanning with skip tables.
Watch out: BMH has the same worst case as naive search and its table setup does not pay for very short patterns; byte-wise matching is only valid for encodings whose continuation bytes cannot collide with ASCII.
Seen in PostgreSQL: 32c6c99e0b0 2002-04-20 The scanner uses flex `-CF` tables and receives the input with its length to "avoid querying the length repeatedly". • 15e4d1e2a7f 2005-05-26 Catch-all rules removed every backup state from the SQL scanner, making it "about a third faster"; 8dfb616606d restored the property a week later after an unrelated change broke it. • 15f8202c204 2007-06-02 All LIKE comparisons became byte-wise, and ILIKE became `lower(a) LIKE lower(b)`; about 400 lines removed. • e6a310b281c 2008-09-07 strpos, replace and split_part use BMH; "the average case is very fast, especially with longer patterns". • ee3a81f0a03 2010-02-01 The regex engine runs the DFA match before recursing, eliminating unworkable midpoints faster. • 604ab08145d 2010-10-19 `levenshtein_less_equal` computes a bounded edit distance.

### postgresql-025 — Prune partitions with structured bound lookups, at plan time and again at run time
Lens: query-planning · Source: PostgreSQL
Principle: Instead of testing every partition's constraint, compile the filters into a small program that binary-searches sorted partition bounds; rerun it at executor startup and when parameter values arrive, and never build per-partition state for partitions that were pruned.
Why it is faster: Constraint-exclusion theorem proving costs O(partitions) per query. Bound lookups cost O(log partitions). Creating planner objects only for surviving partitions turns "practical up to 100 partitions" into thousands. Runtime pruning handles values unknown at plan time, such as prepared-statement parameters and join keys.
Applies elsewhere: Data / databases: Time-partitioned log stores and Parquet row groups selected by binary search over min/max ranges. • Web / backend: Sharded routers that resolve the target shards from the key before opening connections. • Native / systems: Interval trees or sorted range tables for routing instead of testing each rule.
Watch out: Pruning logic must exactly mirror partition semantics (NULLs, collations, default partitions), or rows vanish.
Seen in PostgreSQL: d007a95055b 2005-07-23 Constraint exclusion skips child tables whose CHECK constraints contradict the WHERE clause; 48239e156ff runs the test before building paths for excluded children. • 9fdb675fc5d 2018-04-06 "Faster partition pruning": filters compile to step programs over sorted boundinfo instead of per-partition proofs. • 499be013de6 2018-04-07 Pruning at execution time with external params, nested-loop params and initplans; partitions pruned at init are never initialized; 34c9e455d0e skips subplan remapping unless runtime pruning will happen. • 428b260f87e 2019-03-30 RangeTblEntry and RelOptInfo are created only for partitions that survive plan-time pruning, raising the practical partition count from under 100 to a few thousand. • d47cbf474ec 2025-01-31 Initial pruning runs before plan-tree initialization, and cbc127917e0 tracks unpruned relids so pruned ones get no work; deferring their locks (525392d5727) was reverted.

### postgresql-027 — Split aggregation into partial and combine steps, and divide work by partition
Lens: query-planning · Source: PostgreSQL
Principle: Aggregate partially where the data lives (per worker, per partition, below a join) and combine the partial states at the end; when inputs are partitioned on the join or group key, process matching partitions independently.
Why it is faster: Partial aggregation shrinks row counts before expensive steps, and it is what makes parallel and distributed aggregation possible. Partitionwise joins and grouping use smaller hash tables with better locality. Eager aggregation below a join pays off when it cuts the join's input substantially, and limiting it to the lowest effective level bounds planning time.
Applies elsewhere: Data / databases: MapReduce combiners; distributed SQL partial aggregates; sharded counters merged at read time. • Web / backend: Per-shard pre-aggregation in analytics APIs before a global merge. • Native / systems: Thread-local accumulators combined at the end of a parallel loop.
Watch out: Only aggregates with a combine function (associative state) split cleanly; partial aggregation that does not reduce rows just adds a step.

### postgresql-081 — Compress adaptively, and avoid compression work when possible

### postgresql-089 — Choose the allocator by lifetime pattern (slab, generation)

### postgresql-132 — Compute in the machine's native width and representation
Lens: cpu-microopt · Source: PostgreSQL

### postgresql-133 — Avoid hardware division and checked arithmetic in hot loops
Lens: cpu-microopt · Source: PostgreSQL

### postgresql-153 — Use change counters: lock-free readers and reuse of unchanged results

### postgresql-155 — Fast-path weak locks in per-thread slots; go global only when a strong lock appears
Lens: concurrency · Source: PostgreSQL

### postgresql-156 — Spin briefly, then sleep with randomized backoff; let the releaser barge
Lens: concurrency · Source: PostgreSQL
Principle: Use raw spinlocks only for critical sections a few dozen instructions long, and reader/writer locks with wait queues for longer ones. Keep the uncontended path free of backoff setup.
Why it is faster: Spinning wastes a single CPU, while sleeping in the kernel is the expensive choice on SMP. An adaptive limit finds the balance at run time. Randomized backoff stops synchronized waiters from starving the holder. Direct hand-off forces a context switch per acquisition under contention, while letting the running thread take the lock again avoids that, at the cost of possible starvation.

### postgresql-177 — Look ahead and keep many I/Os in flight
Lens: io · Source: PostgreSQL
Principle: If you know which blocks come next, request them before you need them, either as a hint to the OS or as real asynchronous reads. The consumer then overlaps compute with I/O instead of stalling on each block in turn.
Why it is faster: A synchronous loop pays the full device latency per block. With N requests in flight, latency is hidden and throughput approaches device bandwidth, which matters most on SSDs and network storage that need queue depth. Inverting control helps: the consumer supplies a "next block" callback and a shared stream decides how far to look ahead, merges neighbours and skips advice for cached data. Asynchronous submission removes the remaining blocking syscalls.
Applies elsewhere: Web / backend: fetch the next page of a paginated API while processing the current one. Start all independent downstream calls before awaiting any of them. • Embedded: double-buffer DMA from flash or SD so the CPU decodes one buffer while the next one fills. • Native / systems: use `madvise(WILLNEED)` for mmap readers and io_uring with a bounded queue depth. Put a generic "stream" abstraction between consumers and storage. • Data / databases: add a read-stream layer under every scan type, including maintenance and diagnostic scans, not just the hot query paths.
Watch out: prefetching data that is never consumed wastes I/O and pins memory. Advice calls cost a syscall even when the data is cached, and lookahead across a seek can defeat the OS's own read-ahead. Bound the depth and measure on both cached and uncached data.

### postgresql-178 — Adapt I/O depth and resources to observed stalls
Lens: io · Source: PostgreSQL
Principle: Grow lookahead distance, buffer rings and worker pools only when the consumer actually waits, and shrink them slowly when it stops waiting. Pick synchronous or asynchronous dispatch per request based on its size and the queue depth.
Why it is faster: Fixed settings are either too small (I/O stalls) or too large (wasted pins, CPU and memory when data is already cached). Decaying slowly keeps the system from oscillating, because one synchronous miss costs milliseconds while extra lookahead costs microseconds. Applies elsewhere: Web / backend: grow a DB cursor's fetch size or a Kafka consumer's prefetch only after the consumer stalls. Watch out: adaptive controllers need hysteresis, or they oscillate. Where the signal is noisy (cached versus uncached), make sure growth is triggered by real waits and not by a proxy such as the hit/miss ratio.

### postgresql-181 — Make cache replacement cheap and contention-free (clock sweep)
Lens: io · Source: PostgreSQL
Principle: Approximate LRU with a per-entry saturating usage counter and a rotating clock hand, so a cache hit only bumps a counter and never touches a shared list. Keep the eviction path from holding more than one lock at a time.
Why it is faster: Exact LRU, ARC and 2Q all move an entry in a shared list on every hit, so the list's lock becomes a global contention point. A clock sweep moves that work to eviction time and spreads it over a single hand. Internal accesses (background writes) must not bump usage, or they distort the policy. Changing a buffer's identity should not hold two hash-partition locks while doing I/O.
Applies elsewhere: Web / backend: use CLOCK or second-chance bits in in-process caches (as approximate-LRU caches like Redis do) instead of a mutex-protected linked list. • Embedded: use CLOCK replacement in flash-translation-layer page caches, where RAM for list pointers is scarce. • Native / systems: OS page caches already use CLOCK variants. In concurrent hash maps, avoid holding two stripe locks during slow work. • Data / databases: buffer pools should do no shared-list work on a hit.
Watch out: under heavy churn the clock hand can sweep many times before finding a victim. Counters need a low cap so hot pages can still age out.
Seen in PostgreSQL: 48adc0b34b 2003-11-13 ARC was introduced in 2003, then removed by 5d5087363d: the new `StrategyGetBuffer` loops over `nextVictimBuffer` and `usage_count`, because a global freelist "is a global contention point". • fbbe00242d 2005-10-27 Background-writer and checkpoint accesses no longer increment `usage_count`, which improves eviction choices. • dad50f677c 2023-04-05 Buffer replacement first picks and cleans the victim, then removes it from the old mapping partition and inserts it into the new one, each under a single partition lock. ### postgresql-182 — Keep one-pass bulk operations from flushing the shared cache
Lens: io · Source: PostgreSQL

### postgresql-194 — Skip logging for data that a final sync or a crash makes moot
Lens: storage-engine · Source: PostgreSQL

### postgresql-198 — Log fewer, denser records: deltas, deduplicated plans, one record per page operation

### postgresql-199 — Shrink full-page images: drop the hole, then compress with a fast codec

### postgresql-202 — Make replay fast: decode ahead, prefetch, skip reads and take the weakest correct lock
Lens: storage-engine · Source: PostgreSQL

### postgresql-213 — Leave headroom on bulk-built pages, and don't build side structures for tiny objects
Lens: storage-engine · Source: PostgreSQL

### postgresql-215 — Make instrumentation cheap enough to leave on
Lens: observability · Source: PostgreSQL
Principle: Measure the cost of your own telemetry and drive it toward zero. Offer counting without timing, use the cheapest correct clock, write metrics into shared memory without locks, and remove branches from the reporting hot path.
Why it is faster: Per-event timing can double a query's runtime, which distorts the very profile it produces and keeps people from enabling it in production. A clock read through the OS can cost tens of nanoseconds or more, while the CPU timestamp counter costs a few cycles. Messages to a collector process cost syscalls. A seqlock-style counter lets writers publish status with no lock at all. In a function called millions of times, the branch that checks "is reporting on?" can cost more than the store it guards.
Applies elsewhere: Web / backend: offer a counters-only mode beside full tracing. Sample spans, and keep metrics in in-process registries rather than per-event network sends. • Embedded: timestamp with the cycle counter (DWT CYCCNT) instead of an RTOS call, and use null-object sinks instead of `if (trace)` checks. • Native / systems: rdtsc-based tracers (Tracy-style), seqlock-published per-thread stats, and lock-free reads of fields guarded by a coarser lock. • Data / databases: query-plan instrumentation with optional timing, and shared-memory activity views.
Watch out: TSC readings are unreliable on some virtual machines and older CPUs, so calibrate and fall back. Unserialized timestamp reads can reorder around short code. Lock-free stats readers must tolerate torn or retried reads.

### postgresql-217 — Keep telemetry in memory and persist it rarely, on demand
Lens: observability · Source: PostgreSQL
Principle: Store statistics in shared memory instead of a collector process that rewrites files. Write files only when someone asks, or on a long interval, and fold requests that arrive close together into one write. Don't create entries for objects nobody touched.
Why it is faster: A collector that rewrote a multi-megabyte stats file twice a second spent I/O and CPU in proportion to the number of objects, whether or not anyone read the file. Writing on request, debouncing concurrent requests and eventually moving to shared memory remove that background load and the IPC per update.
Applies elsewhere: Web / backend: serve metrics on scrape from in-process counters instead of pushing per event, and debounce snapshot writes. • Embedded: keep counters in RAM and persist them to flash only on request or on a long interval, to limit wear. • Native / systems: shared-memory telemetry rings (eBPF maps) instead of file- or socket-based IPC. • Data / databases: lazily created per-object stats entries, and single-flight snapshot refreshes.
Watch out: statistics kept only in memory are lost on crash unless they are snapshotted, which matters for autovacuum decisions. Shared-memory stats need a careful concurrency design.

### postgresql-218 — Benchmark the worst case and the losing workloads, and revert when they lose
Lens: observability · Source: PostgreSQL
Principle: Every optimization trades something. Measure the cases it can hurt (small inputs, other CPUs, cached data, contrived worst cases) as carefully as the case it helps, choose limits just below where the losses start, and revert changes whose measured cost outweighs the gain.
Why it is faster: An optimization that helps the benchmark but regresses common cases makes the whole system slower. Measuring the losing side finds the safe operating range: the largest cache before contention starts, or the threshold above which a fast path pays off. Reverting quickly keeps regressions from piling up.
Applies elsewhere: Web / backend: benchmark p99 and small payloads alongside the headline throughput, and gate merges on regression suites. • Embedded: test on the slowest supported MCU and on the cold-cache path, not just the dev board. • Native / systems: run micro-benchmarks on several CPU generations and socket counts, and keep revert commits small and fast. • Data / databases: run contrived worst cases (many partitions, many relations, tiny tables) next to standard benchmarks.
Watch out: a contrived worst case can veto a change that real workloads would welcome, so weigh it by likelihood. Semantics outrank speed: a faster result that is different is a bug.

### postgresql-220 — Keep the benchmark harness itself fast and representative
Lens: observability · Source: PostgreSQL
Principle: The benchmark setup should use the system's own fastest paths (bulk load, frozen data) and scale to large scripts, so measurement runs are cheap enough to repeat and the initial state matches production.
Why it is faster: Slow setup discourages re-measuring, so fewer optimizations are checked. A load that leaves the data unfrozen and not marked all-visible also makes the first runs pay for maintenance that production systems wouldn't see.
Applies elsewhere: Web / backend: seed load-test databases with bulk import and snapshots, not with ORM inserts one row at a time. • Native / systems: keep benchmark fixtures in their final, compacted state so runs measure steady state. • Data / databases: make the benchmark loader use the bulk-load and freeze paths.
Watch out: an idealized initial state (fully frozen, no bloat) can hide maintenance costs that real systems pay. Include an aged-data scenario too.
